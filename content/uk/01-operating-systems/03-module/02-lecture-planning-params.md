## Звідки планувальник знає, кого обирати

Попередня тема закінчилася на тому, що планувальник обирає процес за політикою.
Але політика оперує числами: пріоритет, спожитий час, частка вводу-виводу. Ці
числа і називають **параметрами планування**.

Головна складність у тому, що найкорисніший параметр — скільки процесорного часу
задачі знадобиться далі — планувальникові невідомий. Програма не повідомляє, що
їй лишилося 30 мс обчислень, і сама цього не знає.

**Запитання до аудиторії**: якби ви складали розклад прийому в поліклініці, не
знаючи наперед, скільки триватиме кожен огляд, — на що б ви спиралися?

```
┌─────────────────────────────────────────────────────────────────────┐
│                   ЩО ПЛАНУВАЛЬНИК ЗНАЄ, А ЧОГО НІ                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ЗНАЄ ТОЧНО                      НЕ ЗНАЄ НІКОЛИ                    │
│   ──────────                      ──────────────                    │
│   Хто власник процесу             Скільки лишилося рахувати         │
│   Заданий пріоритет (nice)        Коли процес запросить диск        │
│   Скільки часу вже спожито        Чи зависне він у циклі            │
│   Скільки разів блокувався        Що для користувача важливіше      │
│   Скільки чекав у черзі                                             │
│                                                                     │
│   ВИСНОВОК: майбутнє доводиться ОЦІНЮВАТИ за минулим.               │
│   Уся якість планування тримається на тому, наскільки               │
│   добре така оцінка працює.                                         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## Дві групи параметрів

```
┌─────────────────────────────────────────────────────────────────────┐
│                        ПАРАМЕТРИ ПЛАНУВАННЯ                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ПАРАМЕТРИ ПРОЦЕСУ              ПАРАМЕТРИ СИСТЕМИ                  │
│   ─────────────────              ─────────────────                  │
│   Статичні:                      Кількість ядер                     │
│    • власник, група              Розмір кванта часу                 │
│    • заданий пріоритет           Довжина черги готових              │
│    • граничний термін            Середнє навантаження               │
│    • потреба в пам'яті           Політика планування                │
│                                                                     │
│   Динамічні:                                                        │
│    • спожитий процесорний час                                       │
│    • час очікування в черзі                                         │
│    • частота блокувань на вводі-виводі                              │
│    • оцінка наступного інтервалу обчислень                          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Різниця між статичним і динамічним параметром принципова.** Статичний заданий
ззовні й не змінюється сам: ви поставили `nice 10` — воно таким і лишиться.
Динамічний планувальник рахує сам, спостерігаючи за процесом. Саме динамічні
параметри дають системі здатність пристосовуватися: процес, який щойно був
інтерактивним, а тепер почав рахувати, поступово втратить перевагу.

```bash
# Статичні та динамічні параметри одного процесу поруч
ps -o pid,ni,pri,pcpu,etime,time,stat,comm -p $$

# ni    — задане значення nice (статичний параметр)
# pri   — похідне від nice число для відображення; у Linux воно
#         саме не змінюється, динаміку дає віртуальний час vruntime
# time  — скільки процесорного часу вже спожито (динамічний)
# etime — скільки процес існує (для порівняння з time)
```

Порівняння `time` й `etime` — найпростіший спосіб показати студентам різницю між
двома типами задач: якщо процес існує годину, а процесорного часу спожив дві
секунди, він майже весь час чекав.

## Два типи задач: обмежені процесором та вводом-виводом

```
┌─────────────────────────────────────────────────────────────────────┐
│                      ПРОФІЛЬ ВИКОНАННЯ ЗАДАЧІ                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ЗАДАЧА, ОБМЕЖЕНА ПРОЦЕСОРОМ (CPU-bound) — архівування             │
│                                                                     │
│   ████████████████████ ▌ ████████████████████ ▌ ██████████          │
│   довгий інтервал      IO  довгий інтервал    IO                    │
│                                                                     │
│   ЗАДАЧА, ОБМЕЖЕНА ВВОДОМ-ВИВОДОМ (I/O-bound) — текстовий редактор  │
│                                                                     │
│   █ ▌▌▌▌▌▌▌▌▌ █ ▌▌▌▌▌▌▌▌▌▌▌▌ █ ▌▌▌▌▌▌▌▌▌ █ ▌▌▌▌▌▌▌▌▌▌▌▌▌            │
│   короткі інтервали обчислень, довгі очікування                     │
│                                                                     │
│   █ — процесор зайнятий обчисленням                                 │
│   ▌ — процес чекає на диск, мережу або користувача                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому цей поділ важливіший за пріоритети.** Задача, обмежена вводом-виводом,
рідко тримає процесор довго: попрацювала мікросекунди — і знову чекає. Якщо дати
їй перевагу, вона майже нічого не відбере в інших, зате користувач одразу побачить
реакцію інтерфейсу. Тому практично всі планувальники загального призначення
роблять одне й те саме: **підвищують пріоритет тим, хто часто блокується, і
знижують тим, хто вибирає свій квант повністю**.

Перевірити приналежність процесу до типу можна прямо:

```bash
# Частка процесорного часу від часу існування процесу
ps -o pid,comm,pcpu,time,etime -p PID

# Скільки разів процес блокувався добровільно, а скільки був витіснений
grep ctxt_switches /proc/PID/status
```

Велика частка добровільних перемикань — ознака задачі, обмеженої вводом-виводом.
Перевага примусових — ознака задачі, обмеженої процесором.

## Прогноз наступного інтервалу обчислень

Алгоритми на кшталт «найкоротша задача першою» потребують знання довжини
наступного інтервалу обчислень. Його оцінюють **експоненційним усередненням**:

```
τ(n+1) = α · t(n) + (1 − α) · τ(n)

τ(n+1) — прогноз наступного інтервалу
t(n)   — фактична тривалість останнього інтервалу
τ(n)   — попередній прогноз
α      — вага свіжих даних, 0 ≤ α ≤ 1
```

Формула виглядає складною, поки не підставити числа. Візьмімо α = 0,5 і
початковий прогноз τ₀ = 10 мс.

Таблиця 1 — Робота експоненційного усереднення при α = 0,5

| Крок | Фактично t(n), мс | Прогноз τ(n), мс | Новий прогноз τ(n+1), мс |
|------|-------------------|------------------|--------------------------|
| 1 | 6 | 10 | 0,5·6 + 0,5·10 = 8 |
| 2 | 4 | 8 | 0,5·4 + 0,5·8 = 6 |
| 3 | 6 | 6 | 0,5·6 + 0,5·6 = 6 |
| 4 | 4 | 6 | 0,5·4 + 0,5·6 = 5 |
| 5 | 13 | 5 | 0,5·13 + 0,5·5 = 9 |
| 6 | 13 | 9 | 0,5·13 + 0,5·9 = 11 |
| 7 | 13 | 11 | 0,5·13 + 0,5·11 = 12 |

Видно головне: поки поведінка стабільна, прогноз тримається близько до фактичних
значень; коли процес змінив характер (кроки 5-7 — задача почала рахувати довго),
прогноз наздоганяє її за три кроки, а не стрибає одразу.

### Що насправді робить коефіцієнт α

| Значення α | Поведінка | Наслідок |
|------------|-----------|----------|
| α = 0 | τ(n+1) = τ(n): свіжі виміри ігноруються | Прогноз ніколи не змінюється |
| α = 0,5 | Минуле й сучасне рівноправні | Класичний компроміс |
| α = 1 | τ(n+1) = t(n): врахований лише останній інтервал | Прогноз стрибає за кожним шумом |

**Розгортання формули** показує, звідки береться назва. Підставмо τ(n) у саму
формулу кілька разів:

```
τ(n+1) = α·t(n) + (1−α)·α·t(n−1) + (1−α)²·α·t(n−2) + ... + (1−α)ⁿ⁺¹·τ₀
```

Кожен наступний вимір у минулому входить із вагою, меншою в (1 − α) разів. Ваги
спадають експоненційно — звідси й назва. Пам'ять формули не обмежена жорстко, але
старі дані природно втрачають вплив, і зберігати історію не потрібно: досить
одного числа τ.

**Чому це важливо для викладача.** Студент зазвичай запитує: «навіщо формула,
якщо можна просто взяти середнє за останні п'ять інтервалів?» Відповідь:
ковзне середнє потребує зберігати п'ять значень на кожен процес (а процесів
тисячі) і однаково зважує вимір п'ятикрокової давнини та щойно отриманий.
Експоненційне усереднення дає той самий ефект за одне число на процес.

### Як nice перетворюється на частку процесора

Планувальник CFS зіставляє кожному значенню nice **вагу**. Крок в одну одиницю
nice змінює вагу приблизно в 1,25 раза. Опорна точка: nice 0 — вага 1024.

Таблиця 2 — Ваги для типових значень nice

| nice | Вага | Порівняно з nice 0 |
|------|------|--------------------|
| −5 | 3121 | у 3 рази більше |
| 0 | 1024 | опорне значення |
| +5 | 335 | у 3 рази менше |
| +10 | 110 | у 9 разів менше |
| +19 | 15 | у 68 разів менше |

Частка процесора обчислюється як відношення ваг. Два процеси, `nice 0` і `nice 5`,
на одному ядрі отримають:

```
частка(nice 0) = 1024 / (1024 + 335) = 0,753 ≈ 75 %
частка(nice 5) =  335 / (1024 + 335) = 0,247 ≈ 25 %
```

Перевірити це можна за півхвилини:

```bash
# Два однакові навантаження з різним nice на одному ядрі
taskset -c 0 nice -n 0 sh -c 'while :; do :; done' &
taskset -c 0 nice -n 5 sh -c 'while :; do :; done' &
sleep 20 && ps -o pid,ni,pcpu,comm -p $(jobs -p)
kill %1 %2
```

Співвідношення спожитого часу буде близьким до 3:1 — саме те, що дає таблиця ваг.

### Розбір помилкового міркування

> «Я поставив процесу `nice -20`, тепер він отримає 100 % процесора.»

Ні. Навіть з найвищим пріоритетом процес ділить процесор з іншими: вага 88761
проти 1024 дає приблизно 98,9 % проти 1,1 %, але не 100 %. І це навмисно:
планувальник загального призначення не дає жодному процесу забрати ядро
повністю, інакше помилка в одній програмі вішала б систему. Абсолютну перевагу
дають лише політики реального часу (`SCHED_FIFO`, `SCHED_RR`), і саме тому їх
вмикають окремо й з правами адміністратора:

```bash
# Політика й пріоритет реального часу (потрібні права root)
chrt -f 50 ./критична_програма

# Подивитися політику наявного процесу
chrt -p PID
```

> «Load average 4,0 означає, що процесор завантажено на 400 %.»

Ні. Середнє навантаження — це середня кількість процесів, які **виконуються або
чекають у черзі готових** (у Linux сюди ж потрапляють процеси в непереривному
очікуванні диска). На восьмиядерній машині значення 4,0 означає, що зайнята
приблизно половина потужності. На одноядерній те саме значення 4,0 означає, що
на кожен процес припадає вчетверо менше процесора, ніж він міг би отримати.

**Правило для інтерпретації**: значення порівнюють із кількістю ядер.

```bash
# Середнє навантаження за 1, 5 і 15 хвилин
cat /proc/loadavg

# Кількість ядер, з якою його треба порівнювати
nproc
```

## Параметри системи, які змінює адміністратор

```bash
# Базовий квант планувальника EEVDF (Linux 6.6+), наносекунди
sudo cat /sys/kernel/debug/sched/base_slice_ns

# Скільки процесорного часу ядро лишає задачам реального часу
cat /proc/sys/kernel/sched_rt_runtime_us
```

У CFS (до Linux 6.6) квант задавали два параметри: період `sched_latency_ns`,
за який кожен готовий процес мав отримати процесор хоча б раз, і мінімум
`sched_min_granularity_ns`. Ядро ділило період між готовими процесами, але не
дрібніше за мінімум — інакше перемикання з'їли б більше, ніж корисна робота. Ці
параметри часто трапляються в старих статтях, проте з Linux 5.13 їх перенесено
з `/proc/sys/kernel/` у debugfs, а в EEVDF лишився один базовий квант. Компроміс
той самий, що й у попередній темі: квант проти накладних витрат.

## Практичне завдання

1. Візьміть два процеси: `yes > /dev/null` (обмежений процесором) і
   `ping -i 0.2 127.0.0.1` (обмежений вводом-виводом).
2. Для кожного порівняйте `time` та `etime` у виводі `ps`, а також співвідношення
   добровільних і примусових перемикань контексту.
3. Поясніть, який із процесів планувальник вважатиме інтерактивним і чому.
4. Запустіть два `yes` з різними значеннями nice на одному ядрі й перевірте, чи
   збігається співвідношення спожитого часу з відношенням ваг.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Який параметр планування є статичним?

- спожитий процесорний час
- час очікування в черзі готових
- оцінка наступного інтервалу обчислень
- задане значення nice

**2.** Про що свідчить великий розрив між `etime` та `time` у виводі `ps`?

- процес майже весь час чекав, а не рахував
- процес спожив багато пам'яті
- процес багато разів перезапускався
- процес має високий пріоритет

**3.** Яка задача вважається обмеженою вводом-виводом?

- та, що має найбільший nice
- та, що вибирає свій квант часу повністю
- та, що займає найбільше пам'яті
- та, що часто блокується після коротких обчислень

**4.** Чому планувальники підвищують пріоритет задачам, обмеженим вводом-виводом?

- так вимагає стандарт POSIX
- інакше вони ніколи не завершаться
- вони майже не відбирають процесор, зате дають швидкий відгук
- вони важливіші за розрахункові задачі за визначенням

**5.** Обчисліть прогноз за формулою експоненційного усереднення при α = 0,5, τ(n) = 8 мс і фактичному t(n) = 4 мс.

- 12 мс
- 6 мс
- 8 мс
- 4 мс

**6.** Що станеться, якщо взяти α = 1?

- формула втратить сенс через ділення на нуль
- прогноз дорівнюватиме останньому виміру й реагуватиме на будь-який шум
- прогноз стане середнім за всю історію
- прогноз перестане змінюватися взагалі

**7.** Чому експоненційне усереднення вигідніше за ковзне середнє?

- воно працює лише для задач реального часу
- воно не потребує жодних вимірів
- воно точніше передбачає раптові зміни
- воно потребує зберігати лише одне число на процес

**8.** Які частки процесора отримають два процеси з вагами 1024 і 335?

- приблизно 90 % і 10 %
- 100 % і 0 %
- приблизно 75 % і 25 %
- порівну, по 50 %

**9.** Що означає `nice -20` для процесу?

- найбільшу вагу серед звичайних процесів, але не монопольний доступ
- заборону витіснення цього процесу
- політику реального часу
- гарантовані 100 % процесорного часу

**10.** Середнє навантаження 4,0 на восьмиядерній машині означає, що:

- система перевантажена вчетверо
- зайнято приблизно половину потужності системи
- у системі рівно чотири процеси
- процесор простоює на 400 %

## 🎯 Міні-проект (30 хв)

### Завдання: побудувати профіль власних процесів

Мета — навчитися відрізняти задачі, обмежені процесором, від задач, обмежених
вводом-виводом, за вимірюваними параметрами, а не «на око».

**Кроки:**

1. Запустіть три різні навантаження:

```bash
yes > /dev/null &                      # обчислення без вводу-виводу
ping -i 0.2 127.0.0.1 > /dev/null &    # постійні короткі очікування
sha256sum /dev/zero &                  # обчислення з читанням потоку
```

2. Для кожного зніміть параметри:

```bash
for pid in $(jobs -p); do
  echo "=== $pid $(ps -o comm= -p $pid)"
  ps -o pcpu=,time=,etime= -p "$pid"
  grep ctxt_switches /proc/"$pid"/status
done
```

3. Складіть таблицю: процес, частка процесора, співвідношення добровільних і
   примусових перемикань, ваш висновок про тип задачі.

4. Змініть одному з процесів nice на 10 і повторіть вимірювання через хвилину.

5. Приберіть за собою: `kill $(jobs -p)`.

**Очікуваний результат:** таблиця, з якої видно, що `ping` майже не споживає
процесора, але має багато добровільних перемикань, а `yes` — навпаки.

**Бонус (для допитливих):**

- Перевірте на практиці таблицю ваг: два `yes` з nice 0 і nice 5 на одному ядрі
  мають дати співвідношення часу приблизно 3:1.
- Порахуйте прогноз інтервалу обчислень за формулою для п'яти послідовних
  вимірів, знятих `pidstat 1 5`.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Статичний параметр** | Заданий ззовні й незмінний: власник, nice, граничний термін |
| **Динамічний параметр** | Обчислюється ядром: спожитий час, час очікування, блокування |
| **CPU-bound задача** | Довгі інтервали обчислень, вибирає квант повністю |
| **I/O-bound задача** | Короткі обчислення й часті блокування, інтерактивна |
| **Експоненційне усереднення** | τ(n+1) = α·t(n) + (1−α)·τ(n) — прогноз наступного інтервалу |
| **Вага (weight)** | Число, у яке планувальник (CFS, EEVDF) перетворює nice; частка = вага / сума ваг |
| **Середнє навантаження** | Середня кількість готових процесів; порівнюють із кількістю ядер |

**Ключовий висновок:** планувальник не знає майбутнього й не може його дізнатися.
Уся його робота будується на оцінці майбутнього за минулим — і саме тому якість
планування залежить не від складності формули, а від того, наскільки поведінка
процесу стабільна в часі.

На наступній лекції — самі алгоритми планування: як за цими параметрами
будується порядок виконання й до чого це призводить у числах.
