## Хто вирішує, хто працює наступним

У вашій системі просто зараз сотні процесів, а ядер — вісім. Отже, у кожен момент
часу працює щонайбільше вісім процесів, а решта чекає. Хтось має вирішувати, кого
пустити до процесора наступним, і робити це тисячі разів на секунду.

Здається, що рішення просте: хай виконується той, хто прийшов першим. Але тоді
відеодзвінок чекав би, поки завершиться архівування папки, і співрозмовник бачив
би вас уривками. Або навпаки: хай завжди виконується найкоротша задача — тоді
архівування не завершиться ніколи, бо короткі задачі надходять безперервно.

**Запитання до аудиторії**: ви запустили компіляцію проєкту й одночасно рухаєте
мишею. Компіляція завантажує всі ядра. Чому курсор не застигає?

```
┌─────────────────────────────────────────────────────────────────────┐
│                ДВА РІШЕННЯ, ЯКІ ОС УХВАЛЮЄ ПОСТІЙНО                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     ПЛАНУВАЛЬНИК (scheduler)        ДИСПЕТЧЕР (dispatcher)          │
│     ─────────────────────────       ──────────────────────          │
│     Запитання: КОГО виконувати      Запитання: ЯК передати          │
│     наступним?                      йому процесор?                  │
│                                                                     │
│     Ухвалює рішення за              Зберігає контекст старого       │
│     політикою (пріоритети,          процесу, завантажує контекст    │
│     черги, кванти часу)             нового, стрибає на його код     │
│                                                                     │
│     Це ПОЛІТИКА                     Це МЕХАНІЗМ                     │
│                                                                     │
│     Розділення політики й механізму — той самий принцип побудови ОС,│
│     що й у лекції про архітектуру ядра.                             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## Три рівні планування

Планування відбувається не в одній точці. Класично виділяють три рівні, які
різняться тим, **як часто** вони спрацьовують і **що саме** вирішують.

```
┌─────────────────────────────────────────────────────────────────────┐
│                          РІВНІ ПЛАНУВАННЯ                           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     ДОВГОСТРОКОВЕ (long-term, job scheduling)                       │
│     Вирішує: чи впускати нову задачу в систему взагалі              │
│     Частота: секунди-хвилини                                        │
│     Керує: ступенем мультипрограмування                             │
│          │                                                          │
│          ▼                                                          │
│     СЕРЕДНЬОСТРОКОВЕ (medium-term, swapping)                        │
│     Вирішує: чи вивантажити процес із пам'яті на диск               │
│     Частота: секунди                                                │
│     Керує: тиском на оперативну пам'ять                             │
│          │                                                          │
│          ▼                                                          │
│     КОРОТКОСТРОКОВЕ (short-term, CPU scheduling)                    │
│     Вирішує: кому віддати процесор просто зараз                     │
│     Частота: мілісекунди (сотні-тисячі разів на секунду)            │
│     Керує: розподілом процесорного часу                             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Довгострокове планування: чому його майже не видно

Довгостроковий планувальник вирішує, скільки процесів одночасно перебуває в
системі. Він народився в епоху пакетної обробки: програми подавали колодами
перфокарт, пам'яті було на кілька задач, і хтось мав вирішувати, яку колоду
завантажити наступною.

У сучасній настільній системі ви його не помітите: ви запускаєте програму — вона
запускається. Це не означає, що рівень зник. Він перемістився:

- **у планувальник завдань кластера** — Kubernetes чи Slurm вирішують, чи є місце
  для нового пода або задачі, і ставлять її в чергу, якщо місця немає;
- **у механізми обмеження ресурсів** — cgroups і ulimit не дають одному
  користувачеві створити тисячі процесів;
- **в OOM killer** — коли пам'яті бракує, ядро завершує процес, тобто ухвалює
  рішення про склад задач у системі постфактум.

**Чому саме так.** Коли пам'яті мало, впустити зайву задачу — означає поставити
під загрозу всі наявні. Коли пам'яті багато, вартість зайвого процесу мала, і
зручність користувача переважає. Тому рівень не зник, а перемістився туди, де
ресурс знову дефіцитний, — у кластери й контейнери.

### Середньострокове планування: обмін пам'яті на час

Середньостроковий планувальник вивантажує процеси, які довго не виконуються,
щоб звільнити пам'ять для активних.

```bash
# Скільки пам'яті зараз вивантажено у swap
free -h

# Скільки сторінок ядро вивантажило та підкачало від старту системи
vmstat -s | grep -E "pages swapped"

# Наскільки охоче ядро вивантажує сторінки: 0 — неохоче, 100 — охоче
cat /proc/sys/vm/swappiness
```

**Компроміс тут прямий**: вивантажений процес звільняє пам'ять, але його
повернення коштує читання з диска — мілісекунди на SSD і десятки мілісекунд на
жорсткому диску. Тому вивантажують тих, хто спить, а не тих, хто чекає на
процесор.

### Короткострокове планування: те, що працює тисячі разів на секунду

Це той планувальник, про який зазвичай і говорять. Він спрацьовує щоразу, коли
процесор звільняється, і має ухвалити рішення за одиниці мікросекунд — інакше
сам стане вузьким місцем.

## Черги, між якими рухаються процеси

Планувальник працює не зі списком «усіх процесів», а з кількома чергами.

```
┌─────────────────────────────────────────────────────────────────────┐
│                         ЧЕРГИ ПЛАНУВАЛЬНИКА                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     Нові процеси                                                    │
│          │                                                          │
│          ▼                                                          │
│     ┌──────────────┐   dispatch    ┌───────────┐    exit            │
│     │ ЧЕРГА ГОТОВИХ│──────────────►│ ПРОЦЕСОР  │───────────►        │
│     │ (ready queue)│◄──────────────│ (running) │                    │
│     └──────────────┘   preempt     └─────┬─────┘                    │
│          ▲                               │ запит вводу-виводу       │
│          │                               ▼                          │
│          │                      ┌──────────────────┐                │
│          └──────────────────────│ ЧЕРГА ПРИСТРОЮ   │                │
│            переривання від      │ (device queue)   │                │
│            пристрою: дані є     └──────────────────┘                │
│                                                                     │
│     Черга готових — одна на ядро; черг пристроїв стільки, скільки   │
│     самих пристроїв: диск, мережа, клавіатура.                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Стани процесу з попереднього модуля — це і є позиції в цих чергах: `READY` —
стоїть у черзі готових, `RUNNING` — на процесорі, `WAITING` — у черзі пристрою.

## Чотири точки, де виникає рішення

Планувальник викликають не будь-коли, а в чотирьох ситуаціях:

| № | Ситуація | Перехід стану | Чи обов'язкове рішення |
|---|----------|---------------|------------------------|
| 1 | Процес запитав ввід-вивід або чекає на подію | RUNNING → WAITING | так, процесор звільнився |
| 2 | Вичерпано квант часу або прийшов важливіший процес | RUNNING → READY | ні, можна дати працювати далі |
| 3 | Завершився ввід-вивід, процес знову готовий | WAITING → READY | ні, можна не витісняти поточного |
| 4 | Процес завершився | RUNNING → TERMINATED | так, процесор звільнився |

**Тут і ховається означення двох типів планування.** Якщо планувальник ухвалює
рішення лише в ситуаціях 1 і 4 — коли процесор звільнився сам, — планування
**невитісняльне**: процес віддає процесор добровільно. Якщо рішення ухвалюється
й у ситуаціях 2 і 3 — планування **витісняльне**: ОС може відібрати процесор.

**Чому всі сучасні системи витісняльні.** Невитісняльна система віддає контроль
програмі: цикл без вводу-виводу вішає систему назавжди. Саме так падала Windows 3.x
і класична Mac OS — там була кооперативна багатозадачність, і одна програма, що
не віддала керування, зупиняла всі інші.

## Диспетчер і диспетчерська затримка

Коли рішення ухвалено, справу переймає диспетчер. Його робота — це чистий
накладний час: поки він працює, корисних обчислень не відбувається.

```
┌─────────────────────────────────────────────────────────────────────┐
│              З ЧОГО СКЛАДАЄТЬСЯ ДИСПЕТЧЕРСЬКА ЗАТРИМКА              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     1. Зберегти контекст поточного процесу       ~1 мкс             │
│        (регістри, лічильник команд, стек)                           │
│                                                                     │
│     2. Оновити блок керування процесом (PCB)     ~0,5 мкс           │
│                                                                     │
│     3. Обрати наступний процес у черзі готових   ~0,5-2 мкс         │
│        (власне робота планувальника)                                │
│                                                                     │
│     4. Переключити адресний простір (регістр CR3) ~1 мкс            │
│        + втрата записів TLB                                         │
│                                                                     │
│     5. Завантажити контекст нового процесу       ~1 мкс             │
│                                                                     │
│     РАЗОМ: 3-10 мкс на перемикання процесів                         │
│            1-3 мкс на перемикання потоків одного процесу            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Порахуймо разом.** Нехай квант часу — 10 мс, а перемикання коштує 5 мкс.
Накладні витрати становлять 5 мкс / 10 005 мкс ≈ 0,05 % — непомітно. Тепер
зробімо квант 100 мкс заради «чуйності»: 5 мкс / 105 мкс ≈ 4,8 % процесорного
часу згоряє на самі перемикання. А за кванта 20 мкс — уже 20 %.

Звідси правило, яке має пояснити викладач: **квант часу вибирають не «щоб було
швидше», а так, щоб він був принаймні на два порядки більший за вартість
перемикання**.

```bash
# Скільки перемикань контексту відбулося від старту системи
grep ctxt /proc/stat

# Скільки перемикань за секунду відбувається зараз (колонка cs)
vmstat 1 5

# Добровільні та примусові перемикання конкретного процесу
grep ctxt_switches /proc/self/status
```

Різниця між `voluntary_ctxt_switches` і `nonvoluntary_ctxt_switches` —
діагностична: перші означають, що процес сам чекав вводу-виводу, другі — що його
витіснили. Процес із великою кількістю примусових перемикань бореться за
процесор із кимось іще.

## Критерії: що саме ми оптимізуємо

Сказати «планувальник має бути хорошим» недостатньо — потрібні вимірювані
критерії. Їх шість, і вони конфліктують.

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ШІСТЬ КРИТЕРІЇВ ПЛАНУВАННЯ                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ЗАВАНТАЖЕННЯ ПРОЦЕСОРА (CPU utilization)                          │
│   Частка часу, коли процесор робить корисну роботу. Максимізуємо.   │
│                                                                     │
│   ПРОПУСКНА ЗДАТНІСТЬ (throughput)                                  │
│   Кількість завершених задач за одиницю часу. Максимізуємо.         │
│                                                                     │
│   ЧАС ОБІГУ (turnaround time)                                       │
│   Від надходження задачі до її завершення. Мінімізуємо.             │
│                                                                     │
│   ЧАС ОЧІКУВАННЯ (waiting time)                                     │
│   Скільки задача простояла в черзі готових. Мінімізуємо.            │
│                                                                     │
│   ЧАС ВІДГУКУ (response time)                                       │
│   Від надходження до першої реакції. Мінімізуємо.                   │
│                                                                     │
│   СПРАВЕДЛИВІСТЬ (fairness, predictability)                         │
│   Кожен отримує частку; однакові задачі тривають однаково.          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Чому критерії не можна оптимізувати разом

| Покращуємо | Ціною чого |
|------------|------------|
| Час відгуку (дрібний квант) | Пропускна здатність: більше перемикань контексту |
| Пропускна здатність (великий квант) | Час відгуку: інтерактивна задача довго чекає |
| Середній час очікування (коротші задачі першими) | Справедливість: довгі задачі голодують |
| Справедливість (усім порівну) | Середній час обігу: короткі задачі чекають нарівні з довгими |
| Передбачуваність (жорсткі кванти) | Завантаження процесора: ядро може простоювати |

**Ключова теза лекції:** не існує планувальника, кращого за всіма критеріями
одночасно. Є планувальник, який відповідає типу системи.

| Тип системи | Головний критерій | Чим жертвують |
|-------------|-------------------|---------------|
| Пакетна обробка (розрахунки, рендеринг) | пропускна здатність, завантаження | часом відгуку |
| Інтерактивна (настільна ОС, сервер застосунків) | час відгуку | частиною пропускної здатності |
| Реального часу (верстат, кардіостимулятор) | передбачуваність, гарантований термін | середньою ефективністю |

### Розбір помилкового міркування

> «Хороший планувальник — той, що тримає завантаження процесора на 100 %.»

Міркування здається логічним: простій процесора — це змарнований ресурс. Але:

1. На настільній системі 100 % завантаження означає, що черга готових не
   порожніє ніколи, тобто кожна нова інтерактивна дія чекає. Користувач бачить
   це як підгальмовування інтерфейсу.
2. Завантаження 100 % можна отримати штучно — циклом `while(1);`. Корисної
   роботи при цьому нуль, а метрика ідеальна. Метрика, яку легко обдурити, не
   може бути єдиною метою.
3. Для сервера з чергою запитів завантаження понад приблизно 80 % означає, що
   черга росте швидше, ніж розсмоктується: час відгуку починає зростати різко.

**Правильне формулювання**: завантаження процесора — це критерій ефективності
для пакетних систем і **індикатор**, а не мета для інтерактивних.

**Запитання до аудиторії**: диспетчер таксі має десять машин. Якщо всі десять
постійно в дорозі — це ідеальна робота чи ознака того, що виклику доведеться
чекати?

## Як ці критерії виміряти на реальній системі

```bash
# Завантаження процесора, черга готових (колонка r) та перемикання (cs)
vmstat 1 5

# Середнє навантаження: скільки процесів у середньому готові або чекають
cat /proc/loadavg

# Затримка планувальника для конкретного процесу:
# sum_exec_runtime — виконувався, wait_sum — простояв у черзі готових.
# wait_sum рахується, лише коли ввімкнено статистику планувальника
sudo sysctl kernel.sched_schedstats=1
grep -E "se.sum_exec_runtime|wait_sum" /proc/self/sched

# Стан черг готових по ядрах (з Linux 5.13 — у debugfs, раніше /proc/sched_debug)
sudo grep -E "^cpu#|\.nr_running|\.nr_switches" /sys/kernel/debug/sched/debug | head -12
```

Порівняння `sum_exec_runtime` і `wait_sum` — найпряміший спосіб показати
студентам, що «повільно» буває двох різних природ: процес або справді рахує
довго, або переважно чекає.

## Практичне завдання

1. Запустіть `vmstat 1` і подивіться на колонки `r` (черга готових) та `cs`
   (перемикання контексту) у спокої.
2. Запустіть у сусідньому терміналі `yes > /dev/null` стільки разів, скільки у
   вас ядер, і знову подивіться на `r` і `cs`.
3. Поясніть, чому `r` зросла, а `cs` майже не змінилася.
4. Тепер запустіть удвічі більше таких процесів, ніж ядер. Що сталося з `cs` і
   чому?

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Чим планувальник відрізняється від диспетчера?

- це дві назви одного компонента ядра
- планувальник перемикає контекст, диспетчер обирає процес
- планувальник працює в режимі користувача, диспетчер — у режимі ядра
- планувальник вирішує, кого виконувати, диспетчер виконує саме перемикання

**2.** Що вирішує довгострокове планування?

- чи впускати нову задачу в систему
- який пристрій обслужити першим
- чи вивантажити процес із пам'яті на диск
- кому віддати процесор у наступному кванті

**3.** Як часто спрацьовує короткострокове планування?

- кілька разів на хвилину
- раз на секунду
- тисячі разів на секунду
- лише під час запуску нових програм

**4.** Що робить середньостроковий планувальник?

- створює нові процеси на запит користувача
- вивантажує процеси, що не виконуються, звільняючи пам'ять
- відбирає процесор у процесу з вичерпаним квантом
- обчислює пріоритети процесів

**5.** У якій із ситуацій планувальник викликається обов'язково?

- вичерпано квант часу
- прийшов процес із вищим пріоритетом
- процес завершив роботу
- завершився ввід-вивід іншого процесу

**6.** Чим витісняльне планування відрізняється від невитісняльного?

- витісняльне застосовують лише в системах реального часу
- процес сам вирішує, коли віддати процесор
- різниця лише в розмірі кванта часу
- ОС може відібрати процесор у процесу до того, як той звільнить його сам

**7.** Перемикання контексту коштує 5 мкс. Який квант часу зробить накладні витрати неприйнятними?

- 20 мкс
- 100 мс
- 10 мс
- 1 с

**8.** Про що свідчить велика кількість примусових перемикань контексту у процесу?

- процес має найвищий пріоритет
- процес багато працює з диском
- процес конкурує за процесор з іншими задачами
- процес майже весь час спить

**9.** Чому 100 % завантаження процесора не є метою для настільної системи?

- черга готових не порожніє, і кожна дія користувача починає чекати
- ядро перестає обробляти переривання
- процесор перегрівається й знижує частоту
- такий показник неможливо виміряти

**10.** Який критерій головний для системи реального часу?

- мінімальний середній час обігу
- передбачуваність і дотримання граничного терміну
- максимальне завантаження процесора
- максимальна пропускна здатність

## 🎯 Міні-проект (30 хв)

### Завдання: виміряти, скільки коштує перемикання контексту

Мета — отримати власне число для накладних витрат і зіставити його з тим, що
наведено в лекції.

**Кроки:**

1. Подивіться стан системи у спокої:

```bash
vmstat 1 5
```

2. Створіть два процеси, що передають один одному сигнал через канал: кожне
   передавання — це пара перемикань контексту.

```bash
mkfifo /tmp/ping /tmp/pong
( for i in $(seq 1 20000); do read -r x < /tmp/ping; echo x > /tmp/pong; done ) &
time ( for i in $(seq 1 20000); do echo x > /tmp/ping; read -r y < /tmp/pong; done )
```

3. Поділіть виміряний час на кількість перемикань (20000 передавань — це
   щонайменше 40000 перемикань) і отримайте вартість одного.

4. Порівняйте зі значенням `cs` з `vmstat 1`, знятим під час досліду.

5. Приберіть за собою:

```bash
rm -f /tmp/ping /tmp/pong
```

**Очікуваний результат:** число в межах одиниць-десятків мікросекунд. Воно буде
більшим за «чисті» 3-10 мкс, бо до перемикання додається робота оболонки з
каналом: у кожній ітерації вона заново відкриває й закриває FIFO. Для порівняння
запустіть готовий бенчмарк `perf bench sched pipe`, який робить те саме без
накладних витрат оболонки (пакет `linux-tools-$(uname -r)`).

**Бонус (для допитливих):**

- Повторіть дослід, прив'язавши обидва процеси до одного ядра
  (`taskset -c 0`), а потім до різних. Поясніть різницю.
- Порівняйте з результатом `perf stat -e context-switches -- ваша_команда`.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Планувальник (scheduler)** | Ухвалює рішення, який процес виконувати наступним — політика |
| **Диспетчер (dispatcher)** | Виконує перемикання контексту — механізм |
| **Довгострокове планування** | Чи впускати задачу в систему; керує ступенем мультипрограмування |
| **Середньострокове планування** | Вивантаження процесів у swap для звільнення пам'яті |
| **Короткострокове планування** | Вибір процесу для виконання, мілісекундний масштаб |
| **Диспетчерська затримка** | Час перемикання: 3-10 мкс для процесів, 1-3 мкс для потоків |
| **Витісняльне планування** | ОС може відібрати процесор; основа всіх сучасних систем |

| Критерій | Що вимірює | Напрям |
|----------|------------|--------|
| Завантаження процесора | Частка корисної роботи | максимізувати |
| Пропускна здатність | Задач за одиницю часу | максимізувати |
| Час обігу | Від надходження до завершення | мінімізувати |
| Час очікування | Час у черзі готових | мінімізувати |
| Час відгуку | До першої реакції | мінімізувати |
| Справедливість | Рівність часток | максимізувати |

**Ключовий висновок:** планувальника оцінюють не абстрактно, а за критерієм,
який важливий для цього типу системи. Пакетній системі потрібна пропускна
здатність, інтерактивній — час відгуку, системі реального часу — гарантований
термін. Спроба оптимізувати все одночасно дає посередній результат скрізь.

На наступній лекції — параметри планування: як ОС оцінює, скільки процесорного
часу знадобиться процесу, і звідки беруться пріоритети.
