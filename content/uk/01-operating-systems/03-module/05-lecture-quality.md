## Два сервери з однаковою середньою затримкою

Два сервери обробляють по тисячі запитів. Обидва звітують: середня затримка —
близько 100 мс. На перший користувачі скаржаться, другий хвалять. Обидва звіти
правдиві.

```
┌─────────────────────────────────────────────────────────────────────┐
│                   ОДНЕ СЕРЕДНЄ, ДВА РІЗНІ ДОСВІДИ                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   СЕРВЕР A                          СЕРВЕР B                        │
│   ────────                          ────────                        │
│   985 запитів по 92 мс              1000 запитів по 100 мс          │
│    15 запитів по 600 мс                                             │
│                                                                     │
│   середнє  ≈ 99,6 мс                середнє  = 100 мс               │
│   медіана  = 92 мс                  медіана  = 100 мс               │
│   99-й перцентиль = 600 мс          99-й перцентиль = 100 мс        │
│   максимум = 600 мс                 максимум = 100 мс               │
│                                                                     │
│   Півтора відсотка запитів A        Жоден користувач сервера B      │
│   чекають у 6,5 раза довше.         не чекає довше за 100 мс.       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Чому повільних запитів саме 15, а не 10? Якщо впорядкувати тисячу значень,
99-й перцентиль — це 990-те з них. За 10 повільних запитів на 990-му місці ще
стояв би швидкий, і p99 показав би 92 мс: хвіст ховався б і від цього
показника, і його «ловив» би лише p99,5 або p99,9.

Середнє арифметичне приховало саме те, що відчуває користувач. Тому **якість
диспетчеризації оцінюють не середнім, а розподілом**.

**Запитання до аудиторії**: якщо ваш застосунок робить 50 запитів до сервера на
одне відкриття сторінки, а повільних запитів лише 1 %, яка ймовірність, що хоча б
один із п'ятдесяти виявиться повільним?

## Показники якості

Таблиця 1 — Показники, якими описують якість обслуговування

| Показник | Що показує | Коли критичний |
|----------|------------|----------------|
| Середнє | Загальний рівень | Пакетні розрахунки |
| Медіана (p50) | Типовий випадок | Огляд стану системи |
| p95, p99 | Хвіст розподілу — найгірші випадки | Вебсервіси, ігри |
| Максимум | Найгірший можливий випадок | Системи реального часу |
| Джитер | Розкид затримки між викликами | Звук, відео, керування |

**Чому перцентилі важливіші за середнє.** Запит на 600 мс не «компенсується»
дев'ятьма запитами по 95 мс: користувач не бачить середнього, він бачить кожен
випадок окремо. Ба більше, у типовому застосунку одна сторінка збирається з
десятків запитів, і ймовірність зустріти повільний запит зростає з їхньою
кількістю.

**Порахуймо разом.** Один запит потрапляє в найповільніший 1 % з імовірністю
0,01. Якщо сторінка робить 50 незалежних запитів і чекає на всі:

```
P(усі швидкі) = 0,99 ⁵⁰ ≈ 0,605

Отже, приблизно 40 % відкриттів сторінки зачеплять хоча б один
повільний запит — хоча «повільних» усього 1 %.
```

Це міркування називають **проблемою хвостових затримок** (tail latency). Воно
пояснює, чому великі сервіси оптимізують саме p99, а не середнє.

### Розбір помилкового міркування

> «Система реального часу — це швидка система.»

Найпоширеніша помилка в темі. Система реального часу — це система
**передбачувана**, і вона часто працює повільніше за звичайну.

| | Звичайна ОС | ОС реального часу |
|---|-------------|-------------------|
| Середній час реакції | 0,5 мс | 2 мс |
| Найгірший час реакції | 200 мс (може бути будь-яким) | 3 мс, гарантовано |
| Що оптимізовано | середнє | максимум |

Для верстата, який має зупинити фрезу за 5 мс, друга система придатна, а перша
— ні, попри вчетверо кращий середній показник. Причина проста: перша ніколи не
обіцяла максимуму, і жодне середнє цю обіцянку не замінить.

**Як це пояснювати студентам.** Запитайте: чи поїхали б ви автомобілем, гальма
якого спрацьовують у середньому за 0,1 с, але раз на тисячу натискань — за
3 секунди? Середнє чудове, максимум неприйнятний.

## Планування за термінами

У системах реального часу задачі описують трьома числами: період `T`, час
обчислень `C` і граничний термін `D` (зазвичай `D = T`).

```
┌─────────────────────────────────────────────────────────────────────┐
│                          ПЕРІОДИЧНА ЗАДАЧА                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     T = 4 мс (період)                                               │
│     C = 1 мс (обчислення)                                           │
│                                                                     │
│     0    1         4    5         8    9        12                  │
│     ├────┼─────────┼────┼─────────┼────┼─────────┤                  │
│     │ C  │  вільно │ C  │  вільно │ C  │ вільно  │                  │
│     └────┴─────────┴────┴─────────┴────┴─────────┘                  │
│     ▲              ▲              ▲                                 │
│     термін         термін         термін                            │
│                                                                     │
│     Завантаження задачі: U = C / T = 1 / 4 = 0,25                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Тест на можливість планування

Питання, на яке треба відповісти **до** запуску системи: чи встигне планувальник
виконати всі задачі вчасно?

```
Сумарне завантаження: U = Σ (Cᵢ / Tᵢ)

EDF (найраніший термін першим):      система планована, якщо U ≤ 1
RMS (фіксовані пріоритети за
     періодом, коротший період —
     вищий пріоритет):               достатня умова U ≤ n·(2^(1/n) − 1)
```

**Приклад 1.** Три задачі: (C=1, T=4), (C=2, T=6), (C=1, T=8).

```
U = 1/4 + 2/6 + 1/8 = 0,25 + 0,333 + 0,125 = 0,708
Межа RMS для n = 3: 3·(2^(1/3) − 1) = 0,7798

0,708 ≤ 0,7798 → набір планований і за RMS, і за EDF.
```

**Приклад 2.** Дві задачі: (C=2, T=5), (C=4, T=7).

```
U = 2/5 + 4/7 = 0,4 + 0,5714 = 0,9714
Межа RMS для n = 2: 2·(√2 − 1) = 0,8284

0,9714 > 0,8284 → тест RMS НЕ пройдено.
0,9714 ≤ 1       → EDF упорається.
```

**Важливе застереження, яке часто пропускають.** Умова RMS — **достатня, але не
необхідна**. Якщо тест не пройдено, це не доводить, що набір непланований за
RMS; це означає лише, що проста перевірка гарантії не дає, і потрібен точніший
аналіз. Плутати «тест не пройдено» з «працювати не буде» — типова помилка, і
студентам варто показати цю різницю окремо: достатня умова відповідає на питання
«чи точно так», а не «чи можливо так».

### Чому тоді всюди не використовують EDF

| EDF | RMS / фіксовані пріоритети |
|-----|----------------------------|
| Використовує ресурс до 100 % | Гарантія лише до ~69 % при великому n |
| Пріоритети перераховуються щоразу | Пріоритети сталі, реалізація простіша |
| При перевантаженні деградує непередбачувано: терміни починають зривати всі задачі | При перевантаженні страждають лише низькопріоритетні |
| Потрібне точне знання термінів | Достатньо знати періоди |

Остання відмінність вирішальна для критичних систем: у літаку краще, щоб при
перевантаженні відмовила система розваг, а не керування закрилками. Тому
авіоніка й автомобільні системи традиційно будуються на фіксованих пріоритетах,
а EDF застосовують там, де перевантаження виключене.

## Інверсія пріоритетів

Найвідоміша пастка гарантій: високопріоритетна задача чекає на низькопріоритетну,
і жодні пріоритети цього не рятують.

```
┌─────────────────────────────────────────────────────────────────────┐
│                        ІНВЕРСІЯ ПРІОРИТЕТІВ                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   H — високий пріоритет   M — середній   L — низький                │
│                                                                     │
│   1. L захоплює м'ютекс спільного ресурсу                           │
│   2. H прокидається, витісняє L, хоче той самий м'ютекс             │
│      → H блокується, чекає на L                                     │
│   3. Прокидається M, витісняє L (M пріоритетніший за L)             │
│      → L не виконується → м'ютекс не звільняється                   │
│      → H чекає на M, хоча M має НИЖЧИЙ пріоритет за H               │
│                                                                     │
│   Результат: найважливіша задача стоїть через задачу,               │
│   яка її взагалі не стосується.                                     │
│                                                                     │
│   ЛІКУВАННЯ: успадкування пріоритету — на час утримання             │
│   м'ютекса L тимчасово отримує пріоритет H.                         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Це не теоретична конструкція.** У липні 1997 року марсохід Mars Pathfinder
почав періодично перезавантажуватися вже на поверхні Марса. Причиною виявилася
саме інверсія пріоритетів: високопріоритетна задача шини даних чекала на
низькопріоритетну задачу метеоданих, яку витісняла задача зв'язку середнього
пріоритету. Сторожовий таймер не бачив завершення циклу й перезавантажував
систему. Виправлення полягало в увімкненні успадкування пріоритету —
його передали на Марс оновленням.

Історія корисна тим, що показує: **гарантія, побудована на пріоритетах,
перестає бути гарантією, щойно з'являється спільний ресурс**.

У Linux успадкування пріоритету вмикається явно:

```c
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&mutex, &attr);
```

## Як виміряти якість на практиці

```bash
# Затримка планувальника: скільки процес сумарно чекав у черзі готових
# (потрібна статистика планувальника: sudo sysctl kernel.sched_schedstats=1)
grep -E "wait_sum|wait_max|wait_count" /proc/self/sched

# wait_max — найгірший випадок; саме він цікавить у задачах реального часу

# Розподіл затримок таймера (пакет rt-tests)
# sudo cyclictest -t1 -p 80 -n -i 1000 -l 10000

# Статистика по всій системі: черга готових і перемикання
vmstat 1 5
```

Ключовий рядок тут — `wait_max`. Середнє очікування може бути мікросекундним, а
максимальне — мілісекундним: саме цю різницю і треба показати студентам, бо вона
й є різницею між «зазвичай швидко» та «гарантовано швидко».

## Практичне завдання

1. Зніміть `wait_sum`, `wait_count` і `wait_max` для процесу в спокої, обчисліть
   середнє очікування як `wait_sum / wait_count`.
2. Завантажте систему (`yes > /dev/null` на кожне ядро) і повторіть вимірювання.
3. Порівняйте, у скільки разів зросло середнє й у скільки — максимум. Який із
   показників зріс сильніше та чому?
4. Порахуйте, чи є планованим за RMS набір задач: (C=1, T=3), (C=1, T=5),
   (C=2, T=10).

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Чому середню затримку недостатньо для оцінки якості обслуговування?

- вона приховує рідкісні, але дуже повільні випадки
- вона залежить від кількості ядер
- її неможливо виміряти на практиці
- вона завжди завищена через викиди

**2.** Що показує 99-й перцентиль затримки?

- значення, гірше за яке лише один відсоток випадків
- частку запитів, що завершилися з помилкою
- максимально можливу затримку
- середнє серед найповільніших запитів

**3.** Сторінка робить 50 незалежних запитів, кожен з імовірністю 1 % потрапляє у повільні. Яка приблизно частка відкриттів зачепить хоча б один повільний запит?

- близько 1 %
- близько 40 %
- близько 5 %
- близько 99 %

**4.** Що таке джитер?

- розкид затримки між послідовними операціями
- час обробки переривання
- середня затримка системи
- кількість перемикань контексту

**5.** Чим м'який реальний час відрізняється від жорсткого?

- термін дотримується завжди
- порушення терміну псує якість, але не є відмовою системи
- він застосовується лише в медичному обладнанні
- у ньому взагалі немає термінів

**6.** Яке твердження про систему реального часу правильне?

- вона не має планувальника
- вона передбачувана, але часто повільніша за звичайну
- вона завжди швидша за систему загального призначення
- у ній усі задачі мають однаковий пріоритет

**7.** За якої умови набір періодичних задач гарантовано планований за EDF?

- сумарне завантаження не перевищує 0,69
- усі задачі мають однаковий період
- сумарне завантаження не перевищує 1
- кількість задач не перевищує кількості ядер

**8.** Задачі (C=2, T=5) і (C=4, T=7) дають U = 0,97 при межі RMS 0,83. Що з цього випливає?

- набір планований за RMS
- обчислення містить помилку
- набір гарантовано непланований жодним алгоритмом
- тест RMS не пройдено, але це ще не доводить непланованості

**9.** У чому суть інверсії пріоритетів?

- пріоритети процесів змінюються місцями під час перемикання
- низькопріоритетна задача виконується раніше за високопріоритетну за планом
- високопріоритетна задача чекає через задачу середнього пріоритету
- планувальник ігнорує пріоритети за високого навантаження

**10.** Як лікують інверсію пріоритетів?

- забороною використовувати м'ютекси
- збільшенням кванта часу
- підвищенням пріоритету всіх задач одночасно
- успадкуванням пріоритету на час утримання спільного ресурсу

## 🎯 Міні-проект (30 хв)

### Завдання: побудувати розподіл затримок власної системи

Мета — побачити різницю між середнім і максимумом на власних вимірах.

**Кроки:**

1. Виміряйте затримку сну в циклі: скільки насправді минає там, де програма
   просила 1 мілісекунду.

```bash
python3 - <<'EOF'
import time
delays = []
for _ in range(2000):
    t0 = time.perf_counter()
    time.sleep(0.001)
    delays.append((time.perf_counter() - t0) * 1000)
delays.sort()
n = len(delays)
print("середнє  %.3f мс" % (sum(delays) / n))
print("медіана  %.3f мс" % delays[n // 2])
print("p95      %.3f мс" % delays[int(n * 0.95)])
print("p99      %.3f мс" % delays[int(n * 0.99)])
print("максимум %.3f мс" % delays[-1])
EOF
```

2. Запишіть числа. Потім завантажте систему (`yes > /dev/null` на кожне ядро) і
   повторіть вимір.

3. Складіть таблицю «спокій / навантаження» для всіх п'яти показників.

4. Дайте відповідь: у скільки разів зросло середнє й у скільки — максимум? Який
   висновок це дає для системи, що мала б гарантувати реакцію за 5 мс?

**Очікуваний результат:** під навантаженням середнє зростає помірно, а максимум
— у рази. Саме тому звичайна ОС не дає жорстких гарантій.

**Бонус (для допитливих):**

- Повторіть дослід, запустивши вимірювальний скрипт із політикою реального часу
  (`sudo chrt -f 50 python3 ...`), і порівняйте максимум.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Перцентиль (p95, p99)** | Значення, гірше за яке лише 5 % або 1 % випадків |
| **Хвостова затримка** | Рідкісні повільні випадки, що визначають досвід користувача |
| **Джитер** | Розкид затримки між послідовними операціями |
| **Best-effort** | Обслуговування без гарантії терміну |
| **М'який реальний час** | Порушення терміну погіршує якість, але не є відмовою |
| **Жорсткий реальний час** | Порушення терміну = відмова системи |
| **Тест планованості** | Перевірка U = Σ(Cᵢ/Tᵢ) проти межі алгоритму |
| **Інверсія пріоритетів** | Високопріоритетна задача блокована через задачу середнього пріоритету |

| Алгоритм | Межа завантаження | Поведінка при перевантаженні |
|----------|-------------------|------------------------------|
| EDF | U ≤ 1 | деградують усі задачі одразу |
| RMS | U ≤ n·(2^(1/n) − 1) | страждають лише низькопріоритетні |

**Ключовий висновок:** якість диспетчеризації — це не швидкість, а виконання
обіцянки. Best-effort система не обіцяє нічого й тому не може «порушити» термін;
система реального часу обіцяє максимум і саме за максимумом її й оцінюють. Тому
перше питання до будь-якої системи не «наскільки вона швидка», а «що саме вона
гарантує».

На цьому модуль планування завершено. Наступний модуль — організація віртуальної
пам'яті: як ОС створює для кожного процесу ілюзію власного адресного простору.
