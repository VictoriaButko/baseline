## Суперечку про алгоритм вирішує розрахунок

У темі про алгоритми планування сучасних ОС ми вже назвали основні підходи й
подивилися, як влаштовані CFS у Linux і планувальник Windows. Тепер зробимо те,
без чого ця тема лишається набором слів: **порахуємо**.

Візьмемо один набір задач і проженемо його крізь п'ять алгоритмів. Усі числа в
цій лекції отримані симулятором, код якого наведено наприкінці, — їх можна
перевірити й відтворити.

**Запитання до аудиторії**: якщо алгоритм A дає середній час очікування 3, а
алгоритм B — 5, чи означає це, що A кращий?

```
┌─────────────────────────────────────────────────────────────────────┐
│                  НАБІР ЗАДАЧ ДЛЯ ВСІХ РОЗРАХУНКІВ                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Процес   Час надходження   Потрібно обчислень                     │
│   ──────   ───────────────   ──────────────────                     │
│     P1            0                  7                              │
│     P2            2                  4                              │
│     P3            4                  1                              │
│     P4            5                  4                              │
│                                                                     │
│   Разом 16 одиниць обчислень. Одна одиниця — умовний квант;         │
│   у реальній системі це від часток мілісекунди до десятків мс.      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Три метрики, які рахуємо

```
Час обігу    (turnaround) = час завершення − час надходження
Час очікування (waiting)  = час обігу − час обчислень
Час відгуку  (response)   = перший запуск − час надходження
```

**Чому саме три.** Час обігу цікавить того, хто чекає результату цілком
(розрахунок, збірка проєкту). Час відгуку — того, хто взаємодіє з програмою
(натиснув клавішу — коли побачу літеру). Час очікування показує, скільки часу
задача змарнувала в черзі, і зручний для порівняння алгоритмів між собою.

## FCFS: перший прийшов — перший обслужений

```
┌─────────────────────────────────────────────────────────────────────┐
│                      FCFS: ДІАГРАМА ВИКОНАННЯ                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌──────────────┬────────┬──┬────────┐                             │
│   │      P1      │   P2   │P3│   P4   │                             │
│   └──────────────┴────────┴──┴────────┘                             │
│   0              7        11 12       16                            │
│                                                                     │
│   Процес  прихід  обч.  заверш.  обіг  очік.  відгук                │
│     P1       0      7       7      7      0       0                 │
│     P2       2      4      11      9      5       5                 │
│     P3       4      1      12      8      7       7                 │
│     P4       5      4      16     11      7       7                 │
│                                                                     │
│   Середнє: обіг 8,75   очікування 4,75   відгук 4,75                │
│   Перемикань контексту: 3                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Зверніть увагу на P3: їй потрібна **одна** одиниця обчислень, а прочекала вона
сім. Задача, яка могла б завершитися майже миттєво, затрималася вшестеро довше
за власну тривалість, бо стала в чергу за двома довшими.

Це і є **ефект конвою**: одна довга задача попереду затримує всіх позаду,
незалежно від того, скільки їм потрібно. У реальній системі так виглядає
зависання інтерфейсу, поки в тому ж потоці виконується довга операція.

**Чому FCFS усе одно вивчають.** Він єдиний, хто дає абсолютну передбачуваність
порядку: задача не може бути відсунута тим, хто прийшов пізніше. Саме тому FCFS
досі живе там, де черга має бути чесною за порядком надходження — у чергах
друку, в обробці запитів до диска без перевпорядкування, у найпростіших
мікроконтролерних системах без витіснення.

## SJF: найкоротша задача першою

```
┌─────────────────────────────────────────────────────────────────────┐
│              SJF (НЕВИТІСНЯЛЬНИЙ): ДІАГРАМА ВИКОНАННЯ               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌──────────────┬──┬────────┬────────┐                             │
│   │      P1      │P3│   P2   │   P4   │                             │
│   └──────────────┴──┴────────┴────────┘                             │
│   0              7  8        12       16                            │
│                                                                     │
│   Процес  прихід  обч.  заверш.  обіг  очік.  відгук                │
│     P1       0      7       7      7      0       0                 │
│     P2       2      4      12     10      6       6                 │
│     P3       4      1       8      4      3       3                 │
│     P4       5      4      16     11      7       7                 │
│                                                                     │
│   Середнє: обіг 8,00   очікування 4,00   відгук 4,00                │
│   Перемикань контексту: 3                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Середній час очікування впав з 4,75 до 4,00 — і це не випадковість.

### Чому SJF оптимальний: міркування обміном

Твердження: серед невитісняльних алгоритмів SJF дає **мінімально можливий**
середній час очікування для заданого набору задач.

Доведення спирається на просту думку. Припустімо, у розкладі поряд стоять дві
задачі: спершу довга тривалістю `L`, одразу за нею коротка тривалістю `S`, де
`S < L`. Поміняймо їх місцями й подивімося, що зміниться:

```
Було:   ... │   L   │ S │ ...      Стало:  ... │ S │   L   │ ...

Коротка чекала L одиниць            Коротка чекає 0
Довга чекала 0                      Довга чекає S

Сумарна зміна очікування: було L, стало S. Оскільки S < L,
сума часу очікування ЗМЕНШИЛАСЬ на (L − S).
```

На задачі, що стоять далі в черзі, обмін не впливає: сумарна тривалість цієї
пари не змінилася, тож усі наступні стартують у той самий момент. Отже, будь-який
розклад, де довга задача стоїть перед коротшою, можна покращити обміном. Розклад,
який покращити обміном не можна, — це розклад, упорядкований за зростанням
тривалості, тобто SJF.

**Це міркування варто провести на дошці повністю**: воно показує студентам, що
оптимальність алгоритму не постулюється, а доводиться, причому засобами рівня
першого курсу.

### Ціна оптимальності

| Проблема | У чому суть |
|----------|-------------|
| Тривалість наперед невідома | Її можна лише оцінювати — див. тему про параметри планування |
| Голодування довгих задач | Потік коротких задач може відсувати довгу нескінченно |
| Оптимальність лише за одним критерієм | Час відгуку в SJF гірший, ніж у Round Robin |

## SRTF: витісняльна версія SJF

Дозволимо перервати поточну задачу, якщо прибула коротша за її залишок.

```
┌─────────────────────────────────────────────────────────────────────┐
│               SRTF (ВИТІСНЯЛЬНИЙ): ДІАГРАМА ВИКОНАННЯ               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌────┬────┬──┬────┬────────┬──────────┐                           │
│   │ P1 │ P2 │P3│ P2 │   P4   │    P1    │                           │
│   └────┴────┴──┴────┴────────┴──────────┘                           │
│   0    2    4  5    7        11         16                          │
│                                                                     │
│   Процес  прихід  обч.  заверш.  обіг  очік.  відгук                │
│     P1       0      7      16     16      9       0                 │
│     P2       2      4       7      5      1       0                 │
│     P3       4      1       5      1      0       0                 │
│     P4       5      4      11      6      2       2                 │
│                                                                     │
│   Середнє: обіг 7,00   очікування 3,00   відгук 0,50                │
│   Перемикань контексту: 5                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Найкращі цифри з усіх п'яти алгоритмів: очікування 3,00, відгук 0,50. Але
подивіться на P1: вона прийшла першою, а завершилася останньою — час обігу 16 при
семи одиницях обчислень. Це та сама несправедливість, тільки тепер вона б'є по
довгих задачах.

**Запитання до аудиторії**: якщо P1 — це збірка вашого проєкту, а P2, P3, P4 —
дрібні задачі, що надходять кожні дві секунди, коли завершиться збірка?

## Round Robin: усім порівну, по кванту

```
┌─────────────────────────────────────────────────────────────────────┐
│              ROUND ROBIN, КВАНТ 2: ДІАГРАМА ВИКОНАННЯ               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌────┬────┬────┬──┬────┬────┬────┬────┬──┐                        │
│   │ P1 │ P2 │ P1 │P3│ P2 │ P4 │ P1 │ P4 │P1│                        │
│   └────┴────┴────┴──┴────┴────┴────┴────┴──┘                        │
│   0    2    4    6  7    9    11   13   15 16                       │
│                                                                     │
│   Процес  прихід  обч.  заверш.  обіг  очік.  відгук                │
│     P1       0      7      16     16      9       0                 │
│     P2       2      4       9      7      3       0                 │
│     P3       4      1       7      3      2       2                 │
│     P4       5      4      15     10      6       4                 │
│                                                                     │
│   Середнє: обіг 9,00   очікування 5,00   відгук 1,50                │
│   Перемикань контексту: 8                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Тепер той самий алгоритм із квантом 4:

```
┌─────────────────────────────────────────────────────────────────────┐
│              ROUND ROBIN, КВАНТ 4: ДІАГРАМА ВИКОНАННЯ               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌────────┬────────┬──┬──────┬────────┐                            │
│   │   P1   │   P2   │P3│  P1  │   P4   │                            │
│   └────────┴────────┴──┴──────┴────────┘                            │
│   0        4        8  9      12       16                           │
│                                                                     │
│   Процес  прихід  обч.  заверш.  обіг  очік.  відгук                │
│     P1       0      7      12     12      5       0                 │
│     P2       2      4       8      6      2       2                 │
│     P3       4      1       9      5      4       4                 │
│     P4       5      4      16     11      7       7                 │
│                                                                     │
│   Середнє: обіг 8,50   очікування 4,50   відгук 3,25                │
│   Перемикань контексту: 4                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Квант часу: компроміс у числах

| Квант | Середній обіг | Середній відгук | Перемикань |
|-------|---------------|-----------------|------------|
| 2 | 9,00 | 1,50 | 8 |
| 4 | 8,50 | 3,25 | 4 |
| ≥ 7 (більший за найдовшу задачу) | 8,75 | 4,75 | 3 |

Зменшення кванта вдвічі покращило час відгуку більш ніж удвічі (3,25 → 1,50),
але погіршило час обігу й подвоїло кількість перемикань. За кванта, більшого за
найдовшу задачу, Round Robin **перетворюється на FCFS** — рядок у таблиці
збігається з розрахунком FCFS повністю.

У нашому розрахунку перемикання вважалися безкоштовними. У реальній системі
кожне коштує 3-10 мкс, тож до часу обігу додається `перемикань × вартість`.
Саме тому квант у Linux не робили надто дрібним: CFS ділив період
`sched_latency_ns` між готовими задачами, але не дрібніше за
`sched_min_granularity_ns`, а EEVDF (з Linux 6.6) має базовий квант близько
3 мс, який задача може попросити зменшити.

Зверніть увагу й на інше: зменшення кванта не завжди погіршує час обігу. З
квантом 4 середній обіг (8,50) кращий, ніж у FCFS (8,75), тобто кращий, ніж за
великого кванта: коротка P3 завершилася раніше, бо не чекала повного
виконання P1.

## Планування за пріоритетами й голодування

Якщо задачам приписати пріоритети, планувальник щоразу обирає найпріоритетнішу
з готових. Проблема очевидна: задача з низьким пріоритетом може не отримати
процесор ніколи, якщо високопріоритетні надходять безперервно. Це **голодування**
(starvation).

Класичне лікування — **старіння** (aging): пріоритет задачі, яка чекає,
поступово підвищують.

```
┌─────────────────────────────────────────────────────────────────────┐
│      СТАРІННЯ: +1 ДО ПРІОРИТЕТУ ЗА КОЖНІ 5 ОДИНИЦЬ ОЧІКУВАННЯ       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Задача з пріоритетом 15 (низьким) у черзі, де постійно            │
│   з'являються задачі з пріоритетом 5 (високим):                     │
│                                                                     │
│   час   0    5    10   15   20   25   30   35   40   45   50        │
│   пр.  15   14   13   12   11   10    9    8    7    6    5         │
│                                                          ▲          │
│                               зрівнялася з високим — буде обрана    │
│                                                                     │
│   Без старіння задача не виконається ніколи.                        │
│   Зі старінням час очікування обмежений згори: (15−5)×5 = 50.       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому це важливо сформулювати саме так.** Старіння не робить планувальник
«справедливішим» у побутовому сенсі — воно дає **гарантію**: жодна задача не
чекатиме довше за обчислювану межу. Гарантія, а не середнє значення, — те, що
можна пообіцяти замовникові системи.

## Багаторівневі черги зі зворотним зв'язком

SJF потребує знати тривалість задачі наперед. Багаторівнева черга зі зворотним
зв'язком (MLFQ) обходить це обмеження: вона **спостерігає** за поведінкою задачі
й переміщує її між чергами.

```
┌─────────────────────────────────────────────────────────────────────┐
│                            ПРАВИЛА MLFQ                             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Черга 0 (високий пріоритет, квант 1)   ← нові задачі сюди         │
│        │ вибрала квант повністю                                     │
│        ▼                                                            │
│   Черга 1 (середній пріоритет, квант 2)                             │
│        │ вибрала квант повністю                                     │
│        ▼                                                            │
│   Черга 2 (низький пріоритет, квант 4)                              │
│                                                                     │
│   ПРАВИЛА:                                                          │
│   1. Є задача у вищій черзі — виконується вона.                     │
│   2. Задачі однієї черги виконуються по колу (Round Robin).         │
│   3. Нова задача потрапляє у найвищу чергу.                         │
│   4. Вибрала квант повністю — опускається на рівень нижче.          │
│   5. Заблокувалася до кінця кванта — лишається на рівні.            │
│   6. Раз на період усі задачі повертають у найвищу чергу.           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому це працює.** Правило 4 автоматично виявляє задачі, обмежені процесором:
той, хто щоразу вибирає квант повністю, поступово опускається вниз. Правило 5
лишає нагорі тих, хто часто блокується, тобто інтерактивні задачі. Виходить
наближення до SJF **без знання тривалості наперед** — система вивела її зі
спостереження.

Правило 6 потрібне з двох причин: задача могла змінити характер (після
завантаження даних почала взаємодіяти з користувачем), і воно ж рятує від
голодування, бо ніхто не лишається внизу назавжди.

Правило 5 у такому вигляді має слабке місце: програму можна «навчити» обманювати
планувальник. Якщо щоразу за мить до кінця кванта робити короткий виклик
вводу-виводу, задача назавжди лишиться нагорі й забиратиме майже весь процесор.
Тому в підручнику OSTEP і в реальних системах правило 4 уточнюють: рахують
**сумарний** час, використаний задачею на рівні, і опускають її, щойно цей
«бюджет» вичерпано, — незалежно від того, скільки разів вона блокувалася.

## Порівняння на одному наборі задач

Таблиця 1 — Результати п'яти алгоритмів на наборі P1-P4

| Алгоритм | Сер. обіг | Сер. очікування | Сер. відгук | Перемикань |
|----------|-----------|-----------------|-------------|------------|
| FCFS | 8,75 | 4,75 | 4,75 | 3 |
| SJF (невитісняльний) | 8,00 | 4,00 | 4,00 | 3 |
| SRTF (витісняльний) | 7,00 | 3,00 | 0,50 | 5 |
| Round Robin, q = 2 | 9,00 | 5,00 | 1,50 | 8 |
| Round Robin, q = 4 | 8,50 | 4,50 | 3,25 | 4 |

### Розбір помилкового міркування

> «Таблиця показує, що SRTF найкращий за всіма стовпцями, крім перемикань.
> Отже, його й треба використовувати.»

Три заперечення, кожне з яких сильніше за попереднє:

1. **Дані взяті з майбутнього.** Щоб обрати найкоротший залишок, треба знати
   тривалість кожної задачі. Реальний планувальник її не знає й користується
   оцінкою, яка помиляється.
2. **Середнє ховає розподіл.** У SRTF задача P1 має час обігу 16 при тривалості 7
   — найгірший результат серед усіх алгоритмів для окремої задачі. Середнє
   покращилося коштом одного учасника.
3. **Набір задач фіксований і скінченний.** Якщо короткі задачі надходитимуть
   безперервно, P1 не завершиться ніколи. Таблиця цього не показує, бо в ній
   лише чотири задачі.

**Правильний висновок із таблиці**: вона порівнює алгоритми за *цим* набором
задач і *за умови*, що тривалості відомі. Саме тому реальні системи беруть
Round Robin із динамічними пріоритетами (або CFS), а не SRTF — вони
програють на цій таблиці, але виграють на реальному потоці задач, де майбутнє
невідоме.

## Симулятор для самостійних експериментів

Усі числа вище отримані цією програмою. Змініть набір задач у `PROCS` — і
перевірите власні гіпотези.

```python
# Симулятор планувальників: FCFS, SJF, SRTF, RR
PROCS = [("P1", 0, 7), ("P2", 2, 4), ("P3", 4, 1), ("P4", 5, 4)]


def metrics(name, segments, procs):
    """segments — список (процес, початок, кінець) у порядку виконання"""
    first, done = {}, {}
    for p, s, e in segments:
        first.setdefault(p, s)
        done[p] = e
    rows = []
    for p, arrival, burst in procs:
        tat = done[p] - arrival
        rows.append((p, arrival, burst, done[p], tat, tat - burst, first[p] - arrival))
    n = len(rows)
    avg = (sum(r[4] for r in rows) / n, sum(r[5] for r in rows) / n,
           sum(r[6] for r in rows) / n)
    print(f"--- {name}")
    print("  діаграма:", " ".join(f"{p}[{s}-{e}]" for p, s, e in segments))
    print("  процес  прихід  обч.  заверш.  обіг  очік.  відгук")
    for r in rows:
        print("  %-6s %6d %5d %8d %5d %6d %7d" % r)
    print("  середнє: обіг %.2f, очікування %.2f, відгук %.2f, перемикань %d"
          % (avg[0], avg[1], avg[2], len(segments) - 1))
    return avg


def fcfs(procs):
    t, segs = 0, []
    for p, a, b in sorted(procs, key=lambda x: x[1]):
        t = max(t, a)
        segs.append((p, t, t + b)); t += b
    return segs


def sjf(procs):
    t, segs, left = 0, [], list(procs)
    while left:
        ready = [x for x in left if x[1] <= t] or [min(left, key=lambda x: x[1])]
        p, a, b = min(ready, key=lambda x: (x[2], x[1]))
        t = max(t, a)
        segs.append((p, t, t + b)); t += b; left.remove((p, a, b))
    return segs


def srtf(procs):
    rem = {p: b for p, a, b in procs}
    arr = {p: a for p, a, b in procs}
    t, segs, cur = 0, [], None
    end = sum(rem.values()) + min(arr.values())
    while any(v > 0 for v in rem.values()):
        ready = [p for p in rem if rem[p] > 0 and arr[p] <= t]
        if not ready:
            t += 1; continue
        nxt = min(ready, key=lambda p: (rem[p], arr[p]))
        if nxt != cur:
            segs.append([nxt, t, t]); cur = nxt
        rem[nxt] -= 1; t += 1; segs[-1][2] = t
    return [tuple(s) for s in segs]


def rr(procs, q):
    rem = {p: b for p, a, b in procs}
    order = sorted(procs, key=lambda x: x[1])
    t, segs, queue, i = 0, [], [], 0
    while i < len(order) and order[i][1] <= t:
        queue.append(order[i][0]); i += 1
    while queue or i < len(order):
        if not queue:
            t = order[i][1]
            while i < len(order) and order[i][1] <= t:
                queue.append(order[i][0]); i += 1
        p = queue.pop(0)
        run = min(q, rem[p])
        segs.append((p, t, t + run)); t += run; rem[p] -= run
        while i < len(order) and order[i][1] <= t:
            queue.append(order[i][0]); i += 1
        if rem[p] > 0:
            queue.append(p)
    return segs


for name, segs in [("FCFS", fcfs(PROCS)), ("SJF (невитісняльний)", sjf(PROCS)),
                   ("SRTF (витісняльний)", srtf(PROCS)),
                   ("Round Robin, q = 2", rr(PROCS, 2)),
                   ("Round Robin, q = 4", rr(PROCS, 4))]:
    metrics(name, segs, PROCS)
```

## Підсумок

| Алгоритм | Тип | Сильна сторона | Слабка сторона |
|----------|-----|----------------|----------------|
| **FCFS** | невитісняльний | передбачуваний порядок | ефект конвою |
| **SJF** | невитісняльний | оптимальний середній час очікування | потребує знати тривалість |
| **SRTF** | витісняльний | найкращі середні показники | голодування довгих задач |
| **Round Robin** | витісняльний | добрий час відгуку, справедливість | залежить від вибору кванта |
| **Priority** | обидва | контроль важливості задач | голодування без старіння |
| **MLFQ** | витісняльний | наближає SJF без знання тривалості | складніший у налаштуванні |

| Показник | FCFS | SJF | SRTF | RR q=2 | RR q=4 |
|----------|------|-----|------|--------|--------|
| Середній обіг | 8,75 | 8,00 | 7,00 | 9,00 | 8,50 |
| Середнє очікування | 4,75 | 4,00 | 3,00 | 5,00 | 4,50 |
| Середній відгук | 4,75 | 4,00 | 0,50 | 1,50 | 3,25 |

**Ключовий висновок:** алгоритм не буває кращим сам по собі — він кращий за
конкретним критерієм на конкретному наборі задач. Тому реальні системи не беруть
переможця таблиці, а комбінують: Round Robin для справедливості, пріоритети для
