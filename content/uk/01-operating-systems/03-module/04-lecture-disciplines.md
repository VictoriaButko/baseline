## Чому процес, який щойно був повільним, раптом стає швидким

Відкрийте важкий документ у редакторі: кілька секунд програма рахує, інтерфейс
підгальмовує. Документ відкрився — і та сама програма миттєво реагує на кожне
натискання. Пріоритет ви не змінювали, `nice` лишилося тим самим. Змінилася
**поведінка** процесу, а планувальник це помітив і перерахував його пріоритет.

Механізм, за яким планувальник обирає з черги й перераховує пріоритети,
називають **дисципліною обслуговування**. Алгоритми з попередньої теми — це
окремі випадки дисциплін; тут ми дивимося, як із них складають робочі
планувальники.

**Запитання до аудиторії**: якби пріоритет процесу ніколи не змінювався, як
поводився б браузер після годинної роботи з важкою сторінкою?

```
┌─────────────────────────────────────────────────────────────────────┐
│               ДИСЦИПЛІНА ОБСЛУГОВУВАННЯ = ДВА ПРАВИЛА               │

│   ──────────────                  ───────────────────               │
│   Кого взяти з черги              Як змінюються пріоритети          │
│   наступним?                      з часом?                          │
│                                                                     │
│   За порядком надходження         Не змінюються (статичні)          │
│   За тривалістю                   Зростають при очікуванні          │
│   За пріоритетом                  Спадають при споживанні           │
```

## Класифікація дисциплін

Дисципліни прийнято розрізняти за двома незалежними ознаками.

Таблиця 1 — Класифікація дисциплін обслуговування

| Ознака | Види | Приклади |
|--------|------|----------|
| Чи враховується пріоритет | безпріоритетні / пріоритетні | FCFS, RR / MLFQ, CFS |
| Чи можна відібрати процесор | відносні (невитісняльні) / абсолютні (витісняльні) | SJF / SRTF, RR |
| Чи змінюється пріоритет із часом | зі статичним / з динамічним пріоритетом | SCHED_FIFO / CFS |

Комбінації цих ознак і дають конкретні дисципліни:

```
┌─────────────────────────────────────────────────────────────────────┐
│            ЧОТИРИ КОМБІНАЦІЇ, ЯКІ ТРАПЛЯЮТЬСЯ НАСПРАВДІ             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   БЕЗПРІОРИТЕТНА + ВІДНОСНА                                         │
│   FCFS. Черга друку, обробка заявок «за номером».                   │
│   Передбачувано, але довга задача блокує всіх.                      │
│                                                                     │
│   БЕЗПРІОРИТЕТНА + АБСОЛЮТНА                                        │
│   Round Robin. Проста розподілена система, мережеві черги.          │
│   Справедливо, але важливість задач не врахована.                   │
│                                                                     │
│   ПРІОРИТЕТНА + ВІДНОСНА                                            │
│   Пакетна обробка з класами задач. Задача дорахує до кінця,         │
│   навіть якщо прийшла важливіша. Потрібне старіння.                 │
│                                                                     │
│   ПРІОРИТЕТНА + АБСОЛЮТНА + ДИНАМІЧНИЙ ПРІОРИТЕТ                    │
│   Усі сучасні ОС загального призначення: Linux, Windows,            │
│   macOS. Найскладніша й найгнучкіша комбінація.                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому саме четверта комбінація перемогла.** Три перші мають нерозв'язний
всередині себе недолік: FCFS не вміє розрізняти важливість, Round Robin — теж, а
відносна пріоритетна дисципліна не здатна швидко відреагувати на появу важливої
задачі. Додавання витіснення й динамічного перерахунку знімає всі три обмеження
ціною складності реалізації. Процесорного часу ця складність майже не коштує:
рішення однаково ухвалюють за мікросекунди.

## Динамічний пріоритет у класичному UNIX

Класичний механізм динамічних пріоритетів у тому вигляді, в якому його реалізовано
в 4.3BSD (1986), виглядав так:

```
пріоритет = PUSER + p_cpu / 4 + 2 × nice

PUSER = 50  — базове значення для задач користувача
p_cpu       — накопичений лічильник спожитого процесорного часу
nice        — статична поправка, задана користувачем
```

У цій системі **менше число означає вищий пріоритет**. Логіка проста: що більше
процесор спожитий, то більше `p_cpu`, то більше число, то нижчий пріоритет.

Щоб процес не лишався покараним назавжди, лічильник щосекунди зменшують:

```
p_cpu = p_cpu × (2 × load) / (2 × load + 1)

load — середнє навантаження системи
```

Таблиця 2 — Відновлення пріоритету процесу після завершення обчислень
(load = 1, тобто коефіцієнт спадання 2/3, nice = 0)

| Секунда | p_cpu | Пріоритет |
|---------|-------|-----------|
| 0 | 60,0 | 65,0 |
| 1 | 40,0 | 60,0 |
| 2 | 26,7 | 56,7 |
| 3 | 17,8 | 54,4 |
| 4 | 11,9 | 53,0 |
| 5 | 7,9 | 52,0 |

За п'ять секунд процес із найгіршого пріоритету 65 повертається майже до базових
50. Саме це ви й спостерігаєте, коли редактор «оживає» після важкої операції.

У System V, описаній у книзі Моріса Баха, ідея та сама, але арифметика простіша:
раз на секунду лічильник ділять навпіл, а до пріоритету додають половину
лічильника. Формула BSD зі спаданням, залежним від навантаження, — пізніше
вдосконалення тієї ж ідеї.

**Роль навантаження у формулі спадання варто пояснити окремо.** За великого
навантаження коефіцієнт `(2·load)/(2·load+1)` наближається до одиниці, тобто
`p_cpu` спадає повільніше. Це не помилка, а навмисне рішення: коли система
завантажена, пам'ять про спожитий час має жити довше, інакше всі процеси швидко
зрівняються й дисципліна виродиться в Round Robin.

## Віртуальний час у CFS: динамічний пріоритет без пріоритетів

Сучасний планувальник Linux не зберігає «пріоритет» у звичному сенсі. Він рахує
для кожного процесу **віртуальний час виконання** `vruntime` і щоразу обирає
процес із найменшим значенням.

```
vruntime += реальний_час × (1024 / вага_процесу)

1024 — вага процесу з nice = 0
```

Процес із меншою вагою «витрачає» віртуальний час швидше, тому швидше поступається
чергою. Підставмо ваги з теми про параметри планування:

Таблиця 3 — Приріст віртуального часу за 1 мс реального виконання

| nice | Вага | Приріст vruntime | Скільки реального часу на 1 мс vruntime |
|------|------|------------------|------------------------------------------|
| −5 | 3121 | 0,33 мс | 3,05 мс |
| 0 | 1024 | 1,00 мс | 1,00 мс |
| +5 | 335 | 3,06 мс | 0,33 мс |

**Порахуймо разом.** Два процеси, `nice 0` і `nice 5`, конкурують за одне ядро.
Планувальник вирівнює їхній `vruntime`. Нехай обидва мають `vruntime = 0`, а
ядро роздало 12 мс реального часу:

```
A (nice 0): отримав 9 мс → vruntime = 9 × 1,00 = 9,00
B (nice 5): отримав 3 мс → vruntime = 3 × 3,06 = 9,18

Віртуальний час майже однаковий — далі вони йтимуть поруч.
Реальні частки: 9 мс і 3 мс, тобто 75 % і 25 %.
```

Ті самі 75 % і 25 %, що й у таблиці ваг із теми про параметри планування — і це
не збіг, а той самий механізм, показаний з іншого боку.

### Чому це елегантно

| Класичні пріоритети | Віртуальний час |
|---------------------|-----------------|
| Потрібен окремий механізм старіння | Старіння вбудоване: хто не виконувався, має менший vruntime |
| Потрібні черги за рівнями | Одне дерево, впорядковане за vruntime |
| Голодування треба лікувати окремо | Голодування неможливе за побудовою (в межах класу fair) |
| Частка процесора не обчислюється явно | Частка = вага / сума ваг, перевіряється арифметикою |

**Головна теза**: CFS замінив «пріоритет» на «борг». Процес, який довго не
виконувався, має найменший віртуальний час і тому обирається першим — не тому,
що він «важливий», а тому, що йому **недодали**.

```bash
# Віртуальний час і статистика очікування конкретного процесу
grep -E "se.vruntime|se.sum_exec_runtime|nr_switches" /proc/self/sched

# Вага процесу, обчислена з nice
ps -o pid,ni,comm -p $$
```

З Linux 6.6 місце CFS зайняв EEVDF, але віртуальний час нікуди не зник: він і
далі визначає, скільки задачі «винні». EEVDF додав друге правило — серед задач,
яким винні (відставання ≥ 0), обирати ту, в якої найраніший віртуальний дедлайн.
Докладно про це — у темі «Алгоритми планування процесів у сучасних ОС» (модуль 2).

## Підвищення пріоритету у Windows

Windows зберігає явні пріоритети (32 рівні), але теж змінює їх динамічно.

```
┌─────────────────────────────────────────────────────────────────────┐
│                   ДИНАМІЧНЕ ПІДВИЩЕННЯ У WINDOWS                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ПРИЧИНА ПІДВИЩЕННЯ                        НА СКІЛЬКИ              │
│   ──────────────────                        ──────────              │
│   Завершився ввід-вивід з диска             +1                      │
│   Завершився ввід-вивід з клавіатури/миші   +6                      │
│   Завершився ввід-вивід зі звукової карти   +8                      │
│   Потік звільнив об'єкт синхронізації       +1                      │
│   Вікно потоку стало активним               квант × 3               │
│   Потік не виконувався понад 4 секунди      до 15 на квант          │
│                                                                     │
│   Після підвищення пріоритет спадає на одиницю за кожен             │
│   відпрацьований квант — до базового значення, не нижче.            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Логіка та сама, що й у Linux, але виражена інакше: замість «недоотриманого часу»
Windows оперує подією. Найбільше підвищення дістається вводу з клавіатури й
звуку — тобто саме тому, що користувач помітить негайно.

Рядок «потік не виконувався понад 4 секунди» — це реалізація старіння, вбудована
в систему: планувальник сам виявляє голодування й лікує його.

### Розбір помилкового міркування

> «Динамічний пріоритет означає, що система вважає процес важливішим.»

Ні, і ця різниця принципова. Динамічний пріоритет — це не оцінка важливості, а
**компенсація за недоотриманий процесорний час**. Процес, що чекав на диск,
підвищують не тому, що він цінніший, а тому, що поки він чекав, інші працювали, і
без компенсації він програватиме щоразу.

Перевірити це міркування легко: два однакові процеси з однаковим `nice`, один
читає файли, другий рахує. Читач регулярно отримує перевагу, хоча жодної
«важливості» йому ніхто не приписував.

> «Отже, щоб програма працювала швидше, треба частіше звертатися до диска.»

Наслідок хибний. Підвищення компенсує **простій**: сумарно процес отримує стільки
ж або менше процесорного часу, просто отримує його швидше після пробудження.
Штучні звертання до диска додадуть очікування, а не продуктивності.

## Як побачити дисципліну на власній системі

```bash
# Політика планування процесу: OTHER (CFS), FIFO, RR, BATCH, IDLE
chrt -p $$

# Перелік політик, доступних у системі
chrt --help | head -20

# Скільки часу процес виконувався, скільки чекав у черзі готових
# (wait_* рахуються, коли ввімкнено sudo sysctl kernel.sched_schedstats=1)
grep -E "sum_exec_runtime|wait_sum|wait_count" /proc/self/sched

# Частка процесора для групи процесів (cgroups v2): у кореневої групи цього
# файлу немає, тож дивимося на групу сеансів користувачів
cat /sys/fs/cgroup/user.slice/cpu.weight
```

Показник `wait_sum` — це сумарний час у черзі готових. Порівнявши його з
`sum_exec_runtime` для двох процесів із різним `nice`, студент бачить дисципліну
не на схемі, а у власних числах.

## Практичне завдання

1. Запустіть два однакові навантаження з `nice 0` і `nice 10` на одному ядрі.
2. Через хвилину порівняйте `sum_exec_runtime` обох процесів із `/proc/PID/sched`.
3. Обчисліть очікуване співвідношення за таблицею ваг і порівняйте з виміряним.
4. Запустіть третій процес, який щосекунди читає файл, і подивіться, як його
   `wait_sum` відрізняється від двох перших. Поясніть різницю.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** З яких двох правил складається дисципліна обслуговування?

- правило виділення пам'яті й правило її звільнення
- правило вибору з черги й правило перерахунку пріоритетів
- правило створення процесів і правило їх завершення
- правило обробки переривань і правило маскування

**2.** Яка дисципліна називається абсолютною?

- невитісняльна: процес виконується до завершення
- витісняльна: процесор можна відібрати в поточного процесу
- та, у якій усі процеси рівноправні
- та, у якій пріоритети не змінюються

**3.** Яку комбінацію ознак використовують сучасні ОС загального призначення?

- пріоритетну, абсолютну, з динамічним пріоритетом
- безпріоритетну, відносну, зі статичним пріоритетом
- пріоритетну, відносну, зі статичним пріоритетом
- безпріоритетну, абсолютну, з динамічним пріоритетом

**4.** У класичній формулі UNIX `пріоритет = 50 + p_cpu/4 + 2×nice` більше число означає:

- більшу вагу процесу
- вищий пріоритет
- нижчий пріоритет
- більший квант часу

**5.** Навіщо лічильник `p_cpu` щосекунди зменшують?

- щоб звільнити пам'ять від старої статистики
- щоб пришвидшити перемикання контексту
- щоб процес, який перестав споживати процесор, повернув собі пріоритет
- щоб пріоритет ніколи не змінювався

**6.** Чому за великого навантаження `p_cpu` спадає повільніше?

- щоб пришвидшити завершення довгих задач
- щоб пам'ять про спожитий час жила довше й дисципліна не виродилася
- через обмеження розрядності лічильника
- щоб зменшити кількість перемикань контексту

**7.** Як обчислюється приріст віртуального часу в CFS?

- квант часу помножити на значення nice
- вагу процесу поділити на суму ваг усіх процесів
- реальний час поділити на кількість ядер
- реальний час помножити на 1024 і поділити на вагу процесу

**8.** Процес із `nice 5` отримав 3 мс реального часу. На скільки зросте його vruntime?

- приблизно на 9 мс
- приблизно на 3 мс
- приблизно на 0,3 мс
- приблизно на 1 мс

**9.** Чому в CFS голодування неможливе за побудовою?

- ядро періодично скидає всі лічильники
- усі процеси мають однакову вагу
- процеси з низьким пріоритетом завершуються примусово
- процес, який не виконувався, має найменший vruntime і буде обраний

**10.** Що насправді означає динамічне підвищення пріоритету?

- компенсацію за процесорний час, недоотриманий під час очікування
- збільшення кванта часу назавжди
- перехід процесу в режим реального часу
- визнання процесу важливішим за інші

## 🎯 Міні-проект (30 хв)

### Завдання: виміряти дисципліну власної системи

Мета — переконатися, що таблиця ваг і формула віртуального часу описують реальну
поведінку планувальника.

**Кроки:**

1. Запустіть два однакові навантаження на одному ядрі з різним nice:

```bash
taskset -c 0 nice -n 0  sh -c 'while :; do :; done' &
taskset -c 0 nice -n 5  sh -c 'while :; do :; done' &
sleep 30
```

2. Зніміть для кожного спожитий час і віртуальний час:

```bash
for pid in $(jobs -p); do
  echo "=== PID $pid, nice $(ps -o ni= -p $pid)"
  grep -E "se.sum_exec_runtime|se.vruntime" /proc/"$pid"/sched
done
```

3. Обчисліть співвідношення спожитого часу й порівняйте з відношенням ваг
   1024 : 335.

4. Порівняйте значення `se.vruntime` обох процесів. Поясніть, чому вони близькі,
   хоча реального часу процеси отримали різну кількість.

5. Завершіть навантаження: `kill $(jobs -p)`.

**Очікуваний результат:** реальний час у співвідношенні приблизно 3:1, а
віртуальний — майже однаковий. Це і є пряма демонстрація того, що CFS вирівнює
саме віртуальний час.

**Бонус (для допитливих):**

- Додайте третій процес із політикою `SCHED_FIFO` на тому самому ядрі й з
  обмеженням часу: `sudo timeout 10 taskset -c 0 chrt -f 50 sh -c 'while :; do :; done'`.
  Подивіться, що станеться з двома першими, і поясніть, чому таку політику не
  вмикають без потреби й чому вони все ж отримують близько 5 % часу.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Дисципліна обслуговування** | Правило вибору з черги разом із правилом перерахунку пріоритетів |
| **Відносна дисципліна** | Невитісняльна: процес працює, доки не звільнить процесор сам |
| **Абсолютна дисципліна** | Витісняльна: ОС може відібрати процесор |
| **Статичний пріоритет** | Заданий ззовні й незмінний (nice, клас пріоритету) |
| **Динамічний пріоритет** | Перераховується ядром за поведінкою процесу |
| **p_cpu (UNIX)** | Лічильник спожитого часу, що спадає з часом |
| **vruntime (CFS)** | Віртуальний час; обирається процес із найменшим значенням |

| Система | Як реалізовано динаміку |
|---------|-------------------------|
| Класичний UNIX | Лічильник спожитого часу зі спаданням за навантаженням |
| Linux CFS | Віртуальний час, зважений на вагу процесу |
| Windows | Підвищення за подією + подовжений квант для активного вікна |

**Ключовий висновок:** динамічний пріоритет — це не оцінка важливості процесу, а
компенсація за недоотриманий час. Саме тому механізм працює без участі
користувача: система не намагається зрозуміти, що вам потрібно, вона лише
вирівнює те, що вже сталося.

На наступній лекції — якість диспетчеризації: як виміряти, чи добре працює
дисципліна, і які гарантії можна дати користувачеві.
