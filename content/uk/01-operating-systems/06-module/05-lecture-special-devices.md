## Банкомат, який показав робочий стіл

Фотографії банкоматів і табло на вокзалах із вікном помилки чи робочим столом
стали інтернет-жанром. Смішно там лише перше враження: за кожним таким знімком
стоїть система, яка **не мала показувати нічого, крім свого застосунку**, і
все-таки показала.

Ця тема — про пристрої, у яких немає користувача в звичному сенсі. Є той, хто
натискає кнопки, але він не має ні прав, ні наміру адмініструвати систему. І
саме тому вимоги до такої системи інші.

**Запитання до аудиторії**: чим небезпечний робочий стіл, що з'явився на екрані
банкомата, якщо доступу до клавіатури немає?

## Звідки взялося слово «термінал»

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ВІД ТЕЛЕТАЙПА ДО ЕМУЛЯТОРА                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1960-ті  ТЕЛЕТАЙП (teletype, скорочено tty)                       │
│            Друкарська машинка з лінією зв'язку. Вивід —             │
│            на папір. Звідси й назва пристрою /dev/tty.              │
│                                                                     │
│   1970-ті  ВІДЕОТЕРМІНАЛ (VT100 та подібні)                         │
│            Екран замість паперу, керування курсором                 │
│            спеціальними послідовностями символів.                   │
│                                                                     │
│   1980-ті  ПЕРСОНАЛЬНИЙ КОМП'ЮТЕР                                   │
│            Термінал більше не потрібен — але програми               │
│            вже написані під нього.                                  │
│                                                                     │
│   Сьогодні ЕМУЛЯТОР ТЕРМІНАЛА                                       │
│            Програма, що вдає VT100 сорокарічної давнини.            │
│            Змінна TERM досі каже, який саме термінал                │
│            імітується.                                              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
# Який термінал імітує ваша програма
echo $TERM

# На якому терміналі ви працюєте просто зараз
tty

# Керувальні послідовності VT100 працюють і нині:
printf '\033[1;31m%s\033[0m\n' "червоний жирний"
printf '\033[2J\033[H'   # очистити екран і перевести курсор угору
```

Докладніше про TTY, псевдотермінали й line discipline — у лекції «Консольний
режим Linux» (модуль 1). Це не історична цікавинка, а робоче знання: керувальні послідовності
використовують усі сучасні програми з текстовим інтерфейсом, і саме через них
кольоровий вивід ламається, коли його перенаправляють у файл.

## Пристрої без користувача

Таблиця 1 — Спеціальні пристрої та їхні головні вимоги

| Пристрій | Головна вимога | Чим ризикує |
|----------|----------------|-------------|
| Банкомат | цілісність і облік кожної операції | гроші, репутація банку |
| Касовий термінал | безперервність роботи в години пік | черга й втрачений продаж |
| Інформаційний кіоск | неможливість вийти із застосунку | доступ до системи ззовні |
| Промислова панель | реакція в межах терміну | зупинка або аварія лінії |
| Медичний монітор | достовірність показників | життя пацієнта |
| Табло та вивіски | автоматичне відновлення після збою | зіпсована картинка на видноті |
| Тонкий клієнт | швидке підключення до сервера | простій робочого місця |

Спільне: **пристрій стоїть там, де немає адміністратора**, часто працює
цілодобово й доступний фізично стороннім людям. Три ці обставини й формують
набір рішень.

## Режим кіоска

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ЩО САМЕ РОБИТЬ РЕЖИМ КІОСКА                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. Автоматичний вхід і запуск єдиного застосунку                  │
│      на повний екран, без робочого стола й панелі задач             │
│                                                                     │
│   2. Вимкнення способів вийти із застосунку:                        │
│      сполучення клавіш, контекстні меню, діалоги                    │
│      друку й вибору файлу                                           │
│                                                                     │
│   3. Автоматичний перезапуск застосунку після збою                  │
│      (наглядач процесів, а не людина)                               │
│                                                                     │
│   4. Незмінна коренева файлова система: усі зміни                   │
│      потрапляють у тимчасовий шар і зникають                        │
│      після перезавантаження                                         │
│                                                                     │
│   5. Обмеження прав: застосунок працює від                          │
│      непривілейованого користувача                                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Готові засоби для цього є в кожній системі:

| Система | Засіб режиму кіоска |
|---------|---------------------|
| Windows 10/11 | Assigned Access (один застосунок для облікового запису), Shell Launcher (власна програма замість оболонки) |
| Linux | GNOME Kiosk, композитор Cage (одна програма на весь екран у Wayland), служба systemd з `Restart=always` |
| ChromeOS | Kiosk mode з керуванням через консоль адміністратора |
| Android | Lock Task Mode (закріплення застосунку) для корпоративних пристроїв |

**Пункт 4 заслуговує окремої уваги.** Ідея незмінної кореневої системи розв'язує
одразу кілька задач: збій живлення не пошкодить файлову систему, зловмисник не
лишить закладки, а будь-яка поломка лікується перезавантаженням. Технічно це
роблять накладанням шарів:

```
       ┌──────────────────────────────┐
       │ тимчасовий шар у пам'яті     │ ← усі записи потрапляють сюди
       ├──────────────────────────────┤
       │ незмінний образ системи      │ ← лише читання
       └──────────────────────────────┘
```

```bash
# Подивитися змонтовані накладні файлові системи
mount | grep -E "overlay|squashfs" | head -5

# Які файлові системи змонтовані лише для читання
mount | grep "ro," | head -5
```

Той самий прийом використовують живі образи дистрибутивів: система завантажилася
з носія лише для читання, але ви можете створювати файли — вони живуть у пам'яті.

### Розбір помилкового міркування

> «Щоб зробити кіоск, достатньо вимкнути диспетчер завдань і сховати панель
> задач.»

Це захист інтерфейсу, а не системи, і він неминуче має щілини:

1. **Діалог відкриття файлу** у застосунку часто є повноцінним файловим
   менеджером: із нього можна перейти будь-куди, а інколи й запустити програму.
2. **Обробники помилок** показують вікна, кнопки яких ведуть у систему: «показати
   деталі», «відкрити журнал», «повідомити розробника».
3. **Апаратні події** — підключення клавіатури, зовнішнього накопичувача — можуть
   відкрити шлях, якого не було в задумі.
4. **Перезавантаження** повертає систему в стан, де кіоск ще не запустився: вікно
   в кілька секунд буває достатнім.

Правильний підхід — **багаторівневий**: обмеження прав користувача, незмінна
коренева система, наглядач за процесом, вимкнені непотрібні служби, фізичний
захист портів і лише потім — приховані елементи інтерфейсу. Кожен рівень
розрахований на те, що попередній обійдено.

**Як пояснити це студентам одним питанням**: «що станеться, якщо ваш захист
обійдуть?» Якщо відповідь «усе пропало» — рівень захисту один, і цього мало.

## Оновлення, які не можна зламати

Пристрій без адміністратора не можна оновлювати звичайним способом: якщо
оновлення перерветься посеред процесу, приїхати й полагодити буде нікому.

```
┌─────────────────────────────────────────────────────────────────────┐
│                       ОНОВЛЕННЯ ЗІ СХЕМОЮ A/B                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Накопичувач має ДВА розділи із системою:                          │
│                                                                     │
│     ┌──────────────┐   ┌──────────────┐                             │
│     │  розділ A    │   │  розділ B    │                             │
│     │  працює      │   │  оновлюється │                             │
│     └──────────────┘   └──────────────┘                             │
│                                                                     │
│   1. Система працює з A, оновлення пишеться в B                     │
│   2. Запис перевіряється контрольною сумою                          │
│   3. Завантажувач перемикається на B                                │
│   4. Якщо B не повідомив про успішний старт —                       │
│      автоматичний відкат на A                                       │
│                                                                     │
│   Перерване оновлення не ламає пристрій: він просто                 │
│   лишається на старій версії. Саме так оновлюються                  │
│   Android, ChromeOS і більшість сучасних терміналів.                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Це пряме продовження ідеї журналювання з теми про буферизацію: операція має бути
або виконаною повністю, або не виконаною зовсім, а проміжний стан не повинен
бути робочим.

## Тонкі клієнти

```
┌─────────────────────────────────────────────────────────────────────┐
│                      ДЕ ВИКОНУЄТЬСЯ ОБЧИСЛЕННЯ                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ТОВСТИЙ КЛІЄНТ                  ТОНКИЙ КЛІЄНТ                     │
│   ──────────────                  ─────────────                     │
│   Програми на робочому місці      Програми на сервері               │
│   Дані можуть лишатися локально   Дані не залишають                 │
│                                   дата-центру                       │
│   Потужне залізо на кожному       Дешеве залізо на місці            │
│   місці                           потужне в центрі                  │
│   Оновлювати треба всюди          Оновлення в одному місці          │
│   Працює без мережі               Без мережі не працює              │
│                                                                     │
│   ІСТОРІЯ ПО КОЛУ: мейнфрейм із терміналами (1970-ті) →             │
│   персональні комп'ютери (1990-ті) → хмара з браузером              │
│   (сьогодні). Аргументи ті самі, змінилися лише назви.              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Сучасний тонкий клієнт — це найчастіше браузер: застосунок виконується на
сервері, на місці лишається лише відображення. Тому пристрій на робочому місці
може бути дуже скромним, і тому ж робоче місце повністю залежить від мережі.

## Фізична безпека

Для пристрою, до якого може підійти будь-хто, працює правило: **фізичний доступ
зрештою дає повний доступ**. Захист будують так, щоб зробити атаку дорожчою за
здобич:

| Загроза | Захід |
|---------|-------|
| Підключення власного накопичувача | вимкнені порти або дозволені лише відомі пристрої |
| Завантаження з чужого носія | пароль мікропрограми, порядок завантаження, Secure Boot |
| Виймання диска | повне шифрування носія |
| Підміна пристрою введення | обмеження на клас HID, фізичні замки |
| Спостереження за екраном | плівки, кути огляду, автоматичне блокування |

```bash
# Чи ввімкнено Secure Boot
mokutil --sb-state 2>/dev/null || echo "mokutil недоступний"

# Чи зашифровано розділи
lsblk -o NAME,TYPE,FSTYPE,MOUNTPOINT | grep -i crypt || echo "шифрованих розділів не знайдено"
```

   визначили?
2. Поясніть, чому для інформаційного кіоска незмінна коренева файлова система

3. Опишіть, що станеться при перериванні оновлення в схемі A/B і при звичайному
   оновленні на місці.
4. Складіть перелік із п'яти способів вийти із застосунку в режимі кіоска, які
   треба перекрити.

│   5 непривілейований користувач                                     │
│                                                                     │
│   ОНОВЛЕННЯ A/B:                                                    │
│   працюємо з A → пишемо B → перевірка → перемикання →               │
│   невдача → автоматичний відкат на A                                │
│                                                                     │
│   ТОНКИЙ КЛІЄНТ: обчислення на сервері, на місці —                  │
│   лише відображення; без мережі не працює                           │
│                                                                     │

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Звідки походить назва пристрою `/dev/tty`?

- від англійського terminal type
- від телетайпа — друкарської машинки з лінією зв'язку
- від типу терміналу Teletype Type
- від назви першого емулятора терміналу

**2.** Що показує змінна `TERM`?

- права доступу до термінального пристрою
- скільки терміналів відкрито в системі
- час роботи поточної сесії
- який тип термінала імітує програма

**3.** Яка спільна риса банкомата, каси й інформаційного кіоска?

- вони не мають доступу до мережі
- вони працюють там, де немає адміністратора, і доступні стороннім фізично
- вони використовують однакову операційну систему
- вони не потребують оновлень

**4.** Що робить незмінна коренева файлова система в кіоску?

- прискорює завантаження системи
- забороняє будь-який запис, зокрема тимчасовий
- шифрує дані користувача
- усі зміни потрапляють у тимчасовий шар і зникають після перезавантаження

**5.** Чому приховати панель задач недостатньо для режиму кіоска?

- діалоги відкриття файлу й вікна помилок відкривають шлях у систему
- користувач може перезавантажити комп'ютер
- панель задач неможливо приховати повністю
- це сповільнює роботу застосунку

**6.** У чому суть багаторівневого захисту?

- захист розподіляється між кількома пристроями
- кожен рівень захищає окремий застосунок
- кожен рівень розрахований на те, що попередній обійдено
- рівні дублюють один одного для швидкодії

**7.** Що станеться при перериванні оновлення в схемі A/B?

- пристрій лишиться на старій версії й працюватиме далі
- пристрій не завантажиться до ручного втручання
- оновлення продовжиться після перезавантаження
- обидва розділи стануть непрацездатними

**8.** Чим тонкий клієнт відрізняється від товстого?

- він не потребує мережі
- він має потужніший процесор
- він працює без операційної системи
- програми виконуються на сервері, на місці лишається лише відображення

**9.** Яке правило діє для пристроїв із вільним фізичним доступом?

- фізичний доступ зрештою дає повний доступ, тому атаку роблять дорожчою
- шифрування робить фізичний доступ безпечним
- достатньо заблокувати екран
- фізичний доступ не впливає на безпеку, якщо є пароль

**10.** Який сучасний пристрій є прямим спадкоємцем ідеї мейнфрейма з терміналами?

- смартфон із застосунками
- браузер, у якому працює вебзастосунок із сервера
- ноутбук із локально встановленими програмами
- мікроконтролер у побутовій техніці

## 🎯 Міні-проект (30 хв)

### Завдання: зробити власний кіоск

**Кроки:**

1. Створіть окремого непривілейованого користувача для кіоска:

```bash
sudo useradd -m -s /bin/bash kiosk 2>/dev/null || echo "користувач уже існує"
```

2. Налаштуйте автозапуск браузера на повний екран (приклад для GNOME/X11):

```bash
mkdir -p /home/kiosk/.config/autostart
cat <<'EOF' | sudo tee /home/kiosk/.config/autostart/kiosk.desktop > /dev/null
[Desktop Entry]
Type=Application
Name=Kiosk
Exec=firefox --kiosk https://example.com
X-GNOME-Autostart-enabled=true
EOF
```

3. Додайте наглядача, який перезапускає застосунок після збою:

```bash
cat <<'EOF' | sudo tee /etc/systemd/system/kiosk-watch.service > /dev/null
[Unit]
Description=Kiosk watchdog
[Service]
User=kiosk
ExecStart=/usr/bin/firefox --kiosk https://example.com
Restart=always
RestartSec=3
[Install]
WantedBy=multi-user.target
EOF
```

4. Складіть перелік щілин, які лишилися відкритими у вашому кіоску: сполучення
   клавіш, діалоги, консолі, зовнішні носії.

5. Для кожної щілини запропонуйте захід і вкажіть, до якого з п'яти рівнів він
   належить.

**Очікуваний результат:** таблиця «щілина — захід — рівень» щонайменше на шість
рядків.

**Бонус (для допитливих):**

- Спробуйте зробити кореневу систему незмінною через `overlayfs` у віртуальній
  машині та перевірте, що зміни зникають після перезавантаження.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Термінал (tty)** | Пристрій введення-виведення; назва походить від телетайпа |
| **Емулятор термінала** | Програма, що імітує апаратний термінал 1970-х |
| **Режим кіоска** | Набір заходів, що зводять систему до одного застосунку |
| **Незмінна коренева ФС** | Образ лише для читання з тимчасовим шаром для записів |
| **Оновлення A/B** | Два розділи із системою й автоматичний відкат при невдачі |
| **Тонкий клієнт** | Пристрій, що лише відображає результат обчислень на сервері |

**Ключовий висновок:** спеціальні пристрої проєктують від питання «що станеться,
коли нас там не буде». Звідси незмінна файлова система, наглядачі за процесами,
оновлення з відкатом і багаторівневий захист. Жоден із цих механізмів не є
новим — усі вони вже траплялися в курсі. Новою є лише вимога: працювати роками
без людини поруч.

На завершення модуля — сучасні тренди розвитку операційних систем.
