## Операційна система, яку ви ніколи не побачите

У звичайному автомобілі 2020-х років — від 50 до 150 мікроконтролерів. У кожному
працює програмне забезпечення, у більшості — операційна система. Жодна з них не
має ні робочого стола, ні файлового менеджера, ні можливості встановити щось
іще.

Ці системи роблять одну роботу й мають робити її **завжди в межах відомого
часу**. Про них і піде мова.

**Запитання до аудиторії**: що страшніше для системи керування двигуном —
виконати обчислення за 12 мілісекунд замість 10 чи не виконати взагалі?

## Чим спеціалізована система відрізняється від універсальної

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ДВІ РІЗНІ ІНЖЕНЕРНІ ЗАДАЧІ                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   УНІВЕРСАЛЬНА ОС                 СПЕЦІАЛІЗОВАНА ОС                 │
│   ───────────────                 ─────────────────                 │
│   Невідомий набір програм         Набір задач відомий               │
│                                   на етапі проєктування             │
│   Оптимізує середній випадок      Оптимізує НАЙГІРШИЙ випадок       │
│   Ресурси надлишкові              Ресурси пораховані до байта       │
│   Оновлюється щомісяця            Може не оновлюватися роками       │
│   Збій = незручність              Збій = травма або аварія          │
│   Розмір ядра: десятки МіБ        Розмір ядра: 6-60 КіБ             │
│                                                                     │
│   ГОЛОВНЕ: універсальна система не знає, що виконуватиме;           │
│   спеціалізована знає все наперед — і саме тому може                │
│   давати гарантії.                                                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Це продовження теми про якість диспетчеризації: там ми з'ясували, що гарантію
можна дати лише за найгіршим випадком. Спеціалізовані системи будують саме так.

## Сімейство систем реального часу

Таблиця 1 — Поширені системи реального часу

| Система | Розмір ядра | Ліцензія | Де застосовують |
|---------|-------------|----------|-----------------|
| FreeRTOS | 6-12 КіБ | MIT | побутова електроніка, датчики, IoT |
| Zephyr | 8-60 КіБ | Apache 2.0 | носимі пристрої, промисловість |
| QNX | сотні КіБ | комерційна | автомобілі, медичне обладнання |
| VxWorks | сотні КіБ | комерційна | авіоніка, космос, оборона |
| RTEMS | десятки КіБ | відкрита | космічні апарати |
| PREEMPT_RT (Linux, в основному ядрі з 6.12, 2024) | МіБ | GPL | верстати, аудіо, робототехніка |

**Дві принципово різні стратегії** видно з останнього рядка. Можна взяти
мінімальне ядро, написане під реальний час із нуля, а можна взяти Linux і
доробити його так, щоб майже будь-яка ділянка коду ядра могла бути витіснена.
Перший шлях дає кращі гарантії, другий — усю екосистему Linux: драйвери, мережу,
знайомі інструменти.

```bash
# Чи зібране ваше ядро з підтримкою витіснення (на звичайному Linux)
grep -E "PREEMPT" /boot/config-$(uname -r) 2>/dev/null | head -5 ||   uname -v   # у рядку версії видно PREEMPT або PREEMPT_RT
```

### Чому мале ядро — це не економія, а вимога

| Розмір коду | Наслідок |
|-------------|----------|
| 10 тисяч рядків | можна прочитати повністю й формально перевірити |
| 100 тисяч рядків | можна перевірити критичні шляхи |
| понад 30 мільйонів рядків (ядро Linux) | повна перевірка неможлива в принципі |

Для системи, яка керує гальмами, важливо не «мало займає пам'яті», а **піддається
аналізу**. Мікроядро seL4 узагалі має математичне доведення відповідності коду
специфікації — і це стало можливим лише завдяки розміру приблизно в десять тисяч
рядків.

## Чому в критичних системах забороняють `malloc`

Правило, яке спершу здається дивним: у багатьох стандартах критичного
програмного забезпечення динамічне виділення пам'яті або заборонене, або
дозволене лише під час ініціалізації.

```
┌─────────────────────────────────────────────────────────────────────┐
│             ЧОТИРИ ПРИЧИНИ ЗАБОРОНИ ДИНАМІЧНОЇ ПАМ'ЯТІ              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. ЧАС ВИКОНАННЯ НЕ ОБМЕЖЕНИЙ ЗГОРИ                               │
│      malloc може пройти список вільних блоків за 0,1 мкс,           │
│      а може за 50 мкс — залежно від стану купи.                     │
│      Для гарантії потрібен найгірший випадок, а він                 │
│      невідомий.                                                     │
│                                                                     │
│   2. ФРАГМЕНТАЦІЯ НАКОПИЧУЄТЬСЯ                                     │
│      Система, що працює місяцями без перезапуску, рано              │
│      чи пізно отримає відмову у виділенні при формально             │
│      вільній пам'яті.                                               │
│                                                                     │
│   3. ВІДМОВУ НІКУДИ ОБРОБИТИ                                        │
│      Що має зробити модуль подушки безпеки, якщо malloc             │
│      повернув NULL? Відповіді немає.                                │
│                                                                     │
│   4. АНАЛІЗ СТАЄ НЕМОЖЛИВИМ                                         │
│      Максимальне споживання пам'яті не обчислюється                 │
│      статично, отже, довести достатність пам'яті не можна.          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Що роблять замість.** Уся пам'ять розподіляється статично на етапі компіляції:
масиви сталого розміру, пули об'єктів, стеки задач, відомі наперед. Компонувач
одразу скаже, скільки байтів потрібно, і якщо не вміщується — програма просто не
збереться. Помилка виявляється на робочому місці інженера, а не на дорозі.

```c
/* Замість динамічного створення задач і черг — статичне */
static StackType_t stack_sensor[256];
static StaticTask_t tcb_sensor;

xTaskCreateStatic(sensor_task, "sensor", 256, NULL, 3,
                  stack_sensor, &tcb_sensor);
```

Той самий принцип поширюється й на інші конструкції: немає рекурсії без
обмеження глибини, немає нескінченних циклів очікування, немає бібліотек із
непередбачуваним часом роботи.

## Сторожовий таймер

```
┌─────────────────────────────────────────────────────────────────────┐
│                      WATCHDOG: ОСТАННІЙ РУБІЖ                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Апаратний лічильник, що безперервно зменшується.                  │
│   Програма зобов'язана періодично його скидати.                     │
│                                                                     │
│     програма жива          програма зависла                         │
│     ──────────────         ────────────────                         │
│     скидання, скидання…    скидань немає                            │
│     лічильник не доходить  лічильник доходить до нуля               │
│     до нуля                       │                                 │
│                                   ▼                                 │
│                         АПАРАТНЕ ПЕРЕЗАВАНТАЖЕННЯ                   │
│                                                                     │
│   Важлива деталь: скидати таймер має лише та задача, яка            │
│   справді перевірила, що система працює. Скидання з                 │
│   таймерного переривання «про всяк випадок» знецінює                │
│   механізм: система зависла, а таймер бадьоро скидається.           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Саме сторожовий таймер перезавантажував Mars Pathfinder, поки не виправили
інверсію пріоритетів: він робив свою роботу правильно, хоча причина була в
іншому. Це добра ілюстрація того, що watchdog — не розв'язання проблеми, а
обмеження її наслідків.

```bash
# Апаратний сторожовий таймер, який обслуговує systemd (RuntimeWatchdogSec)
ls /dev/watchdog* 2>/dev/null || echo "пристрій недоступний"
# Програмний «сторож» ядра: виявляє ядра процесора, що зависли (soft lockup)
cat /proc/sys/kernel/watchdog 2>/dev/null
```

## Сертифікація: чому це коштує дорожче за розробку

Для систем, збій яких загрожує життю, недостатньо «ми протестували». Потрібен
формальний доказ, побудований за стандартом.

Таблиця 2 — Стандарти функційної безпеки

| Стандарт | Галузь | Рівні |
|----------|--------|-------|
| DO-178C | авіація | DAL A-E, де A — відмова катастрофічна |
| ISO 26262 | автомобілі | ASIL A-D, де D — найсуворіший |
| IEC 62304 | медичні пристрої | класи A, B, C |
| IEC 61508 | промисловість | SIL 1-4 |
| ECSS | космос | категорії A-D |

Що вимагають стандарти найвищих рівнів:

- простежуваність: кожен рядок коду пов'язаний із вимогою, кожна вимога — з
  тестом;
- покриття тестами на рівні умов і рішень, а не просто рядків;
- аналіз найгіршого часу виконання для кожної задачі;
- доведення відсутності недосяжного коду;
- документування процесу розробки, а не лише результату.

**За галузевими оцінками, вартість рядка сертифікованого коду найвищого рівня
перевищує вартість рядка звичайного коду на порядок і більше.** Саме тому такі
системи пишуть мінімалістично: кожен зайвий рядок коштує не лише часу
написання, а й перевірки, документування та повторної сертифікації після кожної
зміни.

### Розбір помилкового міркування

> «Для критичної системи треба взяти найпотужніший процесор і найновішу ОС — так
> буде надійніше.»

Міркування природне, але хибне, і причин три.

1. **Складність — ворог передбачуваності.** Позачергове виконання команд,
   спекуляція, кеші кількох рівнів роблять час виконання невизначеним. Для
   аналізу найгіршого випадку простий процесор без кеша кращий за потужний із
   кешем, бо його поведінку можна порахувати.
2. **Новизна — ворог довіри.** Систему з двадцятирічною історією експлуатації
   вивчено краще за торішню. У критичних галузях це аргумент, а не консерватизм.
3. **Кожна функція потребує доведення.** Ядро з мережевим стеком, USB і
   графікою доведеться сертифікувати цілком або формально ізолювати невживані
   частини — обидва шляхи дорожчі за використання ядра, у якому цих функцій
   немає.

Правильне формулювання: у критичних системах обирають **найпростіше рішення,
достатнє для задачі**, а не найпотужніше з доступних.

## Практичне завдання

1. Оцініть, скільки мікроконтролерів працює у вашому оточенні: автомобіль,
   пральна машина, навушники, роутер. Які з них потребують реального часу?
2. Поясніть, чому для аналізу найгіршого часу виконання процесор без кеша
   зручніший за процесор із кешем.
3. Знайдіть у документації FreeRTOS розмір мінімальної збірки й порівняйте з
   розміром ядра вашої системи.
4. Сформулюйте, що має робити задача, яка не встигла завершитися до свого
   граничного терміну, у м'якій і в жорсткій системі реального часу.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Чому спеціалізована ОС може давати гарантії, а універсальна — ні?

- набір задач у ній відомий ще на етапі проєктування
- вона не має планувальника
- вона працює на швидшому обладнанні
- вона написана досвідченішими програмістами

**2.** Який випадок оптимізують у системах реального часу?

- середній
- найкращий
- найгірший
- найчастіший

**3.** Чому малий розмір ядра важливий для критичних систем?

- він швидше завантажується
- він займає менше місця на диску
- він дешевший у ліцензуванні
- невеликий код піддається повній перевірці та аналізу

**4.** Чому в критичних системах забороняють динамічне виділення пам'яті?

- мікроконтролери не підтримують купи
- це вимога мови C
- динамічна пам'ять працює повільніше за статичну завжди
- час виконання malloc не обмежений згори, а фрагментація накопичується

**5.** Як виділяють пам'ять замість динамічної?

- виділяють усю пам'ять пристрою одному процесу
- статично на етапі компіляції: масиви, пули, стеки відомого розміру
- використовують лише стек
- запитують у користувача під час запуску

**6.** Що робить сторожовий таймер?

- перемикає задачі за розкладом
- вимірює час виконання кожної задачі
- перезавантажує систему, якщо програма перестала його скидати
- синхронізує годинники кількох пристроїв

**7.** Чому скидання сторожового таймера з таймерного переривання знецінює механізм?

- це заборонено стандартами
- переривання виконується надто повільно
- таймер скидатиметься, навіть коли основна логіка зависла
- апаратура не підтримує такий режим

**8.** Який стандарт регулює програмне забезпечення автомобілів?

- DO-178C
- ISO 26262
- IEC 62304
- ECSS

**9.** Чому для аналізу найгіршого часу виконання простий процесор зручніший за потужний?

- кеші та позачергове виконання роблять час виконання невизначеним
- простий процесор працює швидше
- потужні процесори не підтримують реального часу
- на простому процесорі менше задач

**10.** Яке правило вибору діє в критичних системах?

- обирають найпростіше рішення, достатнє для задачі
- обирають систему з найбільшою кількістю функцій
- обирають найпотужніше залізо з можливих
- обирають найновішу доступну технологію

```bash

import time
worst = 0.0
for _ in range(5000):
    t0 = time.perf_counter()
```

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Система реального часу** | Система, що гарантує виконання в межах відомого терміну |
| **Статичне виділення пам'яті** | Уся пам'ять розподілена на етапі компіляції |
| **Сторожовий таймер** | Апаратний механізм перезавантаження при зависанні |
| **PREEMPT_RT** | Набір змін до Linux, що робить майже все ядро витісненим |
| **Функційна безпека** | Доведення, що система не завдасть шкоди при відмові |
| **DO-178C / ISO 26262 / IEC 62304** | Стандарти для авіації, автомобілів, медицини |

**Ключовий висновок:** спеціалізовані системи будують за протилежним принципом
до універсальних. Універсальна система прагне зробити якнайбільше на невідомому
наборі задач; спеціалізована — зробити рівно одне, але з доведеною гарантією. З
цієї протилежності випливає все інше: мале ядро, заборона динамічної пам'яті,
прості процесори, дорога сертифікація й нелюбов до новизни.

На наступній лекції — операційні системи державного рівня: що змушує країни
створювати власні системи й чи можливо це технічно.
