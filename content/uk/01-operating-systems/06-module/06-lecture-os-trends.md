## Тридцять мільйонів рядків і що далі

Перше ядро Linux 1991 року мало близько десяти тисяч рядків коду — його міг
прочитати одна людина за тиждень. Сучасне ядро — десятки мільйонів рядків, і
жодна людина не знає його цілком.

Зростання складності не може тривати нескінченно, і саме тому більшість сучасних
напрямів розвитку ОС так або інакше відповідають на одне питання: **як лишити
можливості, але зменшити те, чому доводиться довіряти**.

**Запитання до аудиторії**: якщо в ядрі 30 мільйонів рядків, а ваш застосунок
використовує з них кілька сотень тисяч, скільки зайвого коду працює з вашими
даними в найпривілейованішому режимі?

## Зменшення того, чому доводиться довіряти

```
┌─────────────────────────────────────────────────────────────────────┐
│                 ВІД ВІРТУАЛЬНОЇ МАШИНИ ДО UNIKERNEL                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ЗВИЧАЙНА ВІРТУАЛЬНА МАШИНА                                        │
│   [застосунок][повна ОС][гіпервізор][залізо]                        │
│   Запуск: десятки секунд. Образ: гігабайти.                         │
│                                                                     │
│   КОНТЕЙНЕР                                                         │
│   [застосунок][спільне ядро хоста][залізо]                          │
│   Запуск: мілісекунди. Ізоляція слабша: ядро спільне.               │
│                                                                     │
│   МІКРОВІРТУАЛЬНА МАШИНА (Firecracker тощо)                         │
│   [застосунок][мінімальна ОС][тонкий гіпервізор][залізо]            │
│   Запуск: сотні мілісекунд. Ізоляція як у ВМ,                       │
│   а накладні витрати близькі до контейнера.                         │
│                                                                     │
│   UNIKERNEL                                                         │
│   [застосунок + потрібні функції ОС в одному образі]                │
│   Немає режиму користувача, немає зайвих драйверів,                 │
│   немає командної оболонки — отже, немає чого захоплювати.          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Логіка тут послідовна.** Контейнери дали швидкість ціною спільного ядра: уся
ізоляція тримається на тому, що в ядрі немає помилок. Мікровіртуальні машини
повернули апаратну межу, прибравши з віртуальної машини все, що не потрібне
хмарній функції: емуляцію старих пристроїв, BIOS, зайві драйвери. Unikernel
доводить думку до краю: якщо застосунок один, навіщо йому взагалі поділ на
режими?

Ціна теж послідовна: що менша й спеціалізованіша система, то менше готових
інструментів, звичних засобів діагностики й фахівців, які вміють із нею
працювати.

## Безпека пам'яті на рівні мови

Дослідження великих кодових баз, написаних на C і C++, показують подібну
картину: **приблизно дві третини серйозних уразливостей пов'язані з роботою з
пам'яттю** — вихід за межі буфера, використання після звільнення, подвійне
звільнення.

| Підхід | Що дає | Чого не дає |
|--------|--------|-------------|
| Уважність програміста | нічого гарантованого | масштабування на мільйони рядків |
| Аналізатори коду | знаходять частину помилок | доведення відсутності |
| Безпечна мова (Rust) | цілий клас помилок неможливий за побудовою | захисту від логічних помилок |

Саме тому в ядро Linux прийняли підтримку Rust для драйверів: не щоб переписати
ядро, а щоб **нові** драйвери не додавали помилок відомого класу. Перша підтримка
з'явилася в Linux 6.1 (2022); у 6.12 мовою Rust написано генератор QR-коду для
повідомлення про збій ядра, а з 6.15 почали додавати частини драйвера Nova для
відеокарт NVIDIA. Microsoft 2023 року вбудувала перші компоненти на Rust у ядро
Windows (частина графічної підсистеми `win32kbase_rs.sys`).

Найпереконливіші дані дала Google: коли в Android новий код почали писати
здебільшого мовами з безпекою пам'яті (Rust, Kotlin, Java), частка вразливостей,
пов'язаних із пам'яттю, впала приблизно з 76 % у 2019 році до 24 % у 2024-му —
хоча старий код на C і C++ ніхто масово не переписував. Уразливості зосереджені
в новому коді, тож безпечним досить робити саме його.

```bash
# Чи зібране ваше ядро з підтримкою Rust
grep -E "CONFIG_RUST" /boot/config-$(uname -r) 2>/dev/null ||   echo "конфігурація ядра недоступна"
```

**Важливе застереження для чесності викладу**: безпечна мова прибирає клас
помилок роботи з пам'яттю, але не робить код правильним. Драйвер на Rust може
неправильно налаштувати пристрій, помилитися в протоколі або створити
взаємоблокування — просто він не зіпсує чужу пам'ять.

## eBPF: власний код у ядрі без модулів

Раніше вибір був суворий: або писати модуль ядра (повна свобода й повна
відповідальність, помилка валить систему), або лишатися в просторі користувача
(безпечно, але без доступу до подій ядра).

```
┌─────────────────────────────────────────────────────────────────────┐
│                      ЯК eBPF ЗМІНИВ ЦЕЙ ВИБІР                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Ваша програма → перевіряч (verifier) → ядро                       │
│                                                                     │
│   ПЕРЕВІРЯЧ ДОВОДИТЬ ПЕРЕД ЗАВАНТАЖЕННЯМ:                           │
│   • програма завершується (немає нескінченних циклів)               │
│   • немає звернень за межі дозволеної пам'яті                       │
│   • кількість інструкцій обмежена                                   │
│   • використовуються лише дозволені функції ядра                    │
│                                                                     │
│   Не довів — програма не завантажиться взагалі.                     │
│                                                                     │
│   ДЕ ЗАСТОСОВУЮТЬ:                                                  │
│   спостереження без зміни коду програм, мережеві фільтри,           │
│   обмеження системних викликів, збір метрик, балансування           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Розширюваність тут куплено не довірою до автора коду, а **доведенням
властивостей перед запуском**. Але ризик не нульовий: сам перевіряч — складна
програма, і помилки в ньому не раз давали змогу непривілейованому процесу
отримати права root. Тому в більшості дистрибутивів завантажувати програми
eBPF може лише адміністратор. Через eBPF ядро вже розширюють далеко за межі
спостереження: з версії 6.12 так можна замінити навіть політику планування
процесів (sched_ext, модуль 2).

```bash
# Чи підтримує ядро eBPF
grep -E "CONFIG_BPF_SYSCALL" /boot/config-$(uname -r) 2>/dev/null

# Завантажені BPF-програми (потрібні права)
sudo bpftool prog show 2>/dev/null | head -5 || echo "bpftool недоступний"

# Чи дозволено eBPF звичайним користувачам (1 або 2 — заборонено)
cat /proc/sys/kernel/unprivileged_bpf_disabled
```

## Незмінні системи й атомарні оновлення

Ідея, яку ви вже бачили в темі про спеціальні пристрої, переходить у настільні
системи: система постачається **образом**, а не набором пакетів.

| Пакетна модель | Образна модель |
|----------------|----------------|
| Оновлення змінює файли на місці | Оновлення приносить новий образ цілком |
| Перерване оновлення лишає систему в проміжному стані | Проміжного стану не існує |
| Дві машини з однаковим переліком пакетів можуть відрізнятися | Однаковий образ означає однакову систему |
| Відкат складний | Відкат — це вибір попереднього образу при завантаженні |

Так працюють ChromeOS, Fedora Silverblue (і вся лінійка Fedora Atomic),
SteamOS, Ubuntu Core, openSUSE Aeon, більшість систем для пристроїв; NixOS
досягає того самого інакше — описом усієї системи в одному файлі конфігурації. Плата — менша свобода: встановлення сторонньої програми в системний
розділ або неможливе, або відбувається через контейнер.

## Ресурси, яких раніше не планували

Класичний курс ОС розподіляє процесор, пам'ять, диск і мережу. Сучасне
навантаження додало ще два ресурси:

- **прискорювачі**: графічні процесори й нейронні модулі. Вони мають власну
  пам'ять, власні черги й власні особливості, а ОС поки що керує ними значно
  грубіше, ніж процесором: чіткого витісняльного планування з квантами там
  здебільшого немає. З Linux 6.2 для нейронних прискорювачів з'явилася окрема
  підсистема `accel` (пристрої `/dev/accel/*`), а ноутбуки Copilot+ PC (2024)
  вимагають від Windows уміння ділити NPU між програмами;
- **енергія**: у телефоні це заряд, у дата-центрі — рахунок за електрику й межі
  охолодження. Планувальник, що враховує енергію, обирає не лише **кого**
  виконувати, а й **на якому ядрі та з якою частотою**.

## Як відрізнити тренд від моди

```
┌─────────────────────────────────────────────────────────────────────┐
│                 ЧОТИРИ ПИТАННЯ ДО БУДЬ-ЯКОЇ НОВИНКИ                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. ЯКУ КОНКРЕТНУ ПРОБЛЕМУ це розв'язує?                           │
│      Якщо відповідь «це сучасно» — питання лишилося                 │
│      без відповіді.                                                 │
│                                                                     │
│   2. ЩО МИ ВТРАЧАЄМО, узявши це?                                    │
│      Кожне рішення має ціну. Якщо ціни не видно,                    │
│      її просто ще не знайшли.                                       │
│                                                                     │
│   3. ХТО ЗА ЦЕ ПЛАТИТЬ і навіщо?                                    │
│      Технологію, яку розвивають кілька незалежних                   │
│      учасників, підтримуватимуть довше.                             │
│                                                                     │
│   4. ЩО БУДЕ ЧЕРЕЗ П'ЯТЬ РОКІВ із тими, хто вже                     │
│      вклався? Чи є шлях відступу?                                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Історія дає корисну перевірку.** Віртуалізація з'явилася в мейнфреймах 1960-х,
була забута й повернулася в 2000-х. Модель «тонкий клієнт — потужний сервер»
пройшла коло від терміналів до персональних комп'ютерів і назад до браузера з
хмарою. Контейнери спираються на ідеї ізоляції, яким десятки років.

Це не означає, що «нічого нового не буває». Це означає, що нове зазвичай є
**старою ідеєю за нових обмежень**: змінилися швидкість мережі, вартість пам'яті
чи модель загроз — і рішення, яке раніше не мало сенсу, стало найкращим.

### Розбір помилкового міркування

> «Контейнери замінили віртуальні машини, а unikernel скоро замінить контейнери.»

Ця схема «нове витісняє старе» майже ніколи не справджується в системному
програмному забезпеченні. Насправді технології **нашаровуються**: сьогодні
контейнери масово запускають **усередині** віртуальних машин, бо потрібна і
швидкість, і апаратна межа ізоляції. Мейнфрейми досі працюють у банках.
Планувальники 1970-х живуть усередині сучасних ядер.

Правильна модель — не «заміна», а **розширення набору інструментів**: щоразу
з'являється варіант із іншим співвідношенням швидкості, ізоляції та складності,
а вибір лишається за задачею.

## Практичне завдання

1. Перевірте, які з описаних технологій підтримує ваша система: eBPF, cgroups
   версії 2, Rust у ядрі, незмінна коренева файлова система.
2. Для кожного з шести напрямів назвіть проблему, яку він розв'язує, і ціну,
   яку за це платять.
3. Знайдіть приклад технології, яка «повернулася» через десятиліття, і поясніть,
   що саме змінилося, щоб вона стала доречною.
4. Застосуйте чотири питання чек-листа до будь-якої новини про ІТ за цей тиждень.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** На яке спільне питання відповідає більшість сучасних напрямів розвитку ОС?

- як збільшити кількість функцій ядра
- як пришвидшити завантаження системи
- як зменшити розмір дистрибутива
- як зменшити те, чому доводиться довіряти, зберігши можливості

**2.** Чим мікровіртуальна машина відрізняється від звичайної?

- вона не потребує процесорної підтримки віртуалізації
- вона використовує ядро хоста
- вона працює без гіпервізора
- з неї прибрано все зайве, тому запуск швидший при тій самій апаратній ізоляції

**3.** У чому слабке місце контейнерів порівняно з віртуальними машинами?

- ядро спільне, тому ізоляція тримається на відсутності помилок у ньому
- вони займають більше місця
- вони не підтримують мережу
- вони повільніше запускаються

**4.** Що таке unikernel?

- ядро без драйверів
- гіпервізор для одного застосунку
- образ, у якому застосунок і потрібні функції ОС зібрані разом
- контейнер із єдиним процесом

**5.** Яку частку серйозних вразливостей у великих базах коду на C і C++ пов'язують із роботою з пам'яттю?

- приблизно дві третини
- практично всі
- приблизно чверть
- приблизно десяту частину

**6.** Що дає використання Rust у ядрі?

- гарантує відсутність логічних помилок
- пришвидшує роботу драйверів удвічі
- робить неможливим цілий клас помилок роботи з пам'яттю
- усуває потребу в тестуванні

**7.** Що робить перевіряч eBPF перед завантаженням програми в ядро?

- вимірює продуктивність програми
- доводить завершуваність, дотримання меж пам'яті та дозволених функцій
- перевіряє цифровий підпис автора
- компілює програму в машинний код

**8.** Чим образна модель оновлення краща за пакетну?

- вона не потребує перезавантаження
- вона дозволяє встановлювати більше програм
- проміжного стану не існує, а відкат — це вибір попереднього образу
- образи займають менше місця

**9.** Що змінює планувальник, який враховує енергію?

- він обирає не лише процес, а й ядро та частоту
- він працює лише на пристроях з батареєю
- він вимикає фонові процеси
- він замінює собою диспетчер пам'яті

**10.** Яка модель розвитку системних технологій правильніша?

- технології змінюються приблизно раз на рік
- нові технології нашаровуються на старі, а не замінюють їх
- кожне покоління повністю витісняє попереднє
- старі технології зникають, щойно з'являється краща

## Підсумок

| Напрям | Проблема, яку розв'язує | Ціна |
|--------|--------------------------|------|
| **МікроВМ, unikernel** | зайвий код у довіреній зоні | менше інструментів і фахівців |
| **Rust у ядрі** | помилки роботи з пам'яттю | нова мова в екосистемі C |
| **eBPF** | розширюваність без ризику | обмеженість того, що дозволено |
| **Незмінні системи** | ненадійні оновлення | менша свобода змін |
| **Планування прискорювачів** | нові типи ресурсів | складність планувальника |
| **Формальна перевірка** | недостатність тестування | висока вартість і малий розмір |

**Ключовий висновок:** тренди в операційних системах рідко виникають із
технічної цікавості. Майже завжди за ними стоїть зміна обставин: подешевшала
пам'ять, пришвидшилася мережа, змінилася модель загроз або з'явився новий клас
пристроїв. Тому найкорисніша навичка тут — не знати перелік модних назв, а вміти
запитати, яка саме обставина змінилася і що ми віддаємо натомість.

На цьому курс операційних систем завершено. Ви пройшли шлях від питання «що таке
ядро» до вміння аргументовано оцінювати архітектурні рішення — а це саме те, чого
потребує інженер.
