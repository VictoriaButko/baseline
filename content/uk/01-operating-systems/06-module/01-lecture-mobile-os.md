## Той самий комп'ютер, інші обмеження

У сучасному смартфоні вісім ядер, вісім гігабайтів пам'яті й накопичувач на
сотні гігабайтів — характеристики робочої станції п'ятирічної давнини. Але його
операційна система влаштована інакше, ніж настільна. Причина не в слабкості
заліза, а в трьох обмеженнях, яких немає в комп'ютера з розетки:

```
┌─────────────────────────────────────────────────────────────────────┐
│                            ЩО ЗМІНЮЄ ВСЕ                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. ЖИВЛЕННЯ ВІД БАТАРЕЇ                                           │
│      Кожен такт процесора й кожен пакет у мережу коштують           │
│      заряду. Енергія стає ресурсом нарівні з процесором.            │
│                                                                     │
│   2. НЕМАЄ ПІДКАЧКИ НА НАКОПИЧУВАЧ                                  │
│      Флеш-пам'ять має обмежений ресурс перезапису, а                │
│      затримка вбиває чуйність. Система стискає сторінки             │
│      в самій RAM, а коли й цього мало — ЗАВЕРШУЄ фонові             │
│      застосунки.                                                    │
│                                                                     │
│   3. ЧУЖИЙ КОД ЗА ЗАМОВЧУВАННЯМ                                     │
│      Користувач ставить програми від невідомих авторів              │
│      щотижня. Ізоляція має бути не порадою, а замком.               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Запитання до аудиторії**: настільна система, якій бракує пам'яті, починає
вивантажувати сторінки на диск і гальмує. Що має зробити телефон, якому не можна
гальмувати й нікуди вивантажувати?

## Android: Linux під шаром власних рішень

```
┌─────────────────────────────────────────────────────────────────────┐
│                         АРХІТЕКТУРА ANDROID                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌────────────────────────────────────────────────────┐            │
│   │ Застосунки (Java/Kotlin)                           │            │
│   ├────────────────────────────────────────────────────┤            │
│   │ Каркас застосунків: Activity, Service, Provider    │            │
│   ├────────────────────────────────────────────────────┤            │
│   │ ART — середовище виконання + бібліотеки C/C++      │            │
│   ├────────────────────────────────────────────────────┤            │
│   │ HAL — рівень апаратної абстракції                  │            │
│   ├────────────────────────────────────────────────────┤            │
│   │ Ядро Linux (спільне ядро Google, GKI) + Binder,    │            │
│   │ wakeup sources; lmkd і zram — керування пам'яттю   │            │
│   └────────────────────────────────────────────────────┘            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Ядро — звичайний Linux, і з роками воно стало ще звичайнішим. Колись Android
тримав у своєму ядрі десятки власних змін; поступово їх або прийняли в основне
ядро (Binder — у версії 3.19, механізм пробудження wakelocks — як wakeup
sources), або замінили стандартними (ashmem — на memfd). З Android 12 пристрої
працюють на спільному ядрі Google (GKI, Generic Kernel Image), а код виробників
заліза винесено в окремі модулі. Найважливіші для нас три механізми: **Binder**
для обміну між процесами, **завершення процесів за нестачею пам'яті** та
**блокування засинання**.

### Ізоляція: один застосунок — один користувач

Найелегантніше рішення Android побудоване на механізмі, який ви вже знаєте.
Кожному встановленому застосунку система видає **власний ідентифікатор
користувача** UID.

```
Настільний Linux:  усі програми Марії працюють від UID 1000
                   → будь-яка з них читає файли будь-якої іншої

Android:           месенджер   → UID 10087
                   банк        → UID 10142
                   гра         → UID 10203
                   → файли одного застосунку недоступні іншому
                     звичайними правами доступу
```

Жодного нового механізму захисту не знадобилося: узяли класичні права UNIX і
застосували їх до застосунків замість людей. Поверх цього працює SELinux, який
обмежує вже й системні процеси.

**Чому це важливо пояснити саме так.** Студент зазвичай сприймає «пісочницю» як
магію. Насправді це той самий `chmod`, з яким він працював у першому модулі,
застосований під іншим кутом. Нова властивість виникла не з нового механізму, а
з нової **політики** використання старого.

### Binder: чому не звичайний IPC

Android відмовився від класичних засобів обміну між процесами й побудував
власний. Причини суто інженерні:

| Вимога | Класичні засоби UNIX | Binder |
|--------|----------------------|--------|
| Знати, хто викликає | треба передавати самотужки, можна підробити | UID і PID додає ядро |
| Кількість копіювань | дві (відправник → ядро → отримувач) | одна, через спільне відображення |
| Облік посилань на об'єкт | немає | вбудований, автоматичний |
| Поведінка при смерті співрозмовника | треба відстежувати | сповіщення про смерть |

Кожен виклик методу системної служби з застосунку — це транзакція Binder. Саме
тому в Android так багато служб і так мало прямих системних викликів у коді
застосунків.

## Пам'ять без підкачки

```
┌─────────────────────────────────────────────────────────────────────┐
│                   ЩО РОБИТИ, КОЛИ ПАМ'ЯТІ БРАКУЄ                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   НАСТІЛЬНА СИСТЕМА              МОБІЛЬНА СИСТЕМА                   │
│   ─────────────────              ────────────────                   │
│   вивантажує сторінки у swap     завершує фонові процеси            │
│   процес живе, але гальмує       процес зникає повністю             │
│   у найгіршому разі — OOM        завершення — ШТАТНИЙ режим         │
│                                                                     │
│   ПОРЯДОК ЗАВЕРШЕННЯ (від першого до останнього):                   │
│   1. порожні процеси (кеш застосунку без активностей)               │
│   2. фонові застосунки                                              │
│   3. служби                                                         │
│   4. видимий застосунок (частково на екрані)                        │
│   5. активний застосунок на передньому плані                        │
│                                                                     │
│   НАСЛІДОК ДЛЯ РОЗРОБНИКА: застосунок зобов'язаний уміти            │
│   зберегти стан і відновитися після завершення в будь-який          │
│   момент. Це не аварія, а нормальний життєвий цикл.                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Хто саме вирішує, кого завершити? Раніше це робив драйвер `lowmemorykiller`
всередині ядра, але 2017 року його прибрали з Linux. Тепер це служба **lmkd** у
просторі користувача: вона стежить за метрикою тиску пам'яті PSI
(`/proc/pressure/memory`, модуль 2) і завершує процеси, щойно система почала
витрачати помітну частку часу на боротьбу за пам'ять. До цього моменту сторінки
стискаються в **zram** — стиснений swap у самій оперативній пам'яті, без запису
на флеш.

Саме звідси походить життєвий цикл `Activity` з методами `onPause`, `onStop`,
`onSaveInstanceState`: система гарантує лише те, що дасть застосунку шанс
зберегтися, але не те, що він далі існуватиме.

### Розбір помилкового міркування

> «Треба регулярно закривати застосунки списком нещодавніх — це економить пам'ять
> і батарею.»

Найпоширеніша порада, і вона хибна.

1. **Пам'ять не «витрачається» фоновим застосунком.** Він уже зупинений: не
   отримує процесорного часу й не виконує коду. Він займає пам'ять, яку система
   однаково забере, щойно вона знадобиться, — для цього й існує порядок
   завершення.
2. **Повторний запуск коштує дорожче.** Закритий застосунок при наступному
   відкритті проходить холодний старт: читання з накопичувача, створення
   процесу, ініціалізація. Це десятки або сотні мілісекунд роботи процесора на
   повній частоті — тобто саме та витрата заряду, якої користувач хотів
   уникнути.
3. **Система вже оптимізована під протилежну поведінку.** Android тримає
   процес у кеші саме для того, щоб наступне відкриття було теплим.

Обґрунтування для студентів робиться в одну дію: попросіть їх оцінити, що
енергетично дорожче — процес, який спить і не виконує інструкцій, чи повторна
ініціалізація того самого процесу з нуля.

Виняток, який варто назвати чесно: застосунок із помилкою, що втримує блокування
засинання або постійно працює у фоні, справді варто завершити. Але це лікування
конкретної несправності, а не гігієна.

## Боротьба за заряд

```
┌─────────────────────────────────────────────────────────────────────┐
│                     МЕХАНІЗМИ ЕНЕРГОЗБЕРЕЖЕННЯ                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   БЛОКУВАННЯ ЗАСИНАННЯ (wakelock)                                   │
│   Процес просить систему не засинати. Забув відпустити —            │
│   телефон не спить усю ніч. Класичне джерело скарг                  │
│   «батарея сідає за годину».                                        │
│                                                                     │
│   РЕЖИМ СПОКОЮ (Doze)                                               │
│   Пристрій нерухомий і без екрана → система відкладає               │
│   фонові задачі й синхронізації, прокидаючись пачками               │
│   у вікна обслуговування. Що довше спокій, то рідші вікна.          │
│                                                                     │
│   ГРУПУВАННЯ ЗАВДАНЬ                                                │
│   Замість десяти пробуджень по одному завданню — одне               │
│   пробудження на десять завдань. Радіомодуль вмикається             │
│   раз, а не десять.                                                 │
│                                                                     │
│   РІЗНОРІДНІ ЯДРА (big.LITTLE)                                      │
│   Легкі задачі — на економні ядра, важкі — на потужні.              │
│   Планувальник має знати, яке ядро скільки коштує.                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому групування таке важливе.** Увімкнення радіомодуля — не миттєва дія: після
передавання він ще кілька секунд лишається в активному стані. Десять окремих
синхронізацій по одному пакету можуть коштувати більше енергії, ніж одне
передавання десяти пакетів, навіть якщо даних стільки ж. Це той самий принцип
амортизації накладних витрат, що й у буферизації з попереднього модуля.

```bash
# На ноутбуці з Linux видно ті самі механізми:
# стан батареї та поточне споживання
cat /sys/class/power_supply/BAT0/capacity 2>/dev/null
cat /sys/class/power_supply/BAT0/power_now 2>/dev/null

# Хто заважає системі засинати (аналог wakelock)
cat /sys/kernel/debug/wakeup_sources 2>/dev/null | head -5

# Політика керування частотою процесора
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor 2>/dev/null
```

## iOS: інша ставка, ті самі задачі

| | Android | iOS |
|---|---------|-----|
| Ядро | Linux | XNU (гібридне, Darwin) |
| Мова застосунків | Java/Kotlin, ART | Swift/Objective-C, нативний код |
| Ізоляція | окремий UID на застосунок + SELinux | пісочниця на рівні ядра + підписування коду |
| Підкачка на флеш | немає; стиснення в RAM (zram) | немає; стиснення пам'яті (на iPad з M1 — з iPadOS 16) |
| Нестача пам'яті | lmkd на основі PSI | jetsam за тим самим принципом пріоритетів |
| Встановлення | Google Play та інші джерела; Google оголосила 2025 року, що з 2026-го застосунки на сертифікованих пристроях мають бути від верифікованих розробників | App Store; у ЄС з 2024 року (iOS 17.4, закон DMA) — і альтернативні магазини |
| Фонова робота | служби з обмеженнями | суворо визначені фонові режими |

Головна архітектурна відмінність — **ступінь свободи для розробника застосунку**.
iOS дозволяє фонову роботу лише в переліку заздалегідь визначених сценаріїв
(відтворення звуку, навігація, завантаження). Android дає більше, але потім
змушений компенсувати це обмеженнями на кшталт Doze.

Обидва підходи розв'язують ту саму суперечність: користувач хоче, щоб застосунки
працювали у фоні, і водночас хоче, щоб батарея трималася добу.

## Практичне завдання

1. Перелічіть три механізми Android, які походять зі звичайного Linux, і три,
   яких у настільному ядрі немає.
2. Поясніть, чому модель «один застосунок — один UID» неможлива на настільній
   системі в тому ж вигляді.
3. Оцініть, що дорожче за енергією: тримати зупинений процес у пам'яті годину чи
   завершити його й запустити заново. Аргументуйте.
4. Знайдіть на власному ноутбуці аналоги трьох мобільних механізмів
   енергозбереження.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Чому мобільні системи не використовують підкачку сторінок на накопичувач?

- підкачка заборонена стандартом Android
- процесори телефонів не підтримують віртуальної пам'яті
- у телефонах немає файлової системи
- флеш-пам'ять має обмежений ресурс перезапису, а затримка псує чуйність

**2.** Що робить Android, коли пам'яті бракує?

- завершує процеси за порядком пріоритету, починаючи з порожніх
- вивантажує сторінки у swap
- зупиняє всі застосунки до перезавантаження
- першим завершує застосунок на передньому плані

**3.** На якому механізмі побудована ізоляція застосунків в Android?

- усі застосунки шифруються різними ключами
- кожен застосунок працює у власній віртуальній машині з окремим ядром
- застосунки виконуються в режимі ядра з обмеженнями
- кожному застосунку видається власний UID, і працюють звичайні права UNIX

**4.** Яку перевагу Binder має над класичними засобами обміну між процесами UNIX?

- він доступний лише системним службам
- він працює без системних викликів
- ядро саме додає до транзакції UID і PID відправника
- він не потребує пам'яті для передавання

**5.** Скільки копіювань даних потребує передавання через Binder?

- три
- одне
- жодного
- два

**6.** Що таке блокування засинання (wakelock)?

- запит процесу до системи не переходити в сон
- обмеження на кількість фонових процесів
- механізм шифрування екрана блокування
- режим економії заряду під час розмови

**7.** Що робить режим Doze?

- завершує всі фонові застосунки одразу
- відкладає фонові задачі й виконує їх пачками у вікнах обслуговування
- вимикає процесор повністю
- знижує яскравість екрана

**8.** Чому групування фонових завдань економить заряд?

- радіомодуль вмикається один раз замість багатьох
- процесор працює на нижчій частоті
- зменшується обсяг переданих даних
- завдання виконуються швидше

**9.** Чому ручне закривання застосунків зазвичай не економить заряд?

- закривання не впливає на роботу процесора
- пам'ять телефона не звільняється при закриванні
- система однаково перезапускає застосунки автоматично
- зупинений процес не споживає процесорного часу, а холодний старт споживає

**10.** Чим фонова робота в iOS відрізняється від Android?

- в iOS фонові процеси мають вищий пріоритет за активні
- в iOS фонова робота не обмежена нічим
- iOS дозволяє її лише в переліку заздалегідь визначених сценаріїв
- iOS взагалі не має фонової роботи

## 🎯 Міні-проект (30 хв)

### Завдання: знайти мобільні механізми у власному ноутбуці

Мобільні рішення поступово перейшли в настільні системи. Мета — знайти їх.

**Кроки:**

1. Подивіться, скільки енергії споживає система просто зараз і хто заважає їй
   засинати:

```bash
cat /sys/class/power_supply/BAT*/power_now 2>/dev/null
cat /sys/kernel/debug/wakeup_sources 2>/dev/null | head -8
```

2. Знайдіть політику керування частотою й перелік доступних політик:

```bash
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor 2>/dev/null
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_governors 2>/dev/null
```

3. Подивіться, які процеси найбільше «будять» систему:

```bash
sudo powertop --time=10 2>/dev/null | head -20 || echo "powertop не встановлено"
```

4. Складіть таблицю відповідностей: мобільний механізм — його аналог у вашій
   системі — команда, якою ви це побачили.

**Очікуваний результат:** таблиця щонайменше з чотирьох рядків (блокування
засинання, керування частотою, групування пробуджень, завершення при нестачі
пам'яті).

**Бонус (для допитливих):**

- Якщо маєте пристрій на Android і кабель, увімкніть налагодження USB і
  подивіться порядок процесів: `adb shell dumpsys meminfo | head -30`.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **HAL** | Рівень абстракції заліза між ядром і каркасом Android |
| **ART** | Середовище виконання застосунків Android |
| **Binder** | Механізм обміну між процесами з перевіркою відправника ядром |
| **UID на застосунок** | Ізоляція застосунків звичайними правами UNIX |
| **lowmemorykiller / jetsam** | Завершення процесів за пріоритетом замість підкачки |
| **Wakelock** | Запит процесу не давати системі заснути |
| **Doze** | Відкладання фонових задач у вікна обслуговування |
| **big.LITTLE** | Різнорідні ядра: економні та потужні |

**Ключовий висновок:** мобільна ОС не є «спрощеною настільною». Вона розв'язує
ті самі задачі — планування, пам'ять, пристрої — але за інших обмежень, і саме
обмеження визначають рішення. Немає підкачки, отже, потрібен порядок завершення
процесів. Енергія скінченна, отже, потрібні групування й вікна обслуговування.
Код чужий, отже, ізоляція має бути обов'язковою, а не рекомендованою.

На наступній лекції — операційні системи для спеціалізованих задач: реального
часу, вбудовані та системи керування.
