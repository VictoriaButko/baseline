## Дебати Торвальдса і Таненбаума

29 січня 1992 року в групі новин comp.os.minix з'явився допис під заголовком **«LINUX is obsolete»** («LINUX застарів»). Автор — Ендрю Таненбаум, професор з Амстердама, автор підручника з операційних систем і навчальної системи MINIX. Його аргумент:

> «MINIX — система на мікроядрі… LINUX — монолітна система. Це гігантський крок назад, у 1970-ті.»

А в наступному дописі — фраза, яку в університетах переказують досі:

> «Будьте вдячні, що ви не мій студент. За такий проєкт ви не отримали б високої оцінки :-)»

21-річний Лінус Торвальдс відповів того ж дня — і визнав головне:

> «Так, linux монолітний, і я згоден, що мікроядра гарніші.»

Але тут-таки додав шпильку: мовляв, бути професором і дослідником — чудове виправдання для деяких вад MINIX. Його аргумент був практичний: монолітне ядро простіше написати й воно швидше працює на реальному залізі — на 386-му, яке мали студенти.

Минуло понад тридцять років. Linux — ядро Android (близько 70% мобільних ОС за StatCounter, 2026), основа більшості вебсерверів і всіх 500 машин зі списку TOP500. А MINIX 3 з 2015 року непомітно працює в Intel Management Engine — службовому мікроконтролері в чипсетах Intel, — тож формально стала однією з найпоширеніших ОС світу. Сам Таненбаум дізнався про це з новин.

**Обидва виявилися праві — для різних задач.** Нижче розберемо, чому.

## Монолітне ядро (Monolithic Kernel)

**Визначення:** Усі підсистеми ядра — файлові системи, мережа, драйвери — працюють в одному адресному просторі в режимі ядра й викликають одна одну як звичайні функції. Навіть коли частину з них завантажено модулями, як у Linux, вони все одно стають частиною цього спільного простору.

```
┌────────────────────────────────────────────────────────────────┐
│                    МОНОЛІТНЕ ЯДРО (Linux)                      │
│                                                                │
│   User Space                                                   │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │    Firefox    │    Terminal    │    VS Code             │  │
│   └───────────────┴────────────────┴────────────────────────┘  │
│                              │                                 │
│   ═══════════════════════════╪══════════════════════════════   │
│                              │ System Calls                    │
│   Kernel Space               ▼                                 │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │                                                         │  │
│   │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │  │
│   │  │ Process  │  │  Memory  │  │   VFS    │  │ Network  │ │  │
│   │  │ Scheduler│  │ Manager  │  │          │  │  Stack   │ │  │
│   │  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │  │
│   │                                                         │  │
│   │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │  │
│   │  │   ext4   │  │   XFS    │  │   NVMe   │  │  e1000   │ │  │
│   │  │    ФС    │  │    ФС    │  │ драйвер  │  │ драйвер  │ │  │
│   │  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │  │
│   │                                                         │  │
│   │  ВСЕ працює в Ring 0 — повний доступ до заліза          │  │
│   │  Виклик між підсистемами — звичайний виклик функції:    │  │
│   │  одиниці наносекунд                                     │  │
│   │                                                         │  │
│   └─────────────────────────────────────────────────────────┘  │
│                              │                                 │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │                      HARDWARE                           │  │
│   └─────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### Переваги монолітного ядра

| Перевага | Пояснення |
|----------|-----------|
| **Швидкість** | Виклик між підсистемами — звичайний виклик функції, одиниці наносекунд |
| **Простота** | Компоненти напряму викликають один одного |
| **Зрілість** | Десятиліття оптимізацій (Linux, FreeBSD) |

### Недоліки монолітного ядра

| Недолік | Пояснення |
|---------|-----------|
| **Один баг = kernel panic** | Помилка в драйвері "вбиває" всю систему |
| **Складність тестування** | Понад 30 мільйонів рядків коду (Linux 6.x), з них більшість — драйвери |
| **Безпека** | Вразливість у драйвері = доступ до всього |

**Практичний приклад:**

```bash
# Розмір ядра Linux
ls -lh /boot/vmlinuz-$(uname -r)
# ~10-15 МБ (стиснене), ~30 МБ (розпаковане)

# Скільки рядків коду в Linux
# (потрібні вихідники)
# find linux-source -name "*.c" -o -name "*.h" | xargs wc -l
# Результат: понад 30 000 000 рядків — але до вашого ядра
# потрапила лише мала частина: код для чужих процесорів і
# пристроїв, яких у вас немає, просто не компілюється

# Завантажені модулі (частина монолітного ядра, що завантажується динамічно)
lsmod | head -10

# Інформація про модуль
modinfo usb-storage | head -10

# Частина драйверів вбудована в ядро, а не винесена в модулі — у lsmod
# їх не видно. Перелік вбудованих:
grep -E "ext4|usb-storage" /lib/modules/$(uname -r)/modules.builtin
```

### Модульність Linux

Linux — **модульне монолітне ядро**. Драйвери можна завантажувати/вивантажувати без перезавантаження.

```
┌────────────────────────────────────────────────────────────────┐
│                    МОДУЛІ ЯДРА LINUX                           │
│                                                                │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │                    Базове ядро (vmlinuz)                │  │
│   │  Scheduler, MM, VFS, базові драйвери                    │  │
│   └───────────────────────────┬─────────────────────────────┘  │
│                               │                                │
│        ┌──────────────────────┼──────────────────────┐         │
│        │                      │                      │         │
│        ▼                      ▼                      ▼         │
│   ┌─────────┐            ┌─────────┐            ┌─────────┐    │
│   │ nvidia  │            │usb-     │            │bluetooth│    │
│   │  .ko    │            │storage  │            │  .ko    │    │
│   └─────────┘            └─────────┘            └─────────┘    │
│   Коли ядро              Коли вставили         Коли з'явився   │
│   знайшло відеокарту     флешку                адаптер         │
│                                                                │
│   Все одно Ring 0 — повні привілеї                             │
└────────────────────────────────────────────────────────────────┘
```

```bash
# Завантажити модуль
sudo modprobe bluetooth

# Вивантажити модуль (не вийде, поки ним користуються — ядро
# веде лічильник у колонці "Used by" виводу lsmod)
sudo modprobe -r bluetooth

# Список модулів
lsmod | grep -E "bluetooth|nvidia|ext4"

# Параметри модуля: імена й поточні значення
grep -H . /sys/module/usbcore/parameters/*
```

## Мікроядро (Microkernel)

**Визначення:** Ядро містить лише мінімум функцій. Все інше (драйвери, ФС, мережа) працює в User Space як окремі процеси.

Ідея старша за сам термін: ще 1969 року данець Пер Брінч Гансен побудував для комп'ютера RC 4000 «ядро» (nucleus), яке вміло лише запускати процеси й передавати між ними повідомлення, — а всю ОС пропонувалося зібрати з таких процесів.

```
┌──────────────────────────────────────────────────────────────────┐
│                    МІКРОЯДРО (QNX, MINIX, L4)                    │
│                                                                  │
│   User Space                                                     │
│   ┌─────────────────────────────────────────────────────────┐    │
│   │                                                         │    │
│   │  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │    │
│   │  │  App1  │ │  App2  │ │   FS   │ │Network │ │ Driver │ │    │
│   │  │        │ │        │ │ Server │ │ Server │ │ Server │ │    │
│   │  └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ │    │
│   │      │          │          │          │          │      │    │
│   │      │          │          │          │          │      │    │
│   │      └──────────┴──────────┴──────────┴──────────┘      │    │
│   │                           │                             │    │
│   │                      IPC (повідомлення)                 │    │
│   │                           │                             │    │
│   └───────────────────────────┼─────────────────────────────┘    │
│                               │                                  │
│   ════════════════════════════╪════════════════════════════════  │
│                               │                                  │
│   Kernel Space (МІНІМАЛЬНЕ)   ▼                                  │
│   ┌─────────────────────────────────────────────────────────┐    │
│   │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐   │    │
│   │  │     IPC      │  │  Scheduler   │  │  Basic MM    │   │    │
│   │  │ (message     │  │  (перемикання│  │  (сторінки)  │   │    │
│   │  │  passing)    │  │   контексту) │  │              │   │    │
│   │  └──────────────┘  └──────────────┘  └──────────────┘   │    │
│   │                                                         │    │
│   │  seL4: ~10 000 рядків коду (vs 30 000 000+ у Linux)     │    │
│   └─────────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────────┘
```

### Переваги мікроядра

| Перевага | Пояснення |
|----------|-----------|
| **Надійність** | Crash драйвера ≠ crash системи (можна перезапустити) |
| **Безпека** | Мінімальна поверхня атаки в Ring 0 |
| **Модифікованість** | Легко замінити компонент без перекомпіляції ядра |
| **Формальна верифікація** | seL4 — математично доведена коректність |

### Недоліки мікроядра

| Недолік | Пояснення |
|---------|-----------|
| **Overhead IPC** | Кожен виклик = повідомлення через ядро (~1000 нс vs 10 нс) |
| **Складність** | Розподілена система, важче відлагоджувати |
| **Менша екосистема** | Менше драйверів, менше підтримки |

### Де використовуються мікроядра

| Система | Сфера | Чому мікроядро |
|---------|-------|----------------|
| **QNX** | Автомобілі, медицина | Сертифікація безпеки, перезапуск компонентів |
| **seL4** | Оборона, аерокосмос | Математично доведена коректність |
| **MINIX 3** | Intel Management Engine (у чипсетах Intel з 2015) | Мінімальна поверхня атаки |
| **Fuchsia (Zircon)** | Google, IoT | Модульність, безпека |
| **L4 family** | Дослідження, вбудовані | Швидкий IPC |

## Гібридне ядро (Hybrid Kernel)

**Визначення:** Компроміс — частина сервісів у ядрі (для швидкості), частина — в User Space (для надійності).

```
┌─────────────────────────────────────────────────────────────────┐
│                    ГІБРИДНЕ ЯДРО (Windows NT)                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   User Space                                                    │
│   ┌──────────────────────────────────────────────────────────┐  │
│   │  Applications  │  Підсистеми    │  Служби                │  │
│   │  (Win32 apps)  │  (Win32; колись│  (Print, Event Log)    │  │
│   │                │   OS/2, POSIX) │                        │  │
│   └──────────────────────────────────────────────────────────┘  │
│                               │                                 │
│                               │ NT API                          │
│   ┌───────────────────────────▼──────────────────────────────┐  │
│   │                    NTDLL.DLL                             │  │
│   │              (User-mode NT interface)                    │  │
│   └───────────────────────────┬──────────────────────────────┘  │
│                               │ syscall                         │
│   ═══════════════════════════════════════════════════════════   │
│                               │                                 │
│   Kernel Space                ▼                                 │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │                    Executive                            │   │
│   │  I/O Manager · Object Manager · Process Manager ·       │   │
│   │  Memory Manager · Security Reference Monitor            │   │
│   ├─────────────────────────────────────────────────────────┤   │
│   │  win32k.sys — вікна й графіка (з NT 4.0, 1996)          │   │
│   ├─────────────────────────────────────────────────────────┤   │
│   │                    Kernel (microkernel-like)            │   │
│   │  Scheduling, Interrupts, Synchronization                │   │
│   ├─────────────────────────────────────────────────────────┤   │
│   │                    HAL (Hardware Abstraction Layer)     │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│   Деякі драйвери в kernel, деякі в user space                   │
└─────────────────────────────────────────────────────────────────┘
```

Архітектори NT на чолі з Девідом Катлером (раніше автором VMS) закладали дизайн, близький до мікроядра: окремі підсистеми спілкувалися повідомленнями. Але у Windows NT 4.0 (1996) віконну систему й графіку перенесли з режиму користувача в ядро (`win32k.sys`) — інакше інтерфейс працював надто повільно. Саме такі поступки й роблять ядро «гібридним»: мікроядерний задум, монолітна реалізація там, де вирішує швидкість.

### macOS XNU (X is Not Unix)

Назва жартівлива й за іронією хибна: macOS офіційно сертифікована як UNIX 03 — формально вона «справжніший» UNIX, ніж Linux, у якого такого сертифіката немає.

```
┌─────────────────────────────────────────────────────────────────┐
│                    macOS XNU KERNEL                             │
│                                                                 │
│   ┌──────────────────────────────────────────────────────────┐  │
│   │                      User Space                          │  │
│   │  Applications, Frameworks, Daemons                       │  │
│   └───────────────────────────┬──────────────────────────────┘  │
│                               │                                 │
│   ═══════════════════════════════════════════════════════════   │
│                               │                                 │
│   ┌───────────────────────────▼───────────────────────────── ┐  │
│   │                        XNU                               │  │
│   │                                                          │  │
│   │  ┌──────────────────────────────────────────────────┐    │  │
│   │  │                    Mach                          │    │  │
│   │  │  (Мікроядро: IPC, scheduling, VM)                │    │  │
│   │  └──────────────────────────────────────────────────┘    │  │
│   │                          +                               │  │
│   │  ┌──────────────────────────────────────────────────┐    │  │
│   │  │                    BSD                           │    │  │
│   │  │  (UNIX layer: VFS, networking, POSIX)            │    │  │
│   │  └──────────────────────────────────────────────────┘    │  │
│   │                          +                               │  │
│   │  ┌───────────────────────────────────────────────────┐   │  │
│   │  │                   I/O Kit                         │   │  │
│   │  │  (Driver framework, C++)                          │   │  │
│   │  └───────────────────────────────────────────────────┘   │  │
│   │                                                          │  │
│   └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│   Mach + BSD + I/O Kit — в одному адресному просторі ядра       │
└─────────────────────────────────────────────────────────────────┘
```

Важлива деталь: у XNU код Mach не працює як мікроядро з окремими серверами — Mach, BSD і драйвери зібрані в одне ядро й викликають одне одного напряму. Від Mach лишилися абстракції (задачі, потоки, порти повідомлень), а не ізоляція служб.

## Порівняльна таблиця

| Критерій | Монолітне | Мікроядро | Гібридне |
|----------|-----------|-----------|----------|
| **Приклади** | Linux, FreeBSD | QNX, MINIX, seL4 | Windows NT, macOS |
| **Код у режимі ядра** | Десятки мільйонів рядків | Тисячі — десятки тисяч рядків | Мільйони рядків |
| **Ціна взаємодії служб** | Виклик функції | Повідомлення з перемиканням контексту | Здебільшого виклик функції |
| **Наслідок збою драйвера** | Падіння всієї системи | Перезапуск служби | Здебільшого падіння системи |
| **Складність розробки** | Середня | Висока | Висока |
| **Драйвери** | В ядрі | User space | Переважно в ядрі, частина — в user space |

### 3. Принцип шарів

Дейкстра 1968 року побудував систему THE з шести рівнів: апаратура й розподіл процесора, пам'ять, консоль, введення-виведення, програми користувачів, оператор. Кожен рівень користувався лише послугами нижчого — тому його можна було перевіряти окремо, коли нижчі вже перевірено. Чистої шаруватості сучасні ядра не дотримуються (заважає швидкість), але ідея живе: мережевий стек TCP/IP, стек зберігання «VFS → файлова система → блочний рівень → драйвер» — це саме шари.

### 4. Принцип розділення механізму та політики

```
┌────────────────────────────────────────────────────────────────┐
│              МЕХАНІЗМ vs ПОЛІТИКА                              │
│                                                                │
│   МЕХАНІЗМ (Kernel):           ПОЛІТИКА (User Space):          │
│   "Як робити"                  "Що робити"                     │
│                                                                │
│   • Перемикання контексту      • Який процес запустити         │
│   • Блокування сторінок        • Які сторінки вивантажити      │
│   • Передача повідомлень       • Кому дозволити доступ         │
│                                                                │
│   Механізми стабільні          Політики змінюються             │
│   (змінюються рідко)           (налаштовуються)                │
│                                                                │
│   Приклад: Linux scheduler     EEVDF, FIFO, RR — різні         │
│            реалізує механізм   політики на одному механізмі    │
└────────────────────────────────────────────────────────────────┘
```

Найчистіший сучасний приклад — **sched_ext** (Linux 6.12, 2024): ядро надає механізм перемикання задач, а саму політику планування — кого запускати наступним — можна написати як програму eBPF і завантажити з простору користувача, не перезбираючи ядро. Так, наприклад, для ігрової консолі Steam Deck розробили окремий планувальник, що віддає перевагу інтерактивним задачам. Той самий принцип — у керуванні частотою процесора: механізм змінює частоту, а «губернатор» (`schedutil`, `performance`, `powersave`) вирішує, коли саме.

## 🎯 Міні-проект (30 хв)

### Завдання: Карта архітектури вашого ядра

Створіть детальну "карту" архітектури ядра вашої системи — візуалізуйте модулі, підсистеми та їх взаємозв'язки.

**Кроки:**

1. Створіть робочу директорію:
```bash
mkdir ~/kernel-map && cd ~/kernel-map
```

2. Зберіть базову інформацію про архітектуру:
```bash
echo "=== КАРТА АРХІТЕКТУРИ ЯДРА ===" > kernel-map.txt
echo "Дата: $(date)" >> kernel-map.txt
echo "" >> kernel-map.txt

echo "--- БАЗОВА ІНФОРМАЦІЯ ---" >> kernel-map.txt
echo "Тип ядра: $(uname -s)" >> kernel-map.txt
echo "Версія: $(uname -r)" >> kernel-map.txt
echo "Архітектура: $(uname -m)" >> kernel-map.txt

# Визначте тип архітектури
if [ "$(uname -s)" = "Linux" ]; then
    echo "Архітектура ядра: Монолітне модульне" >> kernel-map.txt
elif [ "$(uname -s)" = "Darwin" ]; then
    echo "Архітектура ядра: Гібридне (XNU = Mach + BSD)" >> kernel-map.txt
fi
echo "" >> kernel-map.txt
```

3. Проаналізуйте модулі ядра:
```bash
echo "--- СТАТИСТИКА МОДУЛІВ ---" >> kernel-map.txt
echo "Загальна кількість: $(lsmod | wc -l)" >> kernel-map.txt
echo "" >> kernel-map.txt

echo "Топ-10 модулів за розміром:" >> kernel-map.txt
lsmod | sort -k2 -n -r | head -10 >> kernel-map.txt
echo "" >> kernel-map.txt
```

4. Категоризуйте модулі за типом:
```bash
echo "--- КАТЕГОРІЇ МОДУЛІВ ---" >> kernel-map.txt

echo "Мережеві драйвери:" >> kernel-map.txt
lsmod | grep -iE "net|eth|wifi|wlan|iwl|ath|rtl|e1000" | wc -l >> kernel-map.txt

echo "Файлові системи:" >> kernel-map.txt
lsmod | grep -iE "ext4|xfs|btrfs|ntfs|fat|nfs" | wc -l >> kernel-map.txt

echo "USB драйвери:" >> kernel-map.txt
lsmod | grep -i "usb" | wc -l >> kernel-map.txt

echo "Графіка/GPU:" >> kernel-map.txt
lsmod | grep -iE "drm|nvidia|amd|intel|nouveau|radeon" | wc -l >> kernel-map.txt

echo "" >> kernel-map.txt
```

5. Створіть візуальну структуру:
```bash
echo "--- ВІЗУАЛЬНА СТРУКТУРА ---" >> kernel-map.txt
echo "" >> kernel-map.txt
echo "┌─────────────────────────────────────────┐" >> kernel-map.txt
echo "│              USER SPACE                  │" >> kernel-map.txt
echo "│  (ваші програми: $(ps aux | wc -l) процесів)  │" >> kernel-map.txt
echo "├─────────────────────────────────────────┤" >> kernel-map.txt
echo "│           СИСТЕМНІ ВИКЛИКИ               │" >> kernel-map.txt
echo "├─────────────────────────────────────────┤" >> kernel-map.txt
echo "│              KERNEL SPACE                │" >> kernel-map.txt
echo "│                                          │" >> kernel-map.txt
echo "│  ┌────────────────────────────────────┐ │" >> kernel-map.txt
echo "│  │ Базове ядро (vmlinuz)              │ │" >> kernel-map.txt
echo "│  │ Розмір: $(ls -lh /boot/vmlinuz-$(uname -r) 2>/dev/null | awk '{print $5}')              │ │" >> kernel-map.txt
echo "│  └────────────────────────────────────┘ │" >> kernel-map.txt
echo "│            ↑↓                            │" >> kernel-map.txt
echo "│  ┌────────────────────────────────────┐ │" >> kernel-map.txt
echo "│  │ Модулі (.ko): $(lsmod | wc -l) завантажено │ │" >> kernel-map.txt
echo "│  └────────────────────────────────────┘ │" >> kernel-map.txt
echo "├─────────────────────────────────────────┤" >> kernel-map.txt
echo "│              HARDWARE                    │" >> kernel-map.txt
echo "└─────────────────────────────────────────┘" >> kernel-map.txt
echo "" >> kernel-map.txt
```

6. Порівняйте з теорією:
```bash
echo "--- ПОРІВНЯННЯ З ТЕОРІЄЮ ---" >> kernel-map.txt
echo "" >> kernel-map.txt
echo "Linux (монолітне): ~30M рядків коду, $(ls -lh /boot/vmlinuz-$(uname -r) 2>/dev/null | awk '{print $5}')" >> kernel-map.txt
echo "seL4 (мікроядро): ~10K рядків коду" >> kernel-map.txt
echo "Різниця: у тисячі разів більше коду в режимі ядра" >> kernel-map.txt
```

7. Перегляньте результат:
```bash
cat kernel-map.txt
```

**Очікуваний результат:**
Файл `kernel-map.txt` з повною картою архітектури вашого ядра, статистикою модулів та візуальною структурою.

**Бонус (для допитливих):**
- Знайдіть залежності між модулями (`modinfo <module> | grep depends`)
- Порівняйте розмір ядра до і після завантаження модулів
- Дослідіть, які модулі можна безпечно вивантажити

- відмову від ядра взагалі

**2.** Що характерно для монолітного ядра?

- усі підсистеми працюють у режимі ядра як єдине ціле
- драйвери виконуються як звичайні програми користувача
- у режимі ядра лишається тільки планувальник і IPC
- ядро складається з незалежних процесів, що спілкуються повідомленнями

**3.** Що лишається в режимі ядра в мікроядерній архітектурі?

- усі драйвери пристроїв
- файлові системи й мережевий стек
- графічна підсистема
- мінімум: планування, пам'ять і обмін повідомленнями

**4.** Чому виклик між підсистемами монолітного ядра коштує лічені наносекунди, а міжпроцесовий обмін у мікроядрі — близько 1000 нс?

- мікроядро щоразу звертається до диска
- у монолітному це звичайний виклик функції, а в мікроядрі — передавання повідомлення з перемиканням контексту
- монолітне ядро кешує результати викликів
- мікроядра пишуть менш ефективними мовами

**5.** Що станеться в мікроядрі, якщо аварійно завершиться драйвер?

- процес користувача отримає права ядра
- система зупиниться з kernel panic
- служба перезапуститься, система продовжить роботу
- ядро перейде в режим користувача

**6.** Чому Linux називають модульним монолітним ядром?

- воно поєднує мікроядро з гібридним
- усе працює в режимі ядра, але драйвери можна завантажувати й вивантажувати модулями
- його ядро складається з окремих процесів користувача
- його можна зібрати лише цілком, без модулів

**7.** Яку архітектуру мають Windows NT і macOS XNU?

- монолітну
- мікроядерну
- гібридну
- багаторівневу без ядра

**8.** Для якої задачі мікроядро QNX підходить краще за Linux?

- для зберігання великих обсягів даних
- для високонавантаженого вебсервера
- для настільної робочої станції з іграми
- для автомобільних і медичних систем, де ціна збою надто висока

**9.** У чому суть принципу розділення механізму та політики?

- ядро реалізує «як» робити, а «що саме» робити задають із простору користувача
- ядро задає політику, а програми лише виконують її
- механізм і політика мають бути в одному модулі
- політика безпеки має бути вбудована в драйвери

**10.** Яка команда покаже кількість завантажених модулів ядра?

- lsmod | wc -l
- sysctl -a
- dmesg
- uname -s

## Підсумок

| Архітектура | Коли використовувати | Приклади |
|-------------|---------------------|----------|
| **Монолітне** | Максимальна продуктивність, загальне призначення | Linux, FreeBSD |
| **Мікроядро** | Критична надійність, сертифікація, безпека | QNX (авто), seL4 (оборона) |
| **Гібридне** | Баланс продуктивності та надійності | Windows, macOS |

**Ключовий висновок:** Немає "найкращої" архітектури — є архітектура, оптимальна для конкретної задачі. Linux домінує на серверах через продуктивність. QNX керує автомобілями через надійність. Windows NT — компроміс для десктопів.

На наступній лекції почнемо детальне вивчення операційної системи Windows.
