## Hook / Захоплюючий вступ

Steam Deck, сервери Вікіпедії, робочі станції Google і 8-мегабайтний контейнер Docker працюють на тому самому ядрі Linux. Проте Steam Deck не дасть виконати `apt install`, у контейнері Alpine немає `bash`, а сервер RHEL роками тримає ядро 5.14, хоча на kernel.org уже давно вийшло 6.x. DistroWatch відстежує кількасот живих дистрибутивів. Звідки стільки, якщо ядро одне?

Відповідь — у тому, що ядро саме по собі ще не система. У ньому немає ні `ls`, ні shell, ні способу встановити програму. Усе, що ви бачите після завантаження, — це вибір, зроблений авторами дистрибутива. Восени 2025 року Ubuntu 25.10 замінила звичні `ls`, `cp` і `sudo` новими реалізаціями мовою Rust, і система від цього не перестала бути Ubuntu. Змінився один шар — решта лишилася на місці.

**Запитання до аудиторії**: Android працює на ядрі Linux. Чи є Android дистрибутивом Linux? Тримайте відповідь у голові — повернемося до неї за кілька хвилин.

## Що таке дистрибутив Linux?

**Дистрибутив (distro)** — це ядро Linux, зібране разом із бібліотекою C, системою ініціалізації, базовими утилітами, пакетним менеджером, репозиторіями програм і налаштуваннями «з коробки». Головне, що продає дистрибутив, — навіть не програми, а **узгодженість**: тисячі пакетів зібрані з однаковими версіями бібліотек, перевірені разом і оновлюються однією командою.

```
┌─────────────────────────────────────────────────────────────────────┐
│               АНАТОМІЯ ДИСТРИБУТИВА: UBUNTU 24.04 LTS               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌─────────────────────────────────────────────────────────────┐   │
│   │ Застосунки       Firefox (snap), LibreOffice, Nautilus      │   │
│   ├─────────────────────────────────────────────────────────────┤   │
│   │ Робочий стіл     GNOME 46 на Wayland                        │   │
│   ├─────────────────────────────────────────────────────────────┤   │
│   │ Пакети           dpkg + APT, Snap; репозиторії main,        │   │
│   │                  restricted, universe, multiverse           │   │
│   ├─────────────────────────────────────────────────────────────┤   │
│   │ Утиліти й shell  GNU coreutils, bash; /bin/sh → dash        │   │
│   ├─────────────────────────────────────────────────────────────┤   │
│   │ Ініціалізація    systemd 255                                │   │
│   ├─────────────────────────────────────────────────────────────┤   │
│   │ Бібліотека C     glibc 2.39                                 │   │
│   ├─────────────────────────────────────────────────────────────┤   │
│   │ Ядро             Linux 6.8                                  │   │
│   └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│   Замініть будь-який шар — і вийде інший дистрибутив:               │
│   Alpine = Linux + musl + BusyBox + OpenRC + apk                    │
└─────────────────────────────────────────────────────────────────────┘
```

Кожен шар має альтернативи, і саме їхнє поєднання робить дистрибутив тим, чим він є:

Таблиця 1 — Шари дистрибутива та їхні варіанти

| Шар | Варіанти | Хто що обрав |
|-----|----------|--------------|
| **Бібліотека C** | glibc, musl | glibc — Debian, Fedora, Arch; musl — Alpine, Void (musl-редакція) |
| **Ініціалізація** | systemd, OpenRC, runit | systemd — більшість; OpenRC — Alpine, Gentoo; runit — Void |
| **Базові утиліти** | GNU coreutils, BusyBox, uutils | BusyBox — Alpine і вбудовані системи; uutils (Rust) — Ubuntu з 25.10 |
| **Формат пакетів** | .deb, .rpm, .pkg.tar.zst, .apk, Nix | залежить від сімейства |
| **Модель випусків** | point release, rolling, immutable | див. розділ «Моделі випусків» |

Тепер про Android. Ядро там Linux, але бібліотека C — власна Bionic, а не glibc, GNU-утиліт немає, пакетів у розумінні apt чи dnf теж — застосунки ставляться як APK з окремою моделлю прав. Тому Android зазвичай називають ОС на ядрі Linux, а не дистрибутивом GNU/Linux: з `.deb` чи скриптом для Ubuntu він нічого спільного не має. З тієї ж причини бінарний файл, зібраний для Ubuntu з glibc, не запуститься в Alpine з musl — ядро те саме, а бібліотека інша.

## Родинне дерево дистрибутивів

Більшість дистрибутивів не пишуть з нуля, а беруть за основу інший — **upstream** — і додають своє. Так виникають сімейства, і знання сімейства важливіше за знання конкретної назви: хто вміє в Debian, той за день освоїться в Ubuntu, Mint чи Kali.

```
┌─────────────────────────────────────────────────────────────────────┐
│                       ГЕНЕАЛОГІЯ ДИСТРИБУТИВІВ                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Slackware (1993) — найстаріший дистрибутив, що розвивається досі   │
│                                                                     │
│  Debian (1993)                              формат .deb, dpkg + APT │
│   ├── Ubuntu (2004, Canonical)                                      │
│   │    ├── Kubuntu, Xubuntu, Lubuntu — офіційні «флейвори»          │
│   │    ├── Linux Mint (2006)                                        │
│   │    └── Pop!_OS, elementary OS, Zorin OS                         │
│   ├── Kali Linux (2013, наступник BackTrack)                        │
│   ├── Raspberry Pi OS                                               │
│   └── LMDE — Linux Mint на базі Debian, без Ubuntu                  │
│                                                                     │
│  Red Hat Linux (1994)                       формат .rpm, rpm + DNF  │
│   ├── RHEL (2002) — комерційна гілка                                │
│   └── Fedora (2003) — гілка спільноти                               │
│       Потік коду сьогодні:                                          │
│       Fedora → CentOS Stream → RHEL → Rocky, AlmaLinux, Oracle      │
│                                                                     │
│  SUSE (1994, спершу на основі Slackware)                            │
│   ├── SUSE Linux Enterprise                                         │
│   └── openSUSE Leap (стабільний) і Tumbleweed (rolling)             │
│                                                                     │
│  Arch Linux (2002)                          pacman, rolling release │
│   ├── Manjaro, EndeavourOS                                          │
│   └── SteamOS 3 (2022, Valve, Steam Deck)                           │
│                                                                     │

│                                                                     │
```

Стрілка «Fedora → CentOS Stream → RHEL» — найважливіша зміна останніх років. Раніше CentOS був безкоштовною копією вже випущеного RHEL, тепер CentOS Stream стоїть **перед** RHEL: у нього потрапляють зміни, які увійдуть у наступний мінорний випуск. Копіями RHEL «після виходу» стали Rocky Linux і AlmaLinux.

## Як влаштований пакет і пакетний менеджер

На попередній лекції ви бачили команди `apt install` і `dnf install`. Тепер подивимося, що відбувається всередині, — саме це відрізняє адміністратора від людини, яка копіює команди з форумів.

### Чому Linux не ставить програми інсталяторами

У Windows інсталятор програми зазвичай несе з собою всі потрібні бібліотеки: десять програм можуть покласти на диск десять копій однієї DLL, і кожна оновлюватиметься (або ні) окремо. Linux-дистрибутиви роблять інакше: бібліотека встановлюється **один раз** як окремий пакет, а програми лише посилаються на неї. Коли в OpenSSL знаходять вразливість, оновлюють один пакет `libssl` — і виправлення отримують усі програми одразу. Ціна — **залежності**: пакетний менеджер має знати, що кому потрібно, і не зламати одне, оновлюючи інше.

### Що всередині .deb

Пакет — це звичайний архів із двох частин: **що покласти на диск** і **метадані про це**. Розберіть справжній пакет, нічого не встановлюючи:

```bash
cd /tmp
apt download hello             # завантажити .deb без встановлення
ar t hello_*.deb               # .deb — це архів формату ar
dpkg-deb -I hello_*.deb        # метадані: версія, залежності, опис
dpkg-deb -c hello_*.deb        # файли, які ляжуть на диск
```

`ar t` покаже три члени архіву: `debian-binary` (версія формату), `control.tar.*` (метадані й скрипти встановлення) і `data.tar.*` (самі файли). У Debian частини стиснуті xz, в Ubuntu — zstd. У виводі `dpkg-deb -I` знайдіть рядок `Depends: libc6 (>= …)`: навіть найпростіша програма залежить від бібліотеки C. Пакет `.rpm` влаштований аналогічно, лише в іншому контейнері, і, на відміну від .deb, кожен .rpm підписаний окремо (`rpm -K файл.rpm`).

### Два рівні інструментів

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ЩО РОБИТЬ ПАКЕТНИЙ МЕНЕДЖЕР                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  $ sudo apt install nginx                                           │
│        │                                                            │
│        ▼                                                            │
│  1. Індекс репозиторію     /var/lib/apt/lists/, оновлює apt update. │
│        │                   Файл InRelease підписаний ключем Debian  │
│        │                   чи Ubuntu, у ньому — хеші списків пакетів│
│        ▼                                                            │
│  2. Розв'язання залежностей nginx → nginx-common, libc6, zlib1g…    │
│        │                   що вже стоїть, що треба доставити        │
│        ▼                                                            │
│  3. Завантаження .deb      /var/cache/apt/archives/; SHA256 кожного │
│        │                   файлу звіряється з підписаним індексом   │
│        ▼                                                            │
│  4. dpkg розпаковує        файли з data.tar, потім скрипт postinst: │
│        │                   у nginx він вмикає й запускає службу     │
│        ▼                                                            │
│  5. Облік у базі           /var/lib/dpkg/status: пакет, версія,     │
│                            стан; dpkg -L знає кожен його файл       │
│                                                                     │
│  APT — «мозок» (репозиторії, залежності), dpkg — «руки» (файли).    │
│  У світі RPM так само: dnf зверху, rpm знизу.                       │
└─────────────────────────────────────────────────────────────────────┘
```

Зверніть увагу на крок 1: самі .deb не підписані, підписаний **індекс**, а в ньому записані хеші кожного пакета. Тому дзеркало репозиторію, навіть чуже чи зламане, не може підсунути змінений пакет — хеш не зійдеться з підписаним списком. Це той самий ланцюжок довіри, що й у TLS, тільки для програм.

Таблиця 2 — Найкорисніші запити до бази пакетів

| Питання | Debian/Ubuntu | Fedora/RHEL | Arch |
|---------|---------------|-------------|------|
| Якому пакету належить файл? | `dpkg -S /usr/bin/ls` | `rpm -qf /usr/bin/ls` | `pacman -Qo /usr/bin/ls` |
| Які файли встановив пакет? | `dpkg -L coreutils` | `rpm -ql coreutils` | `pacman -Ql coreutils` |
| Від чого залежить пакет? | `apt-cache depends nginx` | `dnf repoquery --requires nginx` | `pacman -Si nginx` |
| Хто залежить від пакета? | `apt-cache rdepends libssl3` | `dnf repoquery --whatrequires openssl-libs` | `pactree -r openssl` |
| Звідки й яка версія? | `apt-cache policy nginx` | `dnf info nginx` | `pacman -Si nginx` |
| Чи не змінено файли пакета? | `dpkg --verify coreutils` | `rpm -V coreutils` | `pacman -Qkk coreutils` |

Якщо `dpkg -S /usr/bin/ls` відповідає «no path found», спробуйте `/bin/ls`: після об'єднання `/bin` з `/usr/bin` (usrmerge, лекція 2) база dpkg у старіших випусках ще пам'ятає старі шляхи. `pactree` входить до пакета `pacman-contrib`.

## Моделі випусків

Друга річ, яка визначає дистрибутив, — **як він оновлюється**. Від цього залежить, чи можна поставити його на сервер і забути на п'ять років.

Таблиця 3 — Моделі випусків

| Модель | Як працює | Приклади |
|--------|-----------|----------|
| **Point release** | Раз на кілька років виходить версія; версії програм у ній заморожено, приходять лише виправлення | Debian, Ubuntu LTS, RHEL, openSUSE Leap |
| **Rolling release** | Версій системи немає, пакети оновлюються безперервно, щойно їх випустили автори | Arch, openSUSE Tumbleweed, Gentoo |
| **Stream** | Безперервний потік змін, що передує стабільному випуску | CentOS Stream |
| **Immutable (atomic)** | Корінь лише для читання, система оновлюється цілим образом із можливістю відкату | Fedora Silverblue, SteamOS 3, Ubuntu Core, NixOS |

### Бекпортинг: чому стара версія — не обов'язково вразлива

**Запитання до аудиторії**: у RHEL 9 ядро 5.14, хоча на kernel.org давно вийшло 6.x. Чи вразливий такий сервер до всього, що виправили після 5.14?

Ні. Ідея point release — **не змінювати поведінку**: адміністратор, який налаштував сервер, не хоче, щоб після оновлення змінився формат конфігурації чи зникла опція. Тому мейнтейнери дистрибутива беруть з нових версій лише виправлення безпеки й помилок і **переносять** їх у стару версію — це називається **бекпортинг** (backporting). Ядро RHEL 9 має номер 5.14, але містить тисячі латок із пізніших ядер. Звідси практичне правило: вразливість на сервері перевіряють не за номером версії, а за журналом змін пакета (`apt changelog openssl`, `rpm -q --changelog openssl`) або за бюлетенями безпеки дистрибутива.

Rolling release робить протилежне: ви завжди маєте те, що випустили автори, але разом із новими функціями приходять і нові зміни поведінки. Звідси правило Arch: оновлювати систему лише цілком (`pacman -Syu`). Команда `pacman -Sy` з наступним встановленням одного пакета — **часткове оновлення**: новий пакет потягне нові бібліотеки, а решта системи лишиться зі старими, і щось перестане запускатися.

### Незмінні системи

Immutable-дистрибутиви працюють як телефон: коренева файлова система доступна лише для читання, оновлення завантажується цілим образом у другу копію системи, а після перезавантаження можна повернутися до попередньої, якщо щось пішло не так. Програми ставляться поверх — через Flatpak, контейнери чи окремий шар. Саме так влаштовані SteamOS 3 (Valve не може дозволити, щоб мільйони Steam Deck «зламалися» після оновлення) і ОС для вузлів Kubernetes — Talos, Bottlerocket, Flatcar.

## Універсальні формати: Snap, Flatpak, AppImage

Автору програми незручно збирати пакет під п'ять сімейств і десяток версій кожного. Універсальні формати вирішують це тим, що програма несе залежності з собою, як у Windows, але в ізольованому середовищі.

Таблиця 4 — Універсальні формати пакетів

| Формат | Автор, магазин | Як працює | Де використовують |
|--------|----------------|-----------|-------------------|
| **Snap** | Canonical, Snap Store | Стиснутий образ squashfs, монтується під час запуску; ізоляція через AppArmor | Ubuntu: Firefox, серверні й консольні програми |
| **Flatpak** | спільнота, Flathub | Спільні runtime (GNOME, KDE), пісочниця bubblewrap | Настільні програми у Fedora, Mint, SteamOS |
| **AppImage** | автори програм | Один виконуваний файл, без встановлення й ізоляції | Портативні програми з сайтів розробників |

```bash
snap list                      # встановлені snap-пакети
findmnt -t squashfs            # кожен snap змонтований як окремий образ
lsblk | grep loop              # ті самі образи — як пристрої loop0, loop1…
flatpak list --app             # програми з Flathub
```

Якщо ви колись дивувалися десятку пристроїв `loop` у виводі `lsblk` на Ubuntu, — це вони: кожен snap змонтовано з окремого файлу-образу. Звідси й повільніший перший запуск: образ треба змонтувати й розпакувати на льоту.

## Практичне завдання

```bash
# 1. Який дистрибутив і до якого сімейства належить
cat /etc/os-release
. /etc/os-release; echo "$ID | $ID_LIKE | $VERSION_ID"

# 2. Ядро — окремо від дистрибутива
uname -r

# 3. Бібліотека C і shell за замовчуванням
ldd --version | head -1        # glibc і її версія
ls -l /bin/sh                  # dash, bash чи busybox

# 4. Система ініціалізації (процес з PID 1)
ps -p 1 -o comm=

# 5. Скільки пакетів встановлено
dpkg -l | grep -c '^ii'        # Debian/Ubuntu
rpm -qa | wc -l                # Fedora/RHEL
pacman -Q | wc -l              # Arch

# 6. Якому пакету належить команда ls
dpkg -S /usr/bin/ls  ||  rpm -qf /usr/bin/ls  ||  pacman -Qo /usr/bin/ls

# 7. Робоче середовище
echo "$XDG_CURRENT_DESKTOP $XDG_SESSION_TYPE"
```

Поле `ID_LIKE` у `/etc/os-release` — те, на що спираються скрипти встановлення: у Linux Mint там записано `ubuntu debian`, у Rocky Linux — `rhel centos fedora`. Скрипт, який перевіряє це поле, а не назву дистрибутива, працюватиме на всьому сімействі.

## 🎯 Міні-проект (30 хв)

### Завдання: Універсальна обгортка для пакетних менеджерів

Напишіть скрипт `pkg`, який сам визначає сімейство дистрибутива й перекладає одну команду на мову apt, dnf або pacman. Саме так влаштовані скрипти встановлення Docker, Node.js чи Ansible: вони читають `/etc/os-release`, а не вгадують за наявністю програм.

**Кроки:**

1. Створіть файл:
```bash
mkdir -p ~/scripts
nano ~/scripts/pkg.sh
```

2. Напишіть код:
```bash
#!/usr/bin/env bash
# pkg — одна команда для apt, dnf і pacman
# Сімейство визначаємо за ID та ID_LIKE з /etc/os-release

set -u
. /etc/os-release

detect_pm() {
    for id in ${ID:-linux} ${ID_LIKE:-}; do
        case "$id" in
            debian|ubuntu)      echo apt;    return ;;
            fedora|rhel|centos) echo dnf;    return ;;
            arch)               echo pacman; return ;;
        esac
    done
    echo unknown
}

show_help() {
    echo "pkg: сімейство $PM (дистрибутив ${PRETTY_NAME:-невідомий})"
    echo "Використання: pkg <дія> [пакет | файл]"
    echo "  install <пакет>   встановити"
    echo "  remove <пакет>    видалити"
    echo "  search <слово>    знайти в репозиторіях"
    echo "  info <пакет>      опис і версія"
    echo "  files <пакет>     які файли встановив пакет"
    echo "  owner <файл>      якому пакету належить файл"
    echo "  upgrade           оновити всю систему"
    echo "  list              усі встановлені пакети"
}

need_arg() {
    if [ -z "$ARG" ]; then
        echo "Бракує аргументу: pkg $ACTION <пакет або файл>" >&2
        exit 2
    fi
}

PM=$(detect_pm)
ACTION=${1:-help}
ARG=${2:-}

case "$PM:$ACTION" in
    apt:install)    need_arg; sudo apt-get install "$ARG" ;;
    apt:remove)     need_arg; sudo apt-get remove "$ARG" ;;
    apt:search)     need_arg; apt-cache search "$ARG" ;;
    apt:info)       need_arg; apt-cache show "$ARG" ;;
    apt:files)      need_arg; dpkg -L "$ARG" ;;
    apt:owner)      need_arg; dpkg -S "$ARG" ;;
    apt:upgrade)    sudo apt-get update && sudo apt-get upgrade ;;
    apt:list)       dpkg-query -W -f='${Package}\t${Version}\n' ;;

    dnf:install)    need_arg; sudo dnf install "$ARG" ;;
    dnf:remove)     need_arg; sudo dnf remove "$ARG" ;;
    dnf:search)     need_arg; dnf search "$ARG" ;;
    dnf:info)       need_arg; dnf info "$ARG" ;;
    dnf:files)      need_arg; rpm -ql "$ARG" ;;
    dnf:owner)      need_arg; rpm -qf "$ARG" ;;
    dnf:upgrade)    sudo dnf upgrade ;;
    dnf:list)       rpm -qa --qf '%{NAME}\t%{VERSION}-%{RELEASE}\n' ;;

    pacman:install) need_arg; sudo pacman -S --needed "$ARG" ;;
    pacman:remove)  need_arg; sudo pacman -Rs "$ARG" ;;
    pacman:search)  need_arg; pacman -Ss "$ARG" ;;
    pacman:info)    need_arg; pacman -Si "$ARG" ;;
    pacman:files)   need_arg; pacman -Ql "$ARG" ;;
    pacman:owner)   need_arg; pacman -Qo "$ARG" ;;
    pacman:upgrade) sudo pacman -Syu ;;
    pacman:list)    pacman -Q ;;

    unknown:*)      echo "Невідоме сімейство: ${ID:-?}" >&2; exit 1 ;;
    *)              show_help ;;
esac
```

Окремої дії `update` немає свідомо: в Arch оновлення індексу без оновлення пакетів (`pacman -Sy`) веде до часткового оновлення, dnf оновлює індекс сам, тож для всіх трьох сімейств є лише повне `upgrade`. Замість `apt` у скрипті — `apt-get` і `apt-cache`: `apt` призначений для людини і сам попереджає, що його вивід може змінюватися між версіями.

3. Зробіть файл виконуваним і перевірте:
```bash
chmod +x ~/scripts/pkg.sh
~/scripts/pkg.sh                        # довідка й визначене сімейство
~/scripts/pkg.sh owner /usr/bin/ls      # coreutils
~/scripts/pkg.sh files coreutils | head
~/scripts/pkg.sh list | wc -l
```

4. Додайте псевдонім:
```bash
echo 'alias pkg="$HOME/scripts/pkg.sh"' >> ~/.bashrc
source ~/.bashrc
pkg search htop
```

5. Перевірте скрипт на інших сімействах без віртуальних машин — у контейнерах (потрібен Docker або Podman). Дії `owner`, `files` і `list` працюють без sudo і без мережі:
```bash
for img in debian:stable fedora archlinux; do
    echo "== $img"
    docker run --rm -v ~/scripts:/s:ro "$img" /s/pkg.sh owner /usr/bin/ls
done
```

**Очікуваний результат:**

- Скрипт `~/scripts/pkg.sh` і псевдонім `pkg`, що працюють однаково в Debian/Ubuntu, Fedora/RHEL і Arch.
- `pkg owner /usr/bin/ls` у трьох контейнерах назве пакет `coreutils` — у кожного сімейства у своєму форматі.
- Розуміння, що визначати дистрибутив треба за `/etc/os-release`, а не за назвою чи наявністю програм.

**Бонус (для допитливих):**

- Додайте openSUSE (`ID_LIKE="suse opensuse"`, менеджер `zypper`) і Alpine (`ID=alpine`, менеджер `apk`; власника файлу показує `apk info --who-owns`).
- Додайте дію `why <пакет>`: хто залежить від пакета (`apt-cache rdepends --installed`, `dnf repoquery --installed --whatrequires`, `pactree -r`).
- Записуйте кожну дію, що змінює систему, у `~/.pkg.log` з датою: `date '+%F %T'`.

- дистрибутив — це ядро разом з утилітами, пакетним менеджером і налаштуваннями

**2.** До якого сімейства належить Ubuntu?

**3.** Який пакетний менеджер використовують Fedora та Rocky Linux?

- dnf

**4.** Що означає модель rolling release, за якою працює Arch Linux?

- систему оновлюють тільки перевстановленням
- нова версія виходить раз на пів року
- пакети оновлюються безперервно, окремих версій системи немає
- оновлення виходять лише разом із новим ядром

**5.** Чим Ubuntu LTS відрізняється від звичайного випуску?

- виходить щомісяця
- містить більше графічних програм
- працює лише на серверному обладнанні
- має довший строк підтримки, тому підходить для серверів

**6.** Чому компанії обирають RHEL, а не безкоштовні збірки?

- RHEL швидший за решту дистрибутивів
- безкоштовні збірки не мають пакетного менеджера
- разом із системою вони купують комерційну підтримку й тривалий життєвий цикл
- лише RHEL підтримує контейнери

**7.** Чому образи контейнерів на Alpine Linux важать одиниці мегабайтів?

- у ньому стиснуто файлову систему
- дистрибутив зібраний із мінімальних компонентів: musl замість glibc, BusyBox замість GNU-утиліт
- він використовує окреме ядро, оптимізоване під контейнери
- він працює лише в оперативній пам'яті

**8.** Яка команда встановить пакет nginx у Debian?

- apt install nginx
- pacman -S nginx
- rpm -qa nginx
- dnf install nginx

**9.** Яка команда покаже, який саме дистрибутив встановлено?

- df -h
- cat /etc/os-release
- uname -r
- lsmod

**10.** Який дистрибутив радять початківцеві?

- Arch Linux

- Ubuntu або Linux Mint

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Дистрибутив** | Ядро Linux разом із бібліотекою C, утилітами, пакетним менеджером, репозиторіями й налаштуваннями |
| **Upstream / downstream** | Проєкт-джерело і похідний від нього: Debian — upstream для Ubuntu, Fedora — для CentOS Stream |
| **Пакет** | Архів із файлами програми та метаданими: версія, залежності, скрипти встановлення |
| **Залежність** | Інший пакет, без якого програма не працюватиме; пакетний менеджер доставляє їх автоматично |
| **Репозиторій** | Сервер із пакетами й підписаним індексом, з якого їх встановлює пакетний менеджер |
| **dpkg / rpm** | Низькорівневі інструменти: розпаковують пакет і ведуть базу встановленого |
| **APT / DNF** | Високорівневі менеджери: репозиторії, розв'язання залежностей, перевірка підписів |
| **Point release** | Модель, у якій версії програм заморожені на весь строк підтримки |
| **Rolling release** | Модель без версій системи: пакети оновлюються безперервно |
| **Бекпортинг** | Перенесення виправлень з нової версії програми в стару, що постачається в стабільному випуску |
| **LTS** | Випуск із довгою підтримкою: Ubuntu — 5 років, RHEL — 10 |
| **Immutable-система** | Корінь лише для читання, оновлення цілим образом із можливістю відкату |

**Порада:** не витрачайте тижні на вибір першого дистрибутива. Візьміть Ubuntu LTS або Fedora, а коли захочеться зрозуміти, як усе влаштовано зсередини, — встановіть Arch у віртуальній машині.

На наступній лекції — графічні середовища Linux: X11, Wayland і робочі столи.
