## Hook / Захоплюючий вступ

О третій ночі приходить сповіщення: на сервері закінчилося місце. Черговий адміністратор знаходить журнал на 40 ГБ, видаляє його командою `rm`… і `df` далі показує 100 %. `du` запевняє, що файлів на диску вдвічі менше, ніж зайнято. Куди поділися 40 гігабайтів?

Відтворіть цю загадку на своєму комп'ютері — це безпечно:

```bash
dd if=/dev/zero of=/tmp/big bs=1M count=200   # файл на 200 МБ
sleep 600 < /tmp/big &                         # «служба», що тримає його відкритим
rm /tmp/big                                    # видаляємо
df -h /tmp                                     # місце не звільнилося
ls -l /proc/$!/fd                              # 0 -> /tmp/big (deleted)
kill $!                                        # процес закрив файл — місце повернулося
df -h /tmp
```

Щоб зрозуміти, що сталося, треба знати, як файлова система насправді зберігає файли, — і що ім'я файлу та сам файл у Linux не одне й те саме. Наприкінці лекції ви зможете пояснити цей фокус за хвилину.

**Запитання до аудиторії**: де зберігається ім'я файлу — у самому файлі, поруч із даними чи десь іще?

## Все є файлом

Філософія UNIX: **«everything is a file»**. Звичайні документи, каталоги, диски, термінали, канали між процесами, відомості про ядро — усе це має ім'я в дереві каталогів і відкривається тими самими системними викликами `open`, `read`, `write`. Тому `cat` читає і текстовий файл, і `/proc/cpuinfo`, а `dd` пише і у файл, і прямо на флешку.

```
┌─────────────────────────────────────────────────────────────────────┐
│                         ТИПИ ФАЙЛІВ У LINUX                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Символ  Тип                    Приклад                             │
│  ──────  ─────────────────────  ─────────────────────────────       │
│    -     звичайний файл         /etc/passwd                         │
│    d     каталог                /home/student                       │
│    l     символьне посилання    /bin → usr/bin                      │
│    b     блочний пристрій       /dev/sda, /dev/nvme0n1              │
│    c     символьний пристрій    /dev/tty, /dev/null                 │
│    s     сокет                  /run/systemd/journal/socket         │
│    p     іменований канал FIFO  створюється командою mkfifo         │
│                                                                     │
│  Тип — перший символ у виводі ls -l:                                │
│  drwxr-xr-x  каталог     -rw-r--r--  файл     lrwxrwxrwx  посилання │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
file /etc/passwd /dev/sda /usr/bin/ls
# /etc/passwd: ASCII text
# /dev/sda: block special (8/0)
# /usr/bin/ls: ELF 64-bit LSB pie executable, x86-64, ...

ls -l /dev/sda /dev/null
# brw-rw---- 1 root disk 8, 0 ... /dev/sda    — 8, 0: номери драйвера й пристрою
# crw-rw-rw- 1 root root 1, 3 ... /dev/null

head -c 16 /dev/urandom | xxd                  # випадкові байти від ядра
echo "у нікуди" > /dev/null                    # «чорна діра»
```

У файлу пристрою немає вмісту на диску: пара чисел (`8, 0`) каже ядру, якому драйверу передати операції читання й запису. Файли в `/dev` створює не адміністратор, а ядро (devtmpfs) і служба udev, щойно під'єднано пристрій.

## Від диска до файлу

Між байтами на диску і файлом, який відкриває програма, — кілька шарів:

```
┌─────────────────────────────────────────────────────────────────────┐
│                        ВІД ПРОГРАМИ ДО ДИСКА                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Програма:   open("/home/student/звіт.txt"), read(), write()        │
│        │                                                            │
│        ▼                                                            │
│  VFS — віртуальна файлова система ядра: один інтерфейс для всіх ФС  │
│        │                                                            │
│   ┌────┴──────┬────────────┬────────────┬────────────┐              │
│   ▼           ▼            ▼            ▼            ▼              │
│  ext4        vfat         proc         tmpfs        nfs             │
│  (диск)     (флешка)    (дані ядра)   (пам'ять)    (мережа)         │
│   │           │                                                     │
│   ▼           ▼                                                     │
│  розділ /dev/nvme0n1p2   розділ /dev/sdb1                           │
│   │           │                                                     │
│   ▼           ▼                                                     │
│  таблиця розділів GPT → блочний пристрій → драйвер → диск           │
│                                                                     │
│  Усі ці ФС змонтовано в ОДНЕ дерево каталогів від кореня /:         │
│  у Linux немає дисків C: і D:, є лише точки монтування.             │
└─────────────────────────────────────────────────────────────────────┘
```

1. **Блочний пристрій** — диск як послідовність блоків: `/dev/sda` (SATA, USB), `/dev/nvme0n1` (NVMe), `/dev/vda` (віртуальна машина).
2. **Таблиця розділів** ділить диск на частини: `/dev/sda1`, `/dev/nvme0n1p2`. Сучасний стандарт — **GPT** (до 128 розділів, диски понад 2 ТБ), застарілий — **MBR**.
3. **Файлова система** — структура даних усередині розділу: де inode, де вільні блоки, де журнал. Її створює `mkfs`.
4. **Монтування** підвішує файлову систему до каталогу в єдиному дереві.
5. **VFS** (Virtual File System) — шар ядра, який дає програмам однаковий інтерфейс до будь-якої ФС. Саме VFS робить можливим принцип «все є файлом»: `/proc` — теж «файлова система», просто її «диск» — структури ядра в пам'яті.

```bash
lsblk -f                  # диски, розділи, типи ФС, UUID, точки монтування
sudo fdisk -l /dev/sda    # таблиця розділів
findmnt                   # дерево змонтованих ФС, включно з proc, sysfs, tmpfs
cat /proc/filesystems     # які ФС знає ядро (nodev — без диска)
```

## Inode і каталоги: як насправді зберігається файл

Кожен файл у файловій системі описує **inode** (index node) — невелика структура з номером. У ній записано все про файл, **крім імені**: тип, права, власника, розмір, три позначки часу, кількість посилань і де на диску лежать дані. А ім'я живе в **каталозі**: каталог — це теж файл, вміст якого — таблиця пар «ім'я → номер inode».

```
┌─────────────────────────────────────────────────────────────────────┐
│                           INODE І КАТАЛОГ                           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Каталог /home/student — це таблиця «ім'я → номер inode»:           │
│  ┌──────────────────────┬───────────────┐                           │
│  │ .                    │ 1311000       │                           │
│  │ ..                   │ 1310721       │                           │
│  │ звіт.txt             │ 1311234 ──┼───┐                           │
│  │ копія.txt (hard link)│ 1311234 ──┼───┤                           │
│  └──────────────────────┴───────────┘   │                           │
│                                         ▼                           │
│  Inode 1311234 — усе про файл, КРІМ імені:                          │
│  ┌───────────────────────────────────────────────────────────┐      │
│  │ тип і права         -rw-r--r--                            │      │
│  │ власник, група      UID 1000, GID 1000                    │      │
│  │ розмір              4 812 байт                            │      │
│  │ час                 доступу, зміни вмісту, зміни inode    │      │
│  │ лічильник посилань  2                                     │      │
│  │ де лежать дані      extent: блоки 88 400 – 88 401         │      │
│  └───────────────────────────────────────────────────────────┘      │
│                                                                     │
│  rm видаляє рядок із таблиці каталогу і зменшує лічильник.          │
│  Дані звільняються, лише коли лічильник = 0 і файл ніхто            │
│  не тримає відкритим.                                               │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
stat звіт.txt
#   File: звіт.txt
#   Size: 4812        Blocks: 16         IO Block: 4096   regular file
# Device: 259,2       Inode: 1311234     Links: 1
# Access: (0644/-rw-r--r--)  Uid: ( 1000/ student)   Gid: ( 1000/ student)
# Access: 2026-09-17 10:31:02   — останнє читання
# Modify: 2026-09-17 10:30:15   — зміна вмісту
# Change: 2026-09-17 10:30:15   — зміна inode: права, власник, перейменування

ls -li                    # номер inode перед кожним файлом
df -i                     # скільки inode зайнято й вільно
```

З цієї будови випливає кілька речей, які інакше здаються дивними:

- **Перейменування в межах ФС миттєве**, навіть для файлу на 100 ГБ: `mv` лише змінює рядок у таблиці каталогу, дані не рухаються. Переміщення на інший розділ — це вже копіювання й видалення.
- **`rm` не видаляє дані, а видаляє ім'я** (системний виклик `unlink`). Дані звільняються, коли лічильник посилань дорівнює нулю **і** файл ніхто не тримає відкритим. Ось і розгадка вступної загадки: журнал зник з каталогу, але служба досі тримала його відкритим, і inode жив далі. Знайти такі файли допомагає `sudo lsof +L1`, а звільнити місце — перезапуск служби.
- **Можна вичерпати inode, маючи вільне місце.** Кількість inode в ext4 задається під час створення ФС, і мільйони дрібних файлів (кеш, сесії PHP, поштова черга) спричиняють помилку «No space left on device» при вільних гігабайтах. Діагноз — `df -i`.
- **Права на видалення файлу — це права на каталог**, а не на файл: видалення змінює таблицю каталогу.

## Ієрархія каталогів (FHS)

**FHS** (Filesystem Hierarchy Standard) описує, що де лежить, тому структура однакова в Ubuntu, Fedora й Arch.

```
/                          корінь єдиного дерева
├── bin → usr/bin          команди (об'єднання /usr, usrmerge)
├── sbin → usr/sbin        команди адміністрування
├── lib → usr/lib          бібліотеки й модулі ядра
├── boot/                  ядро vmlinuz, initramfs, файли GRUB
├── dev/                   файли пристроїв (devtmpfs)
├── etc/                   конфігурація: passwd, fstab, hostname, ssh/, systemd/
├── home/                  домашні каталоги користувачів
├── media/                 автоматичне монтування флешок: /media/<користувач>/<мітка>
├── mnt/                   тимчасове ручне монтування
├── opt/                   сторонні програми цілими пакетами: /opt/google/chrome
├── proc/                  процеси й ядро (procfs, у пам'яті)
├── root/                  домашній каталог root
├── run/                   стан з моменту завантаження: сокети, PID-файли (tmpfs)
├── srv/                   дані служб: вебсайти, FTP
├── sys/                   пристрої й драйвери (sysfs, у пам'яті)
├── tmp/                   тимчасові файли, зникають після перезавантаження
├── usr/                   усе, що встановлено з пакетів
│   ├── bin/, sbin/, lib/  програми й бібліотеки
│   ├── share/             дані, незалежні від архітектури: man, значки, .desktop
│   └── local/             встановлене вручну, повз пакетний менеджер
└── var/                   змінні дані
    ├── log/               журнали (в Ubuntu є syslog, у Debian 12+ — лише journald)
    ├── lib/               стан програм: бази dpkg, docker, баз даних
    ├── cache/             кеш: пакети apt, man
    ├── spool/             черги друку й пошти
    └── tmp/               тимчасові файли, що переживають перезавантаження
```

Цікава історія: `/usr` ніколи не означав «User System Resources» — це пізніша вигадана розшифровка. У ранньому UNIX на PDP-11 `/usr` був буквально каталогом користувачів (user), на другому диску. Коли перший диск заповнився, частину програм перенесли в `/usr/bin` — і поділ `/bin` проти `/usr/bin` прожив п'ятдесят років, доки дистрибутиви не об'єднали їх посиланнями.

Практичне правило, яке випливає з FHS: `/usr` належить пакетному менеджеру — власні скрипти кладіть у `/usr/local/bin` або `~/.local/bin`, конфігурацію правте в `/etc`, а дані служб шукайте у `/var/lib`.

```bash
ls -l / | grep '^l'            # які каталоги кореня — лише посилання
sudo du -sh /var/* 2>/dev/null | sort -h | tail -5   # хто займає /var
journalctl --disk-usage        # скільки займають журнали systemd
cat /sys/class/net/*/address   # MAC-адреси мережевих карт прямо з ядра
```

## Типи файлових систем

Таблиця 1 — Файлові системи, з якими працює Linux

| ФС | Де використовують | Особливості |
|----|-------------------|-------------|
| **ext4** | Типова ФС Debian, Ubuntu | Журнал, extent-и, перевірена роками |
| **XFS** | RHEL, великі сервери | Паралельний ввід-вивід, великі файли, не зменшується |
| **Btrfs** | Fedora, openSUSE, SteamOS, Meta | Copy-on-write, знімки, стиснення, контрольні суми даних |
| **ZFS** | Сховища даних, FreeBSD, TrueNAS | Власний RAID і знімки; ліцензія CDDL не дозволяє включити її в ядро, модуль збирається окремо |
| **vfat, exFAT** | Флешки, SD-карти, розділ EFI | Сумісність з усіма ОС; немає прав доступу Unix |
| **NTFS** | Диски Windows | Драйвер ntfs3 у ядрі з версії 5.15; раніше — ntfs-3g через FUSE |
| **tmpfs** | `/run`, часто `/tmp` | Живе в оперативній пам'яті, зникає після перезавантаження |
| **proc, sysfs** | `/proc`, `/sys` | Віртуальні: вміст генерує ядро під час читання |
| **squashfs** | Live USB, snap-пакети | Стиснутий образ лише для читання |
| **overlayfs** | Контейнери Docker | Шари образу лише для читання + шар для запису зверху |

### Журналювання і copy-on-write

Що буде, якщо вимкнути живлення посеред запису? Створення файлу — це кілька змін у різних місцях диска: виділити inode, позначити блоки зайнятими, записати дані, додати рядок у каталог. Якщо записалася лише частина, ФС стає суперечливою: блоки зайняті, але нікому не належать, або каталог вказує на порожній inode. Раніше після кожного збою `fsck` годинами перевіряв увесь диск.

**Журнал** вирішує це як бухгалтерська книга: спершу ФС записує в окрему область опис того, що збирається змінити, і лише потім змінює. Після збою досить «програти» або відкинути незавершені записи журналу — секунди замість годин. ext4 і XFS журналюють метадані (структуру ФС), тож сама ФС завжди цілісна, хоча вміст файлу, який писали в момент збою, може бути втрачено.

**Copy-on-write** (Btrfs, ZFS) іде далі: дані ніколи не перезаписуються на місці. Нова версія блоку пишеться в інше місце, а потім одним атомарним кроком перемикається вказівник. Побічний ефект — **знімки** (snapshots) майже безкоштовні: знімок — це просто збережений старий вказівник. Так Fedora й openSUSE роблять знімок перед оновленням і дозволяють завантажитися в стан «до».

```
┌─────────────────────────────────────────────────────────────────────┐
│                          EXT4, XFS І BTRFS                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Критерій            ext4           XFS            Btrfs            │
│  ──────────────────  ─────────────  ─────────────  ──────────────   │
│  Модель              журнал         журнал         copy-on-write    │
│  Макс. розмір ФС     1 ЕіБ          8 ЕіБ          16 ЕіБ           │
│  Знімки (snapshots)  немає          немає          так, миттєві     │
│  Стиснення           немає          немає          zstd, lzo        │
│  Контрольні суми     лише метадані  лише метадані  дані й метадані  │
│  Збільшити онлайн    так            так            так              │
│  Зменшити            лише офлайн    неможливо      так, онлайн      │
│  За замовчуванням    Debian, Ubuntu RHEL, Rocky    Fedora, openSUSE │
│                                                                     │
│  Вибір на практиці:                                                 │
│  • Не знаєте, що обрати — ext4: найперевіреніша й найпростіша       │
│  • Великі сервери, бази даних, RHEL — XFS                           │
│  • Потрібні знімки перед оновленням і відкат — Btrfs                │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
df -hT                               # змонтовані ФС з типами
sudo tune2fs -l /dev/sda2 | head -20 # параметри ext4: розмір блоку, кількість inode
sudo fsck.ext4 -n /dev/sdb1          # перевірка без змін; лише для НЕзмонтованої ФС!
# sudo mkfs.ext4 /dev/sdX1           # створити ФС — знищить усі дані на розділі
```

## Права доступу

Linux — багатокористувацька система: кожен файл має власника, групу і три набори прав. Ядро перевіряє їх під час кожного відкриття файлу.

```
┌─────────────────────────────────────────────────────────────────────┐
│                       ЯК ЧИТАТИ ПРАВА ДОСТУПУ                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  $ ls -l звіт.txt                                                   │
│  -rw-r--r-- 1 student students 4812 Sep 17 10:30 звіт.txt           │
│  │└┬┘└┬┘└┬┘ │ └──┬──┘ └───┬──┘ └─┬┘ └─────┬────┘ └──┬───┘           │
│  │ │  │  │  │    │        │      │        │         └ ім'я          │
│  │ │  │  │  │    │        │      │        └ час зміни вмісту        │
│  │ │  │  │  │    │        │      └ розмір у байтах                  │
│  │ │  │  │  │    │        └ група                                   │
│  │ │  │  │  │    └ власник                                          │
│  │ │  │  │  └ кількість жорстких посилань                           │
│  │ │  │  └ інші (others):  r-- = 4                                  │
│  │ │  └ група (group):     r-- = 4                                  │
│  │ └ власник (user):       rw- = 4 + 2 = 6                          │
│  └ тип: - файл, d каталог, l посилання                              │
│                                                                     │
│  r = 4   w = 2   x = 1          rw-r--r-- = 644                     │
│                                                                     │
│  Ядро перевіряє права по черзі: якщо ви власник — діють лише        │
│  права власника, якщо член групи — лише права групи, інакше —       │
│  права інших. Тому файл ----rwxrwx власник прочитати не зможе.      │
└─────────────────────────────────────────────────────────────────────┘
```

### Що означають права на каталог

Для каталогу ті самі літери означають інше, і саме тут найчастіше помиляються:

| Право | На файлі | На каталозі |
|-------|----------|-------------|
| `r` | читати вміст | бачити список імен (`ls`) |
| `w` | змінювати вміст | створювати, перейменовувати й **видаляти** файли в ньому |
| `x` | запускати як програму | заходити в каталог (`cd`) і звертатися до файлів за іменем |

Наслідки: файл, у який ви не можете писати, ви все одно можете видалити, якщо маєте `w` на каталог. Каталог з правами `--x` дозволяє відкрити файл, ім'я якого ви знаєте, але не показує списку. А без `x` на **кожному** каталозі шляху (`/`, `/home`, `/home/alice`) до файлу не дістатися взагалі, хоч би які права мав сам файл.

```bash
mkdir demo && touch demo/файл
chmod 555 demo          # r-x: бачимо й заходимо, але не змінюємо
rm demo/файл            # rm: cannot remove 'demo/файл': Permission denied
chmod 755 demo && rm -r demo
```

### chmod і chown

```bash
chmod 640 звіт.txt          # rw-r-----: власник пише, група читає, решта — нічого
chmod u+x script.sh         # власнику додати виконання
chmod g-w,o= спільне.txt    # групі забрати запис, іншим — усе
chmod -R u=rwX,go=rX site/  # рекурсивно: X дає виконання лише каталогам
                            # (і файлам, де воно вже було)

sudo chown alice:devs файл  # змінити власника й групу
sudo chown -R alice: ~alice/project   # власник alice, група — основна група alice
```

Рекурсивне `chmod -R 755` — поширена помилка: воно робить виконуваними **всі** файли, зокрема документи й фото. Велика `X` у символьному записі вирішує проблему: виконання отримують тільки каталоги.

### umask: права для нових файлів

Програма, що створює файл, просить права (зазвичай 666 для файлів і 777 для каталогів), а **umask** вказує, які біти з них **прибрати**. Це побітова операція «і не», а не віднімання:

```bash
umask             # 0022 — прибрати w у групи й інших
                  # файл:    666 без 022 = 644 (rw-r--r--)
                  # каталог: 777 без 022 = 755 (rwxr-xr-x)

umask 027         # файл: 666 без 027 = 640, каталог: 777 без 027 = 750
touch a && ls -l a        # -rw-r-----
```

Віднімання дало б для прикладу з 027 число 639 — таких прав не існує, бо біт x, якого у файлі й так немає, прибирати нічого. Змінити umask назавжди можна в `~/.bashrc` або для всієї системи в `/etc/login.defs`.

### Спеціальні біти

```
┌─────────────────────────────────────────────────────────────────────┐
│                           СПЕЦІАЛЬНІ БІТИ                           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  SUID (4000) — програма виконується з правами ВЛАСНИКА файлу        │
│  $ ls -l /usr/bin/passwd                                            │
│  -rwsr-xr-x 1 root root ... /usr/bin/passwd     s замість x         │
│  Звичайний користувач змінює свій пароль у /etc/shadow, хоча        │
│  писати в цей файл може тільки root. На скрипти Linux SUID          │
│  ігнорує: це була б надто легка діра в безпеці.                     │
│                                                                     │
│  SGID (2000) — на каталозі: нові файли отримують групу каталогу     │
│  $ ls -ld /srv/project                                              │
│  drwxrwsr-x 2 root devs ... /srv/project        s у групі           │
│  Спільний каталог команди: усі файли належать групі devs.           │
│                                                                     │
│  Sticky (1000) — на каталозі: видалити файл може лише його власник  │
│  $ ls -ld /tmp                                                      │
│  drwxrwxrwt 20 root root ... /tmp               t в інших           │
│  Писати в /tmp можуть усі, але чужі файли не стерти.                │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
sudo find / -xdev -perm -4000 -type f 2>/dev/null   # усі SUID-програми
chmod 2775 /srv/project                              # SGID на спільний каталог
ls -ld /tmp                                          # drwxrwxrwt
```

Перелік SUID-програм — перше, що перевіряє аудитор безпеки: кожна з них — потенційний шлях до прав root, якщо в ній знайдеться помилка. Сучасні дистрибутиви скорочують цей список: `ping`, наприклад, замість SUID отримує лише одну можливість ядра (capability) `cap_net_raw` або взагалі обходиться без неї.

Права `rwx` — не останнє слово. Розширені списки доступу (**ACL**, `getfacl`/`setfacl`) дають права окремим користувачам понад одного власника й одну групу, а атрибут `chattr +i` робить файл незмінним навіть для root. Докладно — у лабораторній роботі про облікові записи та права доступу.

## Монтування файлових систем

**Монтування** підключає файлову систему до каталогу. Те, що лежало в каталозі-точці монтування до того, стає невидимим, доки ФС не відмонтують.

```bash
findmnt                                    # дерево змонтованих ФС
findmnt -t ext4,xfs,btrfs                  # лише «дискові»

sudo mkdir -p /mnt/usb
sudo mount /dev/sdb1 /mnt/usb              # тип ФС визначиться сам
sudo mount -o ro /dev/sdb1 /mnt/usb        # лише для читання
sudo mount -o uid=1000,gid=1000 /dev/sdb1 /mnt/usb   # vfat, exFAT: у них немає власників
sudo umount /mnt/usb                       # «target is busy» — хтось у каталозі
sudo fuser -vm /mnt/usb                    # хто саме
```

Робочий стіл монтує флешки сам (у `/media/<користувач>/`) через службу udisks — без sudo і без запису в fstab.

### /etc/fstab

`/etc/fstab` описує, що монтувати під час завантаження. Кожен рядок — шість полів:

```bash
# <що>                                     <куди>     <тип> <опції>          <dump> <pass>
UUID=0f3a8c1e-5b7d-4e2a-9c61-2d8e4f7a1b90  /          ext4  errors=remount-ro  0     1
UUID=A1B2-C3D4                             /boot/efi  vfat  umask=0077         0     1
UUID=5e1d9a44-0c2b-4f7e-8a3d-6b9f0e2c7d15  /data      ext4  defaults,nofail    0     2
/swap.img                                  none       swap  sw                 0     0
```

- Диск указують через **UUID**, а не `/dev/sdb1`: імена пристроїв призначаються в порядку виявлення й можуть помінятися, щойно під'єднаєте ще один диск. UUID покаже `lsblk -f` або `blkid`.
- `nofail` — не зупиняти завантаження, якщо диска немає. Без цієї опції помилка в рядку другорядного диска кидає систему в аварійний режим (emergency mode).
- `pass` — порядок перевірки `fsck`: 1 для кореня, 2 для решти, 0 — не перевіряти.

Перевіряйте fstab **до** перезавантаження:

```bash
sudo findmnt --verify          # синтаксис, UUID, типи ФС
sudo systemctl daemon-reload   # systemd будує з fstab юніти .mount
sudo mount -a                  # змонтувати все, що ще не змонтовано
```

## Посилання

```
┌─────────────────────────────────────────────────────────────────────┐
│                          ДВА ВИДИ ПОСИЛАНЬ                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ЖОРСТКЕ ПОСИЛАННЯ (ln)          СИМВОЛЬНЕ ПОСИЛАННЯ (ln -s)        │
│  ──────────────────────          ───────────────────────────        │
│  звіт.txt ──┐                    ярлик ──► "звіт.txt" ──┐           │
│             ├──► inode ──► дані                          │          │
│  копія.txt ─┘                    звіт.txt ──► inode ◄────┘          │
│                                                                     │
│  Друге ім'я того самого inode:    Окремий файл, що містить шлях:    │
│  + видалення одного імені не      + може вказувати на каталог       │
│    зачіпає інше                   + працює між файловими системами  │
│  + права й вміст — спільні        + одразу видно, куди вказує       │
│  − лише в межах однієї ФС         − «битий», якщо ціль видалено     │
│  − не можна на каталоги           − зайвий крок при кожному         │
│  − не відрізнити від «оригіналу»     відкритті                      │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
echo "текст" > оригінал.txt
ln оригінал.txt жорстке.txt        # друге ім'я того самого inode
ln -s оригінал.txt символьне.txt   # файл, що містить рядок "оригінал.txt"
ls -li                             # однаковий номер inode в перших двох, Links: 2

rm оригінал.txt
cat жорстке.txt                    # текст — inode живий, лишилось одне ім'я
cat символьне.txt                  # No such file or directory — посилання «бите»
find . -xtype l                    # знайти биті символьні посилання
```

Відносна ціль символьного посилання (`оригінал.txt`) відраховується від каталогу, де лежить саме посилання, а не від того, звідки ви виконали `ln`. Тому посилання, створене як `ln -s ../conf/app.yml /etc/app.yml`, найчастіше виявляється битим.

Жорсткі посилання на каталоги заборонені, бо з них могли б утворитися цикли в дереві. Але кожен каталог уже має щонайменше два імені: власне ім'я у батьківському каталозі та `.` у самому собі. Тому в `ls -ld` порожній каталог показує лічильник 2, а кожен підкаталог додає ще одиницю (свій `..`).

## Практичні команди

```bash
# Пошук
find ~ -name "*.pdf" -mtime -7          # PDF, змінені за тиждень
find / -xdev -type f -size +500M 2>/dev/null   # великі файли на кореневій ФС

locate звіт                             # швидкий пошук за базою (пакет plocate)

# Розмір
du -sh * | sort -h                      # розмір усього в поточному каталозі
du -xh --max-depth=1 / 2>/dev/null | sort -h   # верхній рівень кореня, без інших ФС
df -hT                                  # місце на ФС
df -i                                   # inode на ФС

# Операції
cp -a src/ dst/        # копія зі збереженням прав, власника, часу, посилань
mv old new             # перейменування — зміна запису в каталозі
rm -ri каталог/        # видалення з підтвердженням кожного файлу
mkdir -p a/b/c         # вкладені каталоги одним рухом
```

## 🎯 Міні-проект (30 хв)

### Завдання: Детектив дискового простору

Напишіть скрипт, який відповідає на три запитання, з якими стикається кожен адміністратор: де закінчується місце, що його займає і чи немає «привидів» — видалених, але відкритих файлів.

**Кроки:**

1. Створіть файл:
```bash
mkdir -p ~/scripts
nano ~/scripts/disk-detective.sh
```

2. Напишіть код:
```bash
#!/usr/bin/env bash
# disk-detective — хто займає місце і куди воно поділося

section() { printf '\n== %s\n' "$1"; }

section "Місце на файлових системах"
df -hT -x tmpfs -x devtmpfs -x squashfs -x overlay

section "Inode (100 % означає «диск повний» навіть при вільному місці)"
df -i -x tmpfs -x devtmpfs -x squashfs -x overlay | awk 'NR == 1 || $5 + 0 > 50'

section "Найбільші каталоги в домашньому каталозі"
du -xh --max-depth=1 ~ 2>/dev/null | sort -hr | head -8

section "10 найбільших файлів у домашньому каталозі"
find ~ -xdev -type f -size +10M -printf '%s\t%p\n' 2>/dev/null \
    | sort -nr | head -10 | numfmt --to=iec --field=1

section "Видалені, але ще відкриті файли"
if command -v lsof > /dev/null; then
    sudo lsof -nP +L1 2>/dev/null | awk 'NR == 1 || $7 > 1048576' | head -10
else
    echo "встановіть lsof: sudo apt install lsof"
fi

section "Що можна почистити"
echo "Кеш користувача: $(du -sh ~/.cache 2>/dev/null | cut -f1)"
echo "Смітник:         $(du -sh ~/.local/share/Trash 2>/dev/null | cut -f1)"
echo "Журнали systemd: $(journalctl --disk-usage 2>/dev/null | grep -o '[0-9.]*[KMGT]')"
echo "Кеш apt:         $(du -sh /var/cache/apt 2>/dev/null | cut -f1)"
```

3. Запустіть:
```bash
chmod +x ~/scripts/disk-detective.sh
~/scripts/disk-detective.sh
```

4. Створіть «привида» і переконайтеся, що скрипт його знаходить. У другому терміналі:
```bash
dd if=/dev/zero of=/tmp/ghost bs=1M count=100
sleep 600 < /tmp/ghost &
rm /tmp/ghost
```
Запустіть скрипт знову: у розділі «Видалені, але ще відкриті файли» з'явиться `/tmp/ghost (deleted)` і PID процесу `sleep`. Завершіть його командою `kill %1`.

5. Перевірте різницю між `df` і `du` на вашій кореневій ФС:
```bash
df -h /                              # скільки зайнято за даними ФС
sudo du -xsh / 2>/dev/null           # скільки займають файли, які видно в дереві
```
Поясніть, звідки може взятися різниця: видалені відкриті файли, зарезервовані для root блоки ext4 (5 % за замовчуванням, `tune2fs -l | grep Reserved`), файли, приховані під точками монтування.

**Очікуваний результат:**

- Скрипт `~/scripts/disk-detective.sh`, що показує місце, inode, найбільші каталоги й файли та видалені відкриті файли.
- Ви можете продемонструвати й пояснити, чому після `rm` місце не звільняється, поки файл відкритий.

**Бонус (для допитливих):**

- Додайте ключ `--clean`, який після підтвердження виконує `gio trash --empty`, `sudo apt clean` і `sudo journalctl --vacuum-size=200M`.
- Вичерпайте inode на маленькій ФС: створіть образ `truncate -s 20M img && mkfs.ext4 -N 256 img`, змонтуйте й створюйте порожні файли, доки не отримаєте «No space left on device» при вільному місці.
- Знайдіть у системі файли з кількома жорсткими посиланнями: `find /usr -xdev -type f -links +1 | head`.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Що означає принцип «усе є файлом»?

- каталоги в Linux не існують
- кожна програма зберігає дані в одному файлі
- пристрої, процеси й налаштування ядра доступні через звичайні файлові операції
- будь-які дані зберігаються лише у звичайних файлах на диску

**2.** Що містить каталог `/dev`?

- журнали системи
- файли пристроїв
- домашні каталоги користувачів
- конфігурацію системи

**3.** Які права відповідають запису 755?

- rwxr-xr-x
- rwxrwxrwx
- rw-r--r--
- rwx------

**4.** Які права зазвичай ставлять приватному файлу з паролями?

- 600
- 777
- 644
- 755

**5.** Що робить біт SUID на файлі програми?

- усі нові файли успадковують групу каталогу
- програма виконується з правами власника файлу, а не того, хто її запустив
- програма стає доступною тільки власнику
- файл не можна видалити нікому, крім власника

**6.** Навіщо sticky-біт на каталозі `/tmp`?

- щоб усі файли в ньому стали виконуваними
- щоб файли автоматично стиралися після перезавантаження
- щоб файл у спільному каталозі міг видалити лише його власник
- щоб каталог не можна було змонтувати

**7.** Чим жорстке посилання відрізняється від символьного?

- жорстке зберігає шлях, а символьне — inode
- символьне працює лише в межах одного каталогу
- різниці немає, це синоніми
- жорстке вказує на той самий inode, а символьне зберігає шлях до файлу

**8.** Що станеться з символьним посиланням після видалення файлу-цілі?

- посилання зникне автоматично
- файл не вдасться видалити, доки є посилання
- дані залишаться доступними через посилання
- посилання залишиться, але стане непрацездатним

**9.** Для чого потрібен файл `/etc/fstab`?

- він описує, які файлові системи й куди монтувати під час завантаження
- він зберігає журнали монтування
- він містить перелік користувачів системи
- він задає права доступу за замовчуванням

**10.** Яка команда покаже розмір каталогу?

- df -h
- du -sh каталог
- mount
- ls -la

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Блочний пристрій** | Диск або розділ, до якого ядро звертається блоками: `/dev/sda`, `/dev/nvme0n1p2` |
| **GPT / MBR** | Сучасний і застарілий формати таблиці розділів |
| **Файлова система** | Структура даних у розділі, що зберігає файли, inode і вільні блоки |
| **VFS** | Шар ядра, що дає однаковий інтерфейс до будь-якої ФС |
| **Inode** | Опис файлу: тип, права, власник, розмір, час, посилання, розміщення даних — усе, крім імені |
| **Каталог** | Файл-таблиця «ім'я → номер inode» |
| **Журнал** | Область ФС, куди спершу записують план змін, щоб пережити збій живлення |
| **Copy-on-write** | Запис нових даних в інше місце замість перезапису; основа знімків Btrfs і ZFS |
| **Монтування** | Підключення ФС до каталогу в єдиному дереві |
| **Жорстке посилання** | Друге ім'я того самого inode |
| **Символьне посилання** | Окремий файл, що містить шлях до цілі |
| **umask** | Біти прав, які прибирають з прав нового файлу |
| **SUID / SGID / sticky** | Спеціальні біти: запуск з правами власника, успадкування групи, захист від видалення чужих файлів |

| Права | Число | Типове використання |
|-------|-------|---------------------|
| `rwxr-xr-x` | 755 | Програми, скрипти, каталоги |
| `rw-r--r--` | 644 | Звичайні файли |
| `rw-r-----` | 640 | Конфігурація, яку читає група служби |
| `rw-------` | 600 | Ключі SSH, паролі |
| `rwxrwxrwt` | 1777 | Спільні каталоги на кшталт `/tmp` |

На наступній лекції — основні властивості робочих столів Linux: віртуальні робочі столи, гарячі клавіші, масштабування й доступність.
