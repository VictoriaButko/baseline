## Як обрати операційну систему?

Уявіть: ви — системний адміністратор у банку. Потрібно обрати ОС для серверів, які обробляють фінансові транзакції. Що важливіше: швидкість чи надійність? Безпека чи зручність? Як порівнювати Windows Server, Linux, FreeBSD?

Або інша ситуація: ви розробляєте програмне забезпечення для медичного обладнання. Збій може коштувати життя. Які вимоги до ОС тут критичні?

Для обґрунтованого вибору потрібно розуміти **критерії оцінки операційних систем**.

## 1. Надійність (Reliability)

**Надійність** — здатність системи працювати коректно протягом тривалого часу без збоїв.

### Ключові аспекти надійності

**Стабільність** — система не "падає" без причини.

```
┌──────────────────────────────────────────────────┐
│          СКІЛЬКИ ДОЗВОЛЕНО ПРОСТОЮВАТИ           │
├──────────────────────────────────────────────────┤
│  Доступність     Назва           Простій за рік  │
│  ───────────     ─────           ──────────────  │
│  99.9%           three nines     ~8.7 години     │
│  99.99%          four nines      ~52 хвилини     │
│  99.999%         five nines      ~5 хвилин       │
└──────────────────────────────────────────────────┘
```

Ці «дев'ятки» описують **сервіс**, а не операційну систему. Однаковий Linux чи Windows Server може дати і 99.9%, і 99.999% — залежно від дубльованого обладнання, кластера, резервних копій і того, як швидко команда реагує на збої. Сама ОС лише не повинна ставати слабкою ланкою.

**Відмовостійкість** — система продовжує працювати навіть при збоях компонентів.

```
┌─────────────────────────────────────────────────────────┐
│                   Кластер серверів                      │
│  ┌─────────┐   ┌─────────┐   ┌─────────┐                │
│  │ Server1 │   │ Server2 │   │ Server3 │                │
│  │  [OK]   │   │  [FAIL] │   │  [OK]   │                │
│  └────┬────┘   └────┬────┘   └────┬────┘                │
│       │             ✗             │                     │
│       └─────────────┴─────────────┘                     │
│                     │                                   │
│              Load Balancer                              │
│       (перенаправляє трафік на живі ноди)               │
└─────────────────────────────────────────────────────────┘
```

**Ізоляція збоїв** — помилка в одному компоненті не руйнує всю систему.

**Практичний приклад**: Kernel panic vs Application crash

```bash
# Якщо падає звичайна програма — система працює далі
./buggy_program
# Segmentation fault (core dumped)
# Інші програми продовжують працювати

# Якщо падає ядро — система зупиняється
# Kernel panic - not syncing: Fatal exception
# Потрібне перезавантаження
```

**Як Linux забезпечує надійність:**

```bash
# Детектор «зависань» ядра: 1 — ядро стежить, чи не застряг якийсь процесор
cat /proc/sys/kernel/watchdog
# Щоб після зависання система ще й перезавантажилася сама, потрібні
# kernel.panic (секунди до перезавантаження) або апаратний сторожовий
# таймер /dev/watchdog, який систематично «гладить» systemd

# Журнали для діагностики
journalctl -p err -b  # Помилки з останнього завантаження

# Реальний uptime сервера
uptime
# 10:30:01 up 547 days, 3:22, 2 users, load average: 0.15, 0.10, 0.08
```

Колись такий uptime був приводом для гордості. Сьогодні він радше тривожний: 547 днів без перезавантаження означають 547 днів без оновлень ядра, а за цей час у ньому гарантовано знайшли вразливості. Надійність тут конфліктує з безпекою. Сучасна практика — або регулярно перезавантажувати вузли по черзі, поки кластер працює, або латати ядро «на ходу» (livepatch).

### Метрики надійності

| Метрика | Визначення | Приклад |
|---------|------------|---------|
| **MTBF** | Mean Time Between Failures | 5 000 годин |
| **MTTR** | Mean Time To Repair | 30 хвилин |
| **Availability** | MTBF / (MTBF + MTTR) | 5000 / 5000.5 ≈ 99.99% |

З формули видно корисну річ: доступність можна підняти двома шляхами — рідше ламатися або швидше лагодитися. Скоротити MTTR з години до хвилини часто простіше, ніж удесятеро підняти MTBF.

### Принцип найменших привілеїв

Програма повинна мати мінімум прав, необхідних для виконання задачі.

**Практичний приклад**: Чому веб-сервер не запускається від root?

```bash
# nginx.conf
# user www-data;

# Від кого працюють процеси nginx
ps -o user,pid,cmd -C nginx
# USER       PID CMD
# root       810 nginx: master process /usr/sbin/nginx
# www-data   811 nginx: worker process
# www-data   812 nginx: worker process
```

Головний процес стартує від root, бо лише root може відкрити порт 80 і прочитати закритий ключ сертифіката. Далі він створює воркери, які одразу відмовляються від прав root і працюють як `www-data`, — а саме вони розбирають запити з інтернету. Якщо зловмисник знайде вразливість в обробці запиту, він отримає права www-data, а не root. Погана практика — не запуск nginx через `sudo`, а рядок `user root;` у конфігурації.

### Механізми захисту в Linux

```bash
# 1. Права доступу до файлів
ls -la /etc/shadow
# -rw-r----- 1 root shadow 1234 Jan 15 /etc/shadow

# 2. Capabilities — дрібнозернистий контроль привілеїв:
#    замість «усе або нічого» root розбитий на ~40 окремих прав
getcap /usr/bin/ping
# /usr/bin/ping cap_net_raw=ep
# (на новіших системах ping обходиться і без цього права —
#  через спеціальні ICMP-сокети, дозволені звичайним користувачам)

# 3. SELinux / AppArmor — обов'язковий контроль доступу
getenforce  # SELinux: Enforcing, Permissive, Disabled
aa-status   # AppArmor: профілі програм

# 4. Firewall
sudo ufw status
sudo nft list ruleset      # сучасний інтерфейс; iptables на Ubuntu — обгортка над ним

# 5. Аудит
sudo ausearch -m avc -ts recent  # SELinux відмови
```

### Типові вразливості та захист

| Загроза | Опис | Захист ОС |
|---------|------|-----------|
| Buffer overflow | Переповнення буфера | ASLR, Stack Canaries, NX bit |
| Privilege escalation | Підвищення привілеїв | Capabilities, namespaces |
| Rootkit | Приховане шкідливе ПЗ | Secure Boot, IMA |
| Brute force | Підбір паролів | PAM limits, fail2ban |

## 3. Ефективність (Efficiency)

**Ефективність** — мінімізація накладних витрат та оптимальне використання ресурсів.

### Метрики ефективності

```
┌─────────────────────────────────────────────────────────────┐
│                    ЕФЕКТИВНІСТЬ ОС                          │
│                                                             │
│  Throughput          Скільки задач за одиницю часу          │
│  ─────────────────────────────────────────────────          │
│  │████████████████████████████████                 │        │
│  └─────────────────────────────────────────────────         │
│                                                             │
│  Latency             Затримка відповіді                     │
│  ─────────────────────────────────────────────────          │
│  │████                                             │        │
│  └─────────────────────────────────────────────────         │
│  (менше = краще)                                            │
│                                                             │
│  CPU Utilization     Використання процесора                 │
│  ─────────────────────────────────────────────────          │
│  │████████████████████████████████████████████████ │ 95%    │
│  └─────────────────────────────────────────────────         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### Накладні витрати ОС

Кожна абстракція має ціну:

| Операція | Типова затримка |
|----------|-----------------|
| Системний виклик | 100-1000 нс |
| Перемикання контексту | 1-10 мкс |
| Page fault із читанням з диска | 10-100 мкс з SSD, мілісекунди з HDD |
| Мережевий пакет (localhost) | 10-50 мкс |

**Практичний приклад**: Вимірювання вартості системного виклику

```bash
# Скільки викликів getpid() за секунду?
# (getpid — найпростіший syscall)

cat > bench.c << 'EOF'
#include <unistd.h>
#include <stdio.h>
#include <time.h>

int main() {
    struct timespec start, end;
    int iterations = 10000000;

    clock_gettime(CLOCK_MONOTONIC, &start);
    for (int i = 0; i < iterations; i++) {
        getpid();
    }
    clock_gettime(CLOCK_MONOTONIC, &end);

    double elapsed = (end.tv_sec - start.tv_sec) +
                     (end.tv_nsec - start.tv_nsec) / 1e9;
    printf("%.0f syscalls/sec\n", iterations / elapsed);
    printf("%.0f ns per syscall\n", elapsed * 1e9 / iterations);
    return 0;
}
EOF

gcc -O2 bench.c -o bench && ./bench
# Приблизний результат: 5-10 млн syscalls/sec
# 100-200 нс на виклик
```

### Як ОС оптимізує продуктивність

**Кешування:**
```
┌────────────────────────────────────────────────────┐
│                  ІЄРАРХІЯ ПАМ'ЯТІ                  │
├────────────────────────────────────────────────────┤
│ Ядро процесора                                     │
│      │                                             │
│      ▼                                             │
│ L1-кеш         десятки КБ        ~1 нс             │
│      │                                             │
│ L2-кеш         сотні КБ – МБ     ~3-5 нс           │
│      │                                             │
│ L3-кеш         десятки МБ        ~10-20 нс         │
│      │                                             │
│ RAM            гігабайти         ~100 нс           │
│      │         (частину RAM займає page cache —    │
│      │          копії нещодавно прочитаних файлів) │
│      ▼                                             │
│ SSD (NVMe)     терабайти         ~20-100 мкс       │
│ HDD            терабайти         ~5-10 мс          │
└────────────────────────────────────────────────────┘
```

Кожен наступний рівень у десятки чи сотні разів більший і повільніший. Кешами L1–L3 керує процесор, а от page cache — це робота ОС: ядро тримає в незайнятій оперативній пам'яті копії файлів, тож повторне читання того самого файлу взагалі не доходить до диска. Тому «вільної пам'яті» в `free -h` на Linux завжди мало, а в колонці `buff/cache` — багато: пам'ять, що простоює, для ядра марнотратство.

```bash
# Статистика page cache
cat /proc/meminfo | grep -E "Cached|Buffers"

# Очистити кеш (для тестування)
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches
```

## 4. Масштабованість (Scalability)

**Масштабованість** — здатність ефективно працювати при збільшенні навантаження або ресурсів.

### Вертикальне масштабування (Scale Up)

Додаємо ресурси до одного сервера:

```
До:                         Після:
┌─────────────────┐         ┌─────────────────┐
│ 4 CPU cores     │         │ 32 CPU cores    │
│ 16 GB RAM       │ ──────→ │ 256 GB RAM      │
│ 500 GB SSD      │         │ 4 TB NVMe       │
└─────────────────┘         └─────────────────┘
```

**Виклик для ОС**: Чи може ядро ефективно використати 256 ядер? Чи працюють алгоритми при 1 ТБ RAM?

### Горизонтальне масштабування (Scale Out)

Додаємо більше серверів:

```
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
│ Node 1  │  │ Node 2  │  │ Node 3  │  │ Node 4  │
└────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘
     │            │            │            │
     └────────────┴────────────┴────────────┘
                      │
              Load Balancer / Orchestrator
```

**Практичний приклад**: Linux на різних масштабах

```bash
# Raspberry Pi Zero (512 МБ RAM, 1 core)
cat /proc/cpuinfo | grep -c processor  # 1
free -h                                  # 512M

# Ваш ноутбук (16 ГБ RAM, 8 cores)
cat /proc/cpuinfo | grep -c processor  # 8
free -h                                  # 16G

# Суперкомп'ютер Frontier (9.2 PB RAM, 9,472 nodes)
# Теж Linux!
```

### Тест масштабованості

Як перевірити, чи масштабується програма?

```bash
# Навантажувальне тестування веб-сервера
# (встановіть: apt install apache2-utils)

# 1 потік, 1000 запитів
ab -n 1000 -c 1 http://localhost/

# 100 паралельних потоків, 10000 запитів
ab -n 10000 -c 100 http://localhost/

# Порівняйте requests/sec
# Ідеально: має рости лінійно з кількістю ядер
```

## 5. Портативність (Portability)

**Портативність** — здатність працювати на різних апаратних платформах з мінімальними змінами.

### Архітектури, що підтримуються Linux

```
┌──────────────────────────────────────────────────────────────────┐
│                           LINUX KERNEL                           │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Підтримувані архітектури (каталог arch/ у коді ядра):           │
│                                                                  │
│  x86-64      ПК, ноутбуки, більшість серверів                    │
│  arm64       смартфони, Raspberry Pi 4/5, сервери AWS Graviton,  │
│              Mac на Apple Silicon (проєкт Asahi Linux)           │
│  arm         32-бітні плати й старіші вбудовані пристрої         │
│  riscv       відкрита архітектура, що швидко набирає обертів     │
│  powerpc     сервери IBM POWER                                   │
│  s390        мейнфрейми IBM Z                                    │
│  mips        роутери, мережеве обладнання                        │
│  loongarch   китайські процесори Loongson                        │
│                                                                  │
│  ... усього близько двох десятків                                │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### Як досягається портативність

**Абстракція апаратного забезпечення:**

```
┌─────────────────────────────────────────────────────────────┐
│   Спільний код ядра: планувальник, пам'ять, VFS, мережа     │
│        (однаковий для всіх архітектур — переважна частина)  │
├─────────────────────────────────────────────────────────────┤
│  arch/x86/  │  arch/arm64/  │  arch/riscv/  │  ...          │
│  (перемикання контексту, таблиці сторінок, обробка          │
│   переривань, завантаження — усе, що залежить від процесора)│
└─────────────────────────────────────────────────────────────┘
```

Щоб перенести Linux на новий процесор, не треба переписувати ядро — достатньо написати власний каталог у `arch/` і драйвери для периферії. Решта коду просто перекомпілюється.

**Практичний приклад**: Та сама програма на різних архітектурах

```bash
# На x86-64 (ваш ПК)
file /bin/ls
# /bin/ls: ELF 64-bit LSB pie executable, x86-64

# На ARM (Raspberry Pi)
file /bin/ls
# /bin/ls: ELF 32-bit LSB executable, ARM

# На Mac (macOS)
file /bin/ls
# /bin/ls: Mach-O universal binary with 2 architectures:
#          [x86_64] [arm64e]

# Linux-версії зібрано з того самого коду GNU coreutils —
# бінарники різні, бо різні інструкції процесора.
# На macOS взагалі інша програма (ls з BSD) і інший формат файлу —
# Mach-O, а в одному «універсальному» файлі лежать версії
# одразу для двох процесорів.
```

### Стандарти портативності

| Стандарт | Призначення |
|----------|-------------|
| **POSIX** | Інтерфейс ОС (системні виклики) |
| **LSB** | Linux Standard Base (бінарна сумісність; фактично занедбаний з 2015 року) |
| **FHS** | Filesystem Hierarchy Standard |
| **SUS** | Single UNIX Specification |

## 6. Зручність використання (Usability)

**Зручність** — простота встановлення, налаштування та щоденного використання.

### Рівні інтерфейсу

```
┌─────────────────────────────────────────────────────────────┐
│ GUI (Graphical User Interface)                              │
```

## Порівняння ОС за характеристиками

Зіркові рейтинги «яка ОС краща» — це думка, а не вимірювання. Порівнювати варто те, що можна перевірити:

| Характеристика | Windows | Linux | macOS | FreeBSD |
|----------------|---------|-------|-------|---------|
| **Архітектури процесорів** | x86-64, arm64 | близько двох десятків | arm64 (раніше й x86-64) | x86-64, arm64, riscv, powerpc |
| **Ліцензія ядра** | закрита | GPLv2 — зміни треба відкривати | XNU відкрите, система — закрита | BSD — зміни можна не відкривати |
| **Обов'язковий контроль доступу** | Integrity Levels, AppLocker | SELinux, AppArmor | Sandbox, SIP | MAC Framework |
| **Хто випускає оновлення** | Microsoft | дистрибутив (Canonical, Red Hat…) | Apple | проєкт FreeBSD |
| **Типова ніша** | робочі місця, корпоративні сервери | сервери, хмари, вбудовані системи, Android | робочі місця розробників і дизайнерів | мережеве обладнання, CDN, сховища |

## Практичні сценарії вибору ОС

### Сценарій 1: Веб-сервер для стартапу

**Вимоги:** низька вартість, надійність, масштабованість

**Рішення:** Linux (Ubuntu Server, Debian)
- Безкоштовний
- Uptime 99.99%+
- Легко масштабувати в хмарі (AWS, GCP, Azure)

### Сценарій 2: Робоча станція для розробника

**Вимоги:** зручність, доступ до інструментів, продуктивність

**Рішення:** macOS або Linux
- Нативний термінал (bash/zsh)
- Docker, Git, компілятори
- Сумісність з серверами (теж Linux)

### Сценарій 3: Медичне обладнання

**Вимоги:** максимальна надійність, сертифікація, детермінованість

**Рішення:** QNX або спеціалізований Linux
- Мікроядро = менше коду = менше багів
- Сертифікація для медичних пристроїв
- Real-time гарантії

### Сценарій 4: Банківська система

**Вимоги:** безпека, надійність, аудит

**Рішення:** Linux з SELinux, AIX — або мейнфрейм IBM Z
- Обов'язковий контроль доступу
- Повний аудит
- Підтримка від вендора

Мейнфрейми — не музейний експонат: значна частина світових карткових транзакцій і досі проходить через IBM Z під z/OS або Linux. Там цінують саме надійність — компоненти можна замінювати, не зупиняючи машину.

## Практичне завдання

Оцініть характеристики вашої системи:

```bash

# 2. Безпека — які механізми захисту активні?

# 4. Архітектура системи
uname -m
cat /proc/cpuinfo | grep "model name" | head -1

# 5. Версія ядра (портативність)
uname -r
cat /proc/version
```

## 🎯 Міні-проект (30 хв)

### Завдання: Аудит вашої системи за вимогами production

Уявіть, що ви — системний адміністратор, який готує звіт для керівництва про готовність сервера до production. Проведіть аудит системи за 6 ключовими вимогами.

**Кроки:**

1. Створіть структуру звіту:
```bash
mkdir ~/system-audit && cd ~/system-audit
echo "=== АУДИТ СИСТЕМИ ===" > audit-report.txt
echo "Дата: $(date)" >> audit-report.txt
echo "Хост: $(hostname)" >> audit-report.txt
echo "" >> audit-report.txt
```

2. Оцініть НАДІЙНІСТЬ (Reliability):
```bash
echo "1. НАДІЙНІСТЬ" >> audit-report.txt
echo "   Uptime: $(uptime -p 2>/dev/null || uptime)" >> audit-report.txt
echo "   Load average: $(cat /proc/loadavg)" >> audit-report.txt
# Порахуйте помилки в логах
ERROR_COUNT=$(journalctl -p err --since "24 hours ago" 2>/dev/null | wc -l || echo "N/A")
echo "   Помилок за 24 год: $ERROR_COUNT" >> audit-report.txt
echo "" >> audit-report.txt
```

3. Оцініть БЕЗПЕКУ (Security):
```bash
echo "2. БЕЗПЕКА" >> audit-report.txt
echo "   SELinux: $(getenforce 2>/dev/null || echo 'не встановлено')" >> audit-report.txt
echo "   AppArmor: $(aa-status 2>/dev/null | head -1 || echo 'не встановлено')" >> audit-report.txt
echo "   Firewall: $(sudo ufw status 2>/dev/null | head -1 || echo 'перевірте iptables')" >> audit-report.txt
echo "   Відкриті порти: $(ss -tuln | grep LISTEN | wc -l)" >> audit-report.txt
echo "" >> audit-report.txt
```

4. Оцініть ЕФЕКТИВНІСТЬ та МАСШТАБОВАНІСТЬ:
```bash
echo "3. ЕФЕКТИВНІСТЬ / МАСШТАБОВАНІСТЬ" >> audit-report.txt
echo "   CPU cores: $(nproc)" >> audit-report.txt
echo "   RAM total: $(free -h | awk '/Mem:/{print $2}')" >> audit-report.txt
echo "   RAM used: $(free -h | awk '/Mem:/{print $3}')" >> audit-report.txt
echo "   Disk usage: $(df -h / | awk 'NR==2{print $5}')" >> audit-report.txt
echo "" >> audit-report.txt
```

5. Оцініть ПОРТАТИВНІСТЬ:
```bash
echo "4. ПОРТАТИВНІСТЬ" >> audit-report.txt
echo "   Архітектура: $(uname -m)" >> audit-report.txt
echo "   Ядро: $(uname -r)" >> audit-report.txt
echo "   POSIX: $(getconf _POSIX_VERSION 2>/dev/null || echo 'N/A')" >> audit-report.txt
echo "" >> audit-report.txt
```

6. Сформулюйте ВИСНОВОК:
```bash
echo "5. ВИСНОВОК" >> audit-report.txt
echo "   Система готова до production: [ТАК/НІ/ПОТРЕБУЄ ДООПРАЦЮВАННЯ]" >> audit-report.txt
echo "   Рекомендації:" >> audit-report.txt
echo "   - [Ваші рекомендації тут]" >> audit-report.txt
```

7. Перегляньте звіт:
```bash
cat audit-report.txt
```

**Очікуваний результат:**
Файл `audit-report.txt` з повним аудитом системи за 6 вимогами та вашим висновком щодо готовності до production.

**Бонус (для допитливих):**
- Додайте оцінку у зірках (1-5) для кожної вимоги
- Порівняйте результати з рекомендованими значеннями для серверів
- Автоматизуйте скрипт для щоденного запуску через cron

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Скільки простою на рік дозволяє доступність 99,99 %?

- близько 52 хвилин
- близько 8,7 години
- близько доби
- близько 5 хвилин

**2.** Що вимірює показник MTBF?

- середній час відгуку на запит
- середній час усунення відмови
- середній час завантаження системи
- середній час напрацювання між відмовами

**3.** За якою формулою рахують доступність системи?

- MTTR / (MTBF + MTTR)
- MTBF − MTTR
- MTBF / (MTBF + MTTR)
- (MTBF + MTTR) / MTBF

**4.** Чому вебсервер не повинен працювати від імені root?

- щоб злам сервера не дав зловмиснику контролю над усією системою
- бо root не має права відкривати мережеві порти
- щоб сервер споживав менше пам'яті
- щоб пришвидшити обробку запитів

**5.** Що таке накладні витрати операційної системи?

- обсяг диска, зайнятий файлами системи
- ресурси, які система витрачає на себе: перемикання контексту, системні виклики, планування
- час, потрібний на встановлення оновлень
- вартість ліцензії на робоче місце

**6.** Чим вертикальне масштабування відрізняється від горизонтального?

- різниця лише в термінології, це те саме
- вертикальне стосується пам'яті, горизонтальне — дисків
- вертикальне нарощує потужність однієї машини, горизонтальне додає нові вузли
- вертикальне додає нові вузли, горизонтальне нарощує потужність однієї машини

**7.** Навіщо потрібен стандарт POSIX?

- щоб та сама програма збиралася й працювала на різних UNIX-подібних системах
- щоб ядро підтримувало лише процесори x86
- щоб усі дистрибутиви мали однаковий графічний інтерфейс
- щоб виробники обладнання відкривали код драйверів

**8.** Яка команда покаже середнє навантаження системи?

- lsusb
- chmod
- cat /proc/loadavg
- df -h

**9.** Яку систему оберуть для медичного обладнання з жорсткими вимогами до часу реакції?

- Ubuntu Desktop
- систему реального часу, наприклад QNX
- Windows 11
- macOS

**10.** Який головний висновок дає порівняння ОС за характеристиками?

- вимоги до ОС однакові для настільних і вбудованих систем
- найкращої ОС не існує: вибір визначає задача та її вимоги
- для будь-якого сервера підходить лише Windows Server
- Linux переважає решту систем за всіма шістьма вимогами

| **Безпека** | Захищена від атак | CVE за рік |
| **Ефективність** | Мінімальні накладні витрати | Latency syscall < 1мкс |
| **Масштабованість** | Росте з навантаженням | Лінійний ріст throughput |
| **Портативність** | Працює на різному залізі | Кількість архітектур |
| **Зручність** | Легко використовувати | Час на типову задачу |

**Ключовий висновок:** Не існує "найкращої ОС" — є ОС, оптимальна для конкретної задачі. Розуміння вимог допомагає зробити правильний вибір.

На наступній лекції розглянемо еволюцію операційних систем: від перших комп'ютерів до сучасних хмарних систем.
