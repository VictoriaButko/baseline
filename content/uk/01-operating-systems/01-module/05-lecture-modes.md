## Чому програма не може форматувати диск без дозволу?

Уявіть ситуацію: ви завантажили гру з інтернету, запустили її, а вона тихо видалила всі файли на диску. Або вірус отримав доступ до вашої веб-камери без вашого відома. Як операційна система захищає від таких сценаріїв?

Відповідь — **апаратне розділення привілеїв**. Процесор фізично не дозволяє звичайним програмам виконувати небезпечні операції.

## Кільця захисту процесора (Protection Rings)

Сучасні процесори x86/x64 мають 4 рівні привілеїв, але більшість ОС використовують лише два:

```
┌────────────────────────────────────────────────────────────────┐
│                    КІЛЬЦЯ ЗАХИСТУ x86                          │
│                                                                │
│                    ┌───────────────────┐                       │
│                    │     Ring 3        │  ← User Mode          │
│                    │   (Найменше      │     Звичайні програми  │
│                    │    привілеїв)    │     Браузер, Word...   │
│                    │  ┌─────────────┐  │                       │
│                    │  │   Ring 2    │  │  ← Не використ.       │
│                    │  │ ┌─────────┐ │  │                       │
│                    │  │ │ Ring 1  │ │  │  ← Не використ.       │
│                    │  │ │ ┌─────┐ │ │  │                       │
│                    │  │ │ │ R 0 │ │ │  │  ← Kernel Mode        │
│                    │  │ │ │     │ │ │  │     Ядро ОС           │
│                    │  │ │ └─────┘ │ │  │     Повний доступ     │
│                    │  │ └─────────┘ │  │                       │
│                    │  └─────────────┘  │                       │
│                    └───────────────────┘                       │
│                                                                │
│   Ring 0: Kernel Mode — повний доступ до заліза                │
│   Ring 3: User Mode — обмежений доступ                         │
│   Ring 1, 2: є в процесорі, сучасні ОС їх не задіюють          │
└────────────────────────────────────────────────────────────────┘
```

Кільця 1 і 2 процесор підтримує ще з 80286, але жодна з поширених сьогодні ОС
їх не використовує: і Windows, і Linux обходяться двома рівнями, бо ядро простіше
переносити між архітектурами, коли рівнів рівно два (на ARM і RISC-V чотирьох
кілець немає). Історичні винятки були: OS/2 виконувала драйвери введення-виведення
в кільці 2, а 32-бітний Xen до появи апаратної віртуалізації запускав гостьові ядра
в кільці 1.

## User Mode vs Kernel Mode

```
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│   USER MODE (Ring 3)              KERNEL MODE (Ring 0)         │
│   ══════════════════              ═══════════════════          │
│                                                                │
│   ✅ Доступ до власної           ✅ Доступ до ВСІЄЇ пам'яті    │
│      пам'яті процесу                                           │
│                                   ✅ Виконання БУДЬ-ЯКИХ       │
│   ❌ Доступ до пам'яті              інструкцій CPU             │
│      інших процесів                                            │
│                                   ✅ Пряма робота з            │
│   ❌ Привілейовані                  пристроями (I/O ports)     │
│      інструкції CPU                                            │
│                                   ✅ Керування перериваннями   │
│   ❌ Прямий доступ до                                          │
│      пристроїв                   ✅ Зміна таблиць сторінок     │
│                                     (віртуальна пам'ять)       │
│   ❌ Зміна системних                                           │
│      структур                                                  │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### Що відбувається при порушенні?

```
┌────────────────────────────────────────────────────────────────┐
│                      ПОРУШЕННЯ ПРИВІЛЕЇВ                       │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   User Mode програма намагається:                              │
│                                                                │
│   1. Прочитати пам'ять ядра                                    │
│      ──────────────────────────────────────────────────────    │
│      → сторінки ядра позначені «лише для режиму ядра»:         │
│        CPU генерує Page Fault (#PF)                            │
│      → ядро надсилає процесу SIGSEGV: "Segmentation fault"     │
│                                                                │
│   2. Виконати привілейовану інструкцію (напр. CLI —            │
│      вимкнути переривання)                                     │
│      ──────────────────────────────────────────────────────    │
│      → CPU генерує General Protection Fault (#GP)              │
│      → ядро завершує процес тим самим SIGSEGV                  │
│                                                                │
│   3. Звернутися до порту введення-виведення (IN/OUT)           │
│      ──────────────────────────────────────────────────────    │
│      → CPU генерує #GP → SIGSEGV                               │
│                                                                │
│   Це АПАРАТНИЙ захист: процес не може його обійти. Обійти      │
│   може лише ядро — і свідомо: виклик ioperm() дає окремому     │
│   процесу root доступ до обраних портів.                       │
└────────────────────────────────────────────────────────────────┘
```

**Практичний приклад:**

```bash
# Спроба прочитати пам'ять ядра
sudo cat /proc/kcore | head -c 100
# Працює тільки з sudo (root має доступ до kernel space)

# Без sudo:
cat /proc/kcore
# cat: /proc/kcore: Permission denied

# Обмеження процесу: фільтр системних викликів seccomp і capabilities
grep -iE "seccomp|cap" /proc/self/status
```

## Перехід між режимами

Єдиний легальний спосіб перейти з User Mode в Kernel Mode — через **системний виклик**.

```
┌────────────────────────────────────────────────────────────────┐
│                    ПЕРЕХІД USER → KERNEL                       │
│                                                                │
│   User Mode                                                    │
│   ┌────────────────────────────────────┐                       │
│   │  Програма: printf("Hello");        │                       │
│   │            ↓                       │                       │
│   │  libc: write(1, "Hello", 5);       │                       │
│   │            ↓                       │                       │
│   │  Інструкція: SYSCALL (x86-64)      │                       │
│   │              або INT 0x80 (x86)    │                       │
│   └──────────────┬─────────────────────┘                       │
│                  │                                             │
│   ═══════════════╪══════════════════════  ← Межа режимів       │
│                  │                                             │
│   Kernel Mode    ↓                                             │
│   ┌────────────────────────────────────┐                       │
│   │  1. SYSCALL запам'ятовує адресу    │                       │
│   │     повернення, код ядра — решту   │                       │
│   │  2. Перемикає Ring 3 → Ring 0      │                       │
│   │  3. Переходить до sys_write()      │                       │
│   │  4. Ядро пише в stdout             │                       │
│   │  5. Відновлює стан                 │                       │
│   │  6. SYSRET — назад в Ring 3        │                       │
│   └────────────────────────────────────┘                       │
│                                                                │
│   Час перемикання: 100-1000 наносекунд                         │
└────────────────────────────────────────────────────────────────┘
```

**Практичний приклад — відстеження системних викликів:**

```bash
# Подивитися syscalls простої команди
strace -c ls /tmp 2>&1 | tail -20

# Приклад виводу:
# % time     seconds  usecs/call     calls    errors syscall
# ------ ----------- ----------- --------- --------- ----------------
#  25.00    0.000050          12         4           openat
#  20.00    0.000040          10         4           read
#  15.00    0.000030           7         4           close
#  ...

# Кожен виклик — це перехід User→Kernel→User
```

Перемикання режимів видно й без `strace` — командою `time`:

```bash
time dd if=/dev/zero of=/dev/null bs=1M count=2000
# real    0m0.120s
# user    0m0.001s
# sys     0m0.118s
```

`user` — час, коли процес виконував власний код у режимі користувача, `sys` — час, який ядро витратило, обслуговуючи його системні виклики. Тут майже все — `sys`: `dd` лише просить ядро копіювати дані з `/dev/zero` в `/dev/null`. Спробуйте для порівняння `time python3 -c "sum(range(10**7))"` — там навпаки, майже весь час `user`.

### vDSO: системні виклики без входу в ядро

Деякі виклики програми роблять так часто, що навіть 100 нс на перемикання режимів — забагато. Найчастіший приклад — поточний час. Тому ядро кладе в кожен процес маленьку бібліотеку **vDSO** (virtual dynamic shared object) з функціями на кшталт `clock_gettime()`, які читають час зі сторінки пам'яті, яку ядро постійно оновлює, — без жодного переходу в режим ядра.

```bash
# vDSO видно в карті пам'яті будь-якого процесу
grep vdso /proc/self/maps
# 7ffd5a3f1000-7ffd5a3f3000 r-xp 00000000 00:00 0      [vdso]

# А в strace виклику clock_gettime не буде: він не дійшов до ядра
strace -e trace=clock_gettime date
```

### 1. Планувальник процесів (Process Scheduler)

**Завдання:** Вирішує, який процес виконуватиметься наступним.

```
┌─────────────────────────────────────────────────────────────────┐
│                 ПЛАНУВАЛЬНИК LINUX: CFS → EEVDF                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Кожна задача накопичує vruntime — «віртуальний» час           │
│   виконання, що росте повільніше для задач з вищим              │
│   пріоритетом:                                                  │
│                                                                 │
│      ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐                              │
│      │ A │ │ B │ │ C │ │ D │ │ E │                              │
│      │ 5 │ │ 8 │ │12 │ │15 │ │20 │  мс                          │
│      └───┘ └───┘ └───┘ └───┘ └───┘                              │
│        ▲                                                        │
│        └── CFS (2007–2023) обирав задачу з найменшим            │
│            vruntime — ту, якій «найменше дісталося»             │
│                                                                 │
│   З ядра 6.6 (2023) — EEVDF: той самий облік vruntime, але      │
│   з кандидатів, яким «недодали», обирається задача з            │
│   найближчим віртуальним дедлайном. Інтерактивні задачі з       │
│   короткими квантами отримують процесор швидше.                 │
│                                                                 │
│   Задачі впорядковані в червоно-чорному дереві: O(log n)        │
└─────────────────────────────────────────────────────────────────┘
```

Детально алгоритми планування — у модулях 2 і 3.

**Практичні команди:**

```bash
# Подивитися пріоритети процесів
ps -eo pid,ni,pri,comm | head -20

# Змінити пріоритет (nice value: -20 до +19)
nice -n 10 ./heavy_task    # Знизити пріоритет
sudo nice -n -10 ./important_task  # Підвищити пріоритет

# Real-time політики (потрібні права root)
sudo chrt -f 50 ./realtime_task  # FIFO з пріоритетом 50
sudo chrt -r 50 ./realtime_task  # Round-robin

# Статистика планувальника
cat /proc/schedstat | head -5
```

### 2. Менеджер пам'яті (Memory Manager)

**Завдання:** Розподіляє RAM між процесами, забезпечує ізоляцію.

Як віртуальні адреси процесу відображаються на фізичні, ми бачили в лекції 2. Тут важливо інше: хто це робить. Відображення виконує апаратний блок процесора — **MMU**, за таблицями сторінок, які складає ядро. Змінювати таблиці сторінок — привілейована операція, дозволена лише в режимі ядра. Саме тому процес не може «дописати» собі чужу пам'ять: він навіть не має інструкції, щоб торкнутися механізму, який його обмежує. Детально — у модулі 4.

**Практичні команди:**

```bash
# Карта пам'яті процесу
cat /proc/self/maps

# Використання пам'яті
free -h

# Детальна інформація
cat /proc/meminfo | head -20

# OOM Killer — хто буде "вбитий" при нестачі RAM: оцінка й ім'я процесу
for p in /proc/[0-9]*; do
    echo "$(cat $p/oom_score 2>/dev/null) $(cat $p/comm 2>/dev/null)"
done | sort -rn | head -5
```

│                              │                                  │
│                              ▼                                  │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │                         VFS                             │   │

**Практичні команди:**

```bash
# Які файлові системи підтримує ядро

mount | grep -E "ext4|xfs|btrfs"

# Відкриті файли процесу

# Файлові дескриптори в системі
cat /proc/sys/fs/file-nr
# формат: allocated  free  max
```

### 5. Підсистема безпеки (LSM)

**Завдання:** Контроль доступу понад стандартні UNIX-права.

```
┌─────────────────────────────────────────────────────────────────┐
│               LINUX SECURITY MODULES (LSM)                      │
│                                                                 │
│   Системний виклик: open("/etc/shadow", O_RDONLY)               │
│                              │                                  │
│                              ▼                                  │
│   ┌──────────────────────────────────────────────────────────┐  │
│   │  1. Discretionary Access Control (DAC)                   │  │
│   │     Перевірка rwx прав (user/group/other)                │  │
│   │                    │                                     │  │
│   │                    ▼ Якщо OK                             │  │
│   │  2. Linux Security Module (LSM)                          │  │
│   │     ┌──────────────────────────────────────────┐         │  │
│   │     │  SELinux  │  AppArmor  │  Smack  │ TOMOYO│         │  │
│   │     └──────────────────────────────────────────┘         │  │
│   │     Mandatory Access Control (MAC)                       │  │
│   │                    │                                     │  │
│   │                    ▼ Якщо OK                             │  │
│   │  3. Виконання операції                                   │  │
│   └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│   DAC: права задає власник файлу (chmod) на свій розсуд         │
│   MAC: політика системи, яку не може змінити навіть root        │
└─────────────────────────────────────────────────────────────────┘
```

**Практичні команди:**

```bash
# Перевірити статус SELinux
getenforce 2>/dev/null || echo "SELinux not installed"

# Перевірити AppArmor
aa-status 2>/dev/null || echo "AppArmor not installed"

# Capabilities процесу
cat /proc/self/status | grep Cap

# Розшифрувати capabilities поточної оболонки...
capsh --decode=$(awk '/CapEff/ {print $2}' /proc/self/status)
# ...і оболонки root — різниця очевидна
sudo sh -c 'capsh --decode=$(awk "/CapEff/ {print \$2}" /proc/self/status)'
```

## Порівняння режимів

| Характеристика | User Mode | Kernel Mode |
|----------------|-----------|-------------|
| **Ring** | 3 | 0 |
| **Доступ до пам'яті** | Тільки своя | Вся RAM |
| **I/O операції** | Через syscall | Прямий доступ |
| **Привілейовані інструкції** | Заборонено | Дозволено |
| **Наслідки помилки** | Crash процесу | Kernel panic |
| **Приклади коду** | Браузер, редактор | Драйвери, VFS |

## 🎯 Міні-проект (30 хв)

### Завдання: Вимірювання "вартості" системних викликів

Створіть benchmark, який виміряє реальний overhead переходу між User Mode та Kernel Mode на вашій системі.

**Кроки:**

1. Підготуйте середовище для експерименту:
```bash
mkdir ~/syscall-benchmark && cd ~/syscall-benchmark
```

2. Створіть простий benchmark-скрипт:
```bash
cat > benchmark.sh << 'EOF'
#!/bin/bash
echo "=== BENCHMARK СИСТЕМНИХ ВИКЛИКІВ ==="
echo "Дата: $(date)"
echo "Система: $(uname -r)"
echo ""

echo "--- Тест 1: 100 000 пар read()/write() ---"
# dd з bs=1 читає й пише по одному байту: кожен байт — два системні виклики
START=$(date +%s%N)
dd if=/dev/zero of=/dev/null bs=1 count=100000 2>/dev/null
END=$(date +%s%N)
DURATION=$((($END - $START) / 1000))
echo "Час: ${DURATION} мкс, на один виклик: $((DURATION * 1000 / 200000)) нс"
echo ""

echo "--- Тест 2: 100 запусків програми ---"
# Кожен запуск head — це fork + execve + завантаження бібліотек + exit
START=$(date +%s%N)
for i in $(seq 1 100); do
    head -c 100 /dev/zero > /dev/null
done
END=$(date +%s%N)
DURATION=$((($END - $START) / 1000))
echo "Час: ${DURATION} мкс, на один запуск: $((DURATION / 100)) мкс"
echo ""
echo "Порівняйте: запуск процесу в тисячі разів дорожчий за системний виклик."
EOF
chmod +x benchmark.sh
```

3. Запустіть benchmark та збережіть результати:
```bash
./benchmark.sh | tee benchmark-results.txt
```

4. Порівняйте User vs Kernel time:
```bash
echo "--- Тест 4: User vs Kernel time ---" | tee -a benchmark-results.txt
echo "Запускаємо 500 ls команд..." | tee -a benchmark-results.txt
time (for i in $(seq 1 500); do ls /tmp > /dev/null 2>&1; done) 2>&1 | tee -a benchmark-results.txt
echo "" | tee -a benchmark-results.txt
```

5. Дослідіть карту пам'яті процесу:
```bash
echo "--- Карта пам'яті shell ---" | tee -a benchmark-results.txt
cat /proc/self/maps | grep -E "heap|stack|vdso" | tee -a benchmark-results.txt
echo "" | tee -a benchmark-results.txt
```

6. Підрахуйте системні виклики «важкої» команди:
```bash
echo "--- Syscalls рекурсивного ls ---" | tee -a benchmark-results.txt
strace -c -o ls-syscalls.txt ls -R /usr/share > /dev/null
tail -15 ls-syscalls.txt | tee -a benchmark-results.txt
```

7. Сформулюйте висновки:
```bash
echo "" | tee -a benchmark-results.txt
echo "=== ВИСНОВКИ ===" | tee -a benchmark-results.txt
echo "1. Системний виклик коштує сотні наносекунд" | tee -a benchmark-results.txt
echo "2. Запуск процесу — сотні мікросекунд і більше" | tee -a benchmark-results.txt
echo "3. sys у виводі time — скільки часу ядро працювало на процес" | tee -a benchmark-results.txt
```

**Очікуваний результат:**
Файл `benchmark-results.txt` з результатами вимірювань overhead системних викликів на вашій конкретній системі.

**Бонус (для допитливих):**
- Порівняйте результати на різних ядрах (якщо є доступ до кількох машин)
- Виміряйте різницю між HDD та SSD для read() syscalls
- Створіть графік залежності часу від кількості syscalls

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Які кільця захисту реально використовують сучасні ОС на x86?

- лише Ring 0
- усі чотири кільця від 0 до 3
- Ring 0, Ring 1 і Ring 2
- Ring 0 і Ring 3

**2.** У якому кільці виконується ядро операційної системи?

- Ring −2
- Ring 0
- Ring −1
- Ring 3

**3.** Що станеться, якщо програма в режимі користувача спробує виконати привілейовану інструкцію?

- процесор проігнорує інструкцію й піде далі
- процесор згенерує виняток, і процес буде завершено
- інструкція виконається з попередженням у журналі
- ядро автоматично підвищить права процесу

**4.** Якою інструкцією виконується перехід із режиму користувача в режим ядра на x64?

- SYSCALL
- HLT
- IRET
- SYSRET

**5.** Скільки приблизно триває перехід між режимами?

- перехід відбувається миттєво
- від 1 до 10 мікросекунд
- від 100 до 1000 наносекунд
- близько мілісекунди

**6.** Чому помилка в драйвері призводить до kernel panic, а помилка в програмі — лише до її аварійного завершення?

- ядро не вміє обробляти винятки
- програма користувача не може звертатися до пам'яті взагалі
- драйвер виконується в режимі ядра, де немає ізоляції від решти системи
- драйвери завжди пишуть мовами без перевірки меж масивів

**7.** Який компонент ядра розподіляє процесорний час між процесами?

- мережевий стек
- віртуальна файлова система
- менеджер пам'яті
- планувальник

**8.** Що забезпечує VFS?

- дефрагментацію розділів
- шифрування даних на диску
- єдиний інтерфейс до різних файлових систем: ext4, XFS, NFS
- резервне копіювання файлів

**9.** Який компонент ядра відповідає за SELinux і AppArmor?

- менеджер пам'яті
- підсистема безпеки LSM
- планувальник
- мережевий стек

**10.** Яка команда покаже статистику системних викликів програми?

- strace -c команда
- dmesg
- lsmod
- free -h

## Підсумок

| Компонент | Функція | Приклад |
|-----------|---------|---------|
| **Protection Rings** | Апаратна ізоляція привілеїв | Ring 0 (kernel), Ring 3 (user) |
| **Scheduler** | Розподіл CPU між процесами | CFS, FIFO, Round-Robin |
| **Memory Manager** | Віртуальна пам'ять, ізоляція | Paging, Swapping, OOM |
| **VFS** | Єдиний інтерфейс до ФС | ext4, XFS, NFS через один API |
| **Network Stack** | Мережеві протоколи | TCP/IP, sockets |
| **LSM** | Обов'язковий контроль доступу | SELinux, AppArmor |

**Ключовий висновок:** Розділення на User Mode та Kernel Mode — це не просто програмна концепція, а **апаратний механізм безпеки**. Процесор фізично блокує небезпечні операції, і жодна програма не може це обійти.

На наступній лекції детально розглянемо архітектури ядер ОС: монолітне, мікроядро та гібридне.
