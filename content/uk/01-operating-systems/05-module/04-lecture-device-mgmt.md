## Секунда між роз'ємом і робочим пристроєм

Ви вставляєте флешку. За секунду вона з'являється у файловому менеджері. За цю
секунду система встигла: помітити зміну електричного стану на шині, опитати
пристрій, дізнатися його ідентифікатори, знайти й завантажити драйвер, створити
файл пристрою, визначити файлову систему й змонтувати її.

Жодної з цих дій не робила людина. У цій лекції розберемо, хто саме їх робить у
Windows і в Linux — і чому дві системи дійшли до різних рішень.

**Запитання до аудиторії**: звідки система знає, який драйвер потрібен пристрою,
якого вона бачить уперше?

## Ідентифікація: як пристрій називає себе

```
┌─────────────────────────────────────────────────────────────────────┐
│               ПРИСТРІЙ ПОВІДОМЛЯЄ СВІЙ ІДЕНТИФІКАТОР                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   USB:   VID:PID   (Vendor ID : Product ID)                         │
│          приклад 046d:c52b → Logitech, приймач Unifying             │
│                                                                     │
│   PCI:   Vendor:Device + Class                                      │
│          приклад 8086:1533 → Intel, мережевий контролер             │
│                                                                     │
│   Клас пристрою дозволяє працювати навіть без «рідного»             │
│   драйвера: клавіатура класу HID, накопичувач класу                 │
│   Mass Storage, вебкамера класу UVC.                                │
│                                                                     │
│   САМЕ ТОМУ звичайна флешка працює в будь-якій ОС без               │
│   диска з драйверами: вона заявляє стандартний клас.                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
# Ідентифікатори USB-пристроїв: перше число — виробник, друге — модель
lsusb

# Те саме для PCI, з назвами драйверів
lspci -k | head -12

# Який драйвер обслуговує конкретний пристрій
ls -l /sys/bus/usb/devices/*/driver 2>/dev/null | head -5
```

Клас пристрою — це стандартизований протокол. Виробник флешки не пише драйвер:
він робить пристрій, сумісний із класом Mass Storage, і будь-яка ОС уже вміє з
ним працювати. Драйвер потрібен лише там, де стандарту немає або можливості
пристрою ширші за клас: відеокарти, принтери, спеціалізоване обладнання.

## Модель драйверів Linux

```
┌─────────────────────────────────────────────────────────────────────┐
│                      LINUX: ЯДРО, SYSFS І UDEV                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Пристрій підключено                                               │
│          │                                                          │
│          ▼                                                          │
│   Драйвер шини (USB, PCI) виявляє пристрій, читає його              │
│   ідентифікатори                                                    │
│          │                                                          │
│          ▼                                                          │
│   Ядро шукає драйвер, що заявив підтримку цих ID                    │
│   (таблиця MODULE_DEVICE_TABLE у кожному модулі)                    │
│          │                                                          │
│          ▼                                                          │
│   Драйвер завантажується як МОДУЛЬ (.ko) і прив'язується            │
│          │                                                          │
│          ▼                                                          │
│   У /sys з'являється об'єкт, ядро надсилає подію uevent             │
│          │                                                          │
│          ▼                                                          │
│   udev у просторі користувача створює /dev/…, застосовує            │
│   правила: права доступу, символьні імена, запуск програм           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
# Завантажені модулі ядра
lsmod | head -10

# Які пристрої підтримує конкретний модуль
modinfo usb_storage 2>/dev/null | grep -E "^(description|alias)" | head -5

# Спостерігати події підключення в реальному часі
# (запустіть і вставте флешку)
udevadm monitor --udev

# Усе, що udev знає про конкретний пристрій
udevadm info /dev/sda 2>/dev/null | head -12
```

**Чому udev працює в просторі користувача.** Створення файлів у `/dev`,
призначення прав, запуск сценаріїв — це політика, а не механізм. Ядро дає
механізм: повідомляє «з'явився пристрій із такими властивостями». Що з цим
робити, вирішує правило udev, яке адміністратор може змінити текстовим
редактором без перезбирання ядра. Це той самий принцип розділення механізму й
політики, що й у планувальнику.

## Модель драйверів Windows

```
┌─────────────────────────────────────────────────────────────────────┐
│              WINDOWS: СТЕК ДРАЙВЕРІВ І ПАКЕТИ ЗАПИТІВ               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Запит від програми перетворюється на IRP                          │
│   (I/O Request Packet) і проходить СТЕК драйверів:                  │
│                                                                     │
│     ┌──────────────────────────┐                                    │
│     │ Фільтрувальний драйвер   │  антивірус, шифрування             │
│     ├──────────────────────────┤                                    │
│     │ Функціональний драйвер   │  «рідний» драйвер пристрою         │
│     ├──────────────────────────┤                                    │
│     │ Драйвер шини             │  USB, PCI                          │
│     └──────────────────────────┘                                    │
│                                                                     │
│   Кожен рівень може обробити запит, змінити його або                │
│   передати нижче. Диспетчер PnP керує підключенням,                 │
│   диспетчер живлення — переходами в режими сну.                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Стек із фільтрами — сильна риса моделі Windows: антивірус або система шифрування
диска вбудовуються в ланцюг, не змінюючи «рідного» драйвера. Зворотний бік той
самий: сторонній фільтр у ланцюзі — часте джерело збоїв і сповільнення.

| | Linux | Windows |
|---|-------|---------|
| Форма драйвера | модуль ядра `.ko` | `.sys` + INF-файл опису |
| Пошук драйвера | таблиця ID у модулі | база INF, потім Windows Update |
| Стабільний інтерфейс ядра | **немає** навмисно | є, гарантується роками |
| Створення вузлів пристроїв | udev у просторі користувача | диспетчер PnP у ядрі |
| Оновлення | разом із ядром або окремим модулем | окремим пакетом, часто без перезавантаження |

**Чому в Linux навмисно немає стабільного інтерфейсу для драйверів.** Це
свідоме рішення розробників ядра: драйвери, прийняті до основного дерева,
оновлюються разом із ядром, а зовнішні змушені або йти в основне дерево, або
підтримувати сумісність самотужки. Наслідок для користувача подвійний: більшість
обладнання працює «з коробки» без встановлення чогось, але свіжий пристрій
може не працювати на старому ядрі. У Windows навпаки: інтерфейс стабільний,
тому драйвер від виробника ставиться окремо й живе роками.

## Гаряче підключення

```bash
# Стежити за журналом ядра наживо (вихід — Ctrl+C) і вставити флешку.
# В Ubuntu журнал ядра читає лише root: kernel.dmesg_restrict = 1
sudo dmesg -w

# Типова послідовність у журналі:
# usb 1-2: new high-speed USB device number 5 using xhci_hcd
# usb-storage 1-2:1.0: USB Mass Storage device detected
# scsi host2: usb-storage 1-2:1.0
# sd 2:0:0:0: [sdb] 15142912 512-byte logical blocks: (7.75 GB)
# sd 2:0:0:0: [sdb] Attached SCSI removable disk
```

Кожен рядок — це перехід відповідальності на наступний рівень: контролер шини →
драйвер класу накопичувачів → підсистема SCSI → блоковий пристрій. Розбір цього
журналу з аудиторією наочно показує вертикаль із попередньої лекції в дії.

### Розбір помилкового міркування

> «Драйвер у просторі користувача працює повільніше, отже, він гірший.»

Повільніше — так, але «гірший» не випливає. Історично **більшість аварійних
зупинок Windows спричиняли саме драйвери сторонніх виробників**, і причина
структурна: код драйвера виконується в режимі ядра, де немає ізоляції. Помилка
адресації у драйвері принтера валить усю систему, а не лише друк.

Найгучніший приклад — 19 липня 2024 року. Оновлення вмісту для драйвера
режиму ядра CrowdStrike Falcon містило помилку, і близько 8,5 мільйона
комп'ютерів з Windows одночасно показали синій екран — зупинилися авіакомпанії,
банки, лікарні. Помилка була не в самій Windows, а в сторонньому коді, якому
довелося довірити режим ядра. Після цього Microsoft оголосила програму
Windows Resiliency Initiative: засоби захисту мають поступово переходити з ядра
в простір користувача.

Переносячи драйвер у простір користувача, ми міняємо продуктивність на
локалізацію відмови. Для принтера чи сканера цей обмін очевидно вигідний: кілька
зайвих мікросекунд ніхто не помітить, а перезапуск служби замість синього екрана
помітять усі. Для мережевої карти на 100 Гбіт/с обмін невигідний — там борються
за наносекунди.

**Як це пояснювати.** Питання не «де швидше», а «яка ціна помилки». Саме тому
одна й та сама система тримає драйвер диска в ядрі, а драйвер сканера — у
просторі користувача.

## Підписування драйверів

Код у ядрі має необмежені права, тому обидві системи вимагають підтвердження
походження коду.

| Механізм | Система | Що гарантує |
|----------|---------|-------------|
| Driver Signature Enforcement | Windows (64-біт) | драйвер підписаний виробником і перевірений Microsoft |
| Secure Boot | обидві | завантажується лише підписаний завантажувач і ядро |
| Module signing | Linux | модуль підписано ключем, якому довіряє ядро |
| Lockdown | Linux | навіть root не може завантажити непідписаний модуль |

```bash
# Чи вимагає ядро підписів модулів
cat /sys/module/module/parameters/sig_enforce 2>/dev/null || echo "параметр недоступний"

# Стан Secure Boot
mokutil --sb-state 2>/dev/null || echo "mokutil не встановлено"

# Чи «забруднене» ядро стороннім модулем (ненульове значення)
cat /proc/sys/kernel/tainted
```

Значення `tainted` — бітова маска причин, через які ядро більше не вважає себе
«чистим». Найчастіші біти: 1 (P) — завантажено пропрієтарний модуль, наприклад
драйвер NVIDIA; 4096 (O) — модуль поза основним деревом ядра; 8192 (E) —
непідписаний модуль; 512 (W) — ядро вже видавало попередження. Розшифрувати
значення можна за таблицею в документації (`docs.kernel.org/admin-guide/tainted-kernels.html`)
або побачити літери в рядку `Tainted:` будь-якого звіту ядра про помилку.
Розробники ядра не прийматимуть звіт із «брудного» ядра: діагностувати
систему з невідомим кодом у ядрі неможливо, і це не бюрократія.

## Практичне завдання

1. Визначте ідентифікатори всіх USB-пристроїв і знайдіть, які драйвери їх
   обслуговують.
2. Запустіть `udevadm monitor`, підключіть будь-який пристрій і випишіть
   послідовність подій ядра та udev.
3. Знайдіть у `dmesg` рядки, що відповідають підключенню накопичувача, і
   зіставте кожен із рівнем вертикалі вводу-виводу.
4. Перевірте, чи «забруднене» ядро вашої системи, і з'ясуйте причину.

```
│   стандартний клас (HID, Mass Storage, UVC) = працює                │
│   без «рідного» драйвера                                            │
│                                                                     │
│   LINUX:                                                            │
│   модуль .ko → таблиця ID → sysfs → uevent → udev → /dev            │
│   стабільного інтерфейсу драйверів навмисно НЕМАЄ                   │
│                                                                     │
│   WINDOWS:                                                          │
│   .sys + INF → стек драйверів (фільтр / функціональний /            │
│   шини), запит проходить стек як IRP; інтерфейс стабільний          │
│                                                                     │
│   ДЕ ВИКОНУВАТИ ДРАЙВЕР:                                            │
│   у ядрі → швидко, помилка валить систему                           │
│   у просторі користувача → повільніше, відмова локальна             │
│   (FUSE, libusb, UMDF, DPDK)                                        │
│                                                                     │
│   КОМАНДИ:                                                          │
│   lsusb, lspci -k          → пристрої та їхні драйвери              │
│   lsmod, modinfo модуль    → модулі ядра                            │
│   udevadm monitor          → події підключення                      │
│   udevadm info /dev/sda    → усі властивості пристрою               │
│   cat /proc/sys/kernel/tainted → чи є сторонній код у ядрі          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Звідки система дізнається, який драйвер потрібен новому USB-пристрою?

- драйвер записаний у завантажувальному секторі пристрою
- система перебирає всі наявні драйвери по черзі
- користувач обирає драйвер зі списку вручну
- пристрій повідомляє ідентифікатори виробника й моделі

**2.** Чому звичайна флешка працює без встановлення драйверів?

- драйвер завантажується з інтернету автоматично
- її драйвер вбудований у кожну материнську плату
- вона відповідає стандартному класу Mass Storage
- вона не потребує драйвера взагалі

**3.** У якій формі існує драйвер у Linux?

- модуль ядра з розширенням .ko
- бібліотека .so у просторі користувача
- сценарій оболонки в /etc
- виконуваний файл, що запускається від root

**4.** Що робить udev?

- завантажує модулі ядра в пам'ять
- керує живленням пристроїв
- створює файли в /dev і застосовує правила за подіями від ядра
- обробляє переривання від пристроїв

**5.** Чому udev працює в просторі користувача, а не в ядрі?

- ядро не має доступу до файлової системи
- це зменшує кількість переривань
- створення вузлів і призначення прав — це політика, а не механізм
- так вимагає стандарт POSIX

**6.** Що таке IRP у Windows?

- формат файлу опису драйвера
- пакет запиту вводу-виводу, що проходить стек драйверів
- ідентифікатор пристрою на шині PCI
- таблиця переривань

**7.** Яку перевагу дає стек драйверів із фільтрами?

- пристрій працює без контролера
- антивірус чи шифрування вбудовуються без зміни «рідного» драйвера
- запити обробляються швидше
- драйвери можна не підписувати

**8.** Чому в Linux навмисно немає стабільного інтерфейсу для драйверів?

- через обмеження мови C
- щоб драйвери входили в основне дерево й оновлювалися разом із ядром
- щоб ускладнити роботу стороннім виробникам
- щоб зменшити розмір ядра

**9.** У чому головна перевага драйвера в просторі користувача?

- він працює швидше за драйвер у ядрі
- він не потребує ідентифікаторів пристрою
- він не може бути заблокований антивірусом
- його помилка не валить усю систему

**10.** Про що свідчить ненульове значення `/proc/sys/kernel/tainted`?

- ядро пошкоджене й потребує перевстановлення
- система працює у віртуальній машині
- увімкнено Secure Boot
- у ядро завантажено модуль поза основним деревом

## 🎯 Міні-проект (30 хв)

### Завдання: простежити життєвий цикл підключення пристрою

**Кроки:**

1. Відкрийте два термінали. У першому запустіть спостереження за подіями:

```bash
udevadm monitor --kernel --udev
```

2. У другому — спостереження за журналом ядра:

```bash
sudo dmesg -w
```

3. Підключіть USB-накопичувач. Збережіть вивід обох терміналів.

4. Складіть таблицю подій: час, джерело (ядро чи udev), підсистема, дія.

5. Знайдіть для пристрою повний набір властивостей і правило, що створило вузол:

```bash
udevadm info --attribute-walk /dev/sdb 2>/dev/null | head -25
```

6. Визначте, який модуль обслуговує пристрій, і перегляньте перелік
   підтримуваних ним ідентифікаторів:

```bash
lsmod | grep -E "usb_storage|uas"
modinfo usb_storage | grep -c alias
```

**Очікуваний результат:** послідовність із кількох десятків подій, у якій видно
чіткий порядок: подія шини → прив'язка драйвера → поява об'єкта в sysfs →
створення вузла в /dev → монтування.

**Бонус (для допитливих):**

- Напишіть власне правило udev, яке створює символьне посилання
  `/dev/my-flash` для вашого накопичувача за його серійним номером.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **VID:PID** | Ідентифікатори виробника й моделі, якими пристрій називає себе |
| **Клас пристрою** | Стандартизований протокол: HID, Mass Storage, UVC |
| **Модуль ядра (.ko)** | Форма драйвера в Linux; завантажується й вивантажується на ходу |
| **udev** | Служба простору користувача, що створює вузли в /dev за подіями ядра |
| **IRP** | Пакет запиту вводу-виводу, що проходить стек драйверів Windows |
| **Фільтрувальний драйвер** | Рівень стека, що перехоплює запити до пристрою |
| **FUSE / libusb / UMDF** | Механізми написання драйверів у просторі користувача |
| **tainted** | Ознака, що в ядро завантажено сторонній код |

| | Linux | Windows |
|---|-------|---------|
| Пошук драйвера | таблиця ID у модулі | INF-файли, Windows Update |
| Вузли пристроїв | udev, простір користувача | диспетчер PnP, ядро |
| Інтерфейс драйверів | нестабільний навмисно | стабільний |

**Ключовий висновок:** обидві системи розв'язують ту саму задачу — зв'язати
невідоме залізо з готовим кодом — але роблять різну ставку. Linux ставить на те,
що драйвер житиме в дереві ядра й оновлюватиметься разом із ним; Windows — на
те, що драйвер прийде від виробника й переживе кілька версій системи. Обидві
ставки мають ціну, і знати цю ціну важливіше, ніж запам'ятати назви механізмів.

Далі в модулі — лабораторні роботи, де ви попрацюєте з пристроями та файловими
системами на практиці.
