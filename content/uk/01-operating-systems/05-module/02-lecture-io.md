## Чому `read()` виглядає однаково для всього

Ця програма прочитає перші байти і з файлу на диску, і з клавіатури, і з
мережевого сокета, і з генератора випадкових чисел:

```c
int fd = open(шлях, O_RDONLY);
char buf[64];
ssize_t n = read(fd, buf, sizeof buf);
```

Пристрої влаштовані абсолютно по-різному: у диска є головки й блоки, у клавіатури
— контролер і скан-коди, у мережевої карти — кільцеві буфери пакетів. Але
програма про це не знає й знати не повинна.

За цією однаковістю стоїть багаторівнева структура, у якій кожен рівень ховає
деталь нижчого.

**Запитання до аудиторії**: що має статися, щоб `read()` із файлу повернув дані,
якщо самих даних у пам'яті ще немає?

## Рівні підсистеми введення-виведення

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ВЕРТИКАЛЬ ВВЕДЕННЯ-ВИВЕДЕННЯ                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌─────────────────────────────────────────────────────┐           │
│   │ Програма користувача: read(), write(), ioctl()      │           │
│   ├─────────────────────────────────────────────────────┤           │
│   │ Бібліотека: fopen/fread, буферизація в user space   │           │
│   ├═════════════════════════════════════════════════════┤           │
│   │ Системний виклик — межа режимів                     │           │
│   ├─────────────────────────────────────────────────────┤           │
│   │ Незалежний від пристрою рівень ядра:                │           │
│   │ VFS, кеш сторінок, перевірка прав, черги запитів    │           │
│   ├─────────────────────────────────────────────────────┤           │
│   │ Драйвер пристрою: знає регістри й протокол          │           │
│   ├─────────────────────────────────────────────────────┤           │
│   │ Обробники переривань                                │           │
│   ├─────────────────────────────────────────────────────┤           │
│   │ Контролер і сам пристрій                            │           │
│   └─────────────────────────────────────────────────────┘           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Що дає кожен рівень.** Незалежний від пристрою рівень робить найважливіше: він
перетворює десятки різних інтерфейсів на один набір операцій. Саме тому драйвер
у Linux реалізує структуру з покажчиками на функції `open`, `read`, `write`,
`ioctl` — і з погляду ядра будь-який пристрій виглядає однаково.

Операція `ioctl` — це визнання того, що уніфікація не буває повною: усе, що не
вкладається в читання й запис (перемотати стрічку, змінити швидкість порту,
дізнатися геометрію диска), передають через неї.

```bash
# Драйвери, зареєстровані в системі
cat /proc/devices | head -20

# Ієрархія пристроїв очима ядра
ls /sys/devices/ | head

# Параметри драйвера, доступні для зміни
ls /sys/module/ | head -10
```

## Три способи обміну даними

```
┌─────────────────────────────────────────────────────────────────────┐
│              ЯК ДАНІ ПОТРАПЛЯЮТЬ ІЗ ПРИСТРОЮ В ПАМ'ЯТЬ              │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. ПРОГРАМНИЙ ОБМІН (опитування, polling)                         │
│      while (регістр_стану != ГОТОВО) { /* чекаємо */ }              │
│      Процесор у циклі перевіряє готовність і сам копіює             │
│      кожен байт. Просто, але процесор зайнятий повністю.            │
│                                                                     │
│   2. ОБМІН ЗА ПЕРЕРИВАННЯМИ                                         │
│      Процесор ініціює операцію й перемикається на іншу              │
│      задачу. Пристрій сам повідомляє про готовність.                │
│      Дані все одно копіює процесор — байт за байтом.                │
│                                                                     │
│   3. ПРЯМИЙ ДОСТУП ДО ПАМ'ЯТІ (DMA)                                 │
│      Процесор каже: «блок за адресою X, обсяг N».                   │
│      Контролер переносить дані самостійно й надсилає                │
│      ОДНЕ переривання на весь блок.                                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Порахуймо різницю.** Читаємо 4 КіБ із диска.

| Спосіб | Дій процесора | Переривань |
|--------|---------------|------------|
| Опитування | 4096 перевірок + 4096 копіювань, увесь час зайнятий | 0 |
| Переривання | 4096 копіювань, між ними може працювати інша задача | 4096 (або за блоками) |
| DMA | 1 команда + 1 обробка завершення | 1 |

Саме тому всі швидкі пристрої працюють через DMA. Опитування ж лишилося там, де
операція завершується швидше, ніж коштує перемикання контексту: наприклад,
читання з регістра готового контролера.

### Розбір помилкового міркування

> «Переривання завжди ефективніші за опитування.»

Порахуймо межу. Мережа 1 Гбіт/с, кадри мінімального розміру:

```
Кадр 64 байти + 20 байтів службових = 84 байти = 672 біти
1 000 000 000 / 672 ≈ 1 488 095 пакетів за секунду

Якщо на кожен пакет — переривання вартістю 2 мкс:
1 488 095 × 2 мкс = 2,98 секунди процесорного часу
на кожну секунду трафіку.
```

Тобто одного ядра не вистачить навіть на самі переривання, не кажучи про обробку
пакетів. Тому мережеві драйвери Linux використовують **NAPI**: при високому
навантаженні переривання **вимикаються**, і драйвер переходить на опитування —
саме те, що вважалося застарілим.

Правильне формулювання: переривання виграють, коли події рідкісні, опитування —
коли вони настільки часті, що вартість переривання перевищує вартість перевірки.

```bash
# Скільки переривань згенерував кожен пристрій
head -5 /proc/interrupts

# Робота NAPI: скільки разів ядро обробляло вхідні пакети опитуванням
grep NET_RX /proc/softirqs
# Статистика по ядрах: оброблено, відкинуто, «не встигли за бюджет» (hex)
cat /proc/net/softnet_stat
```

## Блокуючі, неблокуючі та асинхронні операції

```
┌─────────────────────────────────────────────────────────────────────┐
│                        ТРИ МОДЕЛІ ОЧІКУВАННЯ                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   БЛОКУЮЧА (типова)                                                 │
│   read() не повертається, доки дані не з'являться.                  │
│   Процес переходить у стан WAITING, процесор працює з іншими.       │
│   Просто програмувати; один потік — одна операція.                  │
│                                                                     │
│   НЕБЛОКУЮЧА                                                        │
│   read() повертається негайно: або дані, або EAGAIN.                │
│   Програма сама вирішує, коли спробувати ще.                        │
│   Потрібен механізм очікування багатьох джерел: epoll.              │
│                                                                     │
│   АСИНХРОННА                                                        │
│   Програма ставить запит у чергу й працює далі; результат           │
│   забирає пізніше з черги завершень (io_uring, IOCP).               │
│   Найскладніше, але дає найбільшу пропускну здатність.              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому це не питання смаку.** Сервер, що обслуговує 10 000 з'єднань, не може
виділити на кожне окремий потік: 10 000 потоків — це гігабайти стеків і
постійні перемикання контексту. Тому масові сервери побудовані на неблокуючих
операціях з `epoll` або на асинхронному `io_uring`: один потік обслуговує тисячі
з'єднань, бо не чекає на жодне.

```bash
# io_uring з'явився в Linux 5.1 (2019); 0 — дозволений усім, 2 — вимкнений
cat /proc/sys/kernel/io_uring_disabled 2>/dev/null || uname -r

# Скільки дескрипторів може відкрити процес — межа для моделі «потік на з'єднання»
ulimit -n
```

## Логічна структура драйвера

```
┌─────────────────────────────────────────────────────────────────────┐
│                    ШЛЯХ ОДНОГО ЗАПИТУ НА ЧИТАННЯ                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. read() → системний виклик → VFS                                │
│   2. VFS перевіряє кеш сторінок:                                    │
│      • дані є → повертаємо негайно, пристрій не чіпаємо             │
│      • даних немає → формуємо запит до блокового рівня              │
│   3. Планувальник вводу-виводу ставить запит у чергу,               │
│      може об'єднати його із сусіднім і змінити порядок              │
│   4. Драйвер програмує контролер: адреса, обсяг, DMA                │
│   5. Процес переходить у стан WAITING                               │
│   6. Контролер переносить дані, надсилає переривання                │
│   7. Верхня половина обробника: підтвердити переривання             │
│   8. Нижня половина: розбудити процес, оновити кеш                  │
│   9. read() повертає дані                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Пункт 2 пояснює, чому друге читання того самого файлу відбувається миттєво: до
пристрою справа просто не доходить.

Переконатися в цьому на великому файлі можна в міні-проєкті наприкінці теми:
холодне читання після скидання кеша (`echo 3 > /proc/sys/vm/drop_caches`) і
тепле — одразу після нього — відрізняються в десятки разів.

## Планування запитів до диска

Пункт 3 із попереднього списку заслуговує окремої уваги. Для обертового диска
порядок обслуговування запитів впливає на час радикально: головка рухається
механічно.

| Планувальник | Ідея | Для чого |
|--------------|------|----------|
| `none` / `noop` | не перевпорядковувати взагалі | NVMe, віртуальні диски |
| `mq-deadline` | кожен запит має термін; читання пріоритетніші | загальне призначення, SSD |
| `bfq` | справедливий розподіл смуги між процесами | настільні системи |
| `kyber` | обмежує черги задля низької затримки | швидкі NVMe із великим паралелізмом |

```bash
# Який планувальник обраний для вашого накопичувача
cat /sys/block/sda/queue/scheduler 2>/dev/null ||   cat /sys/block/nvme0n1/queue/scheduler 2>/dev/null

# Глибина черги: скільки запитів пристрій приймає одночасно
cat /sys/block/*/queue/nr_requests 2>/dev/null | head -3
```

**Чому для NVMe обирають `none`.** Перевпорядкування має сенс, коли переміщення
головки коштує мілісекунди. У твердотільного накопичувача часу пошуку немає, а
всередині він і так обслуговує десятки черг паралельно. Сортування в ядрі лише
додає роботи процесору й заважає власному паралелізму пристрою. Це добрий
приклад того, як **зміна заліза знецінює алгоритм**, який десятиліттями вважався
обов'язковим.

## Практичне завдання

1. Знайдіть планувальник вводу-виводу для кожного накопичувача в системі.
2. Порівняйте час читання великого файлу з кеша й без нього (скидання кеша
   потребує прав root).
3. Подивіться `/proc/interrupts` двічі з інтервалом у 10 секунд і визначте, який
   пристрій генерує найбільше переривань.
4. Оцініть, скільки переривань за секунду дала б мережа 10 Гбіт/с при кадрах
   1500 байтів, і зробіть висновок про доцільність NAPI.

## 📋 Cheat Sheet

```
┌─────────────────────────────────────────────────────────────────────┐
│           ШПАРГАЛКА: ЛОГІЧНА СТРУКТУРА ВВЕДЕННЯ-ВИВЕДЕННЯ           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   РІВНІ:                                                            │
│   програма → бібліотека → системний виклик → VFS і кеш →            │
│   планувальник запитів → драйвер → переривання → контролер          │
│                                                                     │
│   СПОСОБИ ОБМІНУ:                                                   │
│   опитування     → процесор зайнятий повністю                       │
│   переривання    → процесор вільний, копіює по байту                │
│   DMA            → контролер сам, одне переривання на блок          │
│                                                                     │
│   МЕЖА ЕФЕКТИВНОСТІ ПЕРЕРИВАНЬ:                                     │
│   1 Гбіт/с, кадри 64 Б → 1,49 млн пакетів/с                         │
│   × 2 мкс на переривання = 2,98 с процесора на 1 с трафіку          │
│   → тому NAPI вимикає переривання й переходить на опитування        │
│                                                                     │
│   МОДЕЛІ ОЧІКУВАННЯ:                                                │
│   блокуюча → просто, один потік на операцію                         │
│   неблокуюча + epoll → тисячі з'єднань на потік                     │
│   асинхронна (io_uring) → найбільша пропускна здатність             │
│                                                                     │
│   КОМАНДИ:                                                          │
│   cat /proc/interrupts            → переривання по пристроях        │
│   cat /sys/block/*/queue/scheduler → планувальник диска             │
│   ulimit -n                       → межа дескрипторів               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Який рівень підсистеми вводу-виводу робить пристрої однаковими для програми?

- обробник переривання
- бібліотека мови програмування
- контролер пристрою
- незалежний від пристрою рівень ядра

**2.** Для чого потрібна операція `ioctl`?

- для прискорення читання великих файлів
- для перевірки прав доступу
- для перемикання між блоковим і символьним режимом
- для дій, які не вкладаються в читання та запис

**3.** Скільки переривань потрібно для читання блока 4 КіБ через DMA?

- одне на весь блок
- жодного
- одне на кожні 512 байтів
- одне на кожен байт

**4.** Коли опитування ефективніше за переривання?

- коли події настільки часті, що вартість переривання перевищує вартість перевірки
- опитування ніколи не буває ефективнішим
- коли в системі одне ядро
- коли пристрій дуже повільний

**5.** Мережа 1 Гбіт/с із кадрами 64 байти дає близько 1,49 млн пакетів за секунду. Що це означає для обробки перериваннями?

- пристрій перейде в режим DMA автоматично
- переривання оброблятимуться вдвічі швидше
- одного ядра не вистачить навіть на самі переривання
- кадри будуть відкинуті мережевою картою

**6.** Що робить механізм NAPI?

- переносить обробку пакетів на графічний процесор
- відкидає пакети, що не вміщуються в чергу
- при високому навантаженні вимикає переривання й переходить на опитування
- збільшує розмір буфера мережевої карти

**7.** Чим неблокуюча операція відрізняється від блокуючої?

- вона працює лише з мережею
- вона повертається негайно, навіть якщо даних ще немає
- вона виконується швидше
- вона не потребує системного виклику

**8.** Чому масові сервери не використовують модель «потік на з'єднання»?

- десятки тисяч потоків дають величезні витрати на пам'ять і перемикання
- потоки працюють лише з блоковими пристроями
- ядро не дозволяє створювати понад сто потоків
- потоки не підтримують мережу

**9.** Чому друге поспіль читання того самого файлу відбувається значно швидше?

- ядро підвищує пріоритет процесу
- дані вже лежать у кеші сторінок, і до пристрою справа не доходить
- диск запам'ятовує позицію головки
- файлова система стискає дані після першого читання

**10.** Чому для NVMe зазвичай обирають планувальник `none`?

- ядро не підтримує планування для NVMe
- часу пошуку немає, а пристрій сам обслуговує черги паралельно
- так зменшується споживання енергії
- NVMe не підтримує черг запитів

## 🎯 Міні-проект (30 хв)

### Завдання: виміряти внесок кожного рівня

**Кроки:**

1. Виміряйте читання файлу без кеша й із кешем:

```bash
dd if=/dev/zero of=./big.bin bs=1M count=512 2>/dev/null
sync
sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches' 2>/dev/null || echo "без прав root крок пропускаємо"
echo "=== холодне читання"; time cat ./big.bin > /dev/null
echo "=== тепле читання";   time cat ./big.bin > /dev/null
```

2. Повторіть холодне читання з прапорцем прямого доступу, який обходить кеш:

```bash
time dd if=./big.bin of=/dev/null bs=1M iflag=direct 2>&1 | tail -1
```

3. Складіть таблицю: холодне читання, тепле читання, прямий доступ — час і
   обчислена швидкість.

4. Зафіксуйте кількість переривань дискового контролера до й після досліду:

```bash
grep -iE "nvme|ahci|sd" /proc/interrupts
```

5. Приберіть за собою: `rm -f ./big.bin`.

**Очікуваний результат:** тепле читання буде в десятки разів швидшим за холодне,
а прямий доступ покаже справжню швидкість пристрою.

**Бонус (для допитливих):**

- Змініть планувальник вводу-виводу й повторіть вимірювання:
  `echo mq-deadline | sudo tee /sys/block/sda/queue/scheduler`

## Підсумок

| Рівень | Що робить |
|--------|-----------|
| **Програма** | Викликає `read`, `write`, `ioctl` |
| **Бібліотека** | Буферизує в просторі користувача |
| **Незалежний рівень ядра** | VFS, кеш сторінок, права, черги запитів |
| **Драйвер** | Знає регістри й протокол конкретного пристрою |
| **Обробник переривання** | Приймає сигнал завершення від пристрою |
| **Контролер** | Виконує операцію, керує самим пристроєм |

| Спосіб обміну | Хто копіює дані | Переривань на блок 4 КіБ |
|---------------|-----------------|--------------------------|
| Опитування | процесор у циклі | 0 |
| Переривання | процесор за сигналом | багато |
| DMA | контролер | 1 |

**Ключовий висновок:** уніфікований інтерфейс `read`/`write` — це не спрощення
задля зручності, а архітектурне рішення, за яке платять рівнями абстракції.
Кожен рівень щось приховує й щось коштує, і тому системи, яким потрібен максимум
(бази даних, мережеве обладнання), навмисно **обходять** окремі рівні: прямий
доступ повз кеш, опитування замість переривань, DPDK замість мережевого стека.

На наступній лекції — буферизація: чому дані майже ніколи не йдуть від програми
до пристрою напряму.
