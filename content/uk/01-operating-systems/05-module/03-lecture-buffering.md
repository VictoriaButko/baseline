## Мільйон системних викликів замість двохсот п'ятдесяти

Запишімо один мегабайт у файл двома способами. Спершу по байту:

```
1 048 576 байтів × 1 системний виклик на байт
× приблизно 1 мкс на виклик ≈ 1,05 секунди
```

Тепер той самий мегабайт блоками по 4 КіБ:

```
1 048 576 / 4096 = 256 системних викликів
× 1 мкс ≈ 0,26 мілісекунди
```

Різниця — приблизно чотири тисячі разів, і жодного стосунку до швидкості диска
вона не має. Диск в обох випадках отримає той самий мегабайт. Уся різниця — у
кількості перетинів межі між програмою та ядром.

**Запитання до аудиторії**: якщо різниця така велика, чому програма, яка пише
у файл по одному символу, все одно працює прийнятно швидко?

Відповідь — буферизація, і ця тема саме про неї.

## Чотири причини існування буферів

```
┌─────────────────────────────────────────────────────────────────────┐
│                        НАВІЩО ПОТРІБЕН БУФЕР                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. РІЗНА ШВИДКІСТЬ                                                │
│      Програма готує дані за наносекунди, диск приймає їх            │
│      за мілісекунди. Буфер розв'язує швидкості.                     │
│                                                                     │
│   2. РІЗНА ОДИНИЦЯ ОБМІНУ                                           │
│      Програма пише рядок у 17 байтів, диск працює блоками           │
│      по 4096. Буфер накопичує до повного блока.                     │
│                                                                     │
│   3. СЕМАНТИКА КОПІЮВАННЯ                                           │
│      Після write() програма має право одразу змінити свій           │
│      масив. Отже, ядро мусить скопіювати дані до себе.              │
│                                                                     │
│   4. ЗГЛАДЖУВАННЯ СПАЛАХІВ                                          │
│      Дані надходять нерівномірно, пристрій хоче рівний              │
│      потік. Буфер приймає спалах і віддає рівномірно.               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Третя причина найменш очевидна, і саме її варто розібрати з аудиторією. Розгляньмо
код:

```c
char buf[64];
strcpy(buf, "data");
write(fd, buf, 4);
strcpy(buf, "junk");   /* змінюємо буфер одразу після write */
```

Якщо ядро не скопіювало дані до себе, а лише запам'ятало адресу, то на диск
потрапить `junk` замість `data`. (Латинські слова тут не випадково: кирилична
літера в UTF-8 займає два байти, і `write(fd, "дані", 4)` записав би лише
половину слова.) Тому `write()` копіює — і ця копія є буфером
за визначенням.

## Схеми буферизації

```
┌─────────────────────────────────────────────────────────────────────┐
│               ОДИНАРНИЙ, ПОДВІЙНИЙ І КІЛЬЦЕВИЙ БУФЕР                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ОДИНАРНИЙ                                                         │
│   [    буфер    ]                                                   │
│   Поки ядро віддає буфер пристрою, програма чекає:                  │
│   писати нікуди. Робота серіалізується.                             │
│                                                                     │
│   ПОДВІЙНИЙ                                                         │
│   [  буфер A  ] [  буфер B  ]                                       │
│   Програма пише в A, пристрій читає B. Потім міняються.             │
│   Обидва працюють одночасно — класичний прийом у графіці.           │
│                                                                     │
│   КІЛЬЦЕВИЙ (circular, ring)                                        │
│          ┌──►[0][1][2][3][4][5][6][7]──┐                            │
│          └─────────────────────────────┘                            │
│     запис ▲ (head)        читання ▲ (tail)                          │
│   Виробник рухає head, споживач — tail. Переповнення,               │
│   коли head наздоганяє tail; порожньо, коли head = tail.            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Кільцевий буфер — найпоширеніша структура в системному програмуванні.** Він
нікуди не рухає дані: рухаються лише два покажчики. Саме так влаштовані:

- буфер повідомлень ядра (`dmesg`);
- черги пакетів мережевої карти;
- звукові буфери;
- журнали з обмеженим розміром.

```bash
# Кільцевий буфер повідомлень ядра: старі записи витісняються новими
# (в Ubuntu читати його може лише root: kernel.dmesg_restrict = 1)
sudo dmesg | tail -5
cat /proc/sys/kernel/printk_ratelimit

# Розміри кільцевих черг мережевої карти
ethtool -g eth0 2>/dev/null || echo "вкажіть свій інтерфейс: ip -brief link"
```

## Буфер і кеш — не те саме

Найчастіша плутанина в темі.

| | Буфер | Кеш |
|---|-------|-----|
| Навіщо | узгодити швидкість і розмір порцій | повторно використати вже прочитане |
| Що зберігає | дані, які **зараз** передаються | дані, які **можуть знадобитися ще раз** |
| Час життя | до завершення передавання | доки не витіснено |
| Якщо видалити | передавання зламається або сповільниться | усе працює, лише повільніше |

```bash
# У виводі free це РІЗНІ стовпці
free -h

# buff/cache у сучасних системах показують суму:
# buffers — метадані блокових пристроїв
# cached  — сторінки файлів (кеш сторінок)
grep -E "^(Buffers|Cached)" /proc/meminfo
```

**Перевірка на розуміння**: якщо система звільнить усю пам'ять під `cached`,
програми працюватимуть далі — просто повільніше, бо доведеться читати з диска
заново. Якщо ж прибрати буфери, які беруть участь у передаванні прямо зараз,
операції зламаються. Звідси й рядок «available» у `free`: кеш вважається вільною
пам'яттю, бо його можна забрати будь-коли.

## Відкладений запис і його ціна

```
┌─────────────────────────────────────────────────────────────────────┐
│                   НАСКРІЗНИЙ І ВІДКЛАДЕНИЙ ЗАПИС                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   НАСКРІЗНИЙ (write-through)                                        │
│   write() → буфер → одразу на пристрій → повернення                 │
│   Надійно: після повернення дані на носії.                          │
│   Повільно: кожен запис чекає на пристрій.                          │
│                                                                     │
│   ВІДКЛАДЕНИЙ (write-back)                                          │
│   write() → буфер → повернення                                      │
│                    ⋮ (пізніше, фоновим потоком)                     │
│                    └──► на пристрій                                 │
│   Швидко: програма не чекає.                                        │
│   Ризик: при збої живлення втрачається те, що в буфері.             │
│                                                                     │
│   Linux використовує відкладений запис за замовчуванням.            │
│   Саме тому існують fsync() і «безпечне витягання».                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Розбір помилкового міркування

> «`write()` повернув успіх — отже, дані на диску.»

Ні. `write()` повертає успіх, коли дані скопійовано в кеш сторінок ядра. На
носій вони потраплять пізніше: фоновий потік раз на 5 секунд
(`dirty_writeback_centisecs`) записує сторінки, брудні довше за 30 секунд
(`dirty_expire_centisecs`), або раніше — коли частка брудних сторінок перевищить
поріг.

```bash
# Скільки даних чекає на запис просто зараз
grep -E "^(Dirty|Writeback)" /proc/meminfo

# Через скільки сотих секунди ядро починає писати брудні сторінки
cat /proc/sys/vm/dirty_expire_centisecs

# За якої частки брудних сторінок процес записування блокується
cat /proc/sys/vm/dirty_ratio
```

Щоб отримати гарантію, потрібен явний примус:

| Спосіб | Що гарантує |
|--------|-------------|
| `fsync(fd)` | дані й метадані цього файлу на носії |
| `fdatasync(fd)` | дані файлу на носії, метадані можуть відстати |
| `open(..., O_SYNC)` | кожен `write` повертається лише після запису на носій |
| `sync` | запуск скидання всіх брудних сторінок системи |

**Чому бази даних такі повільні на дешевих дисках.** Кожна транзакція, що
завершується підтвердженням, зобов'язана викликати `fsync` — інакше обіцянка
«зафіксовано» буде брехнею. Один `fsync` на обертовому диску коштує від 5 до
15 мілісекунд, отже, межа — приблизно 70-200 транзакцій за секунду на одному
потоці, хоч би яким швидким був процесор.

```bash
# Без синхронізації: усе лишається в кеші сторінок
dd if=/dev/zero of=./t1.bin bs=4k count=2000 2>&1 | tail -1
# Один fsync наприкінці (conv=fsync): чесна швидкість запису на носій
dd if=/dev/zero of=./t2.bin bs=4k count=2000 conv=fsync 2>&1 | tail -1
# Синхронізація кожного запису (oflag=dsync) — як «транзакція на кожен блок»
dd if=/dev/zero of=./t3.bin bs=4k count=2000 oflag=dsync 2>&1 | tail -1
rm -f ./t1.bin ./t2.bin ./t3.bin
```

Третій рядок найповільніший у рази: 2000 окремих очікувань на носій проти одного.
Саме так виглядає база даних, яка підтверджує кожну транзакцію окремо, і саме
тому існує групове підтвердження — кілька транзакцій на один `fsync`.

> «Буферизація завжди прискорює роботу.»

Не завжди. Вона додає копіювання й затримку. Там, де програма має власний кеш
(база даних) або де затримка важливіша за пропускну здатність (обмін із
датчиком), буфер ядра шкодить — його вимикають прапорцем `O_DIRECT`. Це той
самий випадок, що й з планувальником `none` для NVMe: прошарок, корисний у
типовому випадку, заважає в спеціальному.

## Три рівні буферів на шляху одного байта

```
┌─────────────────────────────────────────────────────────────────────┐
│            СКІЛЬКИ БУФЕРІВ МІЖ printf І ПЛАСТИНОЮ ДИСКА             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. Буфер бібліотеки (stdio): 4 КіБ у просторі програми            │
│      Скидається при заповненні, \n у термінал або fflush()          │
│                                                                     │
│   2. Кеш сторінок ядра: мегабайти                                   │
│      Скидається фоновим потоком, fsync() або sync                   │
│                                                                     │
│   3. Кеш самого накопичувача: 8-256 МіБ                             │
│      Скидається командою FLUSH CACHE; при збої живлення             │
│      втрачається, якщо немає конденсатора чи батареї                │
│                                                                     │
│   Дані «на диску» лише після проходження ВСІХ трьох.                │
│   Саме тому надійні сервери мають контролери з батареєю.            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Перший рівень легко побачити: вивід у термінал скидається за кожним переходом на
новий рядок, а вивід у файл — лише коли набереться 4 КіБ.

```bash
# У термінал: рядок з'явиться одразу
python3 -c "import sys,time; print('привіт'); time.sleep(2)"

# У файл через конвеєр: буфер більший, тому поведінка інша
python3 -c "import sys,time; print('привіт'); time.sleep(2)" | cat
```

## Практичне завдання

1. Порахуйте кількість системних викликів `write` для двох програм: що пише по
   байту й що пише блоками по 4 КіБ.

```bash
# Без буфера: кожен f.write() — окремий системний виклик write
strace -c -e trace=write python3 -c "
f=open('/tmp/a.bin','wb',buffering=0)
[f.write(b'x') for _ in range(20000)]
f.close()" 2>&1 | tail -4

# Зі звичайним буфером Python (8 КіБ)
strace -c -e trace=write python3 -c "
f=open('/tmp/b.bin','wb')
[f.write(b'x') for _ in range(20000)]
f.close()" 2>&1 | tail -4
rm -f /tmp/a.bin /tmp/b.bin
```

2. Поясніть різницю в кількості викликів через параметр `buffering`. Чому
   рядкова буферизація (`buffering=1` у текстовому режимі) не дала б 20 000
   викликів для рядка без символів нового рядка?
3. Зніміть значення `Dirty` з `/proc/meminfo` до й після копіювання великого
   файлу. Скільки даних чекало на запис у пікові моменти?
4. Виміряйте, у скільки разів `conv=fsync` і `oflag=dsync` уповільнюють запис на вашому носії.

```
│                                                                     │
│   БУФЕР ≠ КЕШ:                                                      │
│   буфер → узгодження передавання, без нього зламається              │
│   кеш   → повторне використання, без нього лише повільніше          │
│                                                                     │
│   ЗАПИС:                                                            │
│   наскрізний  → надійно, повільно                                   │
│   відкладений → швидко, ризик втрати при збої (типово в Linux)      │
│                                                                     │
│   ГАРАНТІЇ:                                                         │
│   fsync()     → дані й метадані файлу на носії                      │
│   fdatasync() → дані файлу на носії                                 │
│   O_SYNC      → кожен write чекає носія                             │
│   O_DIRECT    → обійти кеш сторінок узагалі                         │
│                                                                     │
│   ТРИ РІВНІ БУФЕРІВ: stdio → кеш сторінок → кеш пристрою            │
│                                                                     │
│   КОМАНДИ:                                                          │
│   grep Dirty /proc/meminfo          → скільки чекає на запис        │
│   cat /proc/sys/vm/dirty_ratio      → поріг блокування              │
│   strace -c -e trace=write команда  → скільки викликів write        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Чому запис по одному байту в сотні разів повільніший за запис блоками?

- диск не вміє приймати окремі байти
- ядро шифрує кожен байт окремо
- кожен байт коштує окремого системного виклику
- файлова система створює новий файл на кожен байт

**2.** Навіщо ядро копіює дані з масиву програми у власний буфер?

- щоб перевірити дані на помилки
- щоб стиснути їх перед записом
- щоб порахувати контрольну суму
- бо програма має право змінити свій масив одразу після write()

**3.** У чому перевага подвійної буферизації над одинарною?

- вона гарантує запис на носій
- вона потребує вдвічі менше пам'яті
- одна сторона заповнює буфер, поки друга віддає інший
- вона не потребує системних викликів

**4.** Що рухається в кільцевому буфері під час роботи?

- покажчики запису й читання
- межі буфера
- розмір кожного елемента
- самі дані від початку до кінця

**5.** Чим буфер відрізняється від кеша?

- буфер зберігає дані довше за кеш
- кеш існує лише в процесорі
- буфер узгоджує передавання, кеш зберігає дані для повторного використання
- різниці немає, це синоніми

**6.** Що означає повернення `write()` з успіхом у Linux за замовчуванням?

- дані скопійовано в кеш сторінок, на носій вони потраплять пізніше
- дані поставлено в чергу пристрою
- дані записано й перевірено контрольною сумою
- дані фізично записано на носій

**7.** Який виклик гарантує, що дані та метадані файлу опинилися на носії?

- write()
- fsync()
- sync_file_range()
- flush()

**8.** Чому база даних на обертовому диску обмежена приблизно сотнею транзакцій за секунду в одному потоці?

- кожна транзакція потребує fsync, який коштує 5-15 мс
- процесор не встигає обробляти запити
- файлова система блокує файл журналу
- мережа не пропускає більше запитів

**9.** Скільки рівнів буферів проходить байт від `printf` до пластини диска?

- жодного, якщо файл відкрито на запис
- два: бібліотека та пристрій
- один: тільки кеш ядра
- три: буфер бібліотеки, кеш сторінок, кеш пристрою

**10.** Коли буферизація ядра шкодить?

- коли записує кілька процесів одночасно
- коли програма має власний кеш або коли критична затримка
- коли файл дуже великий
- коли диск твердотільний

## 🎯 Міні-проект (30 хв)

### Завдання: виміряти вартість кожного рівня буферизації

**Кроки:**

1. Порівняйте кількість системних викликів при різних розмірах буфера:

```bash
for b in 1 512 4096 65536; do
  printf "буфер %6s: " "$b"
  strace -c -e trace=write dd if=/dev/zero of=/tmp/t.bin bs=$b count=$((1048576/b))     2>&1 | awk '/write/ {print $4, "викликів"}'
done
rm -f /tmp/t.bin
```

2. Побудуйте таблицю: розмір буфера, кількість викликів, час виконання.

3. Виміряйте вартість гарантії запису:

```bash
time dd if=/dev/zero of=/tmp/t1.bin bs=4k count=5000 2>/dev/null
time dd if=/dev/zero of=/tmp/t2.bin bs=4k count=5000 conv=fsync 2>/dev/null
rm -f /tmp/t1.bin /tmp/t2.bin
```

4. Простежте за брудними сторінками під час копіювання великого файлу:

```bash
(cp /tmp/big.bin /tmp/big2.bin &) ; for i in $(seq 1 10); do
  grep -E "^Dirty" /proc/meminfo; sleep 0.5; done
```

**Очікуваний результат:** кількість викликів падає обернено пропорційно розміру
буфера; `conv=fsync` уповільнює запис у кілька разів; `Dirty` зростає під час
копіювання й повертається до нуля після завершення.

**Бонус (для допитливих):**

- Побудуйте графік «розмір буфера — час виконання» і знайдіть точку, після якої
  збільшення буфера вже не допомагає. Поясніть, чому вона існує.

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Буфер** | Проміжна пам'ять для узгодження швидкості й розміру порцій |
| **Кеш** | Пам'ять для повторного використання вже отриманих даних |
| **Подвійна буферизація** | Дві області: одну заповнюють, другу віддають |
| **Кільцевий буфер** | Область із покажчиками запису й читання, що рухаються по колу |
| **Наскрізний запис** | Дані потрапляють на носій до повернення з `write` |
| **Відкладений запис** | Дані лягають у кеш, на носій потрапляють пізніше |
| **Брудна сторінка** | Змінена сторінка кеша, ще не записана на носій |
| **fsync** | Примусове скидання даних і метаданих файлу на носій |

**Ключовий висновок:** буферизація — це обмін надійності та затримки на
пропускну здатність. Вона майже завжди вигідна, тому ввімкнена за
замовчуванням, але саме вона робить твердження «файл збережено» неточним. Той,
хто пише системи, де втрата даних неприпустима, зобов'язаний знати, на якому
саме рівні зараз лежать його байти.

На наступній лекції — як керування пристроями влаштоване у Windows і Linux:
від моделі драйверів до гарячого підключення.
