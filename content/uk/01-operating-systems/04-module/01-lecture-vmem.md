## Дві програми за однією адресою

Запустіть ту саму програму двічі й подивіться, за якими адресами лежать її код і
дані. Спершу — з вимкненою рандомізацією адрес:

```bash
# setarch -R вимикає ASLR для однієї команди: два різні процеси,
# а адреси сегментів — байт у байт однакові
setarch "$(uname -m)" -R cat /proc/self/maps | head -3
setarch "$(uname -m)" -R cat /proc/self/maps | head -3

# Тепер як зазвичай: адреси щоразу інші
cat /proc/self/maps | head -3
cat /proc/self/maps | head -3
```

Перший дослід дивний: два процеси одночасно можуть користуватися тією самою
адресою `0x555555554000`, і кожен бачить там власні байти. Пояснення в тому, що
адреса, яку бачить програма, **не є адресою в мікросхемі пам'яті**. Це
віртуальна адреса, і між нею та фізичною коміркою стоїть апаратний перекладач.
Другий дослід показує, що ядро ще й навмисно щоразу розкладає сегменти по-новому
(ASLR — Address Space Layout Randomization): зловмисник, який знайшов вразливість,
не знає наперед, за якою адресою лежить потрібний йому код.

**Запитання до аудиторії**: якби програми працювали з фізичними адресами
напряму, що сталося б, якби дві з них вирішили використати ту саму адресу?

## Три задачі, які розв'язує віртуальна пам'ять

```
┌─────────────────────────────────────────────────────────────────────┐
│                  НАВІЩО ВЗАГАЛІ ПОТРІБЕН ПРОШАРОК                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. РОЗМІЩЕННЯ (relocation)                                        │

│      Без трансляції довелося б правити всі адреси при запуску.      │

│      Процес не може звернутися туди, чого немає в його              │

│      а не довірою до програміста.                                   │
│                                                                     │
│   3. ЄМНІСТЬ (capacity)                                             │
│      Сумарний обсяг процесів може перевищувати фізичну              │

│                                                                     │
│   Плюс побічні вигоди: спільні бібліотеки в одному                  │
│   екземплярі, копіювання при записі, випадкове розміщення           │

│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

```
│     висока адреса                                                   │
│     ┌──────────────────────────────┐                                │

│     ├──────────────────────────────┤                                │
│     │  стек                        │  росте вниз ▼                  │
│     │            │                 │                                │
│     │            ▼                 │                                │
│     │                              │                                │
│     │  (незайнятий простір)        │                                │
│     │                              │                                │
│     │            ▲                 │                                │
│     │            │                 │                                │
│     │  бібліотеки, mmap            │  0x00007F…: libc, ld.so,       │
│     │                              │  файли, великі malloc()        │
│     │                              │                                │
│     │            ▲                 │                                │
│     │  купа (heap)                 │  росте вгору ▲                 │
│     ├──────────────────────────────┤                                │
│     │  .bss   — неініціалізовані   │                                │
│     │  .data  — ініціалізовані     │                                │
│     │  .text  — код (лише читання) │  0x0000555555555000 (без ASLR) │
│     └──────────────────────────────┘                                │
│     низька адреса                                                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

```bash
# Реальна карта процесу: адреси, права, файл, з якого спроєктовано сторінки
cat /proc/self/maps

# Скільки пам'яті процес справді займає у фізичній пам'яті
grep -E "^(VmSize|VmRSS|VmData|VmStk|VmExe)" /proc/self/status
```

Різниця між `VmSize` і `VmRSS` — перше, що варто показати студентам: процес може
«займати» гігабайти віртуального простору, маючи в фізичній пам'яті десятки
мегабайтів. Віртуальний простір — це обіцянка, фізична пам'ять — виконання
обіцянки за фактом звернення.

## Сторінкова організація

Простір ділять на **сторінки** сталого розміру, фізичну пам'ять — на **кадри**
такого самого розміру. Типовий розмір — 4 КіБ.

```
┌─────────────────────────────────────────────────────────────────────┐
│         ТРАНСЛЯЦІЯ АДРЕСИ: 4 КіБ СТОРІНКА, 32-БІТНА АДРЕСА          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     Віртуальна адреса 0x00403ABC                                    │
│     ┌────────────────────────┬──────────────┐                       │
│     │  номер сторінки  0x403 │ зсув  0xABC  │                       │
│     │      20 біт            │   12 біт     │                       │
│     └───────────┬────────────┴───────┬──────┘                       │
│                 │                    │                              │
│                 ▼                    │                              │
│        ┌─────────────────┐           │                              │
│        │ таблиця сторінок│           │                              │
│        │  0x403 → 0x1A2  │           │                              │
│        └────────┬────────┘           │                              │
│                 ▼                    ▼                              │
│     ┌────────────────────────┬──────────────┐                       │
│     │   номер кадру  0x1A2   │ зсув  0xABC  │                       │
│     └────────────────────────┴──────────────┘                       │
│     Фізична адреса 0x1A2ABC                                         │
│                                                                     │
│     Зсув НЕ транслюється — він однаковий у сторінці й кадрі.        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Чому розмір сторінки — степінь двійки.** Тоді розділення адреси на номер і зсув
не потребує ділення: номер — це старші біти, зсув — молодші. Апаратно це просто
розрізання шини, тобто нуль тактів. Якби сторінка мала, скажімо, 5000 байтів,
кожне звернення до пам'яті потребувало б ділення — і трансляція стала б
дорожчою за саме звернення.

**Порахуймо разом**, чому сторінка не може бути надто малою. 32-бітна адреса,
сторінка 4 КіБ:

```
кількість сторінок = 2³² / 2¹² = 2²⁰ = 1 048 576
розмір запису таблиці ≈ 4 байти
розмір таблиці сторінок = 2²⁰ × 4 = 4 МіБ НА КОЖЕН ПРОЦЕС
```

Сто процесів — 400 МіБ таблиць, і це ще до того, як програми щось порахували.
Якби сторінка була 512 байтів, таблиці зайняли б у вісім разів більше.

лише ті частини, які справді використовуються.

```
┌─────────────────────────────────────────────────────────────────────┐
│         ЧОТИРИРІВНЕВА ТРАНСЛЯЦІЯ (x86-64, 48-БІТНА АДРЕСА)          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│     47      39 38      30 29      21 20      12 11        0         │
│     ┌─────────┬──────────┬──────────┬──────────┬──────────┐         │
│     │  PML4   │   PDPT   │    PD    │    PT    │   зсув   │         │
│     │  9 біт  │  9 біт   │  9 біт   │  9 біт   │  12 біт  │         │
│     └────┬────┴────┬─────┴────┬─────┴────┬─────┴──────────┘         │
│          │         │          │          │                          │
│          ▼         ▼          ▼          ▼                          │
│       таблиця → таблиця → таблиця → таблиця → кадр                  │
│       рівня 4   рівня 3   рівня 2   рівня 1                         │
│                                                                     │
│     Кожна таблиця має 2⁹ = 512 записів по 8 байтів = 4 КіБ,         │
│     тобто рівно одну сторінку. Це не збіг, а вимога дизайну.        │
│                                                                     │
│     ЦІНА: чотири звернення до пам'яті замість одного.               │
│     РЯТУЄ: TLB.                                                     │
│                                                                     │
│     48 біт — це 256 ТіБ віртуального простору. Серверам цього       │
│     стало мало: процесори Intel з 2019 року (Ice Lake) підтримують  │
│     п'ятий рівень таблиць (LA57) і 57-бітні адреси — 128 ПіБ.       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## TLB: кеш трансляцій

**TLB** (Translation Lookaside Buffer) зберігає кілька десятків або сотень
нещодавніх пар «сторінка → кадр» прямо в процесорі.

**Порахуймо вигоду.** Звернення до TLB — 1 нс, до пам'яті — 100 нс. Обчислимо
середній час доступу для однорівневої таблиці:

```
Влучання в TLB (99 %):  1 + 100 = 101 нс
Промах (1 %):           1 + 100 (таблиця) + 100 (дані) = 201 нс

Середній час = 0,99 × 101 + 0,01 × 201 = 102,0 нс
Втрати проти ідеальних 100 нс: 2 %
```

А тепер погіршимо влучність до 90 %:

```
Середній час = 0,90 × 101 + 0,10 × 201 = 111,0 нс
Втрати: 11 %
```

Дев'ять відсотків влучності коштували п'ять разів більших втрат. Звідси
практичний висновок, який стосується будь-якого програміста: **послідовний обхід
масиву працює швидше за випадковий не лише через кеш даних, а й через TLB**.

```bash
# Скільки промахів TLB дає конкретна програма
# perf stat -e dTLB-load-misses,dTLB-loads ./програма

# Великі сторінки (2 МіБ) зменшують кількість записів у TLB у 512 разів
cat /sys/kernel/mm/transparent_hugepage/enabled
```

## Сторінкова відмова

Якщо в записі таблиці сторінка позначена як відсутня, процесор збуджує виняток —
**сторінкову відмову** (page fault). Це не помилка: так працює підвантаження за
потребою.

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ОБРОБКА СТОРІНКОВОЇ ВІДМОВИ                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   1. Процесор виявляє, що біт присутності = 0 → виняток             │
│   2. Ядро визначає причину звернення:                               │
│      • адреса взагалі не належить процесу → SIGSEGV                 │
│      • сторінка є, але вивантажена на диск → підкачати              │
│      • сторінка ще не виділялася (перший дотик) → виділити          │
│      • запис у сторінку «копіювання при записі» → скопіювати        │
│   3. Процес переводять у стан очікування                            │
│   4. Ядро читає сторінку з диска (мілісекунди)                      │
│   5. Оновлює таблицю сторінок (і скидає застарілий запис TLB,       │
│      якщо сторінка була присутня, як у копіюванні при записі)       │
│   6. Процес стає готовим і ПОВТОРЮЄ ту саму інструкцію              │
│                                                                     │
│   Крок 6 і робить відмову різновидом Fault, а не Trap:              │
│   інструкція виконується заново, ніби нічого не сталося.            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### Чому одна відмова на 500 тисяч звернень — це вже багато

Звернення до пам'яті — 100 нс, читання сторінки з диска — 5 мс, тобто
5 000 000 нс, у 50 тисяч разів довше. Нехай `p` — частка звернень, що
спричиняють відмову:

```
середній час = (1 − p) × 100 + p × 5 000 000

Щоб уповільнення не перевищило 10 % (110 нс):
p × 4 999 900 = 10  →  p ≈ 2 × 10⁻⁶

Це одна відмова приблизно на 500 000 звернень до пам'яті.
```

**Цей розрахунок варто провести на дошці повністю.** Він пояснює, чому підкачка
з диска суб'єктивно «вбиває» систему: досить мізерної частки відмов, щоб
продуктивність упала вдвічі. І він же пояснює, чому перехід на SSD (0,1 мс
замість 5 мс) так помітно рятує машину з малим обсягом пам'яті.

```bash
# Скільки відмов дала програма: minor — без диска, major — з диском
/usr/bin/time -v ls 2>&1 | grep -E "page faults"

# Відмови конкретного процесу: поля 10 (minflt) і 12 (majflt) у /proc/PID/stat
awk '{print "minor:", $10, "major:", $12}' /proc/self/stat
ps -o pid,min_flt,maj_flt,comm -p $$
```

Розрізняти дрібні (minor) і серйозні (major) відмови обов'язково: перші
обходяться сотнями наносекунд (сторінка вже в пам'яті, треба лише оновити
таблицю), другі — мілісекундами, бо потребують диска.

```
┌─────────────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ДО ЗАПИСУ                        ПІСЛЯ ЗАПИСУ В СТОРІНКУ          │
│                                                                     │
│   батько ──┐                       батько ──► [копія 1]             │
│            ├──► [спільна сторінка]                                  │
```

### Розбір помилкового міркування

> «Процес займає 4 ГіБ віртуальної пам'яті — отже, йому потрібно 4 ГіБ RAM.»

Ні. Віртуальний розмір (`VmSize`) — це сума всіх відображень, зокрема:

- ділянок, у які жодного разу не записували (фізичної пам'яті ще не виділено);
- файлів, спроєктованих у пам'ять (лежать на диску, у пам'яті — лише прочитані частини);
- спільних бібліотек, які в фізичній пам'яті існують в одному екземплярі на всю систему.

Реальне споживання показує `VmRSS`, та й воно завищує внесок процесу, бо
враховує спільні сторінки повністю. Ось чому сума `RSS` усіх процесів зазвичай
перевищує обсяг установленої пам'яті — і це не помилка обліку.

```bash
# Порівняйте три числа для того самого процесу
grep -E "^(VmSize|VmRSS|RssAnon|RssFile|RssShmem)" /proc/self/status
```

> «Якщо збільшити розмір сторінки, все стане швидше.»

Частково правда, і саме тому існують великі сторінки (2 МіБ, 1 ГіБ): менше
записів у таблицях, вища влучність TLB. Але плата — **внутрішня фрагментація**:
програмі, якій потрібно 5 КіБ, при сторінці 2 МіБ доведеться віддати цілі 2 МіБ,
з яких 1,995 МіБ пропаде. Тому великі сторінки вмикають для баз даних і
віртуальних машин, а не для всієї системи підряд.

```
│                                                                     │
│   КОНТЕЙНЕРИ                                                        │
│   ├── Ліміт пам'яті cgroups рахує саме фізичні сторінки             │
│   └── Перевищив ліміт — контейнер завершує OOM killer               │
│                                                                     │
│   БЕЗПЕКА                                                           │
│   ├── ASLR щоразу зсуває сегменти: адреса, підібрана                │
│   │   зловмисником учора, сьогодні не працює                        │
```

### Завдання: побачити віртуальну пам'ять власними очима

**Кроки:**

1. Виділіть гігабайт пам'яті, не торкаючись його, і подивіться на різницю між
   віртуальним і фізичним розміром. Використовуємо `mmap`, а не `bytearray`:
   `bytearray` одразу заповнює пам'ять нулями й тим самим торкається кожної
   сторінки.

```bash
python3 - <<'EOF'
import mmap, os
buf = mmap.mmap(-1, 1024 * 1024 * 1024)   # 1 ГіБ анонімної пам'яті, ще не «торкнутої»
pid = os.getpid()
def show(tag):
    with open(f"/proc/{pid}/status") as f:
        vals = {k: v for k, v in (l.split(":", 1) for l in f if l.startswith("Vm"))}
    print(tag, "VmSize:", vals["VmSize"].strip(), "| VmRSS:", vals["VmRSS"].strip())
show("після виділення")
for i in range(0, len(buf), 4096):      # торкаємося кожної сторінки
    buf[i] = 1
show("після запису    ")
EOF
```

2. Поясніть, чому `VmRSS` після виділення значно менший за `VmSize`, а після
   запису зрівнявся з ним.

3. Подивіться кількість дрібних відмов, які спричинив цей запис:

```bash
/usr/bin/time -v python3 -c "b=bytearray(256*1024*1024); b[::4096]=b'\x01'*(len(b)//4096)" 2>&1 | grep -i "page faults"
```

4. Порівняйте отриману кількість дрібних відмов із теоретичною: скільки сторінок
   по 4 КіБ міститься в 256 МіБ?

**Очікуваний результат:** кількість дрібних відмов буде близькою до 65 536 —
саме стільки сторінок у 256 МіБ.

**Бонус (для допитливих):**

- Подивіться режим великих сторінок (`cat /sys/kernel/mm/transparent_hugepage/enabled`).
  Якщо він `always`, кількість відмов буде в сотні разів меншою: одна відмова

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Віртуальна адреса** | Адреса, якою оперує програма; транслюється апаратно |
| **Сторінка / кадр** | Блок віртуального / фізичного простору сталого розміру, зазвичай 4 КіБ |
| **Таблиця сторінок** | Відповідність «номер сторінки → номер кадру» для процесу |
| **TLB** | Апаратний кеш нещодавніх трансляцій |
| **Сторінкова відмова** | Виняток при зверненні до відсутньої сторінки; інструкція повторюється |
| **Дрібна / серйозна відмова** | Без звернення до диска / зі зверненням до диска |
| **Копіювання при записі** | Спільна сторінка копіюється лише тоді, коли в неї записують |
| **VmSize / VmRSS** | Обсяг відображеного простору / обсяг у фізичній пам'яті |

**Ключовий висновок:** віртуальна пам'ять — це не «більше пам'яті, ніж є», а
прошарок непрямої адресації. Саме непрямість дає і захист, і спільні бібліотеки,
і копіювання при записі, і підвантаження за потребою. Ціна прошарку — трансляція
на кожному зверненні, і вся інженерія тут зводиться до того, щоб цю ціну
приховати: TLB, багаторівневі таблиці, великі сторінки.

На наступній лекції — алгоритми виділення пам'яті та заміщення сторінок: як ОС
вирішує, що саме вивантажити, коли пам'яті бракує.
