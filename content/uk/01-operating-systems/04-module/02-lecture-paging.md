## Додали пам'яті — стало гірше

1969 рік, Ласло Біледі з IBM показує результат, який суперечить здоровому глузду:
система з **чотирма** кадрами пам'яті дає більше сторінкових відмов, ніж та сама
система з **трьома**. Не в середньому, не приблизно — на конкретному рядку
звернень, який можна перевірити за хвилину.

У цій темі ми порахуємо цей приклад самі, а заразом розберемо, як ОС виділяє
пам'ять і як обирає, що саме вивантажити, коли її бракує.

**Запитання до аудиторії**: якщо збільшення обсягу пам'яті може погіршити
результат, чи має сенс порада «просто додай оперативної пам'яті»?

## Частина перша: виділення пам'яті

### Стратегії розміщення

Коли є кілька вільних ділянок різного розміру, а запит один, постає питання:
у яку саме ділянку покласти?

```
┌─────────────────────────────────────────────────────────────────────┐
│                       ТРИ КЛАСИЧНІ СТРАТЕГІЇ                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ПЕРША ПРИДАТНА (first fit)                                        │
│   Беремо першу ділянку, у яку запит уміщується.                     │
│   Швидко: пошук завершується на першому влучанні.                   │
│                                                                     │
│   НАЙКРАЩА ПРИДАТНА (best fit)                                      │
│   Беремо найменшу з достатніх ділянок.                              │
│   Ощадно за площею, але лишає багато дрібних «уламків».             │
│                                                                     │
│   НАЙГІРША ПРИДАТНА (worst fit)                                     │
│   Беремо найбільшу ділянку.                                         │
│   Ідея: залишок буде великим і ще на щось згодиться.                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Перевіримо на числах.** Вільні ділянки: 100, 500, 200, 300, 600 КіБ.
Послідовність запитів: 212, 417, 112, 426 КіБ.

Таблиця 1 — Результат трьох стратегій на однакових даних

| Запит | Перша придатна | Найкраща придатна | Найгірша придатна |
|-------|----------------|-------------------|-------------------|
| 212 | ділянка 500 | ділянка 300 | ділянка 600 |
| 417 | ділянка 600 | ділянка 500 | ділянка 500 |
| 112 | залишок 288 | ділянка 200 | залишок 388 |
| 426 | **не вміщується** | ділянка 600 | **не вміщується** |

Два висновки, які варто підкреслити:

1. **Найкраща придатна** — єдина, що розмістила всі чотири запити. Це не загальне
   правило, а результат саме цих даних: змініть порядок запитів, і картина
   зміниться.
2. Дві інші стратегії зазнали невдачі попри те, що **сумарно вільної пам'яті
   вистачало**: після третього кроку вільно 100 + 176 + 200 + 300 + 183 = 959 КіБ
   при запиті на 426 КіБ. Пам'ять є, але вона роздроблена.

### Дві фрагментації

```
┌─────────────────────────────────────────────────────────────────────┐
│                 ЗОВНІШНЯ ТА ВНУТРІШНЯ ФРАГМЕНТАЦІЯ                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ЗОВНІШНЯ (стан «першої придатної» після трьох запитів)            │
│   [100][зайн.][176][зайн.][200][300][зайн.][183]                    │
│   Вільно 959 КіБ, але суцільного шматка на 426 КіБ немає.           │
│   Лікується ущільненням або сторінковою організацією.               │
│                                                                     │
│   ВНУТРІШНЯ                                                         │
│   Запит 5000 Б при сторінці 4096 Б → виділено 2 сторінки            │
│   [██████████████████████████░░░░░░░░░]                             │
│    5000 Б корисних        3192 Б марно = 39 %                       │
│   Лікується зменшенням одиниці виділення.                           │
│                                                                     │
│   Два лікування суперечать одне одному: дрібніша одиниця            │
│   зменшує внутрішню фрагментацію й збільшує накладні                │
│   витрати на облік.                                                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Головне спостереження цієї частини.** Сторінкова організація не «прибирає
фрагментацію», а **міняє зовнішню на внутрішню**. Зовнішня небезпечніша: вона
призводить до відмови у виділенні при формально достатньому обсязі. Внутрішня
лише марнує частку пам'яті, і цю частку можна оцінити наперед: у середньому
півсторінки на кожне виділення.

### Як це влаштовано в Linux

| Механізм | Одиниця | Для чого | Фрагментація |
|----------|---------|----------|--------------|
| Buddy allocator | степені двійки: 4 КіБ … 4 МіБ | Виділення сторінок ядру | Внутрішня до 50 % |
| Slab / SLUB | об'єкти сталого розміру | Структури ядра: inode, dentry | Майже немає |
| `malloc` (glibc) | довільний розмір | Купа процесу | Обидві потроху |

**Чому buddy дає до 50 % втрат.** Він видає лише блоки розміром 2ⁿ сторінок.
Запит на 66 КіБ отримає блок 128 КіБ: 62 КіБ, тобто 48 %, пропаде. Натомість
злиття й поділ блоків роблять пошук майже миттєвим, а зовнішню фрагментацію —
контрольованою. Саме тому поверх buddy працює slab: він бере в buddy великі
блоки й нарізає їх на об'єкти потрібного розміру.

```bash
# Стан buddy-алокатора: скільки вільних блоків кожного розміру
cat /proc/buddyinfo

# Кеші slab: скільки об'єктів і скільки пам'яті вони займають
sudo head -5 /proc/slabinfo 2>/dev/null || echo "потрібні права root"
```

## Частина друга: заміщення сторінок

Пам'ять скінченна. Коли вільних кадрів немає, а сторінку треба підкачати, ОС
мусить щось витіснити. Питання «що саме» і є задачею заміщення.

Усі розрахунки нижче зроблено на одному рядку звернень:

```
7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1
```

### Чотири алгоритми

```
┌─────────────────────────────────────────────────────────────────────┐
│                         АЛГОРИТМИ ЗАМІЩЕННЯ                         │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   FIFO — витісняємо ту, що зайшла найраніше                         │
│   Просто. Не враховує, що сторінка може бути потрібною              │
│   постійно.                                                         │
│                                                                     │
│   OPT — витісняємо ту, яка знадобиться найпізніше                   │
│   Оптимальний алгоритм. Нездійсненний: потребує знання              │
│   майбутнього. Потрібен як ЕТАЛОН для порівняння.                   │
│                                                                     │
│   LRU — витісняємо ту, до якої найдовше не зверталися               │
│   Наближення OPT «дзеркальним» міркуванням: минуле                  │
│   схоже на майбутнє.                                                │
│                                                                     │
│   CLOCK — наближення LRU через біт звернення                        │
│   Сторінки по колу; біт = 1 → скидаємо й ідемо далі,                │
│   біт = 0 → витісняємо. Дешевий у реалізації.                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

Таблиця 2 — Кількість сторінкових відмов на рядку з 20 звернень

| Кадрів | FIFO | LRU | OPT | Clock |
|--------|------|-----|-----|-------|
| 3 | 15 | 12 | 9 | 14 |
| 4 | 10 | 8 | 8 | 9 |

Числа отримано симулятором, код якого наведено наприкінці теми.

**Що з цієї таблиці випливає:**

- OPT недосяжний, але він дає межу: краще за 9 відмов на трьох кадрах не буде
  жодним алгоритмом. Якщо ваш алгоритм дає 12, ви знаєте, що резерв — три
  відмови, а не «можливо, ще багато».
- LRU ближчий до OPT, ніж FIFO, — на трьох кадрах різниця 12 проти 15.
- Clock майже наздоганяє LRU (14 проти 12) за значно меншу ціну реалізації. Саме
  тому реальні ядра використовують варіації Clock, а не чистий LRU.

### Чому чистий LRU не реалізують

| Спосіб реалізації | Ціна |
|-------------------|------|
| Лічильник часу в кожному записі таблиці | Запис у пам'ять на **кожне** звернення |
| Стек сторінок із переміщенням наверх | Переміщення вузла списку на кожне звернення |
| Апаратна підтримка | Потрібні транзистори, яких у процесорах немає |

Звернення до пам'яті відбуваються мільярди разів на секунду. Додати до кожного
запис лічильника — означає подвоїти трафік до пам'яті. Тому апаратура дає лише
**один біт** (звернення відбулося / не відбулося), а ядро будує на ньому
наближення — Clock, він же «другий шанс».

Linux довго використовував саме таке наближення з двома списками — активних і
неактивних сторінок. З версії 6.1 (2022) з'явився **MGLRU** (Multi-Gen LRU,
розробка Google): сторінки розкладаються на кілька «поколінь» за давністю
звернення, а біти звернення збираються обходом таблиць сторінок пачками. На
ChromeOS і Android це помітно зменшило кількість завершених через брак пам'яті
програм; у Fedora й Arch MGLRU увімкнено за замовчуванням.

```bash
cat /sys/kernel/mm/lru_gen/enabled 2>/dev/null   # ненульове значення — MGLRU увімкнено
```

### Аномалія Біледі

```
┌─────────────────────────────────────────────────────────────────────┐
│           АНОМАЛІЯ БІЛЕДІ: БІЛЬШЕ ПАМ'ЯТІ — БІЛЬШЕ ВІДМОВ           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Рядок звернень: 1 2 3 4 1 2 5 1 2 3 4 5                           │
│                                                                     │
│   Алгоритм   3 кадри   4 кадри                                      │
│   ────────   ───────   ───────                                      │
│   FIFO          9        10      ← додали кадр, стало ГІРШЕ         │
│   LRU          10         8                                         │
│   OPT           7         6                                         │
│                                                                     │
│   FIFO не має властивості вкладеності: набір сторінок при           │
│   трьох кадрах НЕ є підмножиною набору при чотирьох.                │
│   LRU і OPT таку властивість мають, тому для них аномалія           │
│   неможлива — це доведено.                                          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Як це пояснювати.** FIFO витісняє за віком запису, а не за корисністю. З
чотирма кадрами сторінка затримується довше, і момент її витіснення зсувається —
інколи рівно на той крок, де вона знову знадобиться. Алгоритми зі стековою
властивістю (LRU, OPT) від цього захищені: якщо сторінка була б у пам'яті при
трьох кадрах, вона напевно там буде й при чотирьох.

Зверніть увагу на другий рядок таблиці: **на трьох кадрах LRU (10) гірший за
FIFO (9)**. Це корисний факт для дискусії: «кращий алгоритм» — твердження про
поведінку в середньому, а не про кожен окремий рядок звернень.

## Робочий набір і пробуксовка

```
┌─────────────────────────────────────────────────────────────────────┐
│                       ПРОБУКСОВКА (THRASHING)                       │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   Процесів багато, кадрів мало:                                     │
│                                                                     │
│   процес A витісняє сторінку процесу B                              │
│          │                                                          │
│          ▼                                                          │
│   B звертається до неї → відмова → підкачує назад,                  │
│   витісняючи сторінку процесу C                                     │
│          │                                                          │
│          ▼                                                          │
│   C звертається до своєї → відмова → …                              │
│                                                                     │
│   Завантаження процесора падає (усі чекають на диск),               │
│   планувальник бачить простій і впускає ще процеси,                 │
│   від чого стає ще гірше. Система «стоїть», хоча                    │
│   процесор майже вільний.                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Робочий набір** `W(t, Δ)` — множина сторінок, до яких процес звертався за
останній проміжок Δ. Правило просте: якщо сума робочих наборів усіх процесів
перевищує кількість кадрів, пробуксовка неминуча.

```
Σ |W(tᵢ, Δ)| > кількість кадрів  →  пробуксовка
```

Саме тому лікування пробуксовки — не «прискорити диск», а **зменшити кількість
одночасних процесів**: середньостроковий планувальник вивантажує когось цілком,
щоб решта вмістилася.

```bash
# Ознаки пробуксовки: si/so (swap in/out) стабільно ненульові,
# wa (очікування вводу-виводу) високе, us+sy низькі
vmstat 1 10

# Скільки серйозних відмов дають найактивніші процеси
ps -eo pid,comm,maj_flt --sort=-maj_flt | head -10

# Наскільки охоче ядро вивантажує сторінки (0-200, типово 60)
cat /proc/sys/vm/swappiness
```

### Розбір помилкових міркувань

> «LRU завжди кращий за FIFO.»

Наша ж таблиця це спростовує: на рядку аномалії при трьох кадрах LRU дає 10
відмов, FIFO — 9. LRU кращий **у середньому на типових навантаженнях**, бо
спирається на локальність звернень. Там, де локальності немає (наприклад,
циклічний обхід масиву, більшого за пам'ять), LRU вироджується в найгірший
можливий варіант: він витісняє рівно ту сторінку, яка знадобиться наступною.

### Стиснення замість диска: zram і zswap

Сучасні системи часто вивантажують сторінки не на диск, а **в стиснену ділянку
тієї самої оперативної пам'яті**. Стиснення сторінки займає мікросекунди, а не
мілісекунди, як читання з диска, і типові дані стискаються в 2-4 рази.

| Механізм | Як працює | Де за замовчуванням |
|----------|-----------|---------------------|
| **zram** | Блочний пристрій у пам'яті зі стисненням, на який іде swap | Fedora з версії 33, Android, ChromeOS |
| **zswap** | Стиснений кеш перед звичайним swap на диску | Частина дистрибутивів, серверні налаштування |
| **Стиснення пам'яті** | Той самий принцип у ядрі XNU | macOS, iOS |
| **Memory compression** | Стиснені сторінки в процесі «Memory Compression» | Windows 10 і 11 |

```bash
swapon --show            # чи є пристрій /dev/zram0 серед swap
zramctl 2>/dev/null      # скільки даних стиснено і в скільки разів
```

> «Вимкнути swap — і система працюватиме швидше.»

Іноді так, але наслідок інший, ніж очікують. Без swap ядро не має куди подіти
анонімні сторінки, тож єдиний спосіб звільнити пам'ять — витісняти сторінки
файлового кеша й коду програм. Результат: замість повільної підкачки ви
отримуєте постійне перечитування виконуваних файлів із диска, а при вичерпанні
пам'яті — OOM killer замість гальмування. Правильне формулювання: swap не
сповільнює систему, він **робить видимим** брак пам'яті, який інакше виявився б
аварійним завершенням процесу.

## Симулятор для самостійних експериментів

```python
# Симулятор заміщення сторінок: FIFO, LRU, OPT, Clock
REFS = [7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1]


def fifo(refs, frames):
    mem, queue, faults = set(), [], 0
    for page in refs:
        if page in mem:
            continue
        faults += 1
        if len(mem) == frames:
            old = queue.pop(0); mem.remove(old)
        mem.add(page); queue.append(page)
    return faults


def lru(refs, frames):
    mem, faults = [], 0
    for page in refs:
        if page in mem:
            mem.remove(page); mem.append(page); continue
        faults += 1
        if len(mem) == frames:
            mem.pop(0)
        mem.append(page)
    return faults


def opt(refs, frames):
    mem, faults = [], 0
    for i, page in enumerate(refs):
        if page in mem:
            continue
        faults += 1
        if len(mem) == frames:
            future = []
            for m in mem:
                future.append(refs.index(m, i) if m in refs[i:] else 10 ** 9)
            mem.pop(future.index(max(future)))
        mem.append(page)
    return faults


def clock(refs, frames):
    mem = [None] * frames
    used = [False] * frames
    hand, faults = 0, 0
    for page in refs:
        if page in mem:
            used[mem.index(page)] = True
            continue
        faults += 1
        while True:
            if mem[hand] is None or not used[hand]:
                mem[hand] = page; used[hand] = True
                hand = (hand + 1) % frames
                break
            used[hand] = False
            hand = (hand + 1) % frames
    return faults


print("Рядок звернень:", " ".join(map(str, REFS)))
print("кадрів   FIFO   LRU   OPT   Clock")
for f in (3, 4):
    print("  %d      %3d   %3d   %3d    %3d" % (f, fifo(REFS, f), lru(REFS, f),
                                                opt(REFS, f), clock(REFS, f)))

ANOMALY = [1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5]
print()
print("Аномалія Біледі, рядок:", " ".join(map(str, ANOMALY)))
for f in (3, 4):
    print("  FIFO, %d кадри: %d відмов | LRU: %d | OPT: %d"
          % (f, fifo(ANOMALY, f), lru(ANOMALY, f), opt(ANOMALY, f)))
```

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Яка стратегія розміщення обирає найменшу з достатніх вільних ділянок?

- найгірша придатна
- перша придатна
- випадкова
- найкраща придатна

**2.** Що таке зовнішня фрагментація?

- процесу видали більше пам'яті, ніж він просив
- таблиця сторінок не вміщується в кеш
- вільної пам'яті достатньо, але суцільного шматка потрібного розміру немає
- пам'ять вивантажено на диск

**3.** Запит на 5000 байтів при сторінці 4096 байтів. Скільки пам'яті пропаде?

- нічого не пропаде
- 904 байти
- 3192 байти
- 1000 байтів

**4.** Чому buddy-алокатор дає до 50 % внутрішньої фрагментації?

- він резервує половину пам'яті для ядра
- він працює лише з великими сторінками
- він видає лише блоки розміром 2ⁿ сторінок
- він не вміє звільняти пам'ять

**5.** Навіщо потрібен оптимальний алгоритм OPT, якщо його неможливо реалізувати?

- він працює, якщо відомий розмір робочого набору
- він дає межу, з якою порівнюють реальні алгоритми
- він застосовується у вбудованих системах
- він використовується в системах реального часу

**6.** Чому чистий LRU не реалізують апаратно?

- він потребує знання майбутнього
- він несумісний зі сторінковою організацією
- він дає гірші результати за FIFO
- довелося б оновлювати лічильник на кожне звернення до пам'яті

**7.** На чому ґрунтується алгоритм Clock?

- на точному часі останнього звернення
- на розмірі процесу
- на порядку завантаження сторінок
- на одному біті звернення, який виставляє апаратура

**8.** У чому полягає аномалія Біледі?

- сторінка витісняється двічі поспіль
- збільшення кількості кадрів збільшує кількість відмов у FIFO
- LRU працює повільніше за FIFO
- таблиця сторінок переповнюється

**9.** Чому аномалія Біледі неможлива для LRU?

- він має стекову властивість: набір при меншій кількості кадрів є підмножиною більшого
- він завжди витісняє найстарішу сторінку
- він зберігає час звернення з точністю до наносекунд
- він працює лише з фіксованою кількістю кадрів

**10.** Як лікують пробуксовку?

- зменшують кількість одночасно виконуваних процесів
- підвищують пріоритет усіх процесів
- вимикають підкачку повністю
- збільшують розмір кванта часу

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Перша / найкраща / найгірша придатна** | Стратегії вибору вільної ділянки під запит |
| **Зовнішня фрагментація** | Вільної пам'яті досить, суцільного шматка немає |
| **Внутрішня фрагментація** | Видано більше, ніж запитано, через сталу одиницю виділення |
| **Buddy allocator** | Блоки розміром 2ⁿ сторінок; швидкий поділ і злиття |
| **Slab / SLUB** | Кеш об'єктів сталого розміру поверх buddy |
| **FIFO / LRU / OPT / Clock** | Алгоритми заміщення сторінок |
| **Аномалія Біледі** | Більше кадрів — більше відмов; можлива для FIFO |
| **Робочий набір** | Сторінки, потрібні процесу за останній проміжок часу |
| **Пробуксовка** | Система витрачає час на підкачку замість обчислень |

| Алгоритм | 3 кадри | 4 кадри | Реалізовність |
|----------|---------|---------|---------------|
| FIFO | 15 | 10 | тривіальна |
| LRU | 12 | 8 | дорога |
| OPT | 9 | 8 | неможлива |
| Clock | 14 | 9 | дешева, використовується насправді |

**Ключовий висновок:** у керуванні пам'яттю не буває безкоштовних рішень.
Сторінки міняють зовнішню фрагментацію на внутрішню; buddy міняє точність на
швидкість; Clock міняє якість рішення на вартість реалізації. Інженерна робота
полягає не в пошуку «найкращого» механізму, а у виборі того, чия ціна прийнятна
для конкретної системи.

Наступний модуль — управління пристроями: як ОС працює з тим, що повільніше за
пам'ять у тисячі разів.
