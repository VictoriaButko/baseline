## Як комп'ютер встигає робити все одночасно?

Відкрийте диспетчер задач або htop прямо зараз. Скільки процесів ви бачите? 200? 400? Можливо, навіть 500? А тепер порахуйте ядра вашого процесора: 4, 8, може 16. Як 500 процесів виконуються на 8 ядрах "одночасно"?

Відповідь криється в механізмі, який виконується **тисячі разів на секунду** на кожному ядрі вашого процесора прямо зараз, поки ви читаєте цей текст. Цей механізм називається **перемикання контексту (context switch)**, а компонент ОС, що його виконує, — **диспетчер (dispatcher)**.

**Запитання до аудиторії**: Скільки разів на секунду, на вашу думку, ваш комп'ютер перемикається між задачами? 10? 100? 1000?

```

│                    ІЛЮЗІЯ ПАРАЛЕЛЬНОСТІ                               │
│                                                                       │

│                                                                       │
│   Час ─────────────────────────────────────────────────────────────►  │

│   └─────────┴─────────┴─────────┴──────────┴─────────┴─────────┘      │

└───────────────────────────────────────────────────────────────────────┘
```

Перемикання контексту коштує дорожче, ніж системний виклик (100–1000 нс,
див. лекцію про режими роботи): сам перехід у режим ядра — лише частина роботи.
Далі ядро зберігає й відновлює регістри, перемикає таблиці сторінок, а нові
дані витісняють із кешів і TLB чужі — саме це витіснення й дає основну частку
з 1–10 мікросекунд.

## Що таке контекст процесу?

**Контекст процесу** — це повний знімок стану виконання програми в конкретний момент часу. Це вся інформація, необхідна для того, щоб зупинити процес, а потім відновити його роботу так, ніби нічого не сталося.

### Аналогія: закладка в книзі

Уявіть, що ви читаєте книгу, і вас перервали. Щоб продовжити потім, вам потрібно запам'ятати:
- Яка книга (який процес)
- На якій сторінці ви зупинилися (instruction pointer)
- Що ви вже прочитали і запам'ятали (регістри, стек)
- Де лежать ваші нотатки (дані в пам'яті)

### Регістри CPU — серце контексту

Регістри — це найшвидша пам'ять процесора. Їх небагато, але вони критичні:

| Регістр (x86-64) | Призначення | Чому важливий для контексту |
|------------------|-------------|------------------------------|
| **RIP** (Instruction Pointer) | Адреса наступної інструкції | Без нього CPU не знатиме, що виконувати далі |
| **RSP** (Stack Pointer) | Вершина стеку | Локальні змінні, адреси повернення функцій |
| **RBP** (Base Pointer) | Основа фрейму стеку | Навігація по стеку викликів |
| **RAX-RDX** | Загального призначення | Аргументи функцій, результати обчислень |
| **R8-R15** | Додаткові регістри | Більше даних без звернення до пам'яті |
| **RFLAGS** | Прапорці стану | Zero, Carry, Overflow — результати порівнянь |
| **CR3** | Page Table Base | Вказівник на таблицю сторінок процесу |
| **FPU/SSE/AVX** | Floating point, SIMD | Обчислення з плаваючою комою, векторні |

```bash
# Регістри процесу видно лише відлагоджувачу: зупинити процес і прочитати
sleep 100 &
sudo gdb -p $! -batch -ex "info registers rip rsp" 2>/dev/null | tail -2

# Розмір task_struct у вашому ядрі: колонка <objsize> у байтах
sudo grep -E '^(# name|task_struct)' /proc/slabinfo
```

## Диспетчер (Dispatcher)

**Диспетчер** — це низькорівневий компонент ядра ОС, який безпосередньо виконує перемикання контексту. Він працює на найнижчому рівні після планувальника.

```
┌───────────────────────────────────────────────────────────────────────┐
│                    ПЛАНУВАЛЬНИК vs ДИСПЕТЧЕР                          │
│                                                                       │
│   ПЛАНУВАЛЬНИК (Scheduler)                                            │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  "ХТО буде виконуватися наступним?"                             │ │
│   │                                                                 │ │
│   │  • Аналізує пріоритети                                          │ │
│   │  • Враховує час очікування                                      │ │
│   │  • Застосовує алгоритм (CFS, Round Robin, Priority)             │ │
│   │  • Обирає процес з черги Ready                                  │ │
│   │                                                                 │ │
│   │  Результат: "Наступним виконуватиметься процес PID 1234"        │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                              │                                        │
│                              ▼                                        │
│   ДИСПЕТЧЕР (Dispatcher)                                              │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  "ЯК переключити процес?"                                       │ │
│   │                                                                 │ │
│   │  1. Зберегти контекст поточного процесу                         │ │
│   │  2. Оновити PCB поточного процесу                               │ │
│   │  3. Завантажити контекст нового процесу                         │ │
│   │  4. Переключити адресний простір (CR3)                          │ │
│   │  5. Передати керування новому процесу                           │ │
│   │                                                                 │ │
│   │  Результат: CPU виконує код процесу PID 1234                    │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   Аналогія:                                                           │
│   Планувальник = менеджер, який вирішує хто працюватиме               │
│   Диспетчер = секретар, який оформляє передачу справ                  │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

### Функції диспетчера

1. **Збереження контексту** — записати всі регістри поточного процесу в його PCB
2. **Переключення режиму** — якщо потрібно, перейти між User/Kernel mode
3. **Завантаження контексту** — відновити регістри нового процесу з його PCB
4. **Переключення адресного простору** — змінити CR3 на таблицю сторінок нового процесу
5. **Стрибок на нову адресу** — завантажити RIP і передати керування

```
│   └────────┬────────────────────────────────────────────────────────┘ │
│            │                                                          │
│            ▼                                                          │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  КРОК 4: Завантаження контексту процесу B                       │ │
│   │  ─────────────────────────────────────────────────              │ │
│   │  Диспетчер відновлює з PCB процесу B:                           │ │
│   │  • Завантажити CR3 → новий адресний простір                     │ │
│   │  • Відновити RAX, RBX, RCX, RDX... з PCB                        │ │
│   │  • Відновити FPU/SSE якщо потрібно                              │ │
│   │  Оновлення стану: Ready → Running                               │ │
│   └────────┬────────────────────────────────────────────────────────┘ │
│            │                                                          │
│            ▼                                                          │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  КРОК 5: Повернення до User Mode                                │ │
│   │  ─────────────────────────────────────────────────              │ │
│   │  IRETQ / SYSRET:                                                │ │
│   │  • Відновити RIP, RSP, RFLAGS зі стеку                          │ │
│   │  • Ring 0 → Ring 3                                              │ │
│   │  • CPU продовжує виконання процесу B                            │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│            │                                                          │
│            ▼                                                          │
│   Процес B виконується                                                │
│   ┌─────────────────┐                                                 │
│   │   User Code     │ ◄── CPU виконує інструкції процесу B            │
│   │   RIP: 0x5678   │     (з того місця, де він зупинився)            │
│   │   RSP: 0x7abc   │                                                 │
│   └─────────────────┘                                                 │
│                                                                       │
│   Загальний час: 1-10 мікросекунд                                     │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

### Коли відбувається перемикання контексту?

| Тригер | Опис | Приклад |
|--------|------|---------|
| **Timer Interrupt** | Спрацьовує таймер (квант часу вичерпано) | Частота тіку `CONFIG_HZ`: 250 Гц в Ubuntu (4 мс), 1000 Гц у Fedora (1 мс) |
| **System Call** | Процес сам віддає CPU (yield, sleep) | `sleep(1)` |
| **I/O Block** | Процес чекає на I/O | Читання з диска, мережі |
| **Preemption** | Прибув процес з вищим пріоритетом | Real-time процес |
| **Signal** | Отримано сигнал | SIGSTOP, SIGCONT |
| **Page Fault** | Потрібна сторінка з диска | Swap-in |

```bash
# Подивитися кількість перемикань контексту
cat /proc/stat | grep ctxt
# ctxt 12345678901  — загальна кількість context switches

# Для конкретного процесу
cat /proc/self/status | grep ctxt
# voluntary_ctxt_switches:   123
# nonvoluntary_ctxt_switches: 456

# Моніторинг в реальному часі
vmstat 1 | head -20
# Колонка "cs" — context switches per second
```

## Накладні витрати на перемикання (Context Switch Overhead)

Перемикання контексту не є безкоштовним. Кожне перемикання "коштує" системі час і ресурси.

```
┌───────────────────────────────────────────────────────────────────────┐
│                    OVERHEAD ПЕРЕМИКАННЯ КОНТЕКСТУ                     │
│                                                                       │
│   ПРЯМА ВАРТІСТЬ (Direct Cost): 1-10 мкс                              │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │                                                                 │ │
│   │  Збереження регістрів        ~100-500 нс                        │ │
│   │  Завантаження регістрів      ~100-500 нс                        │ │
│   │  Зміна CR3 (адресний простір) ~200-1000 нс                      │ │
│   │  Код диспетчера              ~200-500 нс                        │ │
│   │  ─────────────────────────────────────────                      │ │
│   │  Разом:                      ~1-3 мкс (найкращий випадок)       │ │
│   │                                                                 │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   НЕПРЯМА ВАРТІСТЬ (Indirect Cost): 10-1000+ мкс                      │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │                                                                 │ │
│   │  ★ CACHE POLLUTION (Забруднення кешу)                           │ │
│   │    Кеші НЕ очищуються — новий процес поступово витісняє з них   │ │
│   │    дані попереднього своїми. L1 (32–48 КБ) заміщується майже    │ │
│   │    повністю, L2 частково, спільний L3 страждає найменше         │ │
│   │                                                                 │ │
│   │    Повернувся старий процес → cache miss → звернення до RAM     │ │
│   │    Латентність: L1 (1нс) vs RAM (100нс) = 100x повільніше       │ │
│   │                                                                 │ │
│   │  ★ TLB (Translation Lookaside Buffer)                           │ │
│   │    Без PCID новий CR3 скидає TLB; з PCID записи різних          │ │
│   │    процесів співіснують, і скидання немає                       │ │
│   │                                                                 │ │
│   │  ★ BRANCH PREDICTOR                                             │ │
│   │    Історія гілкувань попереднього процесу марна                 │ │
│   │    Branch mispredictions до "навчання"                          │ │
│   │                                                                 │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   РЕАЛЬНИЙ ПРИКЛАД:                                                   │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │                                                                 │ │
│   │   Сервер з 10,000 context switches/sec                          │ │
│   │                                                                 │ │
│   │   Пряма вартість:  10,000 × 5 мкс  = 50 мс/сек = 5% CPU         │ │
│   │   Непряма вартість: до 20-30% продуктивності через cache miss   │ │
│   │                                                                 │ │
│   │   Оптимізація: менше потоків, ніж ядер, для обчислень;          │ │
│   │   async I/O замість потоку на з'єднання; CPU affinity           │ │
│   │                                                                 │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

### Типи перемикань і їх вартість

| Тип перемикання | Вартість | Причина |
|-----------------|----------|---------|
| **Thread switch** (той самий процес) | 1-3 мкс | Той самий адресний простір, не треба змінювати CR3 |
| **Process switch** (різні процеси) | 3-10 мкс | Зміна CR3, TLB flush |
| **Kernel thread switch** | <1 мкс | Немає User/Kernel переходу |
| **VM exit/entry** (гіпервізор) | ~1-2 мкс і більше | Апаратне збереження стану віртуального процесора |

```bash
# Виміряти вартість перемикання: два процеси по черзі пишуть одне одному в канал
sudo apt install linux-tools-common linux-tools-$(uname -r)   # команда perf
perf bench sched pipe                 # 1 000 000 обмінів; результат у usecs/op
taskset -c 0 perf bench sched pipe    # те саме, коли обидва на одному ядрі

# Класичний бенчмарк lmbench: lat_ctx -s 0 2
perf stat -e context-switches,cpu-migrations,cache-misses sleep 1
```

Кожна операція `perf bench sched pipe` — це два перемикання контексту плюс два системні виклики, тож результат у кілька мікросекунд і є практичною оцінкою вартості перемикання на вашій машині. Цикл на кшталт `for …; do echo x | cat; done` вимірював би зовсім інше — створення процесів `fork` і `exec`, яке в сотні разів дорожче.

## Збереження та відновлення регістрів

### Які регістри зберігаються?

### Ліниве збереження FPU: історія однієї оптимізації

Регістри FPU, SSE і AVX великі (з AVX-512 — понад 2 КБ), тож колись їх вирішили зберігати **ліниво**. Під час перемикання ядро не копіювало їх, а вмикало в регістрі `CR0` прапорець TS (Task Switched). Якщо новий процес так і не торкався FPU, копіювання не було взагалі. Якщо торкався — процесор генерував виключення `#NM` (Device Not Available), і лише тоді ядро зберігало стан попереднього власника й завантажувало новий.

```
┌───────────────────────────────────────────────────────────────────────┐
│               LAZY FPU: ЯК БУЛО І ЧОМУ ВІД НЬОГО ВІДМОВИЛИСЯ          │
│                                                                       │
│   Процес A (рахує з FPU) ──► перемикання: FPU не зберігаємо,          │
│                              вмикаємо CR0.TS                          │
│   Процес B (без FPU)     ──► працює; у регістрах FPU досі дані A      │
│   Процес B (торкнувся FPU) ► #NM → зберегти стан A, завантажити B     │
│                                                                       │
│   2018: LazyFP (CVE-2018-3665) — спекулятивне виконання дозволяло     │
│   процесу B прочитати «чужі» регістри FPU ще до виключення #NM.       │
│   Серед них бувають ключі AES, які криптобібліотеки тримають у XMM.   │
│                                                                       │
│   Рішення: Linux прибрав ліниве збереження повністю. Тепер стан       │
│   зберігається завжди, але інструкції XSAVEOPT/XSAVES самі            │
│   пропускають частини, які процес не змінював.                        │
└───────────────────────────────────────────────────────────────────────┘
```

Це типова доля оптимізацій, що заощаджують на ізоляції: після Spectre і Meltdown (2018) ядро пожертвувало кількома відсотками швидкості заради того, щоб процеси не могли «підглядати» один за одним. Та сама історія з таблицями сторінок: захист від Meltdown (KPTI) змусив перемикати `CR3` при кожному вході в ядро, і лише PCID повернув більшу частину втраченої швидкості.

### Приклад коду збереження контексту (спрощено)

```c
// Спрощена структура task_struct (Linux)
struct task_struct {
    // Ідентифікація
    pid_t pid;
    pid_t ppid;
    uid_t uid;

    // Стан
    volatile long state;  // RUNNING, INTERRUPTIBLE, etc.

    // Апаратний контекст
    struct thread_struct thread;  // Регістри CPU

    // Пам'ять
    struct mm_struct *mm;  // Адресний простір

    // Планування
    int prio;
    unsigned int policy;
    u64 vruntime;

    // Файли
    struct files_struct *files;

    // ... багато іншого
};

// Архітектурна частина (спрощено). Регістри програми користувача
// тут не зберігаються: під час входу в ядро процесор і код входу
// кладуть їх на стек ядра цього потоку (struct pt_regs)
struct thread_struct {
    unsigned long sp;        // вказівник стека ядра на момент перемикання
    unsigned long fsbase;    // базова адреса FS: локальні змінні потоку (TLS)
    unsigned long gsbase;
    struct fpu fpu;          // збережений стан FPU/SSE/AVX
};
```

Звідси цікавий факт: ядро перемикає не «процеси», а **стеки ядра**. Функція `switch_to` зберігає кілька регістрів, міняє вказівник стека на стек ядра наступного потоку і повертається — уже «в ньому». Коли той потік дійде до повернення в режим користувача, з його стека ядра відновляться його власні регістри.

```asm
; Спрощений приклад switch_to (x86-64 assembly)
; Зберігає контекст prev, завантажує контекст next

switch_to:
    ; Зберегти callee-saved регістри prev
    push rbp
    push rbx
    push r12
    push r13
    push r14
    push r15

    ; Зберегти stack pointer в task_struct prev
    mov [rdi + TASK_RSP], rsp   ; rdi = prev task

    ; Завантажити stack pointer з task_struct next
    mov rsp, [rsi + TASK_RSP]   ; rsi = next task

    ; Адресний простір (CR3) ядро перемикає ще до цього місця,
    ; у switch_mm(); з PCID це не скидає TLB

    ; Відновити callee-saved регістри next
    pop r15
    pop r14
    pop r13
    pop r12
    pop rbx
    pop rbp

    ret  ; Повертаємося вже в контексті next!
```

## Оптимізації перемикання контексту

Сучасні процесори та ОС використовують багато оптимізацій:

```
┌───────────────────────────────────────────────────────────────────────┐
│                    ОПТИМІЗАЦІЇ CONTEXT SWITCH                         │
│                                                                       │
│   1. PCID (Process Context Identifiers)                               │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  Проблема: Зміна CR3 → TLB flush → повільно                     │ │
│   │  Рішення: TLB entries помічаються PCID (12-bit ID)              │ │
│   │  Результат: Не треба flush TLB, entries з різними PCID          │ │
│   │             співіснують                                         │ │
│   │  Економія: до 50% overhead на context switch                    │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   2. LAZY TLB MODE                                                    │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  Якщо kernel thread (немає user space):                         │ │
│   │  • Не перезавантажувати CR3                                     │ │
│   │  • Використовувати TLB попереднього процесу                     │ │
│   │  • Kernel code однаковий для всіх                               │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   3. XSAVEOPT / XSAVES (замість колишнього lazy FPU)                  │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  Процесор сам відстежує, які частини стану FPU/AVX змінено,     │ │
│   │  і зберігає лише їх — економія без ризику LazyFP                │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   4. CPU AFFINITY                                                     │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  Прив'язати процес до конкретного CPU                           │ │
│   │  Переваги:                                                      │ │
│   │  • Cache залишається "теплим"                                   │ │
│   │  • Немає міграції між ядрами                                    │ │
│   │  • Кращий cache hit rate                                        │ │
│   │                                                                 │ │
│   │  taskset -c 0 ./my_program  # Запустити на CPU 0                │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   5. THREADS vs PROCESSES                                             │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │  Thread switch швидший за process switch:                       │ │
│   │  • Той самий адресний простір (не треба CR3 switch)             │ │
│   │  • Спільний TLB                                                 │ │
│   │  • Спільний cache                                               │ │
│   │  Економія: 50-70% часу на switch                                │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

```bash
# Використання CPU affinity
taskset -c 0 ./program         # Прив'язати до CPU 0
taskset -c 0-3 ./program       # Прив'язати до CPU 0-3
taskset -p 1234                # Показати affinity процесу PID 1234

# Встановити affinity існуючому процесу
taskset -p -c 0 1234           # Прив'язати PID 1234 до CPU 0

# Перевірити підтримку PCID
grep pcid /proc/cpuinfo        # Має бути в flags

# Моніторинг TLB misses
perf stat -e dTLB-loads,dTLB-load-misses ./program
```

```
│  ┌────────────────────────────────────────────────────────────────┐   │
│  │ PCID          → TLB entries з різними ID співіснують           │   │
│  │ XSAVES        → Зберігати лише змінені частини FPU/AVX         │   │
│  │ CPU Affinity  → Прив'язка до ядра, "теплий" cache              │   │
│  │ Threads       → Швидший switch ніж processes (спільний CR3)    │   │
│  │ Async I/O     → Менше блокувань = менше switches               │   │
│  └────────────────────────────────────────────────────────────────┘   │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

## 🎯 Міні-проект (30 хв)

### Завдання: Дослідження Context Switch на вашій системі

Створіть інструмент для аналізу перемикань контексту та їх впливу на продуктивність.

**Кроки:**

1. Створіть робочу директорію та базовий скрипт:
```bash
mkdir ~/context-switch-lab && cd ~/context-switch-lab

cat > analyze_context_switches.sh << 'EOF'
#!/bin/bash
echo "=== АНАЛІЗ CONTEXT SWITCHES ==="
echo "Дата: $(date)"
echo "Система: $(uname -r)"
echo "CPU: $(grep "model name" /proc/cpuinfo | head -1 | cut -d: -f2)"
echo ""
EOF
chmod +x analyze_context_switches.sh
```

2. Додайте збір базової статистики:
```bash
cat >> analyze_context_switches.sh << 'EOF'
echo "--- Загальна статистика системи ---"
CTXT_START=$(cat /proc/stat | grep ctxt | awk '{print $2}')
echo "Context switches на старті: $CTXT_START"

echo ""
echo "--- Статистика для поточного shell ---"
cat /proc/self/status | grep -E "voluntary|nonvoluntary"
echo ""
EOF
```

3. Додайте тест продуктивності:
```bash
cat >> analyze_context_switches.sh << 'EOF'
echo "--- Тест: Багато коротких процесів ---"
echo "Запускаємо 100 коротких процесів..."
START_TIME=$(date +%s%N)
for i in $(seq 1 100); do
    /bin/true              # окрема програма: fork + exec; echo — вбудована
done
END_TIME=$(date +%s%N)
DURATION=$(( ($END_TIME - $START_TIME) / 1000000 ))
echo "Час виконання: ${DURATION} мс"
echo ""

CTXT_AFTER=$(cat /proc/stat | grep ctxt | awk '{print $2}')
CTXT_DIFF=$(( $CTXT_AFTER - $CTXT_START ))
echo "Context switches за час тесту: $CTXT_DIFF"
echo ""
EOF
```

4. Додайте порівняння voluntary vs involuntary:
```bash
cat >> analyze_context_switches.sh << 'EOF'
echo "--- Аналіз типів перемикань ---"
echo ""
echo "Процеси з найбільшою к-стю involuntary switches:"
echo "(involuntary = процес був витіснений)"
for pid in $(ls /proc | grep -E '^[0-9]+$' | head -20); do
    if [ -f /proc/$pid/status ]; then
        NAME=$(cat /proc/$pid/status 2>/dev/null | grep "Name:" | awk '{print $2}')
        INVOL=$(cat /proc/$pid/status 2>/dev/null | grep "nonvoluntary" | awk '{print $2}')
        if [ ! -z "$INVOL" ] && [ "$INVOL" -gt 100 ]; then
            echo "  PID $pid ($NAME): $INVOL"
        fi
    fi
done 2>/dev/null
echo ""
EOF
```

5. Додайте тест CPU affinity:
```bash
cat >> analyze_context_switches.sh << 'EOF'
echo "--- Тест CPU Affinity: обмін через канал ---"
if command -v perf &> /dev/null; then
    echo "Процеси на різних ядрах (як вирішить планувальник):"
    perf bench sched pipe -l 200000 2>&1 | grep -E 'usecs/op'
    echo "Обидва процеси на ядрі 0:"
    taskset -c 0 perf bench sched pipe -l 200000 2>&1 | grep -E 'usecs/op'
else
    echo "perf не встановлено: sudo apt install linux-tools-$(uname -r)"
fi
echo ""
EOF
```

6. Запустіть аналіз та збережіть результати:
```bash
cat >> analyze_context_switches.sh << 'EOF'
echo "--- Рекомендації ---"
echo "1. Voluntary > involuntary: процес здебільшого чекає на I/O сам"
echo "2. Багато involuntary = процеси конкурують за CPU"
echo "3. CPU affinity корисна для latency-sensitive задач"
echo ""
echo "=== КІНЕЦЬ АНАЛІЗУ ==="
EOF

./analyze_context_switches.sh | tee context_switch_report.txt
```

**Очікуваний результат:**
Файл `context_switch_report.txt` з повним аналізом перемикань контексту на вашій системі, включаючи статистику, типи перемикань та рекомендації.

**Бонус (для допитливих):**
- Запустіть `stress-ng --cpu 4` і повторіть аналіз — як змінюється к-сть context switches?
- Порівняйте `voluntary_ctxt_switches` для `sleep 10 &` та `yes > /dev/null &`
- Створіть графік context switches за часом за допомогою `vmstat 1 100 | tee vmstat.log`

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Що входить до контексту процесу?

- перелік відкритих вікон
- історія команд користувача
- лише вихідний код програми
- вміст регістрів, лічильник команд, вказівник стека та посилання на таблицю сторінок

**2.** Чим планувальник відрізняється від диспетчера?

- планувальник обирає, кого виконувати наступним, а диспетчер виконує саме перемикання
- це дві назви одного компонента
- диспетчер обирає процес, а планувальник зберігає регістри
- планувальник працює лише в режимі користувача

**3.** Скільки приблизно триває перемикання контексту між процесами?

- близько секунди
- від 3 до 10 мікросекунд
- від 3 до 10 наносекунд
- близько мілісекунди

**4.** Чому перемикання між потоками одного процесу швидше?

- планувальник не бере участі в перемиканні потоків
- адресний простір той самий, тому не треба міняти CR3 і скидати TLB
- потоки виконуються в режимі користувача без участі ядра
- потоки не мають власних регістрів

**5.** Який регістр указує на таблицю сторінок процесу в x86-64?

- RSP
- RIP
- CR3
- RFLAGS

**6.** Що таке квант часу?

- час, потрібний на збереження контексту
- проміжок, який процес виконується до примусового витіснення, — одиниці мілісекунд
- час очікування завершення введення-виведення
- мінімальний інтервал таймера ядра

**7.** Яка подія найчастіше спричиняє перемикання контексту?

- завершення роботи системи
- запуск нової програми
- переривання від таймера після вичерпання кванта
- натискання клавіші користувачем

**8.** Що таке забруднення кешу під час перемикання контексту?

- новий процес витісняє з кешу дані попереднього, і той після повернення працює повільніше
- у кеші лишаються помилкові дані, які псують обчислення
- кеш переповнюється й вимикається
- процесор змушений вимкнути кеш першого рівня

**9.** Чим допомагає прив'язка процесу до ядра (CPU affinity)?

- процес повертається на те саме ядро, де його дані ще лежать у кеші
- процес перестає витіснятися таймером
- процес переходить у режим реального часу
- процес отримує вищий пріоритет

**10.** Яка команда покаже кількість перемикань контексту за секунду?

- chrt -f 50
- taskset -c 0
- pstree
- vmstat 1

## Підсумок

| Термін | Визначення |
|--------|------------|
| **Контекст процесу** | Повний знімок стану: регістри, пам'ять, PCB |
| **PCB (Process Control Block)** | Структура ядра з інформацією про процес |
| **Диспетчер (Dispatcher)** | Компонент, що виконує перемикання контексту |
| **Планувальник (Scheduler)** | Компонент, що обирає наступний процес |
| **Context Switch** | Збереження контексту одного процесу, завантаження іншого |
| **Voluntary switch** | Процес сам віддав CPU (I/O, sleep) |
| **Involuntary switch** | Процес витіснено (timer, preemption) |
| **CPU Affinity** | Прив'язка процесу до конкретних ядер CPU |
| **Lazy FPU** | Історична оптимізація: зберігати FPU лише при потребі; прибрана 2018 року через LazyFP |
| **XSAVEOPT / XSAVES** | Інструкції, що зберігають лише змінені частини стану FPU/AVX |
| **PCID** | Ідентифікатор для TLB entries, уникнення flush |

| Компонент | Що зберігається | Розмір |
|-----------|-----------------|--------|
| Регістри GP | RAX-R15, RIP, RSP, RFLAGS | ~144 байт |
| FPU/SSE | x87, XMM0-15 | ~300 байт |
| AVX | YMM0-15 | ~500 байт |
| AVX-512 | ZMM0-31 | ~2 KB |
| Загалом (типово) | GP + частково FPU | ~500 байт |

На наступній лекції — переривання: апаратні та програмні, вектор переривань, пріоритети.
