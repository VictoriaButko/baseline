## Хто отримає CPU наступним?

Уявіть чергу в кав'ярні. Є 10 клієнтів, але тільки один бариста. Як вирішити, кого обслуговувати першим? Першого в черзі? Того, хто замовляє найшвидше? Постійного клієнта? А якщо з'явиться VIP?

```
│   │   │CPU│  ← Тільки ОДИН процес може виконуватись!                │ │
│   │   └───┘                                                         │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   SCHEDULER (Планувальник) вирішує:                                   │
│   • Який процес отримає CPU?                                          │
```

Навесні 2007 року Інго Мольнар (Ingo Molnár) написав за 62 години новий планувальник Linux — CFS — після гострої суперечки з анестезіологом Коном Коливасом (Con Kolivas), який у вільний час роками вдосконалював планувальник для настільних систем. CFS прожив у ядрі 16 років. У жовтні 2023 року в Linux 6.6 його замінив EEVDF — алгоритм зі статті 1995 року, на яку чверть століття майже ніхто не зважав. А з кінця 2024-го (Linux 6.12) власний планувальник можна завантажити в ядро як програму eBPF, не перезбираючи ядра. Планування — одна з небагатьох тем ОС, де «класика з підручника» і найсвіжіші новини ядра стоять поруч.

**Запитання до аудиторії**: Ви граєте в онлайн-гру, а фоновий антивірус починає сканування. Що важливіше - ваша гра чи безпека? Хто вирішує?

### Метрики планування

| Метрика | Визначення | Важлива для |
|---------|------------|-------------|
| **CPU utilization** | % часу, коли CPU зайнятий | Сервери, batch-системи |
| **Throughput** | Кількість завершених процесів за час | Сервери |
| **Turnaround time** | Час від submission до completion | Batch jobs |
| **Waiting time** | Час у черзі ready | Всі системи |
| **Response time** | Час від запиту до першої відповіді | Інтерактивні системи |

## Класичні алгоритми планування

Класичні алгоритми — будівельні блоки, з яких складено всі сучасні планувальники. Покрокові розрахунки з діаграмами Ганта для кожного з них розібрано в темі «Алгоритми планування» (модуль 3); тут — ідея, сильна й слабка сторона кожного.

Таблиця 1 — Класичні алгоритми планування

| Алгоритм | Ідея | Сильна сторона | Слабка сторона | Де живе сьогодні |
|----------|------|----------------|----------------|------------------|
| **FCFS** (First-Come, First-Served) | Черга: хто раніше прийшов, той раніше виконується | Найпростіший, без зайвих перемикань | **Ефект конвою**: одна довга задача затримує всі короткі за нею | Черги друку, SCHED_FIFO серед рівних пріоритетів |
| **SJF** (Shortest Job First) | Спершу найкоротша задача | Доведено мінімальний середній час очікування | Треба знати тривалість наперед; довгі задачі можуть **голодувати** | Прогноз тривалості в пакетних системах |
| **SRTF** (Shortest Remaining Time First) | Витісняльний SJF: коротша нова задача перериває поточну | Ще менший середній час очікування | Голодування, часті перемикання | Ідея «коротке — першим» у мережевих чергах |
| **Round Robin** | По черзі, кожному квант часу | Справедливий, швидкий відгук | Малий квант — накладні витрати на перемикання з'їдають час; великий — вироджується у FCFS | SCHED_RR, основа розподілу часу |
| **За пріоритетами** | Виконується найважливіший | Контроль важливості | Голодування низьких пріоритетів; ліки — **aging**, поступове підвищення пріоритету того, хто довго чекає | Windows, реальний час |
| **MLFQ** (Multilevel Feedback Queue) | Кілька черг різного пріоритету; хто використав увесь квант — опускається нижче | Сам розпізнає інтерактивні задачі без підказок | Складний, його можна «обдурити» | Класичний UNIX, Windows, macOS |

Ефективність оцінюють трьома часами. **Час обігу** (turnaround) = завершення − надходження. **Час очікування** (waiting) = час обігу − час виконання, тобто скільки задача простояла в черзі готових. **Час відгуку** (response) = перший запуск − надходження.

## Класи планування Linux

Планувальник Linux — не один алгоритм, а стос **класів**, які опитуються згори донизу. Кожне ядро спершу бере задачу з найвищого непорожнього класу, тож задача реального часу завжди випереджає звичайну.

Таблиця 2 — Класи й політики планування Linux

| Клас | Політики | Алгоритм | Хто там працює |
|------|----------|----------|----------------|
| stop | — | — | Службові потоки ядра, наприклад міграція задач між ядрами |
| deadline | `SCHED_DEADLINE` | EDF + обмеження бюджету (CBS) | Періодичні задачі з гарантованим часом: аудіо, керування обладнанням |
| rt | `SCHED_FIFO`, `SCHED_RR` | Пріоритети 1–99; FIFO або Round Robin серед рівних | Звук JACK/PipeWire, промислове керування |
| fair | `SCHED_OTHER` (`SCHED_NORMAL`), `SCHED_BATCH` | CFS, з 6.6 — EEVDF | Майже всі процеси системи |
| ext | `SCHED_EXT` | Будь-який, завантажений як eBPF | Експериментальні й спеціалізовані політики (з 6.12) |
| idle | `SCHED_IDLE` | Лише коли більше нікому | Фонові задачі найнижчої важливості |

Щоб задача реального часу з помилкою не «повісила» систему, ядро за замовчуванням залишає звичайним задачам частку часу: `cat /proc/sys/kernel/sched_rt_runtime_us` (950 000 мкс з кожної секунди — 95 % для реального часу).

## CFS: справедливий розподіл (2007–2023)

CFS («Completely Fair Scheduler») панував у Linux з версії 2.6.23 (2007) до 6.6 (2023); на ньому досі працюють ядра, що ще широко використовуються, наприклад 5.15 і 6.1, а EEVDF успадкував від нього головні ідеї.

```
┌───────────────────────────────────────────────────────────────────────┐
│                    CFS: COMPLETELY FAIR SCHEDULER                     │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│   ІДЕЯ: Ідеальний процесор ділить час РІВНО між усіма                 │
│                                                                       │
│   Ідеальна багатозадачність (1 CPU, 4 процеси):                       │
│   ┌────────────────────────────────────────────────────────────────┐  │
│   │ P1: ▓░░░▓░░░▓░░░▓░░░▓░░░▓░░░                                   │  │
│   │ P2: ░▓░░░▓░░░▓░░░▓░░░▓░░░▓░░                                   │  │
│   │ P3: ░░▓░░░▓░░░▓░░░▓░░░▓░░░▓░                                   │  │
│   │ P4: ░░░▓░░░▓░░░▓░░░▓░░░▓░░░▓                                   │  │
│   │     ─────────────────────────►                                 │  │
│   │     Кожен отримує 25% CPU в кожен момент часу                  │  │
│   └────────────────────────────────────────────────────────────────┘  │
│                                                                       │
│   Реальність: CPU не можна ділити нескінченно                         │
│   CFS емулює це через "virtual runtime" (vruntime)                    │
│                                                                       │
│   VRUNTIME = реальний час * (nice_weight / process_weight)            │
│                                                                       │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │ Red-Black Tree (відсортовано за vruntime):                      │ │
│   │                                                                 │ │
│   │                     ┌───────┐                                   │ │
│   │                     │vr=100 │                                   │ │
│   │                     └───┬───┘                                   │ │
│   │                   ┌─────┴─────┐                                 │ │
│   │              ┌────▼───┐  ┌────▼───┐                             │ │
│   │              │ vr=50  │  │ vr=150 │                             │ │
│   │              └───┬────┘  └────┬───┘                             │ │
│   │             ┌────┴────┐  ┌────┴────┐                            │ │
│   │        ┌────▼──┐ ┌────▼──┐ ┌──────▼┐                            │ │
│   │        │ vr=25 │ │ vr=75 │ │vr=200 │                            │ │
│   │        └───────┘ └───────┘ └───────┘                            │ │
│   │            ↑                                                    │ │
│   │     Найлівіший = МІНІМАЛЬНИЙ vruntime                           │ │
│   │     ЦЕЙ ПРОЦЕС ОТРИМАЄ CPU НАСТУПНИМ!                           │ │
│   │                                                                 │ │
│   │     O(log N) - час вибору наступного процесу                    │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   WEIGHT (вага): визначається nice value                              │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │ nice =  0 → weight = 1024 (default)                             │ │
│   │ nice = -5 → weight = 3121 (≈3x більше CPU)                      │ │
│   │ nice = +5 → weight =  335 (≈3x менше CPU)                       │ │
│   │                                                                 │ │
│   │ Кожен рівень nice ≈ 10% різниці в CPU time                      │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

Як саме вага перетворюється на `vruntime` і частку процесора, розраховано в темі «Дисципліни диспетчеризації» (модуль 3).

## EEVDF: справедливість плюс дедлайни (з 2023)

CFS був справедливим, але затримку забезпечував набором евристик: скільки «бонусу» дати щойно розбудженій задачі, коли дозволити їй витіснити поточну. EEVDF (Earliest Eligible Virtual Deadline First, Ion Stoica і Hussein Abdel-Wahab, 1995) замінює евристики двома чіткими поняттями:

- **Відставання** (lag) — скільки часу задача недоотримала порівняно з ідеальним справедливим розподілом. Задача з lag ≥ 0 — **придатна** (eligible): їй «винні» час.
- **Віртуальний дедлайн** — момент, до якого задача має отримати свій наступний квант: момент придатності плюс квант, поділений на вагу.

Правило вибору: серед придатних задач виконується та, у якої **найраніший віртуальний дедлайн**. Задача, що просить коротший квант (інтерактивна програма, аудіо), отримує ближчий дедлайн і частіше опиняється першою, але в сумі не отримує більше за свою справедливу частку — вона просто отримує її дрібнішими порціями.

```
Дві задачі з однаковою вагою, обидві придатні:

  A — рендеринг, квант 3 мс     дедлайн = t + 3
  B — аудіо, квант 0,5 мс       дедлайн = t + 0,5    ← виконується першою

B отримує процесор частіше, але щоразу на 0,5 мс; за секунду обидві
отримають по 50 % часу. Справедливість та сама, затримка в B — менша.
```

```bash
uname -r                                  # 6.6 і новіше — EEVDF
sudo cat /sys/kernel/debug/sched/base_slice_ns   # базовий квант (часто ~3 мс)

# Статистика планувальника для процесу
cat /proc/$$/sched | head -20
# se.vruntime            ← віртуальний час, нс
# se.sum_exec_runtime    ← реально відпрацьований час, мс
# nr_voluntary_switches  ← добровільні перемикання (чекав на I/O)
# nr_involuntary_switches← примусові (витіснення)
```

Параметри на кшталт `/proc/sys/kernel/sched_latency_ns`, які досі згадують старі підручники й статті, з Linux 5.13 перенесено в debugfs (`/sys/kernel/debug/sched/`), а з переходом на EEVDF більшість із них зникла зовсім: лишився базовий квант.

## Багатоядерність, енергія і гібридні процесори

Реальний планувальник вирішує не лише «хто», а й **де**:

- **Окрема черга на кожне ядро.** Задачі без потреби не мігрують, щоб дані лишалися в кеші. Періодичне балансування переносить їх з перевантажених ядер на вільні — спершу між гіперпотоками одного ядра, потім між ядрами, і лише в крайньому разі між сокетами NUMA.
- **Energy Aware Scheduling** (Linux 5.0, 2019) — для процесорів big.LITTLE у смартфонах: планувальник знає енергомодель кожного ядра й кладе задачу туди, де вона виконається з найменшими витратами енергії. На цьому працює Android.
- **Гібридні x86-процесори** з продуктивними (P) і енергоощадними (E) ядрами — Intel з Alder Lake (2021). Апаратний Thread Director підказує ОС, яка задача виграє від P-ядра; Windows 11 спирається на ці підказки, Linux підтримує їх частково.

```bash
lscpu --extended | head                 # ядра, сокети, NUMA-вузли, частоти
cat /sys/devices/system/cpu/cpu*/cpu_capacity 2>/dev/null | sort | uniq -c   # «сила» ядер на ARM
```

## sched_ext: планувальник як програма eBPF (з 2024)

З версії 6.12 до ядра можна завантажити власну політику планування, написану як програма eBPF: вона отримує події «задача прокинулася», «ядро звільнилося» й вирішує, кого де запускати. Помилкова політика не зламає систему — ядро автоматично повернеться до EEVDF. Прикладні результати вже є: Meta використовує `scx_layered` у своїх датацентрах, а `scx_lavd`, створений в Igalia на замовлення Valve, зменшує затримки в іграх на Steam Deck.

## macOS, iOS і Android

**macOS та iOS** планують потоки ядра XNU (спадок Mach), але розробник не виставляє числових пріоритетів: він указує **клас якості обслуговування** (QoS) — User Interactive (анімація, реакція на дотик), User Initiated, Utility, Background. На процесорах Apple Silicon QoS визначає й тип ядра: фонові задачі (індексація Spotlight, резервні копії Time Machine) система відправляє на енергоощадні ядра, тому вони не заважають інтерфейсу й майже не розряджають батарею.

**Android** використовує ядро Linux з EEVDF (або CFS у старших пристроях), Energy Aware Scheduling і два додаткові механізми: **cpusets** (програма на екрані — у групі `top-app` з доступом до великих ядер, фонові — лише до малих) і **uclamp** — підказку планувальнику, якої мінімальної продуктивності потребує задача. Коли ви торкаєтеся екрана, система тимчасово підвищує вимоги для інтерфейсу — так смартфон відгукується миттєво, хоча більшість часу працює на малих ядрах.

## Real-Time планування

```
┌───────────────────────────────────────────────────────────────────────┐
│                    REAL-TIME SCHEDULING                               │
├───────────────────────────────────────────────────────────────────────┤
│                                                                       │
│   Для систем, де DEADLINE критичний:                                  │
│   • Автопілот                                                         │
│   • Медичне обладнання                                                │
│   • Промислові роботи                                                 │

│                                                                       │
│   LINUX REALTIME SCHEDULING POLICIES:                                 │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │ SCHED_FIFO:                                                     │ │
│   │ • Виконується, поки не завершиться або заблокується             │ │
│   │ • Вищий RT-priority завжди preempt нижчий                       │ │
│   │ • Priorities: 1-99 (99 = найвищий)                              │ │
│   │                                                                 │ │
│   │ SCHED_RR (Round Robin RT):                                      │ │
│   │ • Як SCHED_FIFO, але з time quantum                             │ │
│   │ • Процеси з однаковим priority чергуються                       │ │
│   │                                                                 │ │
│   │ SCHED_DEADLINE:                                                 │ │
│   │ • Earliest Deadline First (EDF)                                 │ │
│   │ • Процес із найближчим deadline виконується першим              │ │
│   │ • Найпріоритетніший клас для задач користувача (з 3.14)         │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
│   RT PRIORITY VISUALIZED:                                             │
│   ┌─────────────────────────────────────────────────────────────────┐ │
│   │ SCHED_DEADLINE  │  Deadline tasks (найвищий)                    │ │
│   │ SCHED_FIFO/RR   │  RT priorities 1-99                           │ │
│   │ SCHED_OTHER     │  Nice -20..+19 (CFS)                          │ │
│   │ SCHED_BATCH     │  Batch processing                             │ │
│   │ SCHED_IDLE      │  Idle tasks (найнижчий)                       │ │
│   └─────────────────────────────────────────────────────────────────┘ │
│                                                                       │
└───────────────────────────────────────────────────────────────────────┘
```

Теорію реального часу — тест планованості для EDF, інверсію пріоритетів — розібрано в темі «Якість диспетчеризації» (модуль 3).

```bash
chrt -m                                   # діапазони пріоритетів кожної політики
# Запустити процес з SCHED_FIFO
sudo chrt -f 50 ./my_realtime_app

# Подивитися scheduling policy
chrt -p 1234
# pid 1234's current scheduling policy: SCHED_OTHER
# pid 1234's current scheduling priority: 0

# Запустити з SCHED_RR
sudo chrt -r 30 ./my_app

# Змінити policy для існуючого процесу
sudo chrt -f -p 50 1234
```

### Завдання: Класи планування Linux в експерименті

1. З'ясуйте, яка версія планувальника у вас і які діапазони пріоритетів доступні:

```bash
uname -r                      # 6.6+ — EEVDF, старіші — CFS
chrt -m                       # мінімальний і максимальний пріоритет кожної політики
ps -eo pid,cls,rtprio,ni,comm | awk '$2 != "TS"' | head -20   # хто не в класі TS
```
Колонка `CLS`: `TS` — звичайний (SCHED_OTHER), `B` — BATCH, `IDL` — IDLE, `FF` — FIFO, `RR` — Round Robin, `DLN` — DEADLINE.

2. Створіть «пожирач процесора» і запустіть три копії на одному ядрі з різними політиками:
```bash
mkdir -p ~/sched-lab && cd ~/sched-lab
cat > burn.sh << 'EOF'
#!/bin/sh
# нескінченний цикл обчислень; зупиняємо ззовні через 30 секунд
while :; do :; done
EOF
chmod +x burn.sh

taskset -c 0 ./burn.sh &               # звичайна задача
taskset -c 0 chrt -b 0 ./burn.sh &     # SCHED_BATCH
taskset -c 0 chrt -i 0 ./burn.sh &     # SCHED_IDLE
sleep 30
ps -o pid,cls,ni,pcpu,comm -p $(jobs -p | tr '\n' ',' | sed 's/,$//')
kill $(jobs -p)
```

3. Поясніть результат. BATCH отримує приблизно стільки ж, скільки звичайна задача (різниця лише в тому, як часто вона витісняє інших), а IDLE — крихти, бо має мізерну вагу.

4. Повторіть з nice: запустіть на ядрі 0 дві звичайні копії з `nice -n 0` і `nice -n 10` і порівняйте частки з таблицею ваг у темі «Параметри планування».

5. Подивіться, як бачить задачу сам планувальник:
```bash
taskset -c 0 ./burn.sh & P=$!
sleep 5
grep -E 'se.vruntime|se.sum_exec_runtime|nr_involuntary_switches|policy|prio' /proc/$P/sched
kill $P
```

6. Обережно з реальним часом. Задача SCHED_FIFO на ядрі 0 витіснить усе інше на цьому ядрі; `timeout` гарантує, що експеримент завершиться сам:
```bash
taskset -c 0 ./burn.sh &                                  # звичайна задача
sudo timeout 10 taskset -c 0 chrt -f 10 ./burn.sh &       # FIFO на 10 секунд
sleep 5; ps -o pid,cls,rtprio,pcpu,comm -C burn.sh
wait; kill %1
```

**Очікуваний результат:**

- Таблиця «політика — частка CPU» для звичайної, BATCH, IDLE і FIFO задач на одному ядрі.
- Пояснення кожної частки через класи планування й ваги.
- Відповідь, чому під час роботи FIFO-задачі звичайна задача отримує не нуль, а близько 5 % (`sched_rt_runtime_us`).

**Бонус (для допитливих):**

- Перевірте, чи підтримує ваше ядро sched_ext: `ls /sys/kernel/sched_ext 2>/dev/null && cat /sys/kernel/sched_ext/state`.
- Виміряйте затримку планування командою `perf sched record -- sleep 5` і `perf sched latency`.
- Запустіть `burn.sh` на кожному ядрі й подивіться у `htop`, як балансувальник розкладає задачі, якщо не прив'язувати їх `taskset`.

## Тест для самоперевірки

Десять запитань, у кожному одна правильна відповідь. Якщо тема винесена вашій групі на самостійне опрацювання, цей самий тест публікується в Google Classroom — 10 балів, по одному за кожне запитання.

**1.** Чим витісняльне планування відрізняється від невитісняльного?

- за витісняльного ОС може відібрати процесор у процесу до завершення його роботи
- невитісняльне застосовують в усіх сучасних настільних системах
- різниця лише в розмірі кванта часу
- за витісняльного процес сам вирішує, коли віддати процесор

**2.** Що таке ефект конвою у FCFS?

- черга розбивається на кілька рівнів
- одна довга задача затримує всі короткі, що стоять за нею в черзі
- короткі задачі витісняють довгі
- процеси виконуються в порядку зростання пріоритету

**3.** Яку проблему створює алгоритм SJF, розв'язуючи попередню?

- зростає кількість перемикань контексту
- потрібен апаратний таймер
- процеси виконуються не за порядком надходження
- довгі задачі можуть не дочекатися процесора взагалі

**4.** Що станеться в Round Robin, якщо квант часу зробити занадто малим?

- короткі задачі перестануть виконуватися
- алгоритм перетвориться на FCFS
- накладні витрати на перемикання контексту з'їдять корисний час
- процеси втратять пріоритети

**5.** На що перетворюється Round Robin за дуже великого кванта?

- на планування за пріоритетами
- на багаторівневу чергу
- на SJF
- на FCFS

**6.** Що таке aging у плануванні за пріоритетами?

- зниження пріоритету процесів, що довго виконуються
- збільшення кванта часу для старих процесів
- поступове підвищення пріоритету процесу, який довго чекає
- видалення процесів, які чекають надто довго

**7.** Яку структуру даних використовує планувальник CFS у Linux?

- червоно-чорне дерево, впорядковане за vruntime
- хеш-таблицю за PID
- масив із 32 рівнів пріоритету
- звичайну чергу FIFO

**8.** Що таке vruntime?

- залишок кванта часу процесу
- час очікування в черзі готових
- віртуальний час, що його процес уже відпрацював з урахуванням ваги
- загальний час роботи системи

**9.** Скільки рівнів пріоритету має планувальник Windows?

- 40
- 8
- 99
- 32

**10.** Як обчислюється час очікування процесу?

- час завершення мінус час надходження
- час обігу мінус час виконання
- час першого запуску мінус час надходження
- сума квантів часу, виділених процесу

## Підсумок

| Алгоритм | Тип | Переваги | Недоліки |
|----------|-----|----------|----------|
| **FCFS** | Non-preemptive | Простий | Convoy effect |
| **SJF** | Non-preemptive | Оптимальний waiting | Starvation, потрібно знати burst |
| **SRTF** | Preemptive | Кращий за SJF | Starvation, overhead |
| **Round Robin** | Preemptive | Справедливий | Overhead при малому quantum |
| **Priority** | Both | Контроль важливості | Starvation без aging |
| **MLFQ** | Preemptive | Адаптивний | Складний |
| **CFS** (2007–2023) | Preemptive | Справедливий, масштабований | Затримка на евристиках |
| **EEVDF** (з 2023) | Preemptive | Справедливість плюс віртуальні дедлайни | Новий, налаштування ще уточнюються |

| Термін | Визначення |
|--------|------------|
| **Time quantum** | Максимальний час виконання до preemption |
| **Preemption** | Примусове переривання процесу |
| **Starvation** | Процес ніколи не отримує CPU |
| **Aging** | Поступове підвищення пріоритету |
| **vruntime** | Віртуальний час виконання (CFS, EEVDF) |
| **Клас планування** | Рівень у стосі планувальника: deadline, rt, fair, ext, idle |
| **Lag** | Відставання задачі від справедливої частки; основа вибору в EEVDF |
| **sched_ext** | Механізм завантаження політики планування як програми eBPF |
| **EAS** | Energy Aware Scheduling — планування з урахуванням енерговитрат ядер |
| **Context switch** | Перемикання між процесами |
